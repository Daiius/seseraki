# 13. 出題（次の一手・実戦詰将棋）

溜め込んだ棋譜と解析から**問題を作って解く**機能を定める。解析基盤は [05](./05-analysis.md)、
局面評価（名指し評価）は [12](./12-position-lab.md)、悪手判定の語彙は [01](./01-domain.md) §5 を参照。

> 設計は 2026-09-08 の grill で確定。出題・採点は実装済み。
> **問題の一覧と解答履歴の一覧は 2026-09-10 に追記（未実装）**（[08](./08-roadmap.md)）。

---

## 1. 動機

棋譜と解析は、いま**読むもの**にしかなっていない。同じ材料から**解くもの**を作れば、
「毎回同じところで落とす」を身体で覚え直せる。

材料は既に DB にある——`candidateMoves`（MultiPV 3・スコア・pv。[03](./03-data-model.md) §4）、
`kifuPositions`（局面索引。[10](./10-video-analysis.md) §3.2）、`kifus.subjectSide`（自分がどちら側か。
[11](./11-users.md)）。**新しいエンジン解析は要らない。**

## 2. スコープ

出題は 2 種。**器は 1 つ**（局面 + 正解 + 採点）で、違うのは正解の決め方だけ。

| 種別 | 問い | 正解 | 手数 |
|---|---|---|---|
| 実戦詰将棋 | ここで詰ませてください | 詰みが続く手 | **詰み上がりまで指し継ぐ** |
| 次の一手 | ここで何を指すべきでしたか | 最善との差が許容内の手 | **初手のみ** |

- 対象は**自分の対局だけ**。`source <> 'video'` を既定で強制する（[10](./10-video-analysis.md) §2.2 と同じ）。
- 材料は **`profile='full'` の解析行だけ**（[03](./03-data-model.md) §3）。
  🔴 **quick を混ぜない**——出題の答えが探索の浅さで揺れると、問題として成立しない
  （検討盤の再利用が full だけを引くのと同じ筋。[12](./12-position-lab.md) §2.6）。

## 3. 将棋のルールは実装しない

🔒 **合法手生成器は作らない**（[12](./12-position-lab.md) §2.5 の決定をそのまま通す）。
**詰将棋のルール（打ち歩詰め・連続王手の千日手・無駄合い）はフロントにも server にも持たない。**

- **正典はエンジンの側にある。** 「その手で詰みが続くか」は `mate` スコアが答えで、
  打ち歩詰めなら `mate` は返らない。**判定をエンジンに委ねればルールの実装が要らない。**
- フロントが持つのは「**選んだ駒がそのマスへ動けるか**」だけ。これは合法手の全列挙ではなく
  **単手の検証**で、`shared` の利き表（`position-validation.ts` の `STEPS` / `SLIDES`）と
  `validateMoveOnPosition` で足りる。着手可能マスのハイライトもここから出す。
  ⚠ **「合法手生成器を作らない」と矛盾しない**——列挙するのは選んだ 1 枚の行き先だけで、
  局面の全合法手を数え上げるわけではない。
- 二歩・行き所のない駒は既存の `validatePositionForEngine` が入力の時点で弾く。

⚠ **弱点**: 打ち歩詰めを指されたとき「**反則です**」とは言えず「**その手では詰みません**」に
なる。反則だと名指しするには詰み判定（＝受方の合法手の全列挙）が要るので、**やらない**。
出題の答え合わせとしては「詰まない」で十分に成立する。

## 4. 出題の抽出

### 4.1 3 つの条件

| 種別 | 条件 |
|---|---|
| **逃した詰み**（`mate`） | 自分の手番で rank1 が `mate`・`1 ≤ N ≤ 詰み手数上限`・`classifyMateLine` が `checkmate`・**実際には詰まさなかった** |
| **自分の悪手**（`best`） | 自分の手の CPL ≥ 悪手閾値 かつ 未決着（`|bestCp| < decided`。[05](./05-analysis.md) §2.3） |

- 🔴 **`classifyMateLine = checkmate` を条件にする**（[05](./05-analysis.md) §2.2）。**詰将棋の形をした
  mate だけ**が選ばれ、必至や静かな手を含む筋は落ちる——「詰ませてください」という問いに
  `hisshi` / `forced` の筋を出すと、正解手順が王手の連続にならず問題として破綻するため。
- 詰み手数上限は `/settings` の**取りこぼし閾値**（[09](./09-analytics.md) §3.1・既定 10）を流用する。
  ⚠ この N は **engine の詰み距離（plies）**で、詰将棋の「N手詰」ではない（[01](./01-domain.md) §5）。
- 🔴 **rank1 が `mate` の局面は `best` 種別にしない**（決定・2026-09-08。レビュー `OCL-95952BDD`）。
  最善が詰みなら問いは「詰ませてください」で、cp 差の採点（§5.1）が成立しない。
  `classifyMateLine` が `checkmate` なら `mate` 種別として出題し、**それ以外（必至・静かな手を含む筋）は
  出題しない**。⚠ CPL は mate が絡むと算出されない（`cpl.ts`）ので実務上は自然にこうなるが、
  **規則として明示する**（抽出条件を足したときに静かに破れる種類の前提のため）。
- 「逃した詰み」は [09](./09-analytics.md) §3.1 の**取りこぼしと同じ母集団**（あちらは負け局に限るが、
  こちらは勝敗を問わない）。`candidate_moves` の mate 用索引（[03](./03-data-model.md) §4）がそのまま効く。

### 4.2 却下: 「相手の悪手を咎める」を条件にする

**相手の手の CPL ≥ 悪手閾値だった直後の、自分の手番の局面**を拾う案は採らない
（決定・2026-09-08。当初は採用していたが、実データで取り下げた）。

- 🔴 **咎め損ねれば評価値が落ちるので、「自分の悪手」が同じ局面を拾う。** 条件として
  独立に持つ必要が無い。
- 🔴 **咎めた場合に残るのは自明な 1 手だけ。** dev DB で測ったところ、この条件で拾えた
  **13 問すべてが「実戦で自分が正解を指した局面」**だった（損失 0）。相手の悪手の直後は
  取り返すだけのことが多く、実際に取り返している。
- 「咎め損ねた局面だけに絞る」案（実手の損失 ≥ 疑問手閾値）も試したが、**同じデータで 0 問**。
  さらに「自分の悪手」として拾えた 4 問のうち**相手の悪手の直後は 0 問**で、
  **ラベルとしても立たなかった**。
- 🔒 **条件を 1 つ減らす方を採る。** 拾わない条件を持ち続けると、抽出・enum・文書の 3 か所が
  実体の無い分岐を抱える。

### 4.3 却下: 「一手勝負」を軸にする

**rank1 − rank2 の差が大きい局面をすべて出題する**案は採らない（決定・2026-09-08）。
別解の判定が要らなくなる利点はあったが、「**相手が駒を取ってきたので取り返す**」のような
**自明な 1 手が同じ条件に乗る**。自明さを機械的に除く基準（「取り返し」の定義）が作れない。

⚠ **同じ自明さは他の条件にも混ざりうる**ので、§7.1 の**手動除外**を受け皿として置く。
⚠ ただし**除外ボタンは少数の例外を受けるためのもの**で、大量に押させる設計は破綻している
——§4.2 で条件ごと取り下げたのはそれが理由。

## 5. 採点

### 5.1 次の一手

**最善との差（手番側視点 cp）で 3 段階に分ける。**

| 差 | 判定 |
|---|---|
| ≤ `DRILL_CORRECT_MARGIN` | 正解 |
| ≤ 疑問手閾値 | 惜しい |
| それ以上 | 不正解 |

🔴 **差（cp）を取る前にスコア型で分岐する**（レビュー `OCL-95952BDD`）。候補手のスコアには
`cp` と `mate` があり（[03](./03-data-model.md) §4）、**mate が絡む変化では cp 差を計算しない**
（[01](./01-domain.md) §5・`cpl.ts` が CPL を計算しないのと同じ理由）。

| 回答手のスコア | 判定 |
|---|---|
| **正の `mate`**（自分が詰ます） | **正解**。差は取らない——詰みは cp の量ではなく、最善が何であれ上回らない |
| **負の `mate`**（自分が詰まされる） | **不正解**。差は取らない |
| `cp` | 上の許容差表で 3 段階 |

- **`drillAttempts.loss` は null 可**（§6.2）。mate が絡む回答は損失を持たない。
- 🔒 **出題側で rank1 が `mate` の局面を `best` 種別にしない**（§4.1 の kind 決定規則）。
  最善が詰みなら**問いは「詰ませてください」**であり、cp 差で採点する問題ではない。

- 🔴 **`cpl.ts` の閾値を流用しない**（決定・2026-09-08）。疑問手閾値（既定 300）を正解の線に置くと
  **正解がいくつもある局面ができる**。出題は「**実質的に正解が 1 つ**」に寄せたいので、
  **独自の許容差を持つ**（`/settings` で変更可。既定値は実データで決める。§10）。
  🔒 **判定の道具（`labelOf`）は共有するが、線引きの値は共有しない。**
  ⚠ [12](./12-position-lab.md) §3.2 で検討盤の採点を `labelOf` に委ねたのは「**損失の基準が
  2 つあってはいけない**」という理由だったが、そこで揃えたのは**同じ画面に並ぶ悪手マーカー**との
  一貫性で、出題の合否は別の問い（「これを正解と呼ぶか」）である。
- **候補手 3 本に入っている手はその場で採点する**（エンジン往復ゼロ）。
- **3 本の外の手は非同期でエンジンに採点させる**（[12](./12-position-lab.md) §2.4 の名指し評価をそのまま使う。
  **server / worker の変更は要らない**）。「判定しています」を出し、損失と咎め筋まで返す。
  ⚠ 本番は `ENGINE_MOVETIME` 1 秒 + worker の polling 10 秒間隔なので、**待ちは十数秒になりうる**。
  🔒 **正解手順をなぞる限りこの待ちが発生しない**ように設計を組んである（§5.2 も同じ）。

### 5.2 実戦詰将棋（指し継ぎ）

正解手順は rank1 の **pv をそのまま使う**。

1. ユーザーの手が pv の攻方の手と一致 → **受方は pv の応手を自動で指す** → 次を要求。
2. 最後まで一致したら詰み上がり＝正解。
3. 一致しなければ**名指し評価へ回す**。`mate` が返れば**別解として正解**とし、
   🔴 **返ってきた pv を以降の正解手順として引き継ぐ**——別解に入っても最後まで指し継げる。
   ⚠ **その手で詰み上がったなら `continue` ではなく `done`**（レビュー `OCL-0007A49D`）。
   `continue` を「まだ続く」の意味に限らないと、解答後の情報を付けられないまま
   **同じ解答を投げ直しても永久に `continue` が返る**。
4. `mate` が返らなければ「その手では詰みません」＋**咎め筋**（受けの手）を見せる。

🔴 **「候補なし」で返った名指し評価を「詰みません」と読まない**（レビュー `OCL-7ABC2973`）。
`searchmoves` 非対応と判定された worker は**手を適用した局面を評価するフォールバック**に落ちるが
（[12](./12-position-lab.md) §2.2）、**その手が即詰みなら相手に指す手が無く、候補は空で返る**
（数字を捏造しないための正しい挙動）。仕様どおりに `mate` の有無だけで読むと、
**別解の即詰みが「詰みません」になる。**

- **判定は `shared` の `gameover` と同じ観測事実で行う**（[05](./05-analysis.md) §2.2 / `mate-line.ts`）——
  **その手を適用した局面で受方の玉が王手されている**かつ**エンジンが指す手を持たない**なら、
  **詰み上がり＝正解**とする。`isAttackedBy` は `shared` にあり、**新しいルールの実装にはならない**（§3）。
- 🔒 **王手の確認を省かない。** 候補が空になるのは入玉宣言（`win`）でも起きうる。
  `mate-line.ts` が `gameover` から `win` を除いているのと同じ理由で、**王手が条件**。
- 🔒 **`searchmoves` が効く経路のために API を変えない。** そちらは現局面を探索するので
  即詰みの手には `mate` が返り、この分岐に入らない。**判定は出題側に閉じる。**

- ⚠ **受方の応手は pv 1 本の観測**（`mate-line.ts` の但し書きと同じ）。他の受け方は出さない。
  **「受けが無い」ことは mate スコアが保証している**ので、手順が 1 本でも問題は成立する。
- ⚠ pv が mate 距離より短い・読めない場合は分類が `unknown` に落ちるので、そもそも §4.1 で出題されない。

### 5.3 エンドポイント

| Method | Path | 内容 |
|---|---|---|
| GET | `/api/drills/next` | 次の 1 問（`kind` で絞れる）。**答えを含む列は返さない** |
| GET | `/api/drills/counts` | 総数 / 解答済み / 正解の数 |
| POST | `/api/drills/:id/answer` | 解答。`{ line, correctMargin?, closeMargin? }` |
| POST | `/api/drills/:id/exclude` | 「自明だった」（§7.1）。以後の出題から外す |
| GET | `/api/drills` | 問題の一覧（§7.2）。絞り込み・並べ替え・50 件ページング |
| GET | `/api/drills/:id` | 一覧から選んだ 1 問。`/drills/next` と**同じ形**を返す |
| GET | `/api/drills/attempts` | 解答履歴の一覧（§7.3）。50 件ページング |
| POST | `/api/drills/:id/unexclude` | 除外の取り消し（§7.2）。履歴の除外フラグを落とす |

- 🔴 **採点は server が持つ。** 正解手と候補手をクライアントへ先に渡すと、**答えが見えた状態で
  出題する**ことになる（§7.1 で棋譜詳細から出題しないのと同じ理由）。`/drills/next` が返すのは
  **出題局面の SFEN と問いだけ**で、棋譜・手数・正解は解答の応答で初めて返る。
- **`line` は出題局面からの全手順**（受方の応手を含み、最後がユーザーの手）。`best` は 1 手、
  `mate` は詰み上がりまで積み上がる。**server は状態を持たずに手順を再現できる。**
- 🔴 **`line` は「その問いの手順」でなければ受け付けない**（400。レビュー `OCL-41F41851`）。
  `best` は 1 手ちょうど、`mate` は**いま持っている正解手順の先頭と一致**していること。
  任意の派生局面を作らせると、**別の局面で採点して出題局面の最善値と比べる**ことになり、
  採点も解答履歴も問いと噛み合わなくなる。
- 応答は `status`: `done`（採点確定）/ `continue`（詰みが**まだ続く**・`reply` は受方の応手）/
  `pending`（エンジン待ち。`jobId` で `GET /api/positions/evaluate/:jobId` を叩き、同じ body を
  投げ直す）。キューが一杯なら **503**、エンジンが失敗したら **502**。
- 🔒 **別解に入った後の正解手順は server が覚える**（メモリ・30 分）。クライアントへ渡すと
  **以降の答えを渡すのと同じ**になり、覚えないと**1 手ごとにエンジン待ち**が入る（§5.1）。
  再起動で消えるが、そのときは聞き直すだけで答えは変わらない。

### 5.4 一覧と履歴の口

🔴 **一覧も履歴も、答えを含む列を返さない**（`answerMove` / `answerPv` / `candidates` /
`playedMove` / `playedLossCp`）。`/drills/next` と同じ規則（§5.3）。

- 🔒 **棋譜名・対局日・手数は未解答の問題でも返す**（決定・2026-09-10）。伏せるのは
  **解く画面**の規則（§7.1）で、一覧は解く画面ではない。**棋譜詳細を先に開かない**のは
  閲覧者の規律に委ねる——伏せると一覧から問題を見分けられず、一覧の用を成さない。
- `GET /api/drills/:id` は所有者の問題だけを返し（他人の問題は 404）、**除外した問題も返す**
  ——一覧から名指しで開く経路なので、出題順（§6.3）の除外とは別の話。
  ⚠ **`/drills/next` と `/drills/counts` より後ろに登録する**——`:id` が先だと固定の口を飲み込む。

**`GET /api/drills` のクエリ**（[04](./04-ingestion.md) §6.1 の棋譜一覧と同じ形）:

| パラメータ | 値 | 既定 | 説明 |
|---|---|---|---|
| `page` | 1〜 | `1` | 50 件ページング。`pagination.total` も同じ条件で数える |
| `kind` | `mate` \| `best` | なし | 出題の種類。**解くタブと同じつまみ**（§7.4） |
| `status` | `all` \| `unanswered` \| `wrong` \| `correct` | `all` | 解答状況。`wrong` は**まだ正解していない**問題（§6.3 の 2 段目と同じ母集団） |
| `excluded` | `hide` \| `only` | `hide` | 「自明だった」で外した問題（§7.1） |
| `sort` | `played` \| `status` | `played` | `played` は棋譜の対局日（`coalesce(playedAt, createdAt)`）降順。`status` は §6.3 の段順。同値は `drills.id` を副キーに添える |

返す行は **`id` / `kind` / `matePlies` / 解答状況 / 解答回数 / 最終解答日時 / 除外フラグ /
棋譜（`kifuId` / タイトル / 対局日 / 手数）**。

**`GET /api/drills/attempts` のクエリ**: `page`（50 件）/ `kind` /
`verdict`（`all` \| `correct` \| `close` \| `wrong` \| `excluded`）。
並びは `createdAt` 降順で、**同値は `id` 降順を副キーに添える**（ページ間で行が重複・欠落しないため）。

返す行は **`id` / `drillId` / `kind` / 解答時刻 / 指した手 / 判定 / 損失 cp /
その問題の何回目か / 棋譜（`kifuId` / タイトル / 対局日 / 手数）**。

- **指した手は日本語表記にして返す**。web は履歴の画面に盤面を持たないので、
  表記に要る盤面（`shared` の `board.ts`）を **server 側で作る**。
- 🔴 **表記を作る盤面は「出題局面」ではなく「その手を指した局面」**（レビュー `OCL-A1E622FE`）。
  詰将棋は**指し継ぎ**（§5.2）なので、記録される手は手順の**最後の 1 手**で、その駒は
  出題局面には**居ない・別の駒種になっている**ことがある。出題局面から読むと
  **駒名が欠ける・別の駒として表示される**。盤面は**出題局面に `line` の 1 手前までを適用**して作る
  （§6.2 の `line`）。
- ⚠ **`line` を持たない既存の行は USI のまま出す**——復元できない表記を作らない。
- **`POST /api/drills/:id/unexclude`** はその問題の履歴の `excluded` をすべて落とす
  （§6.2 のとおり印は履歴側にある）。所有者の問題だけを対象にし、他人の問題は 404。

## 6. データモデル

### 6.1 `drills`（出題）

- 一意キーは `(kifuId, moveNumber, kind)`（`kind` = `mate` | `best`）。
- **正解の材料を焼き付けて持つ**（rank1 の手・スコア・pv、許容差の判定に使う候補手のスコア）。
  🔴 **解析が再実行されても、出題中の問題の答えが黙って変わらないため。**
- 生成来歴（`analysisRevision` / 生成時の閾値 / 生成器の版）を持つ。**再生成は upsert**（`id` を保つ）。
- 棋譜名・手数・対局者は `kifuId` から引けるので**持たない**（伏せるのは表示の仕事。§7.1）。
- ⚠ **FK に `ON DELETE CASCADE` が乗っているかを `show create table` で確かめる**
  （drizzle-kit が新規テーブルの CASCADE を落とす。`AGENTS.md`。**発現は棋譜の削除時**）。

### 6.2 `drillAttempts`（解答履歴）

- `drillId` / 指した手 / 判定（`correct` | `close` | `wrong`）/ 損失（**null 可**。§5.1）/ 解答時刻。
- 🔒 **不正解も必ず記録する。** 落とすと「以前間違えた」ラベルにも解答済み件数にも
  出題順（§6.3）にも表れない（レビュー `OCL-2652C1DA`）。
- **除外フラグ**（§7.1）もここに持つ。🔒 **出題側に持たない**——再生成で消えうるため。
- **除外だけを記録する行は `move` / `verdict` が null**。⚠ **件数と出題順はこの行を数えない**
  （`drillCounts` が `move is not null` で数えているのと同じ扱い）。履歴の一覧には**出す**（§7.3）。
- 🔴 **履歴の一覧に合わせて `createdAt` の索引を足す**（§7.3 は新しい順で 50 件ずつ引く）。
  現状の索引は `drillId` だけで、所有者で絞るには `drills` → `kifus` の join が要る。
- 🔴 **解答の手順（`line`）を足す**（レビュー `OCL-A1E622FE`。出題局面からの全手順・受方の応手を含み、
  最後がユーザーの手。§5.3 の `line` そのもの）。**日本語表記を作る盤面がこれでしか決まらない**
  ——詰将棋は指し継ぎなので、記録される 1 手だけでは**どの局面で指した手かが分からない**。
  🔒 **表記そのものは持たない。** 保存するのは手順（データ）で、日本語は読み出し側で作る。
  ⚠ **既存の行は `line` が null**（次の一手は 1 手なので実害は無く、詰将棋は USI のまま出す。§5.4）。
- ⚠ **一覧（§7.2）は既にある列の読み出しで足りる。** 列を足すのは履歴の表記のためだけ。

### 6.3 出題順

**未出題 > 間違えた問題 > 正解済み**の 3 段階（決定・2026-09-08）。段の中はランダム。

- **間違えた問題には「以前間違えた」ラベルを出す**（何を復習しているかが分かる）。
- 🔒 **間隔反復（SRS）は採らない。** 次回出題日の管理が要り、得るものに対して重い。
  履歴を持っておけば後から載せられる。

## 7. 画面（web）

### 7.1 解くタブ

- 入口は専用ページ **`/drills`**。
  🔴 **棋譜詳細から直接は出題しない**——その画面では**答えが既に見えている**。
- 出題中は**棋譜名・手数・対局者を伏せる**。解答後にその局面への導線を出す。
- 盤は検討盤と**同じ部品**（`BoardGrid` / `HandDisplay` / `lib/study.ts` のタップ 2 段）を使うが、
  **フル編集はさせない**。動かせるのは**手番側の駒だけ**で、手番トグルも駒箱も出さない。
- **着手可能マスを薄く塗り、そこ以外へは動かせない**（`shared` の `moveDestinations` /
  `dropDestinations`。§3）。⚠ **選択マスより弱い強調にする**——同じ強さだと、どこを
  選んでいるのかが読めなくなる。
  🔴 **塗るだけにしない**（レビュー `OCL-1A2B07B9`）。塗るだけだと**歩を横に動かす・飛車が
  駒を飛び越える**手を盤から作れてしまい、server の `validateMoveOnPosition` は
  **駒の動き方を見ない**（検討盤のフル編集も同じ道を通るため）のでエンジンまで届く。
  🔒 **解答の経路では server も同じ検証を掛ける**（`isReachableMove`）。
  ⚠ `validateMoveOnPosition` には足さない——検討盤で歩を横に動かせるのは**仕様**（prd/12 §2.5）。
- 🔒 **「成」は成れる手のときだけ出す**（`shared` の `canPromoteMove`）。検討盤の
  `canTogglePromotion` はフル編集向けで打った駒まで成らせるため、そのまま使うと
  **押せるのに server が 400 を返すボタン**ができる。⚠ 規則は server の検証と同じ出所にする。
- **種類（すべて / 詰み / 次の一手）で絞れる**。種類は問いそのものなので、
  出題中に見えていても手掛かりにならない。
  ⚠ **絞り込みを変えたら中身ごと作り直す**（レビュー `OCL-5AC2D54A`）。盤・手順・判定を
  state に持って進める画面なので、読み直しだけだと**前の問題が残る**。
- 解答後に出すのは**判定・正解手・詰み手順・咎め筋・実戦の手**と、その対局への導線。
  ⚠ **手数まで飛べる導線は無い**（棋譜詳細は手数を URL に持たない）ので、
  「N 手目を見る」とは書かない——飛べると読めてしまう。
- 解答後に **「自明だった」除外ボタン**を置く（§4.2）。押した問題は以後出題しない。
  🔒 **自動判定は作らない**（「取り返し」の定義から詰まる）。

### 7.2 一覧タブ（問題の一覧）

- 出すのは **種類・問い・解答状況（未解答 / 間違えた / 正解）・解答回数・最終解答日時**と、
  **棋譜名・対局日・手数**（棋譜詳細への導線を添える）。
- 🔴 **答えは一覧に出さない**（正解手・実戦の手・損失）。⚠ **棋譜名と手数は伏せない**
  （決定・2026-09-10。§5.4）——棋譜詳細を先に開かないのは閲覧者の規律に任せる。
- **行からその問題を解きに行ける**（`?tab=solve&drill=<id>`。§7.4）。現状の口は「次の 1 問」しか
  返さないので、**`GET /api/drills/:id` を足す**（§5.3）。
- **除外した問題は既定で出さない**（`excluded=only` で見られる）。
  **除外の取り消しボタンを一覧に置く**（`POST /api/drills/:id/unexclude`。§5.4）——
  外した理由を後から見直せないと、押すのが怖くなる。
- 絞り込みは**種類・解答状況・除外**、並べ替えは**対局日（既定・降順）/ 出題順**（§5.4）。
- ⚠ **正答率などの集計は出さない**（§10）。件数は既存の `/drills/counts` の 3 値だけを見せる。

### 7.3 履歴タブ（解答履歴の一覧）

- **1 行 1 解答**で新しい順。出すのは **解答時刻・種類・指した手・判定・損失 cp・棋譜と手数・
  その問題の何回目か**。⚠ 指した手の表記は `line` から作る（§5.4）。**`line` を持たない
  既存の詰将棋の行は USI のまま**出る。
- 🔒 **同じ問題の複数回をまとめない**——間違えた後に正解した経過が読めなくなる。
  1 問 1 行にまとめるのは一覧タブ（§7.2）の仕事。
- **「自明だった」の行も出す**（`move` / `verdict` が null。判定欄は「除外」）。
  🔒 落とすと、**一覧から問題が消えた理由を辿れない**。
- 絞り込みは**種類・判定**（正解 / 惜しい / 不正解 / 除外）。ページングは 50 件。
- 行から**棋譜詳細**と、**その問題を解き直す導線**を出す。⚠ 手数まで飛べる導線は無い（§7.1）。

### 7.4 タブと URL

🔒 **一覧と履歴は `/drills` の中にタブで置く**（決定・2026-09-10）。**別ルートは作らず、
`/stats` にも寄せない**——材料が同じで、解いた直後に一覧・履歴を見る行き来が多い。

- タブは検索パラメータ **`tab`**（`solve`（既定・省略時）/ `list` / `history`）。
  ルートは **`/drills` 1 本のまま**。
- **`kind` はタブをまたいで効く**（3 つとも種類で絞る意味がある）。
  一覧・履歴だけのつまみ（`page` / `status` / `excluded` / `verdict`）は**タブを移ったら落とす**。
- 一覧から解きに行く問題は **`drill=<id>`**（`tab=solve` のときだけ見る）。
  ⚠ **「次の問題へ」で `drill` を落とす**——残すと同じ問題が出続ける。
- ⚠ **検索パラメータを変えたら中身ごと作り直す**（§7.1 と同じ注意）。`loaderDeps` に
  `tab` / `drill` と一覧・履歴のつまみを含める。
- **成績の集計（種別別・戦型別の正答率・時系列推移）は今回も持たない**（§10）。
  載せるとしても**置き場所はこのタブ列**で、`/stats` へは寄せない。

## 8. 生成の運用

- **full 解析の完了時に生成**する（`analysisCompletedAt` を打つ経路に相乗りする）。
- 🔴 **主体側（`kifus.subjectSide`）が変わったら引き直す**（レビュー `OCL-20A343B8`）。出題は
  「自分の手番の局面」だけを拾う（§4.1）ので、名前候補をいじって主体側が動くと
  **相手側の局面が問題として残る**。名前候補の変更は所有者の全棋譜を舐めるため、
  **主体側が実際に変わった棋譜だけ**引き直す（[11](./11-users.md) §4.2）。
  🔒 **quick では作らない**（§2）。
- 🔴 **抽出の閾値は server が持つ**（`DRILL_BLUNDER_CP` / `DRILL_MATE_MAX_PLIES`。既定は
  `shared` の `DEFAULT_THRESHOLDS` と取りこぼしの既定 10 plies）。**採点の許容差（§5.1）とは
  別のつまみ**——こちらは「どの局面を問題にするか」、あちらは「その手を正解と呼ぶか」で、
  混ぜると閲覧者が閾値を動かすたびに**出題の在庫が入れ替わる**。
- **一括再生成スクリプト**を置く（`redetect-tactics.ts` / `rebuild-positions.ts` と同じ型——
  既定 dry-run・`*_APPLY=1` で実書込・本番はイメージ同梱の `dist/*.js` を使う。`AGENTS.md`）。
  閾値を変えたら流す。
- 🔴 **マイグレーションは空のテーブルを作るだけ**なので、**本番でも一度は一括生成を流す**。
  流し忘れると**出題が 1 問も出ない**（`kifu_positions` で踏んだのと同じ罠。`AGENTS.md`）。

## 9. 実装が要求する前提

- ✅ **`cpl.ts` を `shared` へ移した**（[02](./02-architecture.md) §3 の gap を消化）。出題の抽出は
  server 側で走るのに、CPL の判定は web にしかなかった。⚠ 閾値の**永続化**（localStorage +
  React hook）は web の `lib/thresholds.ts` に残す——**環境依存を `shared` に持ち込まない**ため。
- `classifyMateLine` は既に `shared` にあるのでそのまま使える。
- 名指し評価は [12](./12-position-lab.md) §2.4 の API をそのまま使う（**server / worker の変更は不要**の見込み）。
