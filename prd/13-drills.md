## 1. 動機

棋譜と解析は、いま**読むもの**にしかなっていない。同じ材料から**解くもの**を作れば、
「毎回同じところで落とす」を身体で覚え直せる。

材料は既に DB にある——`candidateMoves`（MultiPV 3・スコア・pv。ブラウザで解析した棋譜は MultiPV 1。[03](./03-data-model.md) §4）、
`kifuPositions`（局面索引。[10](./10-video-analysis.md) §3.2）、`kifus.subjectSide`（自分がどちら側か。
[11](./11-users.md)）。**新しいエンジン解析は要らない。**

## 2. スコープ

出題は 2 種。**器は 1 つ**（局面 + 正解 + 採点）で、違うのは正解の決め方だけ。

| 種別 | 問い | 正解 | 手数 |
|---|---|---|---|
| 実戦詰将棋 | ここで詰ませてください | 詰みが続く手 | **詰み上がりまで指し継ぐ** |
| 次の一手 | ここで何を指すべきでしたか | 最善との差が許容内の手 | **初手のみ** |

- 対象は**自分の対局だけ**。`source <> 'video'` を既定で強制する（[10](./10-video-analysis.md) §2.2 と同じ）。
- 材料は **`profile='full'` の解析行だけ**（[03](./03-data-model.md) §3）。
  🔴 **quick を混ぜない**——出題の答えが探索の浅さで揺れると、問題として成立しない
  （検討盤の再利用が full だけを引くのと同じ筋。[12](./12-position-lab.md) §2.6）。
  ブラウザの深い段（600ms・MultiPV 1）も `full` として保存する（[14](./14-multi-user.md) §5.2。実装済み）ので、この規則のまま材料になる。

## 3. 将棋のルールは実装しない

🔒 **合法手生成器は作らない**（[12](./12-position-lab.md) §2.5 の決定をそのまま通す）。
**詰将棋のルール（打ち歩詰め・連続王手の千日手・無駄合い）はフロントにも server にも持たない。**

- **正典はエンジンの側にある。** 「その手で詰みが続くか」は `mate` スコアが答えで、
  打ち歩詰めなら `mate` は返らない。**判定をエンジンに委ねればルールの実装が要らない。**
- フロントが持つのは「**選んだ駒がそのマスへ動けるか**」だけ。これは合法手の全列挙ではなく
  **単手の検証**で、`shared` の利き表（`position-validation.ts` の `STEPS` / `SLIDES`）と
  `validateMoveOnPosition` で足りる。着手可能マスのハイライトもここから出す。
  ⚠ **「合法手生成器を作らない」と矛盾しない**——列挙するのは選んだ 1 枚の行き先だけで、
  局面の全合法手を数え上げるわけではない。
- 二歩・行き所のない駒は既存の `validatePositionForEngine` が入力の時点で弾く。

⚠ **弱点**: 打ち歩詰めを指されたとき「**反則です**」とは言えず「**その手では詰みません**」に
なる。反則だと名指しするには詰み判定（＝受方の合法手の全列挙）が要るので、**やらない**。
出題の答え合わせとしては「詰まない」で十分に成立する。

## 4. 出題の抽出

### 4.1 3 つの条件

| 種別 | 条件 |
|---|---|
| **逃した詰み**（`mate`） | 自分の手番で rank1 が `mate`・`1 ≤ N ≤ 詰み手数上限`・`classifyMateLine` が `checkmate`・**実際には詰まさなかった** |
| **自分の悪手**（`best`） | 自分の手の CPL ≥ 悪手閾値（[05](./05-analysis.md) §2.3。**局面の評価値の大きさでは除外しない**） |

- 🔴 **`classifyMateLine = checkmate` を条件にする**（[05](./05-analysis.md) §2.2）。**詰将棋の形をした
  mate だけ**が選ばれ、必至や静かな手を含む筋は落ちる——「詰ませてください」という問いに
  `hisshi` / `forced` の筋を出すと、正解手順が王手の連続にならず問題として破綻するため。
- 詰み手数上限は `/settings` の**取りこぼし閾値**（[09](./09-analytics.md) §3.1・既定 10）を流用する。
  ⚠ この N は **engine の詰み距離（plies）**で、詰将棋の「N手詰」ではない（[01](./01-domain.md) §5）。
- 🔴 **rank1 が `mate` の局面は `best` 種別にしない**（決定・2026-09-08。レビュー `OCL-95952BDD`）。
  最善が詰みなら問いは「詰ませてください」で、cp 差の採点（§5.1）が成立しない。
  `classifyMateLine` が `checkmate` なら `mate` 種別として出題し、**それ以外（必至・静かな手を含む筋）は
  出題しない**。⚠ CPL は mate が絡むと算出されない（`cpl.ts`）ので実務上は自然にこうなるが、
  **規則として明示する**（抽出条件を足したときに静かに破れる種類の前提のため）。
- 🔒 **大差の局面の悪手も拾う**（決定・2026-09-16）。以前は「未決着（`|bestCp| < decided`）」を条件に
  含めていたが、決着閾値は判定ごと削除した（[05](./05-analysis.md) §2.3）。規則の変更なので
  `GENERATOR_REV` を `2` に上げてあり、**反映には一括再生成を流す**（§8）。
- 「逃した詰み」は [09](./09-analytics.md) §3.1 の**取りこぼしと同じ母集団**（あちらは負け局に限るが、
  こちらは勝敗を問わない）。`candidate_moves` の mate 用索引（[03](./03-data-model.md) §4）がそのまま効く。

### 4.2 却下: 「相手の悪手を咎める」を条件にする

**相手の手の CPL ≥ 悪手閾値だった直後の、自分の手番の局面**を拾う案は採らない
（決定・2026-09-08。当初は採用していたが、実データで取り下げた）。

- 🔴 **咎め損ねれば評価値が落ちるので、「自分の悪手」が同じ局面を拾う。** 条件として
  独立に持つ必要が無い。
- 🔴 **咎めた場合に残るのは自明な 1 手だけ。** dev DB で測ったところ、この条件で拾えた
  **13 問すべてが「実戦で自分が正解を指した局面」**だった（損失 0）。相手の悪手の直後は
  取り返すだけのことが多く、実際に取り返している。
- 「咎め損ねた局面だけに絞る」案（実手の損失 ≥ 疑問手閾値）も試したが、**同じデータで 0 問**。
  さらに「自分の悪手」として拾えた 4 問のうち**相手の悪手の直後は 0 問**で、
  **ラベルとしても立たなかった**。
- 🔒 **条件を 1 つ減らす方を採る。** 拾わない条件を持ち続けると、抽出・enum・文書の 3 か所が
  実体の無い分岐を抱える。

### 4.3 却下: 「一手勝負」を軸にする

**rank1 − rank2 の差が大きい局面をすべて出題する**案は採らない（決定・2026-09-08）。
別解の判定が要らなくなる利点はあったが、「**相手が駒を取ってきたので取り返す**」のような
**自明な 1 手が同じ条件に乗る**。自明さを機械的に除く基準（「取り返し」の定義）が作れない。

⚠ **同じ自明さは他の条件にも混ざりうる**ので、§7.1 の**手動除外**を受け皿として置く。
⚠ ただし**除外ボタンは少数の例外を受けるためのもの**で、大量に押させる設計は破綻している
——§4.2 で条件ごと取り下げたのはそれが理由。

## 5. 採点

### 5.1 次の一手

**最善との差（手番側視点 cp）で 3 段階に分ける。**

| 差 | 判定 |
|---|---|
| ≤ `DRILL_CORRECT_MARGIN` | 正解 |
| ≤ 疑問手閾値 | 惜しい |
| それ以上 | 不正解 |

🔴 **差（cp）を取る前にスコア型で分岐する**（レビュー `OCL-95952BDD`）。候補手のスコアには
`cp` と `mate` があり（[03](./03-data-model.md) §4）、**mate が絡む変化では cp 差を計算しない**
（[01](./01-domain.md) §5・`cpl.ts` が CPL を計算しないのと同じ理由）。

| 回答手のスコア | 判定 |
|---|---|
| **正の `mate`**（自分が詰ます） | **正解**。差は取らない——詰みは cp の量ではなく、最善が何であれ上回らない |
| **負の `mate`**（自分が詰まされる） | **不正解**。差は取らない |
| `cp` | 上の許容差表で 3 段階 |

- **`drillAttempts.loss` は null 可**（§6.2）。mate が絡む回答は損失を持たない。
- 🔒 **出題側で rank1 が `mate` の局面を `best` 種別にしない**（§4.1 の kind 決定規則）。
  最善が詰みなら**問いは「詰ませてください」**であり、cp 差で採点する問題ではない。

- 🔴 **`cpl.ts` の閾値を流用しない**（決定・2026-09-08）。疑問手閾値（既定 300）を正解の線に置くと
  **正解がいくつもある局面ができる**。出題は「**実質的に正解が 1 つ**」に寄せたいので、
  **独自の許容差を持つ**（`/settings` で変更可。既定値は実データで決める。§10）。
  🔒 **判定の道具（`labelOf`）は共有するが、線引きの値は共有しない。**
  ⚠ [12](./12-position-lab.md) §3.2 で検討盤の採点を `labelOf` に委ねたのは「**損失の基準が
  2 つあってはいけない**」という理由だったが、そこで揃えたのは**同じ画面に並ぶ悪手マーカー**との
  一貫性で、出題の合否は別の問い（「これを正解と呼ぶか」）である。
- **出題に焼き付けた候補手に入っている手はその場で採点する**（エンジン往復ゼロ）。手元 worker で解析した棋譜は 3 本、
  ブラウザで解析した棋譜は最善手 1 本。
- **候補手の外の手はエンジンに名指しで読ませて採点する。** 読む場所は解答した利用者の解析の担当（[14](./14-multi-user.md) §5.7）で決まる:
  - **担当 `worker`**: 手元 worker に非同期で読ませる（[12](./12-position-lab.md) §2.4 の名指し評価をそのまま使う）。
    「判定しています」を出し、損失と咎め筋まで返す。
    ⚠ 本番は `ENGINE_MOVETIME` 1 秒 + worker の polling 10 秒間隔なので、**待ちは十数秒になりうる**。
  - **担当 `browser`**（2026-10-15 決定・2026-10-16 実装）: **ブラウザが出題局面でその手を名指し（`go searchmoves <手>`）で 600ms 読む**
    （全局面解析の深い段と同じ時間。[14](./14-multi-user.md) §5.2）。損失は保存済みの最善手（full の値）との差、
    咎め筋は返った読み筋。受け渡しは §5.3。
    ⚠ 候補手が 1 本なので名指しが要る解答は増える。候補 3 本に入る手ももともと多くはない（実手で 72%・1 位は 43%。
    [決定ログ](./_grilling/decisions.md)「複数ユーザーへの開放」）ので、本数を増やすより外れた手をどう読むかの方が効く
  - 🔒 **正解手順をなぞる限りこの待ちが発生しない**ように設計を組んである（§5.2 も同じ）。
  - ⚠ **詰将棋は 2026-10-23 に改める**（決定のみ・未実装）: 担当によらずブラウザで、詰将棋向けの読み方（MultiPV 1・上限つき・スレッド固定）で読む（§5.5）。
    上の 2 つの分岐は**次の一手にだけ**残る。

### 5.2 実戦詰将棋（指し継ぎ）

正解手順は rank1 の **pv をそのまま使う**。

1. ユーザーの手が pv の攻方の手と一致 → **受方は pv の応手を自動で指す** → 次を要求。
2. 最後まで一致したら詰み上がり＝正解。
3. 一致しなければ**名指し評価へ回す**（担当 `browser` ならブラウザが同じ名指しで読む。§5.1。
   ⚠ 2026-10-23 決定・未実装: **担当によらずブラウザで読む**。§5.5）。`mate` が返れば**別解として正解**とし、
   🔴 **返ってきた pv を以降の正解手順として引き継ぐ**——別解に入っても最後まで指し継げる。
   ⚠ **その手で詰み上がったなら `continue` ではなく `done`**（レビュー `OCL-0007A49D`）。
   `continue` を「まだ続く」の意味に限らないと、解答後の情報を付けられないまま
   **同じ解答を投げ直しても永久に `continue` が返る**。
4. `mate` が返らなければ「その手では詰みません」＋**咎め筋**（受けの手）を見せる。
   **終わりにはしない**（2026-10-19）——その手を取り消して同じ局面で考え直せる（応答は `miss`。§5.3）。

🔴 **攻方の手は王手でなければならない**（2026-10-19 決定）。エンジンの `mate` は王手でない手（静かな手）や回り道も詰みと数えるので、
判定をエンジンに任せると**詰め損なっても延々と指し継げる**。出題の抽出（§4.1。pv の攻方の手が全て王手＝`classifyMateLine` の `checkmate`）と
判定を揃える。
- **王手かは server が盤面で見る**（手を適用した局面で受方の玉が攻方に利かされているか。`shared` の `isInCheck`＝`isAttackedBy`。§3 の
  「新しいルールの実装はしない」に反しない）。**エンジン（棋譜解析の再利用・手元 worker・ブラウザ）に回す前**に掛け、ブラウザに `evaluate` を返さない。
- 王手でなければ「**王手ではありません**」（`miss`・`not_check`）。その手を取り消して続けられる。
- **どの手にも同じに掛ける**（正解手順の手・別解の pv を引き継いだ手も）。ユーザーの手ごとに王手を要求すれば、別解の pv に静かな手が混ざっても一貫する。
- 🔒 **手数の上限は設けない**——王手の連続で詰むなら回り道でも別解として正解（実戦詰将棋なので「ゆるめ」）。受方の応手はエンジンの pv のまま
  （無駄合いもありうる。許容する）。
- 🔒 **盤の入力は王手の手に絞らない**（塗りが答えの手掛かりになる）。判定は server のまま。
- 🔴 **正解手順は元の pv と覚えた別解のどちらでも受ける**（§5.3）。覚えた別解だけで照らすと、「最初から」で元の手順を指したときに 400 になる。
  一致した方の手順から受方の応手を選ぶ。

🔴 **「候補なし」で返った名指し評価を「詰みません」と読まない**（レビュー `OCL-7ABC2973`）。
`searchmoves` 非対応と判定された worker は**手を適用した局面を評価するフォールバック**に落ちるが
（[12](./12-position-lab.md) §2.2）、**その手が即詰みなら相手に指す手が無く、候補は空で返る**
（数字を捏造しないための正しい挙動）。仕様どおりに `mate` の有無だけで読むと、
**別解の即詰みが「詰みません」になる。**

- **判定は `shared` の `gameover` と同じ観測事実で行う**（[05](./05-analysis.md) §2.2 / `mate-line.ts`）——
  **その手を適用した局面で受方の玉が王手されている**かつ**エンジンが指す手を持たない**なら、
  **詰み上がり＝正解**とする。`isAttackedBy` は `shared` にあり、**新しいルールの実装にはならない**（§3）。
- 🔒 **王手の確認を省かない。** 候補が空になるのは入玉宣言（`win`）でも起きうる。
  `mate-line.ts` が `gameover` から `win` を除いているのと同じ理由で、**王手が条件**。
- 🔒 **`searchmoves` が効く経路のために API を変えない。** そちらは現局面を探索するので
  即詰みの手には `mate` が返り、この分岐に入らない。**判定は出題側に閉じる。**

- ⚠ **受方の応手は pv 1 本の観測**（`mate-line.ts` の但し書きと同じ）。他の受け方は出さない。
  **「受けが無い」ことは mate スコアが保証している**ので、手順が 1 本でも問題は成立する。
- ⚠ pv が mate 距離より短い・読めない場合は分類が `unknown` に落ちるので、そもそも §4.1 で出題されない。

### 5.4 一覧と履歴の口

🔴 **一覧も履歴も、答えを含む列を返さない**（`answerMove` / `answerPv` / `candidates` /

  閲覧者の規律に委ねる——伏せると一覧から問題を見分けられず、一覧の用を成さない。
- `GET /api/drills/:kifuNo/:moveNumber/:kind` は所有者の問題だけを返し（他人の問題は 404）、**除外した問題も返す**
  ——一覧から名指しで開く経路なので、出題順（§6.3）の除外とは別の話。
  （パスが 3 段なので、`/drills/next` などの固定の口とはぶつからない）

**`GET /api/drills` のクエリ**（[04](./04-ingestion.md) §6.1 の棋譜一覧と同じ形）:

| パラメータ | 値 | 既定 | 説明 |

| `status` | `all` \| `unanswered` \| `wrong` \| `correct` | `all` | 解答状況。`wrong` は**まだ正解していない**問題（§6.3 の 2 段目と同じ母集団） |

| `sort` | `played` \| `status` | `played` | `played` は棋譜の対局日（`coalesce(playedAt, createdAt)`）降順。`status` は §6.3 の段順。同値は `drills.id` を副キーに添える |

棋譜（`kifuId` / タイトル / 対局日 / 手数）**。

> ⚠ **2026-10-23 の改定案（未実装）**: 解答状況の `wrong` / `correct` を**最後の判定**で読む（§6.4「間違えた問題」）。

> 行に**出題局面の SFEN** を足す（カードの盤の縮図。§7.7。答えではない——解く画面でも最初に見せる局面）。
> 並べ替え（`sort`）は対局日だけにし、`status` の並び（旧 §6.3 の段順）は外す。絞り込みは状態（未解答 / 間違えた / 正解 / 除外）と種類。

**`GET /api/drills/attempts` のクエリ**: `page`（50 件）/ `kind` /
`verdict`（`all` \| `correct` \| `close` \| `wrong` \| `excluded`）。

### 5.5 詰将棋の判定をブラウザで読む（2026-10-23 決定・未実装）

🔒 **詰将棋の 1 手ごとの判定（正解手順と違う手を指したとき。§5.2 の 3）は、解析の担当によらずブラウザの WASM エンジンで読む**
（担当 `worker` の所有者も）。**次の一手は今のまま**（担当に従う。§5.1）。

- **動機**: 手元 worker に回すと 1 手ごとに十数秒待ちうる（§5.1。`ENGINE_MOVETIME` + polling の間隔）。詰将棋は「ゆるめ」（2026-10-19）で、
  間違えた手を取り消して何度でも指し直せるので、エンジンに回る手が増える。やねうら王は MultiPV 1 なら詰みを読み切った時点で自分で止まるので、
  ブラウザで名指しで読めば、短い詰みは一瞬で答えられる。
- **正解手順をなぞる手はエンジンを通らない**（§5.2 の 1。pv との照合）。棋譜解析の再利用（§5.3）を先に引くのも、王手の確認（§5.2）を
  エンジンより前に掛けるのも今のまま。

**読み方**:

- `position sfen <局面>` → **`go movetime <上限> searchmoves <手>`**、**MultiPV 1**。`searchmoves` は最後に置く（§5.3 の注意のまま）。
  読みの間だけ `GenerateAllLegalMoves` を有効にするのも今のまま。
- **根拠**（2026-08-29 の実測。本番の PC のネイティブのやねうら王）: MultiPV 1 のとき、詰みを読み切ると上限の前に自分で止まる——
  7 手詰は 16ms 以内、9 手詰は 66〜200ms。13 手以上の詰みは見つけても止まらない（上限まで読む）が、1 秒で 21 手詰まで見つけた。
  ⚠ **MultiPV 3 では早く止まらない**。
  ⚠ **この値はネイティブのもので、WASM は数倍遅い見込み**（下の実測で確かめる）。
- ⚠ **`go mate` は使わない。** 通常のビルドでは時間で止まらず、エンジンが固まる。
- 判定は今と同じく `judgeNamedEvaluation`（§5.3）: 正の `mate` なら別解として正解（返った pv を以降の正解手順として覚える）、
  それ以外（`cp`・負の `mate`）は「その手では詰みません」（`miss`・`no_mate`）、「候補なし」は盤面で詰み上がりかを見る（§5.2）。

**思考時間の上限**（未決。実測して決める。仮に **1 秒**）:

- 🔴 **時間内に詰みが見つからないことは、不詰の証明ではない。** 上限が短すぎると、**長い別解を「詰みません」と取りこぼす**。
  正解手順そのものは pv との照合なので取りこぼさない——起きうるのは正解手順と違う手（別解）だけ。
- **実測の手順**: dev の詰将棋の在庫の全問について、正解手順の各手と、詰まない手（王手だが詰まない手）を WASM で読ませ、
  **正解を「詰まない」と取りこぼす率**と**所要時間**（手数ごと）を測る。上限の候補ごとに比べる。
- 取りこぼしが出るなら、上限を上げるか、**詰将棋専用のエンジン（df-pn）**を検討する。df-pn は不詰を証明できるが、
  WASM のビルドと配布物が 1 種類増える（[14](./14-multi-user.md) §5.5 の配り方・ライセンスの扱いもそのぶん増える）。
- 値は server の定数で 1 か所に持ち、`evaluate` の応答の `settings` で渡す（全局面解析の full の設定とは別の値。§5.3）。

**スレッド数**（未決。実測して決める）:

- 🔒 **全局面解析の負荷の設定（`engineHost.ts` の `analysisThreads`。[14](./14-multi-user.md) §5.10 の「全力」「控えめ」）とは別に、

**採点と信用**:

- 🔒 **採点は server が持つ**（§5.3）。ブラウザの結果は信用できない入力で、検証は今のまま（`shared` の `analysis-limits.ts` の値・

**ブラウザのエンジンが使えないとき**（既定として決めた）:

- 同意の前・配信の設定で使えない・解析できない環境（[14](./14-multi-user.md) §5.10）では、**今の経路に戻る**——担当 `worker` なら手元 worker
  （`pending`）、担当 `browser` なら「この端末では採点できない」（§5.3）。

  担当 `worker` ならそれを見て手元 worker にジョブを積む。申告が無ければ `evaluate` を返す。申告を偽っても手元 worker を使えるのは
  担当 `worker`（所有者）だけなので、絞り込み（[14](./14-multi-user.md) §5.7）は崩れない。
- ⚠ **担当 `worker` の利用者の端末では、いま常駐の解析が動かない**（エンジンの一覧も取りに行かない。[14](./14-multi-user.md) §5.10）。
  詰将棋の判定のためだけにエンジンを用意する（全局面解析は回さない）経路が要る。同意をどこで求めるかは未決（§10）。

## 6. データモデル

### 6.1 `drills`（出題）

- 一意キーは `(kifuId, moveNumber, kind)`（`kind` = `mate` | `best`）。
- **正解の材料を焼き付けて持つ**（rank1 の手・スコア・pv、許容差の判定に使う候補手のスコア）。
  🔴 **解析が再実行されても、出題中の問題の答えが黙って変わらないため。**
- 生成来歴（`analysisRevision` / 生成時の閾値 / 生成器の版）を持つ。**再生成は upsert**（`id` を保つ）。
- 棋譜名・手数・対局者は `kifuId` から引けるので**持たない**（伏せるのは表示の仕事。§7.1）。
- ⚠ **FK に `ON DELETE CASCADE` が乗っているかを `show create table` で確かめる**
  （drizzle-kit が新規テーブルの CASCADE を落とす。`AGENTS.md`。**発現は棋譜の削除時**）。

### 6.2 `drillAttempts`（解答履歴）

- `drillId` / 指した手 / 判定（`correct` | `close` | `wrong`）/ 損失（**null 可**。§5.1）/ 解答時刻。
- 🔒 **不正解も必ず記録する。** 落とすと「以前間違えた」ラベルにも解答済み件数にも
  出題順（§6.3）にも表れない（レビュー `OCL-2652C1DA`）。
- **除外フラグ**（§7.1）もここに持つ。🔒 **出題側に持たない**——再生成で消えうるため。
- **除外だけを記録する行は `move` / `verdict` が null**。⚠ **件数と出題順はこの行を数えない**。履歴の一覧には**出す**（§7.3）。
- **「答えを見る」（諦め）の行は `verdict='wrong'`・`move` が null**（2026-10-19。`line` はそこまで確定した手順・空配列可・`lossCp` null）。**列は足さない**——
  「`verdict='wrong'` かつ `move` が null」＝諦め、「`verdict` null・`move` null」＝除外だけの行。
  🔴 **「解答した」は `verdict is not null` で数える**（件数・解答回数・最終解答日時・何回目か・判定の絞り込み。`drill-list-query.ts` / `drill-query.ts`）。
  以前は `move is not null` だったので、そのままだと諦めが解答に数えられない。
- 🔒 **記録は 1 問 1 回**（2026-10-19）。詰将棋は「**一度も間違えず・答えも見ずに詰ませた**」ときだけ `correct`。**最初に間違えた時点**
  （その手の行・`wrong`）か**答えを見た時点**（諦めの行）で `wrong` を 1 行記録し、以後のその問題の操作は練習（§5.3）で記録しない。
  1 手戻す・最初からをしただけ（間違えていない）なら記録は未確定のまま。記録が済んだかは web が画面の状態で持つ。
- 🔴 **履歴の一覧に合わせて `createdAt` の索引を足す**（§7.3 は新しい順で 50 件ずつ引く）。
  現状の索引は `drillId` だけで、所有者で絞るには `drills` → `kifus` の join が要る。
- 🔴 **解答の手順（`line`）を足す**（レビュー `OCL-A1E622FE`。出題局面からの全手順・受方の応手を含み、
  最後がユーザーの手。§5.3 の `line` そのもの）。**日本語表記を作る盤面がこれでしか決まらない**
  ——詰将棋は指し継ぎなので、記録される 1 手だけでは**どの局面で指した手かが分からない**。
  🔒 **表記そのものは持たない。** 保存するのは手順（データ）で、日本語は読み出し側で作る。
  ⚠ **既存の行は `line` が null**（次の一手は 1 手なので実害は無く、詰将棋は USI のまま出す。§5.4）。
- ⚠ **一覧（§7.2）は既にある列の読み出しで足りる。** 列を足すのは履歴の表記のためだけ。

### 6.3 出題順

> ⚠ **改定済み** → §6.4「入口ごとの出題順」（2026-10-23。未実装）

**未出題 > 間違えた問題 > 正解済み**の 3 段階（決定・2026-09-08）。段の中はランダム。

- **間違えた問題には「以前間違えた」ラベルを出す**（何を復習しているかが分かる）。

### 6.4 入口ごとの出題順（2026-10-23 決定・未実装）

出題は**入口**（ホームのカード。§7.5）ごとに選ぶ。DB は変えない（`drillAttempts` の判定と時刻、`kifus` の対局日から決まる）。

- 🔒 **「間違えた問題」は、最後の記録の判定が正解でない問題**（既定として決めた）。解き直して正解すると外れる。
  - 「最後の記録」は `verdict is not null` の行のうち最新（§6.2。除外だけの行は数えない・諦めは `wrong` として数える）
  - ⚠ **`close`（惜しい）も「正解でない」に入れる**（解き直して正解するまで繰り返す側。Claude の判断）
  - 除外した問題（§7.1「自明だった」）は**どの入口にも出さない**（今の規則のまま）
  - ⚠ 旧 §6.3 の「間違えた」（一度も正解していない）とは母集団が違う。一覧の解答状況（§5.4）も同じ定義に揃える

| 入口 | 在庫と順序 |
|---|---|
| **おすすめ**（種類混在） | 上の段から順に、**空でない段から選ぶ・段の中はランダム**: ① 間違えてから **1 日以上**経った「間違えた問題」 ② **直近 30 日**の対局の未解答 ③ その他の未解答 ④ 正解済み（最後の解答が古い順） |
| **詰将棋** | 詰将棋の未解答（ランダム） |
| **次の一手** | 次の一手の未解答（ランダム） |
| **間違えた問題** | 「間違えた問題」（種類混在・最後の解答が古い順） |

- 🔒 **間違えた直後は（おすすめに）出さない**——答えを覚えているうちに解き直しても練習にならない。1 日経つまではおすすめのどの段にも入らない
  （未解答でも正解済みでもないため）。「1 日」は最後の解答からの 24 時間。
- 🔒 **間違えた問題は、解き直して正解するまで繰り返し出る**（①に戻ってくる）。間隔反復（旧 §6.3）は今回も採らない——段は 1 日の待ちだけで、
  次回出題日を持たない。
- 「直近 30 日」は対局日（`coalesce(playedAt, createdAt)`。§5.4 の並びと同じ）で数える。
- ⚠ **入口「詰将棋」「次の一手」は未解答だけを在庫にする**（ホームのカードが「未解答 N」を出すのと揃える。Claude の判断）。解き直しはおすすめと
  「間違えた問題」が受け持つ。
- ⚠ **入口「間違えた問題」は 1 日の待ちを掛けない**（自分で選んで入る入口なので。Claude の判断）。最後の解答が古い順なので、間違えた直後の問題は後ろに回る。
- 🔒 **同じ回（§7.6）で記録した問題は、その回には出さない**（入口「間違えた問題」で間違え続けると同じ問題が出続け、④が古い順に一巡しても終わらないため）。
  在庫が尽きたら「この入口の問題はもうありません」とし、ほかの入口とホームへの導線を出す。⚠ 答えずに「次の問題」で飛ばした問題は記録が無いので、
  同じ回にまた出うる（許容する）。
- 「以前間違えた」ラベル（旧 §6.3）は維持する。

### 7.4 タブと URL

> ⚠ **一部改定済み**（タブ式・`tab`・成績の集計を持たない）→ §7.5・§7.8（2026-10-23。未実装）。
> 問題を 3 つ組で指す・表示したら常に URL に載せる・解答の結果を復元しない・盤を読み込みごとに作り直す・検索パラメータの名前を衝突させない、は維持

🔒 **一覧と履歴は `/drills` の中にタブで置く**（決定・2026-09-10）。**別ルートは作らず、
`/stats` にも寄せない**——材料が同じで、解いた直後に一覧・履歴を見る行き来が多い。

- タブは検索パラメータ **`tab`**（`solve`（既定・省略時）/ `list` / `history`）。
  ルートは **`/drills` 1 本のまま**。
- **`kind` はタブをまたいで効く**（3 つとも種類で絞る意味がある）。
  一覧・履歴だけのつまみ（`page` / `solved` / `excluded` / `sortBy` / `verdict`）は
  **タブを移ったら落とす**。
  ⚠ **検索パラメータの名前を他のルートと衝突させない。** 同じ名前は**ルートをまたいで型が
  突き合わされる**ので、棋譜一覧（[04](./04-ingestion.md) §6.1）の `status` / `sort` と
  同名で別の値域を持つと、**関係の無い画面の型が壊れる**（実際に踏んだ）。
  一覧の解答状況は `solved`、並びは `sortBy` にしてある（API 側は `status` / `sort`）。
- 解くタブで表示している問題は **`kifu=<棋譜の番号>&ply=<moveNumber>&drillKind=<種類>`**（`tab=solve` のときだけ見る）。
  🔒 **3 つ揃って 1 問を指し、欠けていればどれも無いのと同じ**（[14](./14-multi-user.md) §4.4。改定・2026-10-12。
  以前は出題の行の ID を `drill=<id>` で載せていた——旧形式の URL は読まず、次の 1 問を選ぶ）。
  ⚠ 名前は絞り込みの `kind` と**ぶつけない**（`drillKind`）。`ply` は棋譜詳細の `ply` と同じ数え方（局面の手数）・同じ型。
  🔒 **表示したら常に URL に載せる**（決定・2026-09-27）——載せないと、解答後に棋譜詳細へ
  移って**戻るボタンで戻ったとき、loader が別の問題を選び直す**。一覧・履歴から名指しで開くのも同じ口。
  - 問題の指定が無いときは loader が次の 1 問を選び、それを載せた URL へ **redirect する**
    （router は loader の redirect を **replace** で扱うので履歴は積まない）。置き換え先は
    問題を指すので 2 度目は名指しの取得に入り、ループしない。取得は 2 回になる
    （`/drills/next` → `/drills/:kifuNo/:moveNumber/:kind`）が、**取得経路を loader の 1 本に保つ**方を取る。
  - **「次の問題」は問題の指定を落として replace で移る**だけ。次の 1 問は上の経路で loader が選ぶ。
  - 戻ってきた問題は**未解答の状態で**出す（解き直しと同じで、答えれば履歴が 1 件増える）。
    🔒 **解答の結果は復元しない**——判定の正典は server で、URL に持つのは問題の指定だけ。
  - 盤は**読み込みごとに作り直す**（読み込みの通し番号を `key` にする）。⚠ 問題の指定を `key` に
    すると、「次の問題」で**同じ問題がまた選ばれた**とき（段の中はランダム。§6.3）に解答後の表示が残る。
    ⚠ そのため loader の読み直しは**裏で走らせない**（`staleReloadMode: 'blocking'`）——既定の
    stale-while-revalidate だと、戻るボタンで古い結果を描いたあとに盤が作り直される。
  - 問題の指定と `kind` が食い違っても指定の問題を出す（名指しが優先）。次の問題から `kind` で絞る。
    指定の問題が存在しない（404）ときは「出題が見つかりません」を出す（「解く」タブで次の問題へ戻れる）。
- ⚠ **検索パラメータを変えたら中身ごと作り直す**（§7.1 と同じ注意）。`loaderDeps` に
  `tab` / `drill` と一覧・履歴のつまみを含める。
- **成績の集計（種別別・戦型別の正答率・時系列推移）は今回も持たない**（§10）。
  載せるとしても**置き場所はこのタブ列**で、`/stats` へは寄せない。
  ⚠ 2026-10-23 改定: 種類ごとの正答率を**ホーム**（§7.5）に持つ。`/stats` へ寄せないのは同じ

### 7.5 ホーム（2026-10-23 決定・未実装）

`/drills`（問題の指定も入口も無いとき）は**ホーム**。押したら解く画面へ入る（§7.6）。

- **入口のカード**: 「**おすすめ**」「**詰将棋**（未解答 N）」「**次の一手**（未解答 N）」「**間違えた問題**（N 問）」。出題順は §6.4。
  在庫が 0 の入口は押せない形で出す（数が 0 と分かれば足りる）。問題が 1 問も無ければ、まだ問題が無い旨だけを出す。
- **種類ごとの正答率**（旧 §10 の未決「成績の集計を持つか」→ 持つ）。詰将棋・次の一手のそれぞれで出す。**推移（時系列）は今回は持たない**。
  - ⚠ **正答率の定義は「初見の正答率」**＝解いた問題のうち、**最初の記録が正解**だった割合（分母は記録のある問題の数。除外した問題は数えない。
    Claude の判断——「最後の記録」で数えると、間違えた問題を解き直すほど 100% に近づき、実力を映さない。記録の延べ数で数えると、
    間違えた問題を繰り返すほど下がる）。解いた問題の数も並べる。
- **問題の一覧へのリンク**（§7.7）。
- 🔒 `/stats` には寄せない（旧 §7.4 のまま）。画面に内部の用語を出さない（§7.1 のまま）。

### 7.6 解く画面の流れ（2026-10-23 決定・未実装）

> 盤・判定・操作ボタン・伏せる規則は §7.1 のまま。ここで決めるのは入り方・続け方・解いた後のボタンの並び。

- 🔒 **連続出題は区切らない。**「次の問題」で、その入口の在庫が尽きるまで続く（「10 問で 1 セット」のような区切りは置かない）。
- **画面の上部**に「**この回 N 問中 M 問正解**」程度の経過と「**ホーム**」ボタンを置く。
  - 「この回」はホームの入口から入ってから、ホームへ戻るまで。⚠ 解いた後の「次は詰将棋」などで入口を切り替えても同じ回のまま（Claude の判断）。
  - 数えるのは**記録した解答**（§6.2。1 問 1 回）で、練習（記録しない操作）は数えない。M は記録の判定が正解の数。
  - 🔒 **クライアント側で持ち、永続化しない**（タブの寿命の記憶で足りる。棋譜詳細へ移って戻るボタンで戻っても続くように、
    画面のコンポーネントの状態ではなくタブ単位で持つ）。根拠: 判定の正典は server の解答履歴で、成績はホームの正答率（§7.5）が集計する。
    この回の数は解いている間の手応えで、消えても記録は何も失われない。server に「回」を持たせると、回がいつ終わったか（閉じた・放置した）を
    決める必要が出るのに、得るものが無い。
  - 回の開始時刻を次の 1 問の取得に渡し、この回で記録した問題を出さない（§6.4）。
- **解いた後のボタン**（上から）:
  1. **大きいボタン**: 入ってきた入口の続きの次の問題（「次の問題（詰将棋）」のように入口が分かる文言）
  2. **入口の切り替え**: 「次は詰将棋」「次は次の一手」（今の入口と同じになるものは出さない）
  3. その下に「**元の対局**」（§7.1 の導線）・「**やり直す**」（§7.1 の解答後の「最初から」。練習）・「**自明だった**」・「**ホーム**」
  - 一覧（§7.7）から名指しで開いた問題（入口が無い）は、大きいボタンを「**一覧に戻る**」にする（Claude の判断）
- **在庫が尽きたら**「この入口の問題はもうありません」と出し、ほかの入口とホームへの導線を置く。
- 解答後に「**この問題の解答履歴**」を出す（§7.7）。

### 7.7 問題の一覧（カード）（2026-10-23 決定・未実装）

🔒 **一覧と履歴を統合する**——問題ごとに**カード 1 枚**。**スマホ前提**で、今の横長の表をやめる（狭い幅では 1 列）。

- カードに出すのは **小さな盤の縮図**（出題局面。解く画面と同じ向き）・**種類**（詰将棋なら手数。出題中のバッジと同じエンジンの手数）・
  **状態**（未解答 / 間違えた / 正解 / 除外。§6.4 の定義）・**解答回数**・**対局日**。
  ⚠ 棋譜名と棋譜詳細への導線はカードに載せない（Claude の判断。決定のカードの項目に無く、狭い幅を取る。対局へは解いた後の「元の対局」で辿る）。
- **押すとその問題を解く**（名指し。§7.8）。
- 🔴 **答えは出さない**（旧 §7.2 のまま。正解手・実戦の手・損失）。盤の縮図は出題局面なので答えではない。
- **絞り込みは状態・種類**。並びは対局日の新しい順、ページングは今の 50 件のまま。**除外した問題は既定で出さず**、状態「除外」で見られる。
  除外のカードに「除外を取り消す」を置く（旧 §7.2 の理由のまま——外した理由を後から見直せないと、押すのが怖くなる）。
- **解答ごとの履歴は問題を開いた先で見る**（解く画面の解答後。時刻・指した手・判定・損失。諦め・除外の行の出し方は旧 §7.3 のまま）。
  🔒 **解答の前には出さない**——正解の記録の「指した手」は答えそのもの。解答の前に見せてよいのは回数と状態（カードと同じ）。
  ⚠ 全体の解答履歴（旧 §7.3）が担っていた「問題が一覧から消えた理由を辿る」は、状態「除外」の絞り込みが受け持つ。

### 7.8 URL（2026-10-23 の改定案・未実装）

ルートは **`/drills` 1 本のまま**。検索パラメータで画面が決まる:

| URL | 画面 |
|---|---|

  一覧の状態は今の `solved` を使い、値に `excluded` を足す（今の `excluded=only` はこれに畳む）。

- 「この回」の開始時刻は URL に載せない（§7.6。タブの寿命の記憶）。

  「自分の手番の局面」だけを拾う（§4.1）ので、名前候補をいじって主体側が動くと
  **相手側の局面が問題として残る**。名前候補の変更は所有者の全棋譜を舐めるため、

- 🔴 **抽出の閾値は server が持つ**（`DRILL_BLUNDER_CP` / `DRILL_MATE_MAX_PLIES`。既定は
  `shared` の `DEFAULT_THRESHOLDS` と取りこぼしの既定 10 plies）。**採点の許容差（§5.1）とは
  別のつまみ**——こちらは「どの局面を問題にするか」、あちらは「その手を正解と呼ぶか」で、
  混ぜると閲覧者が閾値を動かすたびに**出題の在庫が入れ替わる**。
- **一括再生成スクリプト**を置く（`redetect-tactics.ts` / `rebuild-positions.ts` と同じ型——
  既定 dry-run・`*_APPLY=1` で実書込・本番はイメージ同梱の `dist/*.js` を使う。`AGENTS.md`）。
  閾値や抽出規則（`GENERATOR_REV`）を変えたら流す。
- 🔴 **マイグレーションは空のテーブルを作るだけ**なので、**本番でも一度は一括生成を流す**。
  流し忘れると**出題が 1 問も出ない**（`kifu_positions` で踏んだのと同じ罠。`AGENTS.md`）。
