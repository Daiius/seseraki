# 11. ユーザー（自分）

本章は「**自分**」を server 側のデータとして持つ仕組みを定める。現在は「自分」の定義が
**web の env**（`VITE_SELF_NAMES` ∪ `VITE_SWARS_USER_ID`）にあり、server は何も知らない。
これを DB へ移し、勝敗・戦型の自分/相手判定、および局面検索の主体側モード
（[10](./10-video-analysis.md) §3.3）を server 側で解けるようにする。

認証そのものは [07](./07-auth-and-privacy.md)、棋譜スキーマは [03](./03-data-model.md) を参照。

> **全体が計画中**（2026-08-17 時点で未実装）。設計判断とその根拠を定め、実装はここを正典とする。

---

## 1. 目的とスコープ

### なぜ移すのか

1. 🔒 **判定の正が 2 つある状態を作らない。** 局面検索の主体側モード（[10](./10-video-analysis.md) §3.3）は
   server が「どちらが自分か」を知らないと解けない。web の env を server にも複製すると、
   **片方だけ更新して食い違ったとき、画面のどの数字が正しいか分からなくなる**
2. **将来の他ユーザー招待に備える。** 時期は先だが、`ownerId` を後から足すのは
   「nullable で追加 → 全行 backfill → NOT NULL へ」の 3 手順になり、**招待というもっとも忙しいときに乗る**

### 今回やること

- `users` / `userAliases` を作り、**名前候補を DB に持つ**
- `kifus.ownerId`（このデータを持っている人）と `kifus.subjectSide`（主体の手番）を足す
- web の「自分」判定（`lib/self.ts`）を server へ移し、env を廃止する

### スコープ外

- **招待の本体** — ユーザーごとの資格情報、セッションへの userId 紐づけ、全クエリの所有者スコープ。
  ログインは当面**単一アカウント**（[07](./07-auth-and-privacy.md)）のままで、
  **セッションは常にただ一人の `users` 行を指す**
- **動画解析の可視性** — 他ユーザーへ見せるかは [10](./10-video-analysis.md) §8.3 で保留した論点。
  判断材料（棋譜データの共有可否）が揃っていない

## 2. `users` と `userAliases`

```
users
├── id: serial PK
├── displayName: varchar(100)    -- 画面に出す名前。対局者名とは別
├── createdAt / updatedAt

userAliases
├── id: serial PK
├── userId: bigint FK → users.id (CASCADE)
├── name: varchar(100) UNIQUE    -- 棋譜の対局者名と突き合わせる値
├── validFrom: date?             -- 有効期間（§4）。既定は無期限
├── validTo: date?
└── createdAt
```

### 2.1 名前候補は別テーブルにする

🔒 **`name` に UNIQUE を張る。** 別のユーザーが同じ対局者名を登録できると、
**同じ棋譜が 2 人の「自分の対局」になり、両方の成績に入る**。json 列やカンマ区切りでは
この制約を DB で守れない。

クエリの形はどの持ち方でも同じ（候補を読んで `inArray` に渡す）ので、差が出るのは
**一意性を DB で守れるか**だけ——そしてそれは、将来ユーザーが増えたときに問題になる場所。

⭐ **swars の ID も同じ表の 1 行**として入れる。現在も `VITE_SELF_NAMES ∪ VITE_SWARS_USER_ID` と
区別せず統合しており、扱いを変える理由がない。

### 2.2 名前候補は「これまで使った名前の集合」

⚠ **旧名を候補から消してはいけない。** 消すと、その名前で指した過去の棋譜が「自分の対局」で
なくなり、**成績から静かに落ちる**。名前を変えたときは**足す**。

## 3. `kifus.ownerId`

```
kifus.ownerId: bigint NOT NULL → users.id
```

🔒 **意味は「このデータを持っている人」であって、対局者ではない。** 動画解析の棋譜も
**投入した人**が所有者で、対局者は別の話（`sente` / `gote`）。消す権利を持つのは所有者。

**単一ユーザーの間は全行が同じ値になる**が、それでも今入れる。理由は
**「誰のものか」を判断せずに埋められるのが今だけ**だから——現時点では全行が自明にただ一人のもので、
`NOT NULL` まで一気に持っていける。ユーザーが増えてから足すと、既存行の所有者を**推定する**ことになり、
`sente`/`gote` の名前から当てるか、当たらない行を手で振り分けることになる。

🔴 **ただし「既存行があるので nullable を経由する」ことは避けられない。** `NOT NULL` の列を
既存データのあるテーブルへいきなり足すと、MySQL は暗黙の既定値（`bigint` なら `0`）を入れ、
**`users` に存在しない値を指すので FK の作成で落ちる**。移行の手順は §6.1 に定める。

## 4. `kifus.subjectSide`（主体の手番）

```
kifus.subjectSide: enum('sente' | 'gote')?   -- 導出値
```

「この棋譜の主体はどちらの手番か」。局面検索の主体側モード（[10](./10-video-analysis.md) §3.3）と、
勝敗・戦型の自分/相手判定に使う。

### 4.1 導出規則

| `source` | 規則 |
|---|---|
| `video` | `videoKifuSources.bottomIsSente`（画面の下＝録画者）から決まる |
| それ以外 | **所有者の名前候補**と `sente` / `gote` の突き合わせ |

**両対局者とも候補に一致したら NULL**（ambiguous）。側を確定できない対局は実在し、
[09](./09-analytics.md) §4 でも勝率の分母から外している。**同じものを、ここでは「後手」として数えない。**

### 4.2 保存する。クエリ時に導出しない

**導出規則が `source` ごとに違う**（上表）ので、クエリ時に解くと
`EXISTS(alias for sente)` と `EXISTS(alias for gote)` と `bottomIsSente` を組み合わせた `CASE` を
検索・集計のたびに評価することになる。索引が効かず、同じ式が何箇所にも散る。

🔒 **派生値なので、作り直しの経路を用意する**（`kifuTactics` / `kifuPositions` と同じ立場）:

1. **棋譜の投入 / `reanalyze`** — その棋譜だけ
2. **名前候補の変更** — **その所有者の棋譜だけ**（`ownerId` で絞る）を**同一トランザクション**で更新。
   ⚠ 手動の再導出に頼ると、名前候補を変えた直後に**画面の数字が古いまま**になり、
   しかも間違っていることが画面から分からない
3. **全件再構築コマンド** — 導出規則そのものを直したとき

## 5. 名前の有効期間

### 5.1 何を解くのか

名前候補は集合（§2.2）なので、**旧名を他人が使い始めたとき**に衝突する:

```
自分が "A" → "B" に改名。"A" は候補に残す（過去の棋譜のため）
  ↓ 別の誰かが "A" を名乗る
その人と対局: sente="B"（自分）/ gote="A"（相手）
  ↓ 両方が候補に一致
主体側を確定できない（ambiguous）
```

`userAliases.validFrom` / `validTo` で**時間で分離する**。

### 5.2 既定は無期限。衝突したときだけ埋める

🔒 **最初から正確に入力させない。** 既定は両方 NULL（無期限）で、**衝突に気づいたときに調整する**。
改名日の境界がずれても、**直せばよい**——そして 1 回の設定で**複数局がまとめて直る**。

⚠ **期間で解けないもの**: **同時期に同名の別人**（同姓同名・アプリ間の名前衝突）は時間で分離できない。
**1 局ごとの主体側の上書き**を将来の拡張として残す（§7）。実際に発生したら足す。

### 5.3 対局日時が不明な棋譜では期間を無視する

`playedAt` が NULL の棋譜（日時不明の手動 KIF）では、**期間を見ずに名前の一致だけで判定する**。

⚠ **これは意図的な妥協**。「この名前はこの時期だけ自分」と言った意図を、日時の分からない棋譜には
適用できない。厳密には「判定しない」方が筋だが、**日時不明の棋譜で主体側が決まらない方が実害が大きい**
（日時不明の棋譜は少数で、かつそれが衝突している確率はさらに低い）。

🔒 **`createdAt` で代用しない。** `createdAt` は「取り込んだ日」であって対局日ではない。
過去の KIF をまとめて貼り付けると全部「今日」になり、**期間判定が根本から狂う**。
一覧の並び順に `coalesce(playedAt, createdAt)` を使うのとは意味が違う
（並びは「だいたいの新しさ」で足りるが、こちらは判定の根拠になる）。

## 6. 移行

🔒 **名前候補を 2 箇所で持つ期間を作らない。** 片方だけ更新して食い違うと、
一覧の勝敗バッジと局面検索の主体側が黙って食い違う。

### 段階 A — server に持たせる（web は変えない）

- `users` / `userAliases` / `kifus.ownerId` / `kifus.subjectSide` をスキーマに入れる（順序は §6.1）
- **初期データを backfill**（§6.2）
- API が `subjectSide` を返し始める

⭐ **[10](./10-video-analysis.md) の段階 3b（主体側モード）は、ここで通せる。** `subjectSide` が DB に
あれば局面検索は動くので、web の切り替えを待たない。

#### 🔒 段階 A と B の間に名前候補を変えない

この段階では web はまだ env を見ている。**backfill した時点では両者は一致する**（DB の値は env から
作ったもの）が、**その後 env を変えても DB へ同期する経路が無い**。変えると、一覧の勝敗バッジ（env 由来）と
局面検索の主体側（DB 由来）が黙って食い違う。

したがって:

- **段階 A と B は連続してリリースする。** A を出したまま放置しない
- **その間に名前候補を変えない。** 変える必要が生じたら、**B を先に終わらせてから** `/settings` で変える
- ⚠ この条件は**運用でしか守れない**（server は env を読めないので、食い違いを検知できない）。
  A と B を分けるのは PR を読める大きさに保つためであって、**中間状態を長く置くためではない**

### 段階 B — web を切り替え、env を廃止

- `lib/self.ts` の `getSelfNames` / `resolveUserSide` を廃止し、API が返す `subjectSide` を使う
  （呼び出しは一覧・棋譜詳細・エクスポート・分析・盤の反転の 5 箇所）
- `VITE_SELF_NAMES` / `VITE_SWARS_USER_ID` を削除する
- **`/settings` に「自分」セクション**を足す（§6.3）

### 6.1 `ownerId` を足す順序

🔴 **既存データのあるテーブルに `NOT NULL` + FK の列をいきなり足せない**（§3）。**同じデプロイの中で**
次の順に進める:

1. `users` / `userAliases` を作る
2. **単一ユーザーの行を作る**（backfill の `--apply`。§6.2）
3. `kifus.ownerId` を **nullable** で足す
4. **全行を埋める**（backfill）
5. `ownerId` に **`NOT NULL` と FK** を付ける

⚠ **3〜5 の間に棋譜が投入されると `ownerId` が NULL のまま残り、5 で落ちる。** 投入経路は
web（`POST /kifus`）と動画解析の取り込み（API_KEY）で、いずれも**人が明示的に叩く**ものなので、
**移行の間は投入しない**。worker は `kifus` に行を足さない（`moveAnalyses` だけ）ので影響しない。

### 6.2 初期データは backfill の引数で渡す

```bash
pnpm db:backfill-user --display "<表示名>" --names "<名前1>,<名前2>,..." [--apply]
```

1. `users` 行を作る（無ければ）
2. `userAliases` に名前候補を入れる
3. `kifus.ownerId` を全行に設定する
4. `kifus.subjectSide` を導出する

🔒 **env にもコードにも名前を残さない。**
- **env に置くと消し忘れる。** そして env の方が目に付くので、後から読んだ人が**そちらを正だと思う**
- **コードに埋めると公開される。** 対局者名・swars ID は公開リポに置かない
  （[README](./README.md) §秘匿方針）

⚠ **既定は dry-run**（`--apply` を付けたときだけ書き込む）。既存の backfill（`db:backfill-tz`）と同じ姿勢。

### 6.3 管理 UI（`/settings`）

表示名・名前候補の一覧（追加/削除）・各候補の有効期間。**期間の欄は既定で空**にし、
「名前の衝突が起きたときだけ埋める」ことを画面の説明文で明示する。

⚠ **CLI だけにしない。** 期間の調整は「衝突に気づいたときに直す」操作なので、
画面から触れないと実質使われない。
