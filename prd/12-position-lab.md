# 12. 検討モードと局面評価（position lab）

本章は「元の棋譜から派生した任意局面をエンジンに評価させる」機能群を定める。
worker の解析基盤は [05](./05-analysis.md)、LLM 解説との接続は [06](./06-llm-commentary.md) を参照。

---

## 1. 動機

- 棋譜解析（[05](./05-analysis.md)）は**実戦に現れた手**しか評価しない。MultiPV 3 の候補手に
  入らなかった手について「なぜこの手はダメなのか」を知る手段がない。
- 「銀が 1 つ横にいたら評価はどうだったか」のような**到達不能な仮想局面**も確かめたい。
- この評価能力を LLM にツールとして渡せば、「この手はダメだったのか」という問いかけに
  答えられる解説（[06](./06-llm-commentary.md)）へ発展する。

## 2. 評価基盤（worker / server）

### 2.1 worker: 既存エンジンへの相乗り

- interactive な局面評価ジョブは、**棋譜解析の局面境界で優先処理**する（新プロセスは立てない）。
  worker は 1 局面解析するごとにループを回っており（[05](./05-analysis.md) §1.1b）、そこが自然な割り込み点。
  最大待ち ≈ 現局面の解析残り時間 + ポーリング間隔。
- USI は毎回 `position` で局面を明示するため、割り込みによるエンジン状態の汚染はない。
  置換表の共有は許容する（interactive 局面は閲覧中の棋譜の派生局面で、むしろエントリを共有できる側）。
- **探索時間のパラメータは棋譜解析と同一**（`ENGINE_MOVETIME` / `ENGINE_DEPTH`）。

### 2.2 評価は 2 種

| 種別 | USI | 返すもの |
|---|---|---|
| 局面評価 | `go`（MultiPV 3） | 候補手 3 本とスコア |
| 名指し評価 | `go searchmoves <手>` | **その手の**スコアと読み筋（= 相手の最善の咎め筋） |

- 名指し評価が本命。「候補に現れなかった手はなぜダメか」に、損失（最善との差）と咎め筋で直接答える。
- 🔴 **局面評価は MultiPV を自分で設定してから探索する**（worker・実測 2026-08-28）。棋譜解析
  （[05](./05-analysis.md)）は解析の終わりに MultiPV を 1 へ戻すため、エンジンの設定に乗るだけだと
  **同じ要求が「棋譜解析の最中なら 3 本・アイドルなら 1 本」と worker の状態で揺れる**。
  設定した値は探索後に元へ戻すので、割り込まれた棋譜解析の候補手数は変わらない。
  名指し評価は返すのがその手 1 本だけなので MultiPV を触らない。
- 🔴 **局面評価の 3 本は固定で、棋譜解析の `ENGINE_MULTIPV` には乗らない。** `ENGINE_MULTIPV` は
  運用で増減してよいつまみだが、3 本は API の契約で web / MCP（§4）がこれを前提に組む。
  同じ値に乗せると `ENGINE_MULTIPV=1` の構成で局面評価まで 1 本になり、契約が壊れる。
- ⚠ 実装時にやねうら王の `searchmoves` 対応を確認する。非対応なら「手を適用した局面を評価し
  符号を反転して返す」フォールバックで同じ API 契約を守る（エンジン的には裏表の関係）。

### 2.3 評価値は手番側から見た値

- **評価値は常にその局面の手番側から見た値**（プラス = 手番側が有利）とする（決定・2026-08-28）。
  評価値グラフ（先手視点・[05](./05-analysis.md) §2.4）とは視点が異なるが、検討盤は
  「この局面で指すならどうか」の文脈なのでこちらを優先する。
- 🔴 **「評価リクエストは自分手番の局面のみ受け付ける」（決定・2026-08-20）は撤回する**（決定・2026-08-28）。
  **手番を問わず評価できる。** server は単体の SFEN から「どちらが自分か」を知りようがなく、
  実装は元からこの読み方になっていた。検討盤には手番トグル（§3）があるので、
  「相手にこう指されたらどうか」も同じ道具で調べられる。

### 2.4 server: メモリ内キュー兼キャッシュ

- ジョブキューと結果キャッシュを **server プロセスのメモリ内**に持つ（DB テーブルは足さない。決定・2026-08-20）。
  キーは正規化 SFEN（+ 評価種別・名指し手）。同一局面の再訪は即答。
- 再起動で消えることは許容する（web が再要求すれば済む）。エンジン構成変更時の古いキャッシュも
  再起動で消えるため、[08](./08-roadmap.md) の「解析来歴は持たない」と整合する。
- worker 向けに claim / 結果報告のエンドポイントを追加（既存 worker API と同じ API_KEY 系統・outbound polling は不変）。
- web / LLM 向けは**結果が出るまで待って返す**（long-poll。数秒〜十数秒で LLM ツール呼び出しのタイムアウトに収まる）。
- ジョブの完了には**失敗も含む**（`failed` + エラー内容）。失敗したジョブは待機中の long-poll に
  エラーを返して完了させる（結果もエラーも返さないまま待たせ続けない）。

#### エンドポイント（M1 実装）

| Method | Path | 認証 | 内容 |
|---|---|---|---|
| POST | `/api/positions/evaluate` | セッション | `{ sfen, move? }`。`move` があれば名指し評価。**結果が出るまで待って返す**（long-poll） |
| GET | `/api/worker/position-jobs` | API_KEY | 待っているジョブを 1 件 claim（無ければ `null`） |
| POST | `/api/worker/position-jobs/:id/result` | API_KEY | 結果 `{ candidates, fallback }` または失敗 `{ error }` を報告 |

- 応答は `{ sfen, move, status: 'done' | 'failed', … }`。`sfen` は**読み直して書き戻した正規化キー**
  （手数の有無や書き方の揺れで同じ局面が別扱いにならないようにする）。
- 検証で弾いた局面・指し手は **400**（違反の一覧を添える）、キューが一杯なら **503**。
- 期限（`POSITION_EVAL_QUEUE_TIMEOUT_MS` / `POSITION_EVAL_RUN_TIMEOUT_MS`・既定 120 秒）を過ぎた
  ジョブは `failed` で完了させる。**待たせ続けない**ための最後の砦。

### 2.5 局面検証（エンジン保護）

- 合法手生成器は**作らない**（決定・2026-08-20。フル編集を許すため合法性は問わない）。
- 代わりに**エンジンをクラッシュ・ハングさせない最小検証**を `shared` に置く:
  両玉の存在 / 二歩 / 行き所のない駒（1 段目の歩香・1〜2 段目の桂）/ 駒数上限
  （歩 18・香桂銀金各 4・角飛玉各 2）/ 手番側が相手玉を即取れる状態。
- 検証失敗はエンジンに渡さず 4xx で返す。
- **名指し評価の手も同じ検証で見る。** 駒の動き方（合法性）は判定しないが、**その手を適用した
  局面**に上と同じ検証をかける——フォールバックは `position … moves <手>` で**適用後の局面を
  エンジンに渡す**ので、渡る局面が条件を満たさなければ意味がない（相手玉を取る手・成れない駒の
  成り・打って二歩になる手・自玉を取られる形で手番を渡す手は、いずれもここで落ちる）。
- 検証を通ってもエンジンが落ちる・返ってこない可能性は残る。このときは**当該ジョブを `failed` で完了**させ（§2.4）、
  worker は**エンジンを再起動して次のジョブへ進む**。エンジン再起動・タイムアウトの機構は棋譜解析の
  ポイズンピル対策（[05](./05-analysis.md) §1.1a）と共通でよいが、**失敗の記録先は独立**——interactive ジョブには
  対応する棋譜も世代も無いため、元棋譜の `analysisError` / `analysisRevision` には一切触れない。
- SFEN 直列化・検証は `shared`（既存 `position.ts` / `board.ts` を確認して拡張）。web と server の双方が使う。

### 2.6 既に分かっている評価値を先に引く

🔴 **エンジンに投げる前に、既存の棋譜解析の結果を引く**（決定・2026-08-28）。検討の起点は閲覧中の
棋譜の局面で、数手動かすまでは**解析済みの局面をなぞっているだけ**のことが多い。同じ答えを
待って計算し直す理由がない。

- 渡された正規化 SFEN が**解析済みの棋譜局面と一致する**なら、答えは `moveAnalyses` / `candidateMoves`
  （[03](./03-data-model.md) §3・§4）に既にある。局面索引 `kifuPositions`（[10](./10-video-analysis.md) §3.2）が
  正規化 SFEN から棋譜局面を引けるので、それを使う。
- **局面評価**（`move` なし）: 一致する棋譜局面があり、**保存された候補手が 3 本揃っている**なら、
  それをそのまま返す。🔴 **3 本に満たない解析結果は再利用せず、エンジン評価へ回す**（`source: 'engine'`）。
  棋譜解析の候補手数は運用つまみ `ENGINE_MULTIPV` で変わりうる一方、**局面評価の 3 本は web / MCP が
  前提にする API の契約**（§2.2）だからで、M1 で候補手数を `ENGINE_MULTIPV` から切り離したのと同じ理由。
  **再利用の都合で契約を崩さない。**
- **名指し評価**: その手が候補手に入っていればそのスコアと読み筋を返す。実手は**次の局面の評価から引ける**
  （手番が入れ替わるので符号を反転する）。⚠ **こちらは 3 本揃っている必要はない**——返すのは名指しした
  その手 1 本なので、候補手にその手が入ってさえいれば足りる。
  **候補手に無い手・棋譜から離れた派生局面はこれまでどおりエンジンへ。**
- DB の候補手スコアは**手番側から見た値**（エンジンが返す生の値）で入っているので、検討盤の表示視点（§2.3）と
  そのまま噛み合う。
- ⚠ **応答に「どちらから来た値か」を示す印を付ける**（例: `source: 'kifu' | 'engine'`）。解析時のエンジン設定
  （depth / movetime）が現在と違いうるため、**黙って混ぜない**。
- 🔒 **判定は server の 1 か所に置く。** web と MCP（§4）の双方に効かせるためで、web 側に同じ判定を持たせない。

## 3. 検討盤（web）

🔴 **「検討モード」というモードは作らない**（決定・2026-08-28）。棋譜詳細ページ（[05](./05-analysis.md) §2）の
盤面がそのまま検討盤で、**駒を動かした時点で検討が始まる**。§3 冒頭にあった「検討モードトグルを置く」は撤回する。

### 3.1 検討の始まり方

- **盤面をタップ（クリック）したら、それが駒の選択。** タップ 2 段（駒を選ぶ → 行き先を選ぶ）で駒が動く。
  ドラッグ&ドロップは採らない（リポジトリに前例が無く、[05](./05-analysis.md) §2.1 の
  「連打・誤タップに強く」という方針とも噛み合わないため）。
- 🔴 **盤面の左右半分タップによる手送りは廃止する**（決定・2026-08-28。[05](./05-analysis.md) §2.1
  「盤面の左右タップ」（決定・2026-07-21）を撤回）。**駒の選択と真正面から衝突する**ので両立できない。
  手送りは既存の操作ボタン行（◀ ▶・スライダー）とキーボードに一本化する。廃止してよい根拠は、
  この導線が実際にはほとんど使われていないこと。
- **駒を動かすまで画面は今と変わらない。** 動かすと操作パネル（棋譜に戻る / 手番トグル /
  成・不成 /「評価する」）が現れる（段階的開示）。
- 🔴 **操作パネルは 1 行に収める**（決定・2026-08-29）。ラベルのままだと 390px で 2 行に
  折り返していたので、**主操作以外をアイコン・1 文字に畳む**:

  | ボタン | 見た目 | 幅 |
  |---|---|---|
  | 棋譜に戻る | 戻るアイコンのみ | 正方形（44px） |
  | 手番 | 入れ替えアイコン + **`☗` / `☖` の記号** | 内容ぶん（下限 44px） |
  | 成 / 不成 | **`成` / `不成` の字** | 内容ぶん（下限 44px） |
  | 評価する | **ラベルのまま** | **md 未満は残り幅いっぱい / md 以上は内容ぶん** |

  - 🔴 **手番の記号は落とさない。** このボタンは操作であると同時に「**今どちらの手番か**」の
    状態表示を兼ねている。手番を自由に入れ替えられる検討盤で記号を消すと、今どちら番なのかが
    画面から消える——**評価値の視点は手番側**（§2.3）なので読み違いに直結する。
    ⚠ 記号は**枠内で読める大きさ**にする（390px の実機で ☗ と ☖ の塗り分けが判別しづらかった）。
    **字（先 / 後）を足すのではなく、今ある記号を読めるようにする**——足すと 1 行に収めた意味が薄れる。
  - 🔴 **「評価する」の幅は md を境に規則を変える**（決定・2026-08-29）。
    **md 未満は残り幅いっぱい**（`flex-1`）で、「成」の出入りで空く幅をこのボタンが吸うので
    行の見え方が安定する。**md 以上は内容ぶん**に戻す。
    - **なぜ境を作るか**: 390px の実測では残り幅いっぱいでも内容ぶんでも**差は 10px**しかない
      （アイコン 3 つと「検討中」バッジで幅がほぼ埋まっている）。一方デスクトップ（棋譜詳細の
      行幅 736px）では**「評価する」が 534px の帯**になる。1 つの規則で通すと
      **狙いだったモバイルでは効かず、デスクトップだけ壊れる**。
  - 🔒 **アイコンのみのボタンは正方形にして 44px 基準を守る**（[05](./05-analysis.md) §2.1）。
    高さだけ 44px にして幅が潰れれば的は小さいままなので、高さと同じ幅を明示する。
    **`aria-label` を必ず付ける**（ラベルが画面から消えるため。`title` も残す）。
  - 🔒 **枠を付ける**（`btn-outline`）。アイコンのみのボタンは、枠が無いと**押せるものだと
    分からず、44px のタップ範囲も画面から読めない**。4 つの見た目を揃える。
  - ⚠ 「成 / 不成」は条件付きで出入りするので、**その分の幅が動いても崩れない**組み方にする。
  - ⚠ **320px のような狭い幅では折り返して 2 行になる**（許容）。パネルはコントローラー行より
    **下**にあるので、折り返しても盤・◀ ▶ の位置は動かない（[05](./05-analysis.md) §2.1）。
- 🔴 **検討中は既存の操作ボタン行が検討の操作になる**（決定・2026-08-28）。

  | ボタン | 棋譜を見ているとき | 検討中 |
  |---|---|---|
  | ◀ | 1 手戻る | **検討を 1 手戻す（undo）** |
  | ▶ | 1 手進む | **戻したのをやり直す（redo）** |
  | ≪ | 最初へ | **検討の起点まで戻す**（検討は続く） |
  | ≫ | 最後へ | **検討の最後まで進む** |
  | スライダー | 手数移動 | **無効**（検討中は棋譜の手数を動かさない） |
  | `←` `→` `Home` `End` | 手送り | **上と同じ割り当て** |

  - **なぜこうするか**: 「検討中」の表示があれば**棋譜とは異なる状態に入っていることは分かる**ので、
    undo 用のボタンを増やすより**既存の操作子に意味を持たせる**方がよい（ユーザ判断）。
    操作パネルから「1 手戻す」ボタンは無くす。
  - ⚠ **起点まで戻しても検討からは抜けない**（「検討中」の表示は出たまま、◀ は無効）。
    抜けると**同じ ◀ が 1 回のタップで「undo」から「棋譜の手送り」へ意味を変える**ことになり、
    どちらが起きるか押す前に分からない。**検討の出口は「棋譜に戻る」だけ**にする。
- 🔴 **「検討中に手送りを操作したら検討を破棄して棋譜に戻る」は撤回する**（決定・2026-08-28。
  同日に置いた決定を同日中に上書きした）。上のとおり手送りの操作子そのものが検討の操作になるため、
  **手送りで暗黙に検討が消えることはなくなった**。

### 3.2 検討盤でできること

- **フル編集**: 盤上の駒の自由移動（相手駒に重ねたら持ち駒へ）+ **駒台での受け渡し** + 手番トグル。
  合法性は問わない（§2.5）。
- 🔴 **駒箱は UI に持たない**（決定・2026-08-28）。盤の駒を選んだ状態で**駒台の受け皿を叩けば
  その駒が駒台に移る**（先手・後手どちらの駒台にも置ける）。
  - **なぜ廃止できるか**: 駒箱は「盤にも持ち駒にもない駒」の置き場だが、**初期状態では空**で、
    中身が入るのは盤から駒を抜いたときだけ——つまり**退避先でしかない**。駒台がその役を兼ねれば
    駒箱を出す理由が無くなる。**駒の総数は元から変えられない**ので、失われる機能もない。
  - ⚠ 駒台では**駒そのものが「打つための選択」・受け皿が「置く先」**という 2 つの意味が同居する。
    **受け皿は盤の駒を選んでいる間だけ現れる**——選んでいないときに出しておいても意味が読めない。
  - 🔴 **玉だけは駒台へ移せない**（決定・2026-08-28）。玉は持ち駒になりえないので、移すと
    **盤から消えるだけ**になり、駒箱を廃した今は元に戻す手段が無い（「駒の総数は変えられない」
    という上の根拠が玉について崩れる）。玉の無い局面は §2.5 の検証で弾かれ**そもそも評価できず**、
    玉を動かしたいだけなら盤上の移動で足りるので、**戻せない操作を UI に残さない**。
- 🔴 **持ち駒は盤のマスと同じ寸法で並べ、そこから直接打てる**（決定・2026-08-28）。
  持ち駒を選んでから盤のマスを叩く——**盤上の駒を動かすのと同じタップ 2 段**（§3.1）に揃える。
  打つのは検討中に最も多い操作の 1 つなので、折り畳みの中に押し込まない。
  寸法を盤に合わせるのは、タップの的として盤マスと同じ扱い（§3.3 の 44px 例外の側）に
  なるため。⚠ **閲覧しているだけのときも同じ寸法にする**——検討を始めた瞬間に持ち駒欄の
  高さが変われば盤ごと下の操作ボタンがずれる（[05](./05-analysis.md) §2.1）。
- 手順は**一本道 + undo / redo**。セッション内限定・保存しない（分岐ツリー・variations 保存は
  後続候補・§6）。**戻したぶんはやり直せる**（§3.1 の ▶）が、⚠ **戻した先で新しい手を指したら、
  その先のやり直し分は捨てる**——残すと分岐ツリーになり、後続候補に回した話に踏み込むため。
- 評価は**明示ボタン 1 つ**「評価する」（決定・2026-08-29）。自動評価はしない
  （決定・2026-08-20。設定で足す場合も既定はオフ）。押すと**現在の検討局面の局面評価**を投げ、
  **直前が盤上の指し手なら 1 手前の局面の局面評価も並行して投げて、直前の手を採点する**:
  - **指した手の評価値** = 現局面の評価値の**符号反転**（現局面の評価は相手番視点のため）
  - **最善** = 1 手前の局面の rank 1 の候補手とそのスコア（指した側視点）
  - **損失** = 最善のスコア − 指した手のスコア。🔒 **数値を出すのは両方 `cp` のときだけ**——
    どちらかが `mate` なら損失は出さず両者を並べるに留める（`mate` は「詰みまでの手数」で
    単位が違い、`mate` 同士でも引き算に意味が無い）。指した手が最善手そのものなら「最善手」と出す。
  - 🔒 **1 手前の評価が失敗・busy・中断でも、主の局面評価の結果は必ず出す**（採点だけ省く）。
    副次的な要求が主を壊さない。⚠ 2 本並行になっても**世代（token）は 1 つ・`AbortSignal` は共有**
    （§3.1 の「待ちの間に盤を動かしたら要求を捨てる」を 2 本まとめて守るため）。
  - 結果の見出しは**評価値と出所バッジの 1 行**（`+42 (先手有利)` + `既存解析` / `エンジン`）。
  - 🔒 **採点の出所バッジは「最善」の行に置く**（決定・2026-08-29）。バッジが指すのは
    **1 手前の局面の評価**（= 最善の出所）で、「直前の手」の行の評価値は**主の局面評価の符号反転**
    だから見出しのバッジと同じもの。⚠ **「直前の手」の行にバッジを出さない**——実機で
    「その数字が既存解析から来た」と読めてしまい、§2.6 の「値の出所を黙って混ぜない」に反した。
    指した手が最善手だったときは「最善」の行が出ないので、**「最善手」の結論にバッジを添える**
    （その結論自体が 1 手前の評価から導かれている）。主の評価と採点は別々の要求なので、
    片方だけ既存解析ということが起きる。
  - 🔒 **損失の色分けは悪手判定の閾値（[05](./05-analysis.md) §2.5 の `dubious` / `blunder`）に従う**
    （決定・2026-08-29）。閾値未満は無色、疑問手の閾値以上で warning、悪手の閾値以上で error。
    **なぜ**: 同じ画面に棋譜側の評価値グラフの悪手マーカーが並んでおり、**1 つの画面に「損失」の
    基準が 2 つあってはいけない**。実機で「損失 5」（探索誤差の範囲）が警告色になり、
    咎めるべき手のように見えた。⚠ **閾値はハードコードせず設定の実効値を使う**（棋譜側と同じ供給元）。
    判定も棋譜側と同じ関数に委ねる。損失が負のとき・`mate` が絡むときは色を付けない。
- 🔴 **かつての「この手を読む」（名指し評価）は web から外した**（決定・2026-08-29。ボタン 2 つを
  1 つに統合）。
  - **なぜ**: 名指し評価は「盤に指した直後の手」しか対象にできず、**指してしまえば局面評価が
    同じ数字を符号だけ反転して返す**（§2.6 には名指し評価を「手を適用した局面の評価の符号反転」で
    代用する経路すらある）。読み筋も名指しの `pv[1]` 以降は相手の応手なので、
    **候補手を 3 本返す局面評価が上位互換**だった。**同じ数字を 2 つのボタンで出していた**ことになる。
  - 🔒 **API の名指し評価（`move` 付き `POST /api/positions/evaluate`）はそのまま残す。**
    `go searchmoves` が代替不能になるのは「**盤に指さずに手を指定する**」場合だけで、それは
    §4 の MCP（`evaluate_move`）の用途。**web の UI から外すだけで、server / worker には触らない。**
- **咎め筋（PV）の再生は読み専用の一時状態**（決定・2026-08-28）。1 手ずつ進めて
  「なぜダメか」を自分の目で確かめられるが、**その先で編集はできず**、「戻る」で元の検討局面に戻る。
  手順と undo スタックの意味を保つため。
- ⚠ エンジンが返すのは数字と手順（証拠）まで。**理由の言語化は §4 の LLM の役割**。

### 3.3 盤マスの寸法は幅と高さから算出する

🔴 **盤マスの寸法は、利用できる幅と高さから算出する**（決定・2026-08-28）。固定値をブレークポイントで
刻むのはやめる。タップが操作の主役になる以上、**その端末で入る限界まで大きくしたい**。

- **なぜ算出にするか**: 固定値を刻むと**境界のすぐ下の端末が恩恵を受けられない**。盤に使える幅は
  ページの余白（`max-w-3xl mx-auto p-4` で左右 16px ずつ）を引いた残りで、盤は「9 マス + 段番号列」が入る:

  | 端末 | 幅 | 盤に使える幅 |
  |---|---|---|
  | iPhone 14 | 390px | 358px |
  | iPhone SE ほか | 375px | 343px |
  | 小型端末 | 320px | 288px |

  🔴 **現在の 32px マス（盤 308px）は、320px 端末では既に溢れている。** 算出にすれば
  **この既存の不具合も同時に解消する**。
- **上限**: モバイル（md 未満）40px / md 40px / lg 48px / xl 56px 相当。
  🔴 **モバイルの 40px は現行の 32px からの意図的な拡大**（決定・2026-08-28）。タップが操作の主役に
  なるため、**盤を大きくすること自体が目的**であって、現状維持ではない。
  **md 以上の上限は現行どおりで、デスクトップの見え方は変わらない。**
  ⚠ **md 以上では上限を忘れると、大画面で盤が今より小さくなる劣化になる。**
- **多くのモバイル端末では上限に届かず、幅から算出した値がそのまま効く。** 上限が効くのは
  幅にかなり余裕がある端末だけ。
  - 🔴 **狭い端末では現在の 32px より小さくなる。** これは劣化ではなく**溢れの解消**で、意図した挙動
    （現在 320px 端末では盤がはみ出している）。⚠ **M2b の表示確認で「小さくなった」ことを不具合と
    判断しないこと。**
  - ⚠ **具体的なマス寸法や、上限に達する幅の境界は PRD には置かない。** 段番号列の扱いなど
    **実装式によって変わる**ため、書けば誤った期待値として使われる。
- **横画面や高さの足りない画面では、高さからも算出する。** 盤と操作行が画面内に収まることを優先する
  （盤だけが縦に溢れて操作行が画面外に出ると、連打しづらくなる）。
- ⚠ [05](./05-analysis.md) §2.1 が定めるタッチターゲット 44px 基準を盤マスは下回るが、
  **9 列 × 44px = 396px は iPhone 14 の 390px にも収まらない**ため、**盤だけは例外**とする。
  算出にすることで**「その端末で入る限界まで大きい」ことは保証される**。加えて選択が 2 段であることが
  この例外を支える——**行き先を選ぶ前なら 1 回目の選択は選び直せる**ので、誤タップがそのまま操作にならない。

## 4. LLM への提供（REST + 薄い MCP）

- server に REST を用意（[07](./07-auth-and-privacy.md) の API_KEY 別系統）。実体は §2 のエンドポイントの外向け整理。
- **`packages/mcp`**: REST をツール定義に翻訳するだけの **stdio MCP サーバ**。デスクトップ側で動かし、
  まず MCP 対応の LLM クライアント（ローカルの LLM CLI 等）から接続する（チャット UI は作らない。決定・2026-08-20）。
- ツールは 4 つ（最小セット・決定・2026-08-20）:

| ツール | 中身 |
|---|---|
| `list_kifus` | 条件検索（「昨日の対局」を特定する入口） |
| `get_kifu` | USI 手順・評価値推移・候補手・悪手判定（既存解析の読み出し） |
| `evaluate_position` | §2.2 の局面評価 |
| `evaluate_move` | §2.2 の名指し評価 |

- 将来: commentator（[06](./06-llm-commentary.md) §3）に同じツールを渡し、解説生成中に LLM が
  気になる手を自分で裏取りしてから書く形へ発展させる。

## 6. 却下・後続に回した案（決定・2026-08-20）

- **合法手生成器**: フル編集方針により不要。作らない。
- **interactive 専用エンジン / 別 worker**: 個人用途の同時要求はほぼ 1 件で過剰。相乗りで足りる。
- **評価結果の DB 永続化**: 応答が速くキャッシュ喪失の痛みが小さい。メモリで足りる。
- **評価の自動トリガー**: 明示ボタンを選択。
- **分岐ツリー / 変化の保存（variations）**: 後続候補。
- **web チャット UI**: LLM 実行環境の VPS 問題（server 内で LLM を動かさない方針）と状態管理が絡む大物。後続候補。

**（決定・2026-08-28）**

- **検討モードのトグル**: モードの出入りを覚える負担と、モードごとに盤面の意味が変わる曖昧さが残る。
  **駒を動かしたら検討**という一本の規則で置き換えた（§3）。
- **盤面の左右半分タップによる手送り**: 駒の選択（§3.1）と同じジェスチャを奪い合う。実際にほとんど
  使われていない側を落とし、手送りは操作ボタンとキーボードに一本化した。
- **ドラッグ&ドロップでの駒移動**: リポジトリに前例が無く、[05](./05-analysis.md) §2.1 の
  「連打・誤タップに強く」という方針とも噛み合わない。タップ 2 段を採る。
- **盤マスを固定寸法でブレークポイントごとに刻む案**: **境界のすぐ下の端末が恩恵を受けられない**
  （幅 375px の端末が 390px 向けの段に届かず、一段下の小さいマスのままになる）。現在の 32px マスが
  320px 端末で溢れている問題も残る。**幅と高さからの算出**に置き換えた（§3.3）。
- その他の後続候補: 詰み探索ツール（`go mate`）/ 分析ページ連携（同戦型の過去局から類似局面）/
  commentator のツール裏取り解説。
