## 1. 目的とスコープ

### 方針

- 🔒 **最初から一般公開する。** 許可リスト制の招待段階は置かない。
  → 利用上限・規約は「悪意のある他人」を前提に決める（§7）
- 🔒 **手元 worker は所有者専用。** 一般ユーザーの解析は**すべてブラウザで行う**（§5）。
  手元 worker の容量（1 日 500〜600 局の見積もり）は 10 人が同時に使うだけで待ちが大きく、他人に回す余力が無い
- 🔒 **解析結果はグラフ用も詳細も永続保存する**（その場で再計算して捨てる設計にしない）。
  容量は保存形式と保存する量の設計で抑える（§6）

### スコープ外

- 課金・プラン管理
- ユーザー間の共有（棋譜・局面検索の横断）。**既定は所有者に閉じる**
- 動画解析は**所有者専用。一般ユーザーには出さない**（取り込みは API_KEY の口だけ・web の画面は撤去済み。[10](./10-video-analysis.md) §6.1・§8.3。2026-10-17 確定）
- 一般ユーザー向けの出題（§8）と評価関数の持ち込み（§5.5）は後の段階

## 2. 現状の制約（見積もり）

配置は「単一の小規模 VPS（メモリ 1GB 級）に server + DB」「解析は手元マシンの worker 1 プロセス」。

| 資源 | 何が効くか | 限界の目安 |
|---|---|---|
| 解析（worker） | quick + full で 1 局 ≒ 2.5 分、1 プロセス直列 | 1 日 500〜600 局 |
| VPS メモリ | MySQL の常駐 + buffer pool 既定 128MB。`kifu_positions` の sfen 索引 3 本が 1 局 ≒ 50KB | 全体 2,000〜3,000 局で局面検索の索引が載らなくなる |
| VPS ディスク | 1 局 ≒ 230KB（大半は行ごとの固定コストと索引の文字列の重複）+ binlog（既定 30 日保持） | 所有者と同じ保存量なら 10 万局前後 |
| server CPU | 取り込み（KIF 解析・全局面の SFEN 生成・戦型判定）と `/positions/similar` の距離計算がメインスレッドで同期実行 | 一括取り込み中は全員の応答が止まる |

⚠ **gzip はほとんど効かない。** gzip が効く大きなテキストは KIF 本文の数 % だけで、容量の大半は
行数 × 固定オーバーヘッドと索引の文字列の重複から来る。

## 3. 認証

> **詳細設計は [07](./07-auth-and-privacy.md)**（表・移行手順・dev の扱い・環境変数・ルート保護）。ここは方針の要約。
> **段階 1（Google ログイン・所有者ゲート・新規登録の拒否・dev ログイン）は実装済み**（2026-09-29）。退会（§3.1）は後の段階。

- 🔒 **パスワードを持たない。** 第一は Google。**実装は Better Auth**（drizzle / MySQL）
- **認可コードフロー + PKCE の、リダイレクト型**にする。ポップアップ型（`window.opener` に依存）は
  ブラウザ解析の COOP（§5.5）と衝突する
- 🔒 **ユーザーの同定は IdP の `sub` で行う。メールアドレスでは同定しない**（メールは変わりうる）
- 複数プロバイダの**アカウント連携は当面しない**（同じメールでの自動連携は乗っ取りの経路になりやすい）
- 今の cookie は「発行時刻の署名」だけで **userId も失効手段も持たない**（[07](./07-auth-and-privacy.md) §8）。
  **失効できるサーバ側セッション**に置き換える
- 🔒 **表の持ち方**: Better Auth の `user` / `session` / `account` / `verification` を `schema.ts` に**手書き**する
  （CLI は drizzle 1.0 の relations v2 に追いついていない）。**既存の `users` を Better Auth の user 表に作り替え**、
  ID は `varchar(36)`。`displayName` は独自列として Google の `name` と分けて持つ（[07](./07-auth-and-privacy.md) §3）
- 🔒 **既存の行の ID は文字列 `"1"` として残す。** `kifus.ownerId`・`user_aliases.userId` も `varchar(36)` に変えるが、
  値は書き換えない
- **既存アカウントの移行**: 所有者が初めて Google でログインすると新しい user（X）ができるので、
  **account を X → `"1"` に付け替え、Google の値を写し、X を消す**（SQL は [07](./07-auth-and-privacy.md) §4）。
  棋譜・出題・名前候補はそのまま引き継がれる（[11](./11-users.md) §3 で `ownerId` を先に入れておいた理由）
- 🔒 **旧ログイン（ID/パスワード・署名 cookie）は切り替えと同時に削除する。** 利用者が所有者 1 人のうちに切り替えるので、
  失敗しても DB を直接触って戻せる
- **dev**: `NODE_ENV=development` のときだけ email+password と dev ログインの抜け道（`/api/dev/login`）を有効にする
  （Playwright の E2E を Google なしで通すため）。それ以外では登録すらしない（fail-closed）
- 🔴 **所有者スコープ（§4）が入るまでは、所有者以外のセッションを通さない**（所有者ゲート。[07](./07-auth-and-privacy.md) §5.1）。
  今のクエリは所有者で絞っていないので、**他人がログインできると全データが見える**。新規登録も閉じておく（作成を拒否し、移行の間だけ
  `AUTH_ALLOW_SIGNUP=true` で開ける。[07](./07-auth-and-privacy.md) §5.2）
  - ⚠ **所有者スコープが入った後も、ゲートと登録の拒否は段階 3・4 が済むまで残す**（2026-10-14 決定。§10）

### 3.1 退会

- **猶予期間を置いてから削除する**（例: 30 日）。退会すると「退会予約中」になり、期間中にログインすれば復帰できる。
  期限を過ぎた行はバッチ処理で削除する
- 🔒 **削除は削除処理が明示的に行う。`kifus.ownerId` の FK は CASCADE にしない。**
  CASCADE にすると、ユーザー行を 1 度誤って消しただけで全データが道連れになる
- Better Auth の `deleteUser` は即時削除なので使わない（有効にするなら `beforeDelete` で止める）。
  自前の `deletionRequestedAt` とバッチで作る（[07](./07-auth-and-privacy.md) §7）

## 4. 所有者スコープ

- 🔒 **アプリ層と RLS の両方でスコープする**（§9。Postgres へ移ってから行う。[15](./15-postgres.md) §11）。
  - アプリ層: 取り違えを構造で防ぐため、**所有者を引数に取るクエリ関数からしか `kifus` 系のテーブルに触れない**形にし、テストで検査する
  - RLS: アプリ層の書き忘れを DB が止める多層防御。仕組みは下の「RLS の形」（2026-10-11 決定）
- 🔒 **RLS の形**（2026-10-11 決定。経緯は [決定ログ](./_grilling/decisions.md)「所有者スコープの RLS の形」）:
  - **「誰として動くか」はリクエストごとのトランザクションで DB に伝える。** ログインしたリクエストごとにトランザクションを開き、
    最初に `set_config('app.user_id', <ユーザー ID>, true)`（`true` = そのトランザクションの間だけ。`SET LOCAL` と同じ）を流す。
    `kifus` 系に触るクエリ関数は**その tx を引数で受け取る**（モジュールの `db` を直接使わない）。プールの接続を使い回しても
    設定が次のリクエストに漏れない
  - **全員ぶんを扱う経路は BYPASSRLS の別ロール＋別プール。** worker の報告（API_KEY）・一括処理のエントリ（`rebuild-positions.js` など）は
    ユーザーとして動かないので、RLS を迂回するロールで繋ぐ。常駐 server のリクエスト用のプールとは分け、取り違えを接続の単位で防ぐ。
    🔒 **ロールは migration で作らない**——BYPASSRLS の付与には superuser が要り、管理ロール（`migrate.js`）には無い。
    dev は `scripts/postgres-init/` が、本番は手順で作る（PR 2。[15](./15-postgres.md) §2・§11）
  - 🔒 **`app.user_id` が未設定なら常に 0 件（fail-closed）。** `current_setting('app.user_id', true)` は未設定で NULL を返し、
    `owner_id = NULL` は真にならない。⚠ 一度 `set_config` した接続では、トランザクションが終わると NULL ではなく**空文字**に戻る
    （Postgres の独自設定の性質）が、`owner_id` に空文字は無いのでやはり 0 件。tx を通し忘れたクエリは「全件見える」ではなく
    「何も見えない」で表に出る
  - **子の表すべてに `owner_id` と複合 FK を持たせ、ポリシーは全表で一様に `owner_id = current_setting('app.user_id', true)`**（§4.1）。
    子の表から親（`kifus`）を引いて判定する形にしない
- 他人の棋譜・問題は **404**（存在を明かさない。[13](./13-drills.md) の既存の扱いと同じ）
- ✅ **アプリ層は実装済み**（2026-10-11・所有者スコープ 2a）: ログインの経路（`sessionRequired`）がリクエストごとに tx を開いて
  `app.user_id` を設定し（`user-tx.ts`）、ハンドラは `c.get('tx')` を使う。棋譜系のクエリ関数（`kifu-queries.ts` / `position-queries.ts` /
  `drill-query.ts` / `users.ts` / `position-kifu-reuse.ts`）は tx と所有者を引数に取る。グローバルの `db` を import してよいモジュールは
  `db-import-boundary.test.ts` が限る。全員ぶんの経路（worker の報告・動画解析の取り込み）は `worker-routes.ts`
- ✅ **RLS も実装済み**（2026-10-11・所有者スコープ 2b）: `kifus` と子の表 6 つは `owner_id`、`user_aliases` は `user_id` を
  `current_setting('app.user_id', true)` と比べるポリシー（USING と WITH CHECK。schema の `ownerPolicy`）。`FORCE` は付けない
  （[15](./15-postgres.md) §11）。全員ぶんの経路は BYPASSRLS の system ロールの別プール（`db/system.ts`。[15](./15-postgres.md) §2.1）。
  Better Auth の表（`users` / `session` / `account` / `verification`）には掛けない——所有者で絞る行ではなく、
  ログインの経路は自分の `users` の行を ID で引くだけ。dev ログイン・Better Auth・所有者の付け替えは server ロールのまま
- 現状で `ownerId` を見ているのは**出題系だけ**。一覧・詳細・統計・削除・再解析・局面検索・worker 系を直す。
  加えて、棋譜を直接引かないので見落としやすい次の 2 つも直す（2026-10-11 のコード調査で判明）:
  - **名前候補の更新・削除**（`users.ts` の `updateAliasPeriod` / `removeAlias`）: ID だけで引いている。所有者の条件を付ける
    （他人の名前候補を消すと、相手の棋譜の主体側が NULL に落ち、成績から棋譜が黙って消える）
  - 🔴 **検討盤の評価で棋譜解析を再利用する問い合わせ**（`position-kifu-reuse.ts` の `lookupKifuEvaluation`。[12](./12-position-lab.md) §2.6）:
    全棋譜から所有者を問わず引いている。**所有者の棋譜からだけ引く。** ブラウザで計算した解析結果は server で正しさを検証できない（§5.1）ので、
    利用者をまたいで解析結果が流れる経路が 1 つでも残ると「改ざんの影響は本人に閉じる」が崩れる

> ✅ **実装済み**（2026-10-11・所有者スコープの PR 1。[15](./15-postgres.md) §11）。クエリの読み取り側のスコープと RLS は PR 2（✅。§4）。

### 4.4 URL に出す ID（ユーザーごとの番号）

> ✅ **実装済み**（2026-10-12）。🔴 **所有者ゲートを外して新規登録を開く PR（§10 の段階 5。2026-10-14 に「段階 2 の最後」から改定）より前に本番へ入れる**——公開後に替えるとユーザーのブックマークが切れ、
> 開放後に替えると下の「`displayNo = id` で埋める」が成り立たない（他のユーザーの棋譜に通しの番号が残る）。経緯は
> [決定ログ](./_grilling/decisions.md)「URL に出す ID と共有リンク」（2026-10-12）。

棋譜の主キーは全ユーザーで通しの連番（identity）で、以前は URL（`/kifus/1234`）にも API にもそのまま出ていた。
他人の棋譜は 404 なので読まれはしないが、**サービス全体の棋譜数や増え方が番号から分かる**。棋譜は公開したい人ばかりではないので、
「自分の棋譜の中での番号」で見せる。

- 🔒 **棋譜に、所有者ごとの連番 `displayNo` を持たせる**（`UNIQUE(ownerId, displayNo)`）。`/kifus/42` は「自分の 42 番」を指す。
  サーバーはセッションの所有者と番号で引くので、所有者スコープ（§4）とそのまま噛み合う
  - 採番はユーザーごとの「次の番号」を取り込みの tx の中で進める（その行のロックで同じユーザーの取り込みどうしが順に並ぶ。他のユーザーは待たない）。
    **実装**: カウンタは `users.lastKifuNo`（最後に振った番号）で、`kifu-number.ts` の `insertKifu` が `UPDATE … RETURNING` で進めてから挿入する。
    🔴 **`kifus` を作る経路はすべて `insertKifu` を通す**（KIF/CSA 貼り付け・動画解析の取り込み・seed・テスト。`insert(kifus)` は
    `kifu-number.ts` だけ。`kifu-number.test.ts` が検査する）。⚠ `max(displayNo) + 1` では振らない（末尾を消すと番号が再利用される）。
    ⚠ カウンタを進めると `users.updatedAt` もトリガーで進む（`users` は Better Auth の表で RLS の対象外なので、system ロールの経路からも進められる）
  - 🔒 **削除した番号は再利用しない**（欠番を許す）。古いメモや履歴の「42 番」が別の棋譜を指さないため
  - 既存の棋譜はすべて所有者のものなので、`displayNo = id` で埋める。今の URL がそのまま生きる。
    この前提は新規登録を開く前だけ成り立つ（上の順序）。マイグレーション（`kifu_display_no`）はカウンタを所有者ごとの最大値に揃え（所有者は `kifus.id` の identity が発行済みの番号まで。末尾を消していても再利用しない。⚠ MySQL 時代に消した末尾の番号は守らない——Postgres への移行で identity が残存の最大 + 1 から始まり記録が無く、移行の時点で既に再利用されうる状態だった（許容。レビュー OCL-7F7C1CC7・2026-10-12））、
    埋め戻しの間は `updated_at` のトリガーを止める
- 🔒 **内部の主キーは外に出さない。** URL だけでなく **API のパスと応答も番号で扱い**、応答に内部 ID が含まれないことをテストで検査する。
  内部の主キーは FK・worker・ログで使う（worker の API は API_KEY の内部経路なので内部 ID のまま）。MCP からも番号で参照する。
  **実装**: 棋譜は `/api/kifus/:no`、応答は一覧・詳細が `no`、他の応答（局面検索・解析の進捗・出題）の棋譜の参照は `kifuNo`。
  検査は test:db の `display-no.db.test.ts`（ログインの経路の**全ルート**を叩き、応答に `id` / `kifuId` / `drillId` が無いことを見る。
  ルートを足したらそこにも足さないと落ちる）
  - **範囲外**: 名前候補の ID（`/users/me/aliases/:id`・`GET /users/me` の `aliases[].id`）——棋譜ではなく件数も少ないので、
    増え方からサービス規模は読めない。評価ジョブの ID は §4.2 で別に扱う。共有リンクは §8
- **一覧などの画面にも番号を出す**（「#42」）。「42 番の棋譜」と呼べるようにし、LLM や MCP とのやり取りでも同じ言葉で参照する
- **出題は棋譜の番号から辿る**（「42 番の 37 手目の悪手」= `(displayNo, 手数, 種類)`。`drills` の一意制約と同じ組）。
  出題は一括生成の upsert で作り直されることがあり、行の ID で指すと作り直しで URL が切れる。出題に独自の番号は持たせない
  （生成順の番号には意味が無く、作り直すたびに番号が飛ぶ）。パラメータ名は既存の絞り込み（`kind` など）とぶつからないように付ける。
  **実装**: API は `/api/drills/:kifuNo/:moveNumber/:kind`（`moveNumber` は出題局面）、画面の URL は
  `/drills?kifu=<番号>&ply=<moveNumber>&drillKind=<種類>`（[13](./13-drills.md) §5.3・§7.4）。出題・解答の行の ID は応答に載せない
- 局面ページ（`/positions?pos=…`）は局面そのものから決まる値で引くので、変えない（総数も所有者も漏れない）

**評価関数の選択（つようら王11mini / micro）**（2026-10-16 決定・**実装済み（本番は未反映）**。経緯は [決定ログ](./_grilling/decisions.md)
「ブラウザ解析と手元 worker の評価関数をつようら王11 にする」）:

- 🔒 **ブラウザ解析の評価関数は、つようら王11mini（既定）と つようら王11micro から端末ごとに選ぶ。** 水匠5 は配らない
  - **既定を mini にする**: 作者の説明では mini の方が局面の評価の精度が高い（micro は NPS が高い代わりに大局観が劣る）。解析では速さより評価の精度を取る
  - 選ぶ場所は端末の設定（§5.10。localStorage）。ユーザーの設定（server）には持たない
- **arch**: mini = `SFNN_ka2_4096_8_64_progress8`、micro = `SFNN_ka2_2048_8_64_progress8`。どちらも進行度つきで、
  `nn.bin` とは別に `progress.bin` を `EvalDir` から読む。作者は水匠5 より R150〜200 強いと述べている
- **上流のコミットは今の固定（c1b80ea・2026-09-14）のまま**。このコミットで、パッチ無しにネイティブ・WASM ともビルドでき、評価関数を読めた（実測・2026-10-16）
- 🔴 **`EvalDir` は絶対パス `/eval` にする**（`.` にしない）。上流の WASM では `progress.bin` を「実行ファイルのフォルダ + `EvalDir`」から探す
  （`nn.bin` は `EvalDir` をそのまま仮想 FS のパスにする）ので、`.` だと `progress.bin` が見つからず、`isready` で**黙って終了する**。
  上流のパスの結合は絶対パスをそのまま返すので、`/eval` なら両方とも見つかる（パッチは要らない）。水匠5（`halfkp`）でも `/eval` で動くことを確かめた
  - ⚠ 改定前（2026-10-14）: `EvalDir .`・`EvalFile nn.bin`・仮想 FS の `/nn.bin`
- **速さ**（node・WASM・4 スレッド・600ms の実測・2026-10-16）: 水匠5 350 万 nps / mini 125 万 / micro 190 万。深さはどれも 16〜20 程度。
  段の思考時間（§5.2・§5.8）は変えない
- **評価値の尺度**（本番 full = 水匠5・`FV_SCALE` 16・1000ms・MultiPV 3 と同じ局面で比べた。4 局ぶん・閾値 600 / 300。2026-10-16）:

  | 対象 | 水匠5 に対する評価値の倍率（相関） | 悪手 | 疑問手 | 最善手の一致 |
  |---|---|---|---|---|
  | 水匠5（本番 full） | — | 22 | 27 | — |
  | 水匠5 をもう一度 | 1.01 倍（1.00） | 23 | 26 | 74% |
  | mini・`FV_SCALE` 24（作者の推奨） | 0.56 倍（0.99） | 7 | 16 | 65% |
  | micro・`FV_SCALE` 24 | 0.53 倍（0.99） | 5 | 19 | 64% |

  → **`FV_SCALE` は 16**（上の 🔴）。24 では悪手の印が 3 分の 1 に減る
- 🔒 **manifest は「評価関数の一覧と既定」を持つ形に変える**（型と検証は引き続き `shared` の `engine-manifest.ts`）。各エントリ:
  - `id`・表示名
  - エンジン: ビルド識別・上流のコミット・emsdk・`YANEURAOU_EDITION`・グルーの公開名・ファイルと sha256（arch ごとに別のディレクトリ）
  - 評価関数のファイル: `nn.bin` と `progress.bin` のそれぞれにファイル名・大きさ・sha256（`engine/eval/` に内容ハッシュ入りの名前）
  - `FV_SCALE`（16）
  - ライセンスと出典（MIT・配布元）
  - ⚠ 改定前（2026-10-14）: エンジン 1 つ・評価関数 1 つ（`eval`）・`fvScale` をトップに持つ形
- **来歴の `evalHash` は `nn.bin` の sha256**（§5.9）。`progress.bin` は同じ配布物の一部で、manifest の sha256 で照合する（来歴には載せない）。
  `engineBuild` は arch ごとのエンジンのビルド識別なので、mini と micro は来歴の上でも別のエンジンになる
- **配布物の固定値**（URL・7z と中身の sha256）は実装側の `packages/engine-wasm/UPSTREAM` に書く。取得したものは sha256 が合わなければ置かない（今と同じ）
- **選択を切り替えたとき**:
  - **進行中の段は §5.9 の規則どおりやり直す**（エンジンのビルドか評価関数が違う途中の解析。full の途中なら全消去して quick から）
  - **完了済みの解析はそのまま**。評価関数を変えても過去の棋譜は解析し直さない（必要なら利用者が再解析する）。どの評価関数の結果かは来歴で分かる
  - ⚠ **端末ごとに違う評価関数を選んだ端末が、同じ棋譜を同時に解析すると、互いの途中の解析をやり直させ合う**（§5.9 の照合で
    相手のチャンクが破棄され、開始の口で全消去と世代の更新が起きる）。端末をまたぐ同時解析は今も許容している（§5.10）。
    止まり続けないかは実装時に確かめる
- 🔒 **server は変えない。** 評価関数の許可リストは持たない——ブラウザから届く来歴は信用しないが、影響は本人の結果に閉じる（§5.1）

**web からの読み込み**（✅ 実装済み・2026-10-14。`packages/web/engine-plugin` と `packages/web/src/lib/browserAnalysis`）:

- **配信物は web と同じオリジンの `/engine/` に置く。** Vite のプラグイン（`engine-plugin`）が受け持つ:
  - dev / preview: `/engine/*` を `ENGINE_DIST_DIR`（既定は `packages/engine-wasm/dist/engine`）から配る。
    wasm は `application/wasm`・`manifest.json` は `no-cache`・ほか（内容ハッシュ入りのパス）は長期キャッシュ。
    無いパスは 404（SPA のフォールバックの index.html を返さない）
  - build: 同じディレクトリを `dist/engine/` へコピーする。**無ければ警告して飛ばす**（エンジンなしの web ができる）。
    `ENGINE_REQUIRED=1` のときは落とす（`pnpm deploy:web` が立てる。エンジンを入れ忘れたデプロイを止める）
  - dev / preview の**全応答**に COOP / COEP を付ける
- 🔒 **エンジン本体も、エンジンのホストも、Vite のバンドルに通さない。**
  - **エンジンのホスト**（`engine-plugin/engine-host.js`）は **classic の Web Worker** のスクリプト。`importScripts` でグルーを読み、
    manifest の `exportName` のグローバルを `locateFile` と `mainScriptUrlOrBlob` を付けて呼ぶ。評価関数を fetch して
    （受信バイト数を通知しながら）大きさとハッシュを manifest と照合し、仮想 FS の `/nn.bin` に置く
    （2026-10-16 改定・未実装: 選んだ評価関数のエンジンを読み、`nn.bin` と `progress.bin` を `/eval/` に置く）
  - ホストは import を持たない素の JavaScript で、プラグインが**変換せずそのまま**配る（dev は固定のパス、build は
    `assets/engine-host-<内容ハッシュ>.js`）。web のコードは仮想モジュール `virtual:engine-host` から URL を受け取る。
    Vite の Worker の仕組み（`new Worker(new URL(…))`）に載せなかったのは、dev での classic の Worker の配り方に依存しないため
- **エンジンとのやり取り**: ホストの Worker との行の送受信を `UsiTransport`（§5.11）に包む。ホストが伝える終了（`dead`）・
  Worker の `error`・送信の例外を**エンジンの死**として扱い、Worker ごと作り直す
- **オプション**: `EvalDir .`（2026-10-16 改定・未実装: `/eval`）・`EvalFile nn.bin`・`FV_SCALE`（manifest の値）・`Threads`（論理コア数と server の上限の小さいほう）・
  `USI_Hash`（server の設定）・`BookFile no_book`・`ConsiderationMode true`（手元 worker と同じ）
- **manifest が無い**（エンジンを含めずに配信した）ときは解析せず、案内を出す。無いパスに index.html を 200 で返す配信でも
  そう判定できるよう、ステータスではなく中身（形の検証）で見る
- ⚠ `shared` の報告の検証（`analysis-limits.ts`）が zod を使うので、**zod が web のバンドルに入る**（gzip で約 20KB）

**本番の配信で要ること**（✅ 済み・2026-10-15。リポジトリの外の設定。具体は公開文書に書かない）:

- **全応答に COOP / COEP**（上の値）。`index.html`・`assets/*`・`engine/*` と、`/api` の応答にも
- `engine/**/*.wasm` を `application/wasm` で返す（違うとストリーミングのコンパイルが失敗する）
- `engine/manifest.json` はキャッシュさせない。それ以外の `engine/*` と `assets/*` は内容ハッシュ入りなので長期キャッシュ
- 評価関数（64MB）と wasm を圧縮して返す（brotli で評価関数は ≒ 25MB。つようら王11 に替えた後は mini 約 8.7MB・micro 約 4.9MB の無圧縮が上限）
- `engine/` は `deploy:web` の世代管理の外にある（消されない。[02](./02-architecture.md) §5）。古いビルド・古い評価関数の
  ディレクトリは溜まるので、手で消す

  `browser` 担当の未解析の棋譜が手元 worker の full を止め続ける
- **検討盤の評価の要求（`POST /positions/evaluate`）も担当が `worker` のユーザーだけ**（手元 worker にジョブを積む口のため。
  [12](./12-position-lab.md) §2.4）。`browser` 担当の検討盤はブラウザで評価する（2026-10-29 実装。この口は使わない。
  [12](./12-position-lab.md) §2.4。⚠ 改定前: 「§5.11 の 3 番目が入るまでは使えない」）。
  **実装**: `browser` 担当には 403。局面の検証の後・棋譜解析からの再利用より前に断る（一部の局面だけ答えが返る口にしない）
  - 🔒 **出題の解答の評価も担当が `worker` のユーザーだけ**が手元 worker にジョブを積む（2026-10-15 改定・2026-10-16 実装。`drill-engine.ts` の `evaluationSourceOf`）。
    担当 `browser` のユーザーの解答は、ジョブを積む代わりに「この局面のこの手を名指しで読んでほしい」と返し、**ブラウザが読む**
    （流れは [13](./13-drills.md) §5.3）。ブラウザの full の完了でも出題が生成されるので、絞らないとログインした誰もが
    所有者の worker を使える
    - ⚠ **2026-10-23 改定（2026-10-25 実装）**: **詰将棋の 1 手の判定は担当によらずブラウザで読む**（Threads 2・上限は残り手数で 1000ms / 2000ms・MultiPV 1・詰みが見えたら打ち切り。
      [13](./13-drills.md) §5.5）。手元 worker に積むのは、担当 `worker` の利用者の端末でブラウザのエンジンが使えないときだけ。
      次の一手はこの節のまま
    - ⚠ 改定前（2026-10-14 決定）: **絞らない**。出題は手元 worker の full の完了時にだけ生成され、出題を持つのは
      所有者だけ、という前提だった。2 段化でこの前提が崩れる
- **担当を切り替えても、完了済みの解析は残る**（§5.9。full の途中結果を持つ棋譜だけは例外。下の規則 1）。**再解析（`reanalyze`）は `browser` 担当でも使える**
- 🔒 **担当を切り替えた前後で、守ること**（レビュー OCL-0BE57AA6・2026-10-14）: 取得の条件を絞るだけでは、切り替えの時点で
  解析の途中だった側（手元 worker が取得済みの棋譜・開いたままのタブ）が報告を続けられる。
  - **切り替え前に始めた側の報告（チャンク・失敗）が、切り替え後の解析に効かないこと**
  - **1 つの棋譜の途中の解析に、両方の結果が混ざらないこと**（§5.9 と同じ不変条件。完了済みは残す）
  - 🔒 **規則 1: 切り替えは、そのユーザーの「full まで完了していない棋譜」すべての `analysisRevision` を進める。**
    担当の設定の更新と同じトランザクションで、対象の棋譜を行ロック（`FOR UPDATE`）して行う。
    - **途中の棋譜は、解析の行も消す**（§5.9 のやり直し・`reanalyze` と同じ全消去で、完了の印も戻す。[16](./16-analysis-storage.md) §4.3）。
      「途中」は次の 2 つ:
      - **初めての完了の前**（quick の途中。quick が無効な worker なら full の途中）
      - **quick は完了し、full が途中まで入っている**（`0 < fullCount < 局面数`。レビュー OCL-84D984B2）。
        保存は局面ごとに 1 つで full が quick を上書きしている（[16](./16-analysis-storage.md) §4.2）ので、full の途中ぶんだけを
        取り除いて quick に戻すことはできない。残すと、担当 `browser` の棋譜に手元 worker の full が残ったまま
        「quick は完了済み」としてブラウザでは解析されなくなる（2 段化の後は、手元 worker の full の途中にブラウザの full を
        続けて重ねることになり、同じ段の途中でエンジンが替わる。どちらにしても消す）
      次に解析する側は 0 から始めるので、途中の解析に両方の結果が混ざらない（`browser` → `worker` に戻したときも、
      手元 worker が残りから再開することは無い）
    - **それ以外は行を残す**: quick が完了して full が 1 局面も入っていない棋譜（世代だけ進める）と、full まで完了した棋譜（何もしない）
    - 🔒 **世代を進める棋譜は、失敗の記録（`analysisError`）も消す**（2026-10-14 決定）。失敗は前の担当の進行中の段階のもの。
      残すと、quick 完了・full 失敗の棋譜が `browser` では完了扱いなのに、失敗の表示だけが残り続ける
      （2 段化の後は、失敗の記録が残ると新しい担当が full を回さない）。
      途中で失敗して止まっていた棋譜は、新しい担当が最初から解析する
    - 🔒 **同じ値への切り替えは何もしない**（実装時に決定）。同じ値を送るたびに途中の解析を消さない
    - **実装**: `switchAnalysisAssignee`。`users` の行を先にロックしてから、そのユーザーの未完了の棋譜を `id` 順に
      `FOR UPDATE` で取る。取り込み（番号の採番）も `users` の行を先に取るので、切り替えと取り込みは直列になり、
      切り替えの途中に生まれた棋譜を取りこぼさない。「解析中」の表示（§4.2）はコミットの後に所有者の単位で落とす
    - ⚠ **`browser` → `worker` に戻したとき**、ブラウザの quick が完了した棋譜（full は 0 局面）は残り、手元 worker の full の対象になる。
      full の進行中は 1 つの棋譜にブラウザの quick と手元 worker の full が並ぶ。これは既存の「full が quick を上書きしていく」
      （[05](./05-analysis.md) §1.1d）と同じ扱いで**許容する**——完了すれば full にそろう。「別のエンジンの結果を混ぜない」
      （[16](./16-analysis-storage.md) §8）が禁じるのは、**同じ段の途中でエンジンを替えること**。
      2 段化の後は逆向き（`worker` → `browser`）も同じで、手元 worker の quick の上をブラウザの full が上書きしていく
    - 切り替え前に取得・開始していた側の報告は、**既存の世代の照合で破棄される**（[05](./05-analysis.md) §1.1c）。
      報告は棋譜の行ロックの下で世代を読むので、切り替えと報告は棋譜の行で直列になる——報告が先なら切り替えがそれを含めて
      消し、切り替えが先なら報告は古い世代として落ちる。`worker` → `browser` → `worker` と戻しても、世代は戻らない
  - 🔒 **規則 2: 受ける側も今の担当を確かめる。** ブラウザの受け口（§5.8。開始・チャンク・失敗）は担当 `browser` のユーザーだけ、
    手元 worker の報告は担当 `worker` のユーザーの棋譜だけを受ける（書き込みと同じ行ロックの下で）。規則 1 の後から
    担当でない側が新しく始めるのを止める
    - 🔒 **担当違い・古い世代の報告は「破棄」で、4xx にしない**（実装時に決定）。応答は 201 `applied: false`。
      手元 worker は 4xx を恒久的な失敗として棋譜に記録するので、4xx にすると切り替えのたびに失敗が残る。
      ブラウザの報告も同じ形にそろえ、`applied: false` を受けたブラウザは開始からやり直す。**開始だけは 409**
      （担当が `browser` でない）で、ブラウザは `GET /api/me` を取り直す
    - 手元 worker の進捗の報告（`POST /api/worker/analyses/progress`）も担当を見る（担当でなくなった棋譜の「解析中」を出さない）

### 5.8 ブラウザ解析の受け口

> ✅ **実装済み**（2026-10-14・1 段。**2 段化は server・web とも 2026-10-15 に実装**・本番は未反映）。呼ぶ側（web）は `lib/browserAnalysis/kifuAnalysis.ts`（下の「呼ぶ側のふるまい」。応答の分類は `apiResult.ts`）。
> 下の表と本文の形は今のコード（2 段）。**2 段化で変えたこと**は表の後。

- **ログインの経路に 3 つ足す**（＋バックグラウンド解析用の一覧）:

  | 口 | パス | すること |
  |---|---|---|
  | 開始 | `POST /api/kifus/:no/analysis/start` | 世代（`analysisRevision`）・再開位置・指し手列・解析の設定を返す。途中の解析をやり直すかの判定もここ（§5.9） |
  | チャンクの報告 | `POST /api/kifus/:no/analysis/chunks` | 解析した局面を送る（チャンク submit。[16](./16-analysis-storage.md) §4） |
  | 失敗の報告 | `POST /api/kifus/:no/analysis/error` | 解析の失敗を記録する（`analysisError`。[05](./05-analysis.md) §1.1a） |
  | 未解析の一覧 | `GET /api/analysis/pending?limit=` | バックグラウンド解析（§5.10）が次に解析する棋譜の番号。新しい順 |

  - **開始**: 本文は `{ engineBuild, evalHash }`（配信物の manifest の値。§5.5）。応答は
    `{ status: 'run', revision, profile, startMoveNumber, usiMoves, settings }` か、解析しない理由
    `{ status: 'complete' | 'failed' | 'unanalyzable' }`（full まで解析済み・失敗の記録あり・指し手列が無い）。
    担当が `browser` でなければ 409、他人の番号・無い番号は 404
    - **段（`profile`）は棋譜の状態から決める**: quick が未完了なら `quick`、quick が完了して full が未完了なら `full`。
      `startMoveNumber` はその段の再開位置（quick は入っている局面数・full は `fullCount`）
    - 🔒 **指し手列は世代と同じ tx で返す。** 再解析は指し手列を作り直すので、別の口で読むと世代とずれうる
    - **`settings` は server の定数**（段で共通の `BROWSER_ANALYSIS_SETTINGS` に、段の思考時間 `BROWSER_ANALYSIS_MOVETIME_MS` と
      段のスレッド数の上限 `BROWSER_ANALYSIS_STAGE_MAX_THREADS` を足したもの）:
      `{ movetimeMs: 100（quick）| 600（full）, stageMaxThreads: 8（quick）| 4（full）, multiPv: 1, hashMb: 64, maxThreads: 8, chunkIntervalMs: 5000, chunkMaxPositions: 32, pvMaxPlies: 128 }`。
      web に焼き込まないのは、値を調整するときに web の再デプロイを要さないため。
      `stageMaxThreads` は 2026-10-29 に足した任意の欄（§5.5）。`maxThreads` はエンジンの上限で段で共通
  - **チャンクの報告**: 本文は `{ revision, profile?, engineBuild, evalHash, engineName?, fvScale, threads, hashMb, movetimeMs, analyses }`。
    🔒 **段（quick / full）は server が棋譜の状態から決める**（開始の口と同じ規則・棋譜の行ロックの下で）。届いたチャンクの段の申告と
    照合し、状態の段と違えば破棄する。🔴 **申告は再送しても変わらない値から読む**（レビュー OCL-35F059B0・実装時に決定）:
    本文の `profile`、無ければ `movetimeMs`（開始の口が返した値をそのまま載せる）が full の時間なら full・それ以外は quick
    （`browserClaimedProfile`）。状態だけで決めると、quick の最後のチャンクの保存後に応答だけが失われたとき、その再送が full として
    扱われる（複数チャンクなら 400 で棋譜の失敗に、1 チャンクなら 100ms の結果が full として保存される）。**実行環境（`wasm`）・MultiPV（1）・定跡（なし）は server が固定する**（本文で受けない）。
    応答は 201 `{ ok, applied, completed, stageCompleted, profile }`: `completed` は **full まで揃ったか**（解析全体の完了）、
    `stageCompleted` は届いた段が揃ったか、`profile` は受けた段（破棄なら null）。
    破棄（古い世代・担当違い・段違い・その段が完了済み・失敗の記録あり・同じ段の行と別のエンジン）は `applied: false`。
    局面が棋譜の手数を超える・連続していないは 400
  - **失敗の報告**: 本文は `{ revision, error }`。進行中の段の失敗として、同じ世代で **full が未完了**のときだけ記録する（手元 worker と同じ）。
    応答は 201 `{ ok, applied }`
  - **未解析の一覧**: `{ kifuNos }`。full が未完了・失敗の記録なし・指し手列あり。**quick が未完了のものが先**、その中はそれぞれ新しい順
    （§5.10 の順序）。担当が `browser` でなければ空。
    ⚠ 一覧の「未解析」の絞り込み（[05](./05-analysis.md) §2.5）は指し手列の無い棋譜も含むので流用しない

- **2 段化で変えたこと**（2026-10-15 決定・**server は実装済み**。§5.2・§5.7）:
  - **設定の定数を段ごとに持つ**: 思考時間を quick（100ms）と full（600ms）に分けた（確定。§5.2）。
    MultiPV（1）と置換表・スレッドの上限・チャンクの値は段で共通
    （⚠ 2026-10-29 改定: スレッドの上限は段ごと（full は 4）。エンジンの上限 `maxThreads` は段で共通のまま。§5.5）
  - **開始の口が、どの段を回すかを返す**（`profile` と、その段の再開位置）。完了（`status: 'complete'`）は full の完了で返す
  - 🔒 **段はブラウザが決めない。** 照合の具体（実装時に決定）: **チャンクの段は、棋譜の状態（世代・`analysisProfile`・quick の完了）から
    server が決める**——開始の口と同じ規則を同じ行ロックの下で読む。本文の `profile` は任意の申告で、載っていて状態と合わなければ破棄。
    段が合わない報告（quick の途中に full が届く・full の完了後に quick が届く）は破棄（`applied: false`）。
    full が quick を上書きする規則と `fullCount` の扱いは手元 worker と同じ（[05](./05-analysis.md) §1.1d・[16](./16-analysis-storage.md) §4）。

  - **失敗の報告**は「進行中の段の失敗」として、full が未完了なら記録する（手元 worker と同じ。[05](./05-analysis.md) §1.1d）
  - **未解析の一覧**は full が未完了の棋譜を返し、**quick が未完了のものを先に**並べる（順序は §5.10）
  - 🔒 **1 段のままの web を壊さない**（実装時に決定。web の 2 段化は別の変更で入れたため。その間の互換として残す）:

    - チャンクの応答の `completed` は **full まで揃ったか**にした（届いた段の完了は `stageCompleted` で別に返す）。今の web は

  - **出題の採点の読み**（[13](./13-drills.md) §5.3）はこの受け口を使わず、出題の解答の口に結果を付けて送り直す（**2026-10-16 実装**）。

**呼ぶ側のふるまい**（実装時に決定・2026-10-14。`kifuAnalysis.ts`）:

| 起きたこと | ブラウザの動き |
|---|---|
| チャンクが破棄された（`applied: false`） | 中断して開始からやり直す（開始の口が、世代・再開位置・やり直しを決める）。続けて 3 回破棄されたら後回し |
| 5xx・通信の失敗・408 / 429 | 同じ要求を後退しながら再試行する（1・2・4・8・16 秒）。尽きたらその棋譜を後回しにする（**失敗とは記録しない**） |
| 開始が 409（担当が `browser` でない） | 解析を止め、`GET /api/me` を取り直す |
| 401（開始・チャンクの報告・未解析の一覧） | 解析を止め、`GET /api/me` を取り直す（ログイン画面へ）。未解析の一覧の 401 も通信の失敗と分ける（分けないと 1 分ごとに叩き続ける） |
| 失敗の報告が破棄された（201 `applied: false`） | **失敗済みとして扱わない**（server に失敗は残っていない）。開始からやり直して今の状態を聞く。続けて 3 回破棄されたら後回し |
| 403（Origin の検査など） | 解析を止め、続けられないことを画面に出す |
| チャンクが 4xx で拒否された | 送り直しても同じなので、棋譜の失敗として報告して止める |
| エンジンの失敗（死・応答の時間切れ・`info string Error!`） | エンジンを作り直して開始からやり直す。🔒 **作り直した後に同じ局面でもう一度失敗したときだけ**、棋譜の失敗として報告する |
| ページが隠れている間のエンジンの失敗 | 数えない。見えるまで待ってやり直す（スマホはバックグラウンドで凍結し、応答が時間切れになる） |
| エンジンを読み込めない（評価関数を取得できないなど） | 1 回やり直し、だめなら解析を止めて画面に出す（**棋譜の失敗にしない**） |

- 🔒 **端末の不調で棋譜を失敗にしない。** 失敗の記録（`analysisError`）は再解析するまで残り、その棋譜はどの端末でも解析されなくなる。
  メモリ不足や凍結でエンジンが 1 度落ちただけで記録すると、その端末で開いた棋譜が次々に失敗になる
- 後回しにした棋譜・解析が一区切りした棋譜は、しばらく（完了 15 秒・後回し 1 分・失敗や対象外 5 分）選ばない。
  画面のデータが古いまま同じ棋譜を指し続けても、開始の口を叩き続けないため。詳細ページを開き直す・再解析すると、待たずに試す

### 5.9 来歴と、エンジンが違う結果の混在

> ✅ **実装済み**（2026-10-14。server 側）。項目の形は [16](./16-analysis-storage.md) §3.1。
> 2026-10-16 決定（実装済み・本番は未反映）: 手元 worker の評価関数をつようら王11mini に替えるのに合わせ、worker も `evalHash`・`fvScale` を送る
> （`ENGINE_EVAL_SHA256` / `ENGINE_FV_SCALE` が設定されているときだけ。今動いている本番の worker はまだ送っていない。
> [05](./05-analysis.md) §1.2）。手元 worker の経路では、これを上書き・再開の条件に使わない点は変えない（下の ⚠）。

- **来歴（`runs`）に足す項目**: 実行環境（native / wasm）・エンジンのビルド識別・評価関数のハッシュ・`FV_SCALE`・スレッド数・
  置換表の大きさ・定跡の有無。既存の行は項目なしのまま読める
- 🔒 **途中の解析だけ、エンジンのビルドか評価関数が違えば先頭からやり直す。** 判定は開始の口（§5.8）で行う。
  - 🔒 **やり直しは「続きに重ねる」ではなく作り直し**（レビュー OCL-51D1C579・2026-10-14）: 開始の口が行ロックの下で
    **途中の解析の行を消し、`analysisRevision` を進めて**から、新しい世代と再開位置 0 を返す（[16](./16-analysis-storage.md) §4.3）。
    消さずに 0 手目から送ると、前の解析の末尾が残り、再開位置と完了の判定がそれを数えてしまう。
    前の世代の報告は世代の照合で破棄される（[05](./05-analysis.md) §1.1c）
  - **「違う」の判定**（実装時に決定）: 入っている解析の来歴のどれかが、今のビルド識別か評価関数のハッシュと違えばやり直す。
    **項目を持たない来歴（手元 worker・項目を足す前の解析）も「違う」に数える**
  - 🔒 **チャンクの報告でも同じ照合をする**（実装時に決定）: 入っている解析と別のエンジンのチャンクは破棄する（`applied: false`）。
    開始の口を通さない報告——別のタブ・別の端末が同じ世代を掴んだまま、配信物の更新の前後で別のビルドを動かしている——で
    1 つの解析に別のエンジンの結果が混ざるのを止める。破棄された側は開始からやり直し、そこで行が消えて世代が進む
  1 つの棋譜の中で別のエンジンの結果を混ぜないため（[16](./16-analysis-storage.md) §8）
  - **端末・スレッド数の違いは許し、記録するだけ**
  - 🔒 **2 段化では、照合の対象を「進行中の段の行」の来歴に絞る**（2026-10-15 決定・**実装済み**。レビュー OCL-C064EC8D。
    開始の口の判断は `planBrowserStart`、段の行の来歴は `runsOfStage`——`profile` がその段の run。どこからも指されない run は詰めて
    いるので、これが「その段の行の来歴」になる）:
    - **完了した quick はエンジンが違っても引き継ぐ。** full の開始（full が 0 局面）では照合せず、そのまま full を始める。
      手元 worker の quick（項目を持たない来歴）の上をブラウザの full が上書きしていく場合（§5.7 の `worker` → `browser`）や、
      quick の完了後に配信物が更新された場合がこれにあたる。full が quick を上書きしていく間の混在は §5.7 と同じく許容する
    - **full の途中**（`0 < fullCount < 局面数`）で full の行の来歴が今のエンジンと違えば、full の途中ぶんだけは取り除けないので
      （§5.7 の規則 1 と同じ理由）**全消去して quick から作り直す**。quick の途中で違うときは今と同じ
    - **チャンクの報告**も、届いた段と同じ段の行の来歴とだけ照合する（full のチャンクを quick の行の来歴では破棄しない）
  - **評価関数の選択の切り替え**（§5.5。2026-10-16 決定・未実装）もここに載る: 選んだ評価関数で `engineBuild` と `evalHash` が変わるので、
    進行中の段は「違う」と判定されてやり直しになる。新しい規則は足さない
  - 🔒 **完了済みの解析は不変**（[05](./05-analysis.md) §1.1c）。エンジンを更新しても、担当を切り替えても、評価関数を切り替えても、完了済みはそのまま残る
    （担当の切り替えで、full の途中結果を持つ棋譜だけは消す。§5.7 の規則 1）。
    完了済みの作り直しは `reanalyze` だけ
- ⚠ **[05](./05-analysis.md) §1.1d「エンジン識別子を上書き・再開の条件に使わない」との関係**: あちらが避けたのは
  「手元 worker の再ビルドで版文字列が変わり、**全棋譜の意図しない全再解析**が起きる」こと。ここでやり直すのは
  **途中の解析だけ**で、完了済みには触れないので全棋譜の再解析は起きない。この 1 点だけを例外として置く
  （手元 worker の経路の扱いは変えない）

    full は全力 4・控えめ 2、quick は今までどおり。段の上限の違いは作り直さず、段の開始で `setoption Threads` で合わせる（§5.5）。
    下の「負荷の設定の変更は作り直す」は変えない
- **負荷の設定の変更は、次の解析の開始（次の段・次の棋譜）から効く**。動いているエンジンに `setoption Threads` で変えず、
  開始の口を叩くたびに今の設定を読み、前と違えばエンジンを作り直す（WASM のスレッドの確保を実機で確かめていないため。
  評価関数は HTTP キャッシュから読み直す）。変更で常駐の解析は作り直さない（解析中の棋譜は区切りまで今の負荷のまま）
- **解析中の円環**: 手元 worker の進捗と同じ見え方にした——段ごとに 0 から数え直し、quick は薄く・full は濃く出す
  （quick が 100% になった後、濃い円環が 0 から出直す）。円環の意味（その段の解析済みの局面の割合）は変えない

**検討盤の局面評価**（2026-10-29 決定・実装。[12](./12-position-lab.md) §2.4）:

- 🔒 **採点の読みと同じ割り込みを使う**（下の「採点の読みで実装時に決めたこと」）。常駐（`controller.ts`）が採点の読みと局面評価の両方を受け持ち
  （`grading.ts` の `setBrowserReader`）、`scheduler.runPriority` の下で全局面解析より先に読む。ほかのタブへの印のロックも同じ
- スレッド数は負荷の設定の数で、上限は full の段と同じ 4（控えめは 2）。動いているエンジンには `setoption Threads` で合わせ、作り直さない（§5.5）
- 同意の前なら、押した時点で同意を求める（評価結果の枠に案内を出す）。同意すれば全局面解析にも効く（同意は 1 つ）
- 頼んだ側が取り下げたら（局面が変わった）、順番を待つ間なら読まず、読みの途中なら `stop` で打ち切る

**採点の読みで実装時に決めたこと**（2026-10-16。`grading.ts`・`scheduler.ts` の `runPriority`・`engineReads.ts` の `evaluateNamed`）:

- **出題の画面から常駐の解析へ頼む**（`requestBrowserGrading`）。常駐（`controller.ts`）が受け持ち手を登録し、全局面解析と**同じエンジン**
  （棋譜をまたいで使い回すもの）で読む。負荷の設定と、設定が変わったときの作り直しも全局面解析と同じ規則
- **同じタブの全局面解析**: 頼まれたら解析中の棋譜を既存の中断で止め（局面の境目で未送信のチャンクを送ってから止まる）、同じロックの下で
  採点の読みを済ませてから選び直す。止めた棋譜は空け時間を置かずにまた選ばれ、開始の口が返す再開位置から続く
- **ほかのタブの全局面解析**: 採点の読みは、印のロック（`seseraki:browser-analysis:drill`）を取ってから解析のロックを待つ。
  解析中のタブは**局面の境目ごと**に Web Locks の照会でこの印を見て、取られて（待たれて）いれば未送信のチャンクを送って止まる（`paused`）。
  止まったタブは空け時間なしで選び直してロックを待つが、採点の読みのほうが先に並んでいるので先に通る
  - 🔒 **ページが見えるのを待つ間も聞く**（レビュー OCL-62435AC8）。隠れている間のエンジンの失敗で見えるのを待つタブはロックを持ったままなので、
    局面の境目だけで聞くと、採点の読みがそのタブを表示するまで止まる。待つ間も 1 秒ごとに聞き、待っていれば `paused` で止まってロックを手放す
- **常駐が動いていない**とき: 状態が同意の前・解析できない環境・エンジンが無い・止まっている（`error`）なら、待たずに「この端末では採点できない」。
  起動の途中なら 15 秒まで待つ（ページを開いた直後の解答）
- エンジンの失敗は 1 度だけ作り直して読み直す。だめなら採点できない旨を出す（棋譜の失敗とは関係しない）
- 経過はコンソールに `[browser-analysis] drill: …` で出す（`reading <手> for 600ms`・`score cp <値> depth <深さ>` など）

## 6. 保存と容量（一般ユーザー）

### 6.1 1 局あたり

| 部分 | 1 局あたり |
|---|---|
| 棋譜本体 | ≒ 6KB |
| 全局面解析（MultiPV 1・読み筋は全部。1 棋譜 1 行に詰める。2 段でも full が quick を上書きするので 1 段ぶん。[16](./16-analysis-storage.md)） | ≒ 8KB |
| 局面検索の索引（ハッシュ化。§6.3） | ≒ 36KB |
| **合計** | **≒ 50KB**（詳細検討した局面ぶんは別） |

> 改訂（2026-10-07）: 当初は行ごとの形のまま 55KB と見積もっていた。解析結果を 1 棋譜 1 行に詰めると、何も捨てずに 10 分の 1 前後になる（[16](./16-analysis-storage.md) §2 の実測）。

### 6.2 上限

- **1 ユーザー 3,000 局**（≒ 150MB。設定値で変えられる）。全体の空きを見て引き上げる
- **取り込み頻度にも制限を付ける**（取り込みは server のメインスレッドを塞ぐ）
- 🔒 **件数だけでなく、1 件あたりの大きさにも上限を付ける。** 件数の上限は「普通の棋譜」を前提にした容量の見積もりで、
  巨大な棋譜・メモ・解析結果を送られると 3,000 局に届く前に容量と CPU を使い切られる。
  **解析結果はブラウザから届く＝信用できない入力**（§5.1）なので、server の検証で落とす
  （解析結果の検証と上限は段階 3 の受け口と同時に入れる。§5.8）:

  | 対象 | 上限の考え方 |
  |---|---|
  | リクエスト本文 | 取り込み・解析報告とも本文サイズに上限 |
  | 棋譜 | 手数（実戦の棋譜に収まる値）・KIF 本文のバイト数 |
  | メモ | 文字数 |
  | 解析結果 | 1 局面の候補手数（一般ユーザーは MultiPV 1 + 名指し 1）・読み筋の手数・局面数（= 手数 + 1 を超えない） |
  | 詳細検討 | 1 ユーザーあたりの保存件数（局面数）。超えたら古いものから消すか、新規を断る |

  具体値は実装時に決める（実戦の分布から余裕を持たせる）

### 6.3 局面検索の索引

> ✅ **実装済み**（ハッシュ化と照合・`ownerId` の非正規化と所有者を先頭にした索引。`/positions/similar` の所有者専用化と検索の所有者での絞り込みは所有者スコープの PR 2）。
> 列と検索の形は [10](./10-video-analysis.md) §3.2・§5.1、ハッシュ関数は `shared` の `position-hash.ts`。

- 🔒 **局面の文字列ではなく 8 バイトのハッシュで索引し、引いた後に盤のバイト列で照合する。** 誤ヒットは起きない
  （[10](./10-video-analysis.md) §5.1 がハッシュを避けた理由は衝突で、照合でそれを消す）。文字列は盤と持ち駒から作り直せるので保存を省ける
- **所有者を含む全員に適用する**（仕組みを 1 本に保つ）。≒ 80KB → 36KB/局
- **完全一致（主体側）の検索（`/positions/subject`）は一致した行を SQL の上限なしで全部読む**（照合をアプリ側でするため）。所有者で絞ったうえで、**読み出す行数に上限を設ける**（打ち切ったことは応答で示す）。序盤の配置は 1 人 3,000 局でもほぼ全局に一致する
- **近い局面の検索（`/positions/similar`）は所有者だけ。** 手数帯の全局面を読み出して盤を比べる処理で、
  server のメインスレッドを使う。局数が多いほど読み出しの打ち切り（2 万行）で結果も不正確になる
