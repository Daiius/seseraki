# kifu-vision（実験）

将棋アプリの録画から**盤面の変化を読み取って棋譜（USI 手列）を復元する**実験パッケージ。
取り出した手列は `shared` の戦型判定やエンジン解析に載せることを狙っている。

> ⚠ **実験中。** まだ通しで棋譜を起こせる状態ではない。素材は追跡しない
> （`data/` は `.gitignore` 済み）。

## なぜテンプレート照合で足りるのか

実物の将棋盤を撮った写真から局面を読む研究は、輪郭検出・線分検出・射影変換に加えて
駒の分類に CNN を使うのが普通である。**それはカメラで撮るからで、対象がアプリの
画面出力なら事情が変わる。**

- 盤の位置とマスの大きさが**動画をまたいで一定** → 1 度測った定数を使い回せる
- 同じ駒は**毎回ほぼ同じ画素で描かれる** → 照合で分類できる
- 射影変換も照明補正も要らない

結果として依存は `ffmpeg` だけで済み、画像ライブラリも機械学習も使っていない。

## 組み立て

| ファイル | 役割 |
|---|---|
| `src/geometry.ts` | 盤の位置とマスの大きさ。持ち駒が並ぶ帯の座標も |
| `src/frame.ts` | ffmpeg から生の画素を受け取る。1 枚取り／全編を流す／マスの平均色だけ流す |
| `src/occupancy.ts` | マスに駒があるか（輝度の散らばりで判定） |
| `src/template.ts` | 駒テンプレートの生成と NCC 照合 |
| `src/recognize.ts` | 盤面画像 → 駒の配置 |
| `src/moves.ts` | 配置の差分 → USI の手。`applyMove` による検算 |
| `src/legality.ts` | 駒の動きとして有り得るか（合法手生成器ではない） |
| `src/sanity.ts` | 配置が将棋として成立しているか。偽の駒の除去 |
| `src/solve.ts` | 読めなかったマスの駒種を手の整合性から逆算 |
| `src/calibrate.ts` | 盤の格子を動画ごとに測り直す。駒の絵の位置で詰め直す |
| `src/template-store.ts` | テンプレートの保存と読み込み（寸法が違えば引き伸ばして合わせる） |
| `src/movegen.ts` | その局面で指せる手を全部並べる |
| `src/candidate.ts` | 候補手と読みを突き合わせ、いちばん整合する手を選ぶ |
| `src/tracking.ts` | 盤面だけでなく持ち駒と手番も追う |
| `src/montage.ts` | テンプレートを並べて 1 枚の絵にする（目視で確かめるため） |
| `src/segments.ts` / `src/events.ts` | 局面が変わらない区間の検出（現在は使っていない。下記） |

実行は `extract-simple.ts` が主。`probe-*.ts` は調べもの用。

```
pnpm --filter kifu-vision exec tsx extract-simple.ts <動画パス> [開始秒] [終了秒] [間隔秒]
pnpm --filter kifu-vision test
```

`ffmpeg` のスレッド数は `KIFU_VISION_THREADS`（既定 4）で変えられる。

## 分かったこと

### 駒の有無は完全に分かれる

マス内側の輝度の**標準偏差**を見ると、空マス 2〜9 / 駒あり 51〜71 と 2 山に割れ、
間に 40 以上の隙間があった。盤の背景演出で明るさの水準は動くが、標準偏差は
水準に依らないので影響を受けない。

### テンプレートは外から用意しなくてよい

平手初期局面が映るフレームさえ見つかれば、そこに並ぶ 40 枚の正解ラベルは
初期配置から自明なので、生駒 8 種 × 2 向きが自動で揃う。

成駒は初期局面に無いが、**読めなかったマスに駒種を総当たりで割り当て、
ちょうど 1 手で説明が付く割り当てを探す**ことで確定できる（`solveUnknowns`）。
画像ではなく論理で決まるラベルなので信頼でき、そのままテンプレートに加えられる。

⚠ ただし**候補を絞らないと必ず曖昧になる**。角が敵陣に入る手は、移動先を「角」と
置けば成らず、「馬」と置けば成りとして、どちらも 1 手で説明が付いてしまう。
「まだ覚えていない駒種」に候補を限ると一意に定まる。

逆算は 2 段階で試す。まず未学習の駒種（＝成駒の学習）、駄目なら全駒種。
**駒を動かす瞬間マウスは必ず盤上にあり、しかも移動先の上にあることが多い**ので、
読めない駒が成駒とは限らないため。全駒種で曖昧になれば null が返るだけなので、
誤って覚えることはない。

### 合法手生成器は要らない

1 手で変わるマスは高々 2 つなので、差分の形から手が決まる。

```
移動（取らない）: 移動元が空になり、移動先が埋まる
移動（取る）    : 移動元が空になり、移動先の駒が入れ替わる
打ち            : 移動先が埋まるだけ
```

正しさは `shared` の `applyMove()` を適用して次の配置と一致するかで確かめる。

⚠ **`applyMove` の検算だけでは足りない。** あれは「その手を指せばその配置になるか」
しか見ないので、認識がずれて生まれた「銀が届かない距離を飛ぶ」ような手も通る。
駒の動きの側からも弾く必要がある（`legality.ts`）。

### 変化の検出に凝る必要は無かった

「盤面が変わった瞬間」を安く見つけようと、駒の有無や**マスの平均色**で区間を切る
方法を試したが、どちらも「盤面が変わった」以外の理由で立つ。

- 駒の有無 → マウスポインタが空マスに重なると揺れる
- マスの平均色 → 直前に指した手のマスに付くハイライトの明滅でも動く

**読んだ配置そのものを比べれば、こうした揺れは最初から入り込まない。** 認識は
安定している（NCC 中央値 0.98）ので、一定間隔で読んで配置を比べるだけでよい。

唯一の落とし穴は駒がスライドしている途中の絵で、移動元が空いてから移動先が
埋まるまでの数フレーム、駒はどのマスにも属さない。ただし**駒が盤から消えるだけの
手は将棋に無い**ので、この形（`piece-vanished`）は確実に見分けられる。

### マウスポインタは輝度で見つかる

盤の木目は実測 130〜210、ポインタの白い矢印は 240 以上とはっきり分かれる。
マス内に極端に明るい画素が一定割合あれば、そこにポインタがいると判定できる
（`hasPointer`）。**駒を動かす瞬間ポインタは必ず盤上にいる**ので、いちばん
読みたい場面でいちばん邪魔になる。

⚠ この結論に辿り着くまで遠回りした。「桂が 5 枚（上限 4）」という数字から
「5 枚目は成桂だろう」と推測して成駒テンプレートの不足を疑ったが、**実際に
そのマスの画像を集めて並べたら大半がポインタだった**。数字から原因を推測せず、
先に絵を見るべきだった。

### マウスポインタは偽の駒を作る

空マスにポインタが重なると輝度の散らばりが増えて「駒あり」と判定され、照合が
適当な駒を当ててしまう。「桂が 5 枚」「角が 3 枚」といった盤面が実測で 4 割に出た。

対処は**削るのではなく引き継ぐ**のがよい。覆われただけなら駒はそこにあり続けて
いるので、読めなかったマスは「変わっていない」と見なして直前の配置を持ってくる
（`carryUnknowns`）。誤った駒として読むと差分が壊れるが、引き継げば壊れない。

駒が取られて消えた場合は駒の有無の方が変わるので、引き継いでも 1 手差分にならず
`piece-vanished` に落ちる。覆われている間に相手の駒へ置き換わった場合だけは
見逃しうるが、次に読める時点で辻褄が合わなくなるので気付ける。

⚠ 成った駒もテンプレートが無いうちは「読めなかったマス」に入る。引き継ぐと成りが
消えてしまうので、**引き継ぎ版 → 素の読み → 駒種の逆算**の 3 段構えで試す。

一致度の低いマスを**削る**方法（`pruneOverflow`）も書いて試したが、
**逆効果だった**。ポインタは本物の駒にも重なり、そのとき本物の一致度も下がるので、
本物を削って差分を壊す。実測では捨てる絵が減った代わりに
`too-many-changes` が 145 件、`illegal-shape` が 111 件出て、読めた手は増えなかった。
関数は残してあるが使っていない。

### 「駒があるか」と「何の駒か」で見る範囲を変える

どちらもマスの内側を切って見るが、**見たいものが違うので同じ範囲である必要はない**。

- 駒の有無（`CELL_INSET` = 0.18）… 駒の輪郭まで含めた方が輝度が散らばる
- 駒の種類（`MATCH_INSET` = 0.24）… 中心の字だけを見る方がよい

実測（ある局面の 39 マス）では、照合の範囲を 0.18 → 0.24 に寄せると
**最低の一致度が 0.490 → 0.662 に上がった**（いちばん読みにくいマス＝ポインタに
覆われたものが読みやすくなった）。正解数と中央値は変わらない。0.30 まで寄せると
0.640 に下がるので、駒の形の情報が減りすぎる。

直前に指した手のマスに付くハイライトも駒の周囲に強く出るので、同じ理屈で影響が減る。

### 新しいテンプレートは「駒でないもの」とも照合して確かめる

成駒のテンプレートを足したら読める手が減った（61 → 52）。テンプレートどうしの
相関を測ると、龍は生駒どうし（最大 0.415）より紛らわしくない（最大 0.306）。
それでも悪化した。

原因は**マウスポインタだった**。龍が 2 マス出ている局面を見に行くと、片方は
本物の龍で、もう片方は**ポインタしかない空マス**。白い矢印の濃淡が「ス」の字と
相関していた。盤上に龍は 1 枚しかいないので `R` が上限を超え、`sanity` が
盤面ごと捨てる。**「盤面が成立せず捨てた」が 10 件から 507 件に増えていた。**

⚠ **駒どうしで区別できることと、駒でないものを駒と間違えないことは別の話。**
新しいテンプレートを採るときは、ポインタや演出の絵とも照合して確かめる必要がある
（`data/unknown/` に集めたものが使える）。単純な字ほど駒以外と衝突しやすい。

### ポインタと成駒は、性質が違う

どちらも「読めないマス」を作るが、効き方がまったく違う。

| | マウスポインタ | テンプレートの無い成駒 |
|---|---|---|
| 現れ方 | 一時的（動けば消える） | **居座り続ける** |
| 影響 | その瞬間の絵が読めない | **その駒がある間ずっと読めない** |

手順が細切れに途切れる原因は後者。実測では龍（草書体で「ス」と書かれる）が
「桂」と読まれ続け、**8 分間が丸ごと落ちていた**。

成駒は手の整合性から逆算して覚えられる（`solveUnknowns`）が、成りが起きる瞬間は
駒が動いていてポインタも近く、いちばん読みにくい。実際 1 種しか取れなかった。
そこで **`seed-templates.ts` で「この時刻のこのマスはこの駒」と与えて起こす**。
画像を見れば駒種は一目で分かる。作ったものは `data/templates/` に残り、
**レイアウトが変わらない限り他の動画にも使い回せる**。

### テンプレートの無い駒は「居座る」

ポインタの誤認識は動けば消えるが、**テンプレートを持っていない駒はそこに
あり続ける**。実測では 2 分間まるごと「桂が 5 枚（上限 4）」で全フレームが捨てられ、
1 手も読めなかった。盤上の桂は 4 枚しかないので、5 枚目は成桂（圭）が「桂」と
読まれたもの。これが**手順が細切れに途切れる主因**だった。

対処は同じく引き継ぎで、**規定より多い駒種のマスを「読めなかったマス」として
挙げ**（`overflowCells`）、前の配置を持ってくる。駒の枚数という将棋の側の制約が、
そのまま誤認識の検出器になっている。

### 🔴 格子線が合っていても、照合は通らないことがある

外から受け取った盤面の絵（別の端末で撮った解析画面など）をテンプレートの採取源に
使おうとして踏んだ。格子線の当てはめは**うまくいっていた**——線のくっきりさは
盤が写っていない絵の 3 倍以上あり、目視の当たりからのずれも 1 画素以内だった。

ところが、その格子で切り出すと**正解が分かっている 20 マス中 12 マスしか読めず、
NCC も 0.4 前後**。数画素ずらすと 20/20・NCC 0.9 に跳ね上がる。

⭐ **測るべきものが違っていた。** 格子線の位置は合っている。合っていないのは
**駒の絵がマスの中のどこに描かれるか**で、そこは端末やアプリの版で微妙に変わる。

さらに、**最良のずれが列ごとに増えていた**（端から端で 4 画素）。原点だけの
問題ではなく**マス寸法の誤り**である。1 マスずつ測ったずれに直線を当てはめ、
切片を原点の補正、傾きを寸法の補正として取り出す（`refineByTemplates`）。

⚠ 当てはめは**中央値**（Theil–Sen）で行う。手掛かりのマスは全部が読めるとは
限らず、読めなかったマスは「探索範囲の端」というでたらめなずれを返す。
最小二乗は二乗で効かせるので、**外れ値が 2 枚混ざるだけで当てはめが動かなくなった**。

### ⚠ 閾値は代用でしかない。代用が外れたら閾値を動かさない

「新しいテンプレートが既存のものと 0.6 以上相関したら、それは読み違えである」
という規則を使っていた。これは**「別の駒の写しになっていないか」を相関で代用**
している。

成銀（`全`）がこれに引っ掛かった。金と **0.7〜0.8** 相関し、しかも**位置合わせを
良くするほど上がる**。対照として、同じ出所の生駒どうしの最大相関は 0.415 しか
ないので、閾値をどこに引いても成銀だけが弾かれる。

⭐ 目で見れば簡単だった。**金は点が二つ付き、全は付かない。字は違う。**
似ているのは字画の重心がほぼ同じだからで、NCC はそこをよく拾う。

判定を代用から**本物**へ変えた——**「その生駒自身のマスを横取りするか」**を見る。
ラベルが誤っている（＝実は別の駒の写しである）なら、その駒の本物のマスに対して
本物のテンプレートより高い点を出すはずである。材料は初期局面に全部ある。
この判定なら成銀も通る。ただし余裕は他の 3〜4 分の 1 しかなく、
**読みだけでは決められない**ことが数字として残る。

### ⭐ 絵で割り切れないものが、ルールでは 1 つに決まる

その成銀と金の紛れが、実際に手順を切った。相手が**金を打った**のに、成銀の
テンプレートの方が一致してしまったのである。

だが**打つ手に成駒はあり得ない**。候補は金打ちしか無い。

ここまでの読み方は「81 マス読む → 差分を 1 手として説明できるか」という向きで、
**開いた集合に問いを投げていた**。マスごとに「20 種のどれか」を当てるので、
読めないマスが 1 つあると手が決まらない。合法手はルールで閉じた集合なので、
向きを逆にすると詰まりが消える——**未確定のマスは「情報が無い」として飛ばせばよい**。

設計で効いたのは 3 点:

1. **未確定のマスは数えない**（一致にも食い違いにも入れない）。「読めなかった」を
   「違っていた」と混ぜると、正しい候補が沈む
2. **「食い違いが 0 か」ではなく「食い違いが最も少ないのが 1 つに決まるか」で判断する。**
   追跡中の盤面に古い誤りが残っていると**全候補に等しく食い違いが乗る**ので、
   絶対値で切ると何も選べなくなる
3. 🔒 **分からないときは候補が広がる方へ倒す。** 途中の局面から追跡を始めると、
   盤に無い駒がどちらの持ち駒かは**盤面からは決して分からない**。「持ち駒は無い」と
   狭めると、本当に指された打ちが候補から消えてそこで追跡が切れる

⭐ 副産物として、**成/不成が成駒のテンプレート無しでも決まる**。移動元と移動先が
同じ候補は「X か +X」の 2 つしかなく、**生駒のテンプレートは必ず持っている**ので、
「生駒に見えないなら成っている」という消去法が使える。

### 持ち駒を追うと、偽の打ちが原理的に消える

マウスポインタや演出で駒が湧いて見えると、差分は「空 → 駒」になる。これは
ちょうど**打ちの形**なので、盤の 81 マスだけを見ていると弾けない。
`BoardState`（盤＋持ち駒＋手番）ごと進めれば、持っていない駒の打ちは
候補に現れない。

## 残っていること

- 通しで 1 局ぶんの手列を復元する
- 対局以外の場面を弾く（感想戦は盤のレイアウトが違う。冒頭に対局者紹介が入る）
- 1 本の動画に複数の対局が入るので切り分ける
- 駒のデザインは利用者が変更できる。保存先をデザイン別にし、初期局面の生駒を
  照合して自動判定する。未知のデザインでも**生駒は自動生成されるので同じ性能で動く**
- 画面の持ち駒欄を読む。棋譜の復元には要らない（初期局面から追えば確定する）が、
  追跡した持ち駒と突き合わせれば**手の取りこぼしを独立に検出**できる
