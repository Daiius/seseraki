# 01. ドメインとプロダクト動機

このアプリが扱う対象は **将棋の棋譜** と、その **エンジン解析結果** である。
データモデル（[03](./03-data-model.md)）・投入（[04](./04-ingestion.md)）・解析（[05](./05-analysis.md)）は、
すべてこの章のドメイン事実を地盤とする。実装エージェントはまずここを参照すること。

---

## 1. プロダクトの動機（なぜ作るか）

個人が自分の対局を振り返るための道具である。市販・無料の将棋ソフトでも解析はできるが、次の 3 点を
「自分の運用に合う形」で束ねたい、というのが出発点:

1. **棋譜を溜め込んで自動で解析したい。** 対局のたびに手動で解析させるのは面倒なので、対局履歴から
   まとめて取り込み、対局相手・勝敗・日時を起こしてタイトルを付け、あとは放っておけばデスクトップ PC が
   順番に解析してくれる、という状態を作る（[04](./04-ingestion.md) / [05](./05-analysis.md)）。
2. **疑問手と分岐を一望したい。** 「どこで形勢を損ねたか」「その局面で最善は何だったか」を、評価値グラフ・
   悪手マーカー・候補手の読み筋として並べて眺める（[05](./05-analysis.md)）。
3. **LLM に講評させたい。** 棋譜と解析結果を整形して LLM に渡すと、意外と的を射た分析が返る。
   その「貼るだけ」の下準備をアプリ側で用意する（[06](./06-llm-commentary.md)）。

将棋ソフトとの相互運用も視野に入れ、**KIF 形式の棋譜を読める**ようにしておく（貼り付け。ファイルアップロードは対象外・§6）。
これにより取り込み経路によらず、いろいろな出所の棋譜が同じパイプラインに乗る。

## 2. 棋譜フォーマット（KIF / CSA / USI）

本アプリは複数の棋譜表現を扱い、内部処理は **USI** に寄せる。

| 形式 | 役割 | 扱い |
|---|---|---|
| **KIF** | 人間可読な標準形式。ユーザーの入力窓口 | 原本を `kifText` に保管。登録時に server が USI へ変換 |
| **CSA** | swars 取り込み時の中間形式 | swars 取り込みフローで CSA→KIF 変換してから登録（[04](./04-ingestion.md)） |
| **USI** | エンジン・内部処理用の指し手表記 | `usiMoves`(string[]) として保持。worker と Web 盤面が消費 |

- **KIF→USI 変換は server 側で棋譜登録時に一度だけ実行する**（`packages/server/src/kif`）。
  worker は KIF パーサーを持たず、`usiMoves` だけを受け取って解析する（[05](./05-analysis.md)）。
- 日本語の指し手表記（例 `▲７六歩(77)`）は Web 側で USI から盤面追跡で復元する（[05](./05-analysis.md) §日本語表記）。

## 3. 対局のメタ情報

1 局の棋譜からは、指し手列のほかに次のメタが取れる（取れないものは nullable）:

| 項目 | 説明 |
|---|---|
| `sente` / `gote` | 先手 / 後手プレイヤー名 |
| `senteDan` / `goteDan` | 先手 / 後手の**段級**（取得元にあれば）。段位ではなく段と級の両方を持つ |
| `result` | 対局結果（勝敗・決着の種類） |
| `playedAt` | 対局日時 |

- これらは対局メタであり、**登録時に抽出して `kifus` に格納する**（現行の KIF 貼り付け経路、および
  残置している swars 経路の両方で抽出は実装済み。KIF 経路はヘッダ〔先手/後手/段級/開始日時〕を読み、
  `result` は終局マーカー＋手番 parity から導出。[04](./04-ingestion.md) §3）。
- **段級の表現**（`senteDan` / `goteDan` の永続化契約）:
  - **段は正・級は負**の単一の数値で持つ。初段=`1` / 九段=`9` / 1級=`-1` / 30級=`-30`。
  - 受け入れ範囲は**段 1〜9・級 -1〜-30**。将棋ウォーズは 30 級から始まるためこの下限を採る。
    範囲外（10 段以上・31 級以上）は誤記・異常入力として `null` にする（符号付き `smallint` に
    収まらない値を DB へ渡さないため。[03](./03-data-model.md)）。
  - `null` は「取得元に段級が無い / 段級として解釈できない」を表す。`竜王` のような段級以外の称号は
    段級ではなく**プレイヤー名側に残す**。
  - **値の大小がそのまま棋力の順序**になる（`senteDan > goteDan` なら先手が格上）。格上格下の比較・
    並び替え・絞り込みにこの値を直接使ってよい。負数表現を採るのはこの順序性のためで、
    「数値 + 種別（段/級）」の 2 カラムだと種別が符号から一意に決まり冗長なうえ、比較が複合条件になる。
  - カラム名は `Dan` のままだが**保持するのは段級**である。既存データと API の互換のため改名しない。
    `Dan` を正数限定の段位と解釈してはならない。
- **対局タイトルの自動生成**に使う: 「誰と対戦したか」を人間可読なタイトルに起こす（KIF 貼り付けは `title` 任意で、
  空なら `${sente} vs ${gote}` を自動生成）。これがあると一覧画面（[05](./05-analysis.md)）で対局を見分けられる。
- Web 一覧では、自分の名前候補（`VITE_SELF_NAMES` のカンマ区切り ∪ `VITE_SWARS_USER_ID`）のいずれかが
  対局者名に一致すれば、そのユーザー視点で**勝敗バッジ**を出す。将棋アプリごとに自分の表示名が異なる
  （例: `Daiius` / `daiius`）ため複数候補を許容する。両対局者とも候補に一致した場合は側を確定できない
  ため自分視点表示は無効化し、詳細画面で警告を出す。

## 4. 棋譜の供給源

- 現行の入り口は **KIF 貼り付け**（[04](./04-ingestion.md)）。かつては **swars からの一括取り込み**も
  あったが、**無効化した**（実装は残置。[04](./04-ingestion.md) §4）。
- swars 一括取り込みは複数対局をまとめて登録できた。**swars の正式名称・取得の詳細な仕組み・アクセス姿勢・資格情報**は
  公開文書に書かず、`.claude-personal/` の運用メモに集約する（[README](./README.md) §公開リポジトリでの秘匿方針）。
- **KIF→USI 変換・対局メタ抽出・解析の下流は入り口に依らず共通**（メタ抽出は残置の swars 経路・KIF 経路とも
  実装済み。§3 / [04](./04-ingestion.md) §3）。

## 5. 解析ドメイン（評価値・候補手・疑問手・分岐）

エンジン解析が生む概念。用語と数値の意味を固定する（実装は [05](./05-analysis.md)）。

- **局面（moveNumber）**: `moveNumber = N` は **N 手適用後・N+1 手目を指す前の局面**（`0` は初期局面）。
  **偶数 = 先手番 / 奇数 = 後手番**（その局面で指す側）。1 棋譜 = 局面の列。
- **評価値（score）**: **保存値は USI エンジンが返す手番視点のスコア**（正規化せず `candidateMoves` にそのまま格納。[03](./03-data-model.md)）。
  型は `cp`（centipawn）または `mate`（詰みまでの手数）。表示・判定時に **moveNumber の parity で先手視点へ正規化**する
  （後手番＝奇数の局面は符号反転。実装 `toSenteEval`。[05](./05-analysis.md)）。形勢判断ラベル（互角/有利/優勢/勝勢/詰み）は先手視点値に写像。
- **候補手（MultiPV）**: 各局面でエンジンが返す上位 N 手（既定 3）。`rank=1` が最善。
  各候補は指し手・スコア・**読み筋（pv）**・探索深さ（depth）を持つ。
- **CPL（centipawn loss）**: **最善手の評価 − 実手の評価**（手番側視点）。実手の評価は、**実手が候補手に
  含まれていればその `scoreValue`、含まれていなければ次局面の最善値を符号反転**して得る（後者は近似。
  [05](./05-analysis.md) §2.3）。同一局面・同一手番の比較なので先手視点への正規化は要らない。
- **疑問手 / 悪手**: 実際に指された手が最善から大きく外れた手。判定は CPL の 2 段階
  ——**悪手**（CPL ≧ 悪手閾値）/ **疑問手**（疑問手閾値 ≦ CPL < 悪手閾値）。**「好手」は設けない**
  （相手が損したのは相手の悪手であって自分の好手ではなく、真の好手は MultiPV=3 では判定できない）。
  閾値は UI から変更でき、既定は悪手 600cp / 疑問手 300cp（[05](./05-analysis.md) §2.3・§2.5）。
- **詰み系（詰み逃し / 詰まされ）**: **mate が絡む変化は CPL を計算せず別カテゴリとして扱う。**
  詰みは連続量ではなく、cp に写像すると 30000 級の損失になって平均 CPL を 1 局で壊すため。
- **決着**: 局面の最善評価値の絶対値が決着閾値（既定 3000cp）以上なら勝負が決したとみなし、
  **ラベルを付けない**（CPL の計算自体はする）。詰み系は cp の量ではないのでこの対象外。
- **分岐**: ある局面で実手の代わりに候補手を選んで読み筋を辿る操作。「もしこう指していたら」を Web で再生できる。

> ⚠️ 評価値は評価関数に依存する。開発環境の MATERIAL（駒得ベース）は序盤で大きめに振れ、
> 本番の NNUE（評価関数同梱）の方が安定する（[05](./05-analysis.md) §エンジン構成）。同じ棋譜でも
> 解析エンジンが変われば数値が変わることを前提にする。

## 6. 戦型（戦法ラベル）

棋譜の指し手列から導ける**対局の型**。**エンジン解析を必要とせず `usiMoves` だけで決まる**のが
評価値まわり（§5）との一番の違いで、解析待ちの棋譜にも付けられる。

溜め込んだ棋譜を横断する軸として使う: 一覧を「角換わりだけ」に絞る / 「振り飛車相手だと勝率が落ちる」を
数字で見る / 棋譜詳細から「同じ戦型の過去局へ」飛ぶ。

### 6.1 判定は 3 層で行う

| 層 | 何を持つか | 例 | 保存 |
|---|---|---|---|
| **内部ラベル** | 局面述語の**真偽の時系列**。ユーザーには出さない | `_飛車68` `_角交換` `_飛車先歩交換` `_銀77` | しない |
| **一次ラベル** | 内部ラベルの時系列に対する論理式（同時 / 順序 / 否定）。戦法名 | 四間飛車・向かい飛車・角換わり・相掛かり・矢倉 | する |
| **二次ラベル** | 一次ラベル + 内部ラベルから導く派生・関係ラベル | 石田流・ひねり飛車・対抗形・相居飛車・相振り飛車 | する |

- **3 段目より下は作らない。** 層を増やすのではなく内部ラベルを足す。
- **内部ラベルは「事象」であって戦法ではない。** `_角交換`（事象）と `角換わり`（戦法）は将棋の用語としても
  別語で、角換わりは角交換に「序盤 / 相居飛車 / 交換後に駒組みを進める」を足したもの。3 手目▲2二角成・
  筋違い角・鬼殺しはいずれも角交換だが角換わりではない。この区別を層で表現する。
- **内部ラベルは単体で評価しない。** 精度は下流の一次 / 二次ラベルでのみ測る。
- **判定は手番ごと**に行う。先手・後手を独立に見て、盤面を反転して常に先手基準へ正規化する。

### 6.2 観測窓は「駒がぶつかるまで」（手数の定数を置かない）

戦法は**駒組み段階の形**なので、中盤の駒運びを戦法として拾わないための観測窓が要る。
窓は次の 1 つの規則で決め、**「30 手まで」のような手数の定数は置かない**:

> 窓は「駒がぶつかったら閉じる」。ただしその内部ラベルの述語が**駒を取った結果**を見ているなら、
> その駒種は "ぶつかった" に数えない。
> **一次 / 二次ラベルの窓は、それが参照する内部ラベルの除外集合の和**。

| 内部ラベルの例 | 除外する駒種 | 理由 |
|---|---|---|
| 飛車の位置・歩の伸び・銀の位置 | なし | 駒取りを見ていない |
| `_飛車先歩交換` / `_飛車34`（横歩取り） | 歩 | 歩を取った結果を見ている |
| `_角交換` / `_馬33` / `_筋違い角` | 角 | 角を取った結果を見ている |

- 除外する駒種が**定義の形から機械的に決まる**ので、判定を調整するための恣意的な数値が入らない。
- **和を取るのは必須**。角換わりは `_角交換`（角を除外）と `_双方飛車初期位置`（除外なし）を同時条件で
  組むため、和を取らないと「除外なし」側の窓が角交換の手で閉じ、**永久に成立しない**。
- **一律の窓では成立しない。** 窓を狭めると飛車の位置で決まる戦法の精度は上がるが、
  **交換そのものが定義の一部である戦法**（角換わり・相掛かり・横歩取り）は定義が成立する前に窓が閉じて
  全滅する。逆に緩めると中盤の駒運びが混ざる。ラベルごとに上の規則で決めるのが両立の条件。

**層をまたぐときの窓**（二次ラベルが一次ラベルを参照する場合）:

- **一次ラベルの判定結果は「その一次ラベル自身の窓で判定済みの値」として受け取る。**
  二次ラベルの側で再評価しないので、参照した一次ラベルの除外集合を二次ラベルの窓へ持ち込む必要はない。
  例: `対抗形` は `振り飛車` / `居飛車` の成否だけを見るので、窓を持たない。
- **二次ラベルが内部ラベルを直接参照するときは、その内部ラベルを参照先の宣言に含める**
  （§6.1 の 3 層は「二次 = 一次 + 内部」なので、この経路は実在する）。窓はそれらの除外集合の和で決まる。
  例: `ひねり飛車` は `_飛車先歩交換`（歩を除外）を直接参照するので、二次ラベル自身の窓が歩を除外する。
- **推移的に和を取る（参照した一次ラベルの依存を再帰的に足す）ことはしない。** 窓が必要以上に広がり、
  中盤の駒運びを拾う方向に働くため。**必要な除外は「直接参照するものを宣言する」ことで漏れなく入る。**
- 参照先の宣言と実際の参照がずれると窓が静かに間違うので、**宣言外の内部ラベルを読んだら失敗させる**
  （実装側の契約）。

### 6.3 記録の方針

- **経由形は誤検出ではない。** 2八→6八→8八 と振り直す途中で四間飛車が立つのは、
  `四間飛車 → 向かい飛車` という**正しい記録**。判定側で消すと「振り直しが本体」の戦法の情報が失われる。
  よって**飛車の移動元は条件に使わない**。
- **1 局・1 手番に複数のラベルが立ってよい。** 例えば角換わりと矢倉は排他ではない
  （7 七銀が角交換の前か後かで片方を消すと、角換わり腰掛け銀のような形が落ちる）。
- **合成タグを作らない。** `早石田` のような派生名では親（`石田流`）が立つ。派生名まで細分しない。
- **残余のラベルは他の一次ラベルの判定結果で取り下げる。** 相掛かりは「角道を止めずに駒組みを進める戦型」から
  角換わり・横歩取りなどが独立した**残り**なので、除外条件を相掛かり側に書き直さず、他のラベルの成否に委ねる。
  除外は**双方の判定を見る**（相手が横歩を取れば局面全体が横歩取りになる）。
- **否定条件は「そのラベルが成立する時点まで」で見る。** 窓いっぱいで否定を見ると、
  後から別の戦法へ組み替えただけの棋譜まで落とす。

### 6.4 派生値として扱う

- 戦型は `usiMoves` から**いつでも再計算できる派生値**。投入時に判定して `kifus` 側へ保存するが、
  正は指し手列であって保存値ではない（[03](./03-data-model.md) §2.1）。
- **判定ロジックを更新したら一括再判定する。** 保存値に判定バージョンは持たせない
  （解析来歴を持たないのと同じ立場。[03](./03-data-model.md) §7）。
- 判定は将棋ドメインの純ロジックなので、**`shared` に置く**（[02](./02-architecture.md) §3.2）。
