# 10. 動画解析

本章は**動画解析**——将棋アプリの録画から盤面の変化を読み取って復元した棋譜——を、自分の対局と区別して
保存・閲覧・検索する仕組みを定める。棋譜の復元そのものは `packages/kifu-vision`（実験パッケージ）の
責務で、本章は**復元された棋譜を seseraki に載せてからの話**を扱う。

ドメイン用語は [01](./01-domain.md)、スキーマ全体は [03](./03-data-model.md)、投入ルートは
[04](./04-ingestion.md)、解析は [05](./05-analysis.md) を参照。

> **段階 1（取り込み）と段階 2（局面索引・検索）は実装済み**（2026-08-17）。段階 3（近さ検索・
> 主体側モード）は未実装で、`kifus.subjectSide` もまだ無い（§7 / §8.1）。設計判断とその根拠を
> 定め、実装はここを正典とする。
> ⚠ 棋譜を復元する側（`packages/kifu-vision`）は**実験ブランチにのみ存在し、main には無い**。
> 本章は**復元された棋譜を受け取る側**の設計なので、復元側の実装状況とは独立に読める。

---

## 1. 目的とスコープ

**動画解析は「自分ではない誰かの対局」を集める経路**である。自分の対局（手動 KIF 貼り付け / swars）とは
出所も性質も違い、**勝敗の集計に混ぜても意味のある数字にならない**。

やりたいことは 3 つ:

1. **区別して溜める** — 自分の成績を汚さずに保存し、戦型ラベルとエンジン解析は既存の仕組みに載せる
2. **局面で探す** — 手順前後を吸収し、盤の配置で「同じ局面 / 近い局面」を横断検索する
3. **流れを追う** — 定跡データのように、局面から枝分かれを辿る

### スコープ外

- **棋譜の復元そのもの**（`packages/kifu-vision` の責務）
- **不確定手の解決**（§8.2。現時点で復元側が候補を出力しないため設計できない）
- **他ユーザーへの公開**（§8.3。単一ユーザー前提が続く間は判断材料が揃わない）

## 2. 自分の対局との区別

### 2.1 `kifus` に同居させ、`source` で区別する

動画解析の棋譜も `kifus` に入れる。**別テーブルに分離しない。**

理由は解析系の構造にある。`moveAnalyses` / `candidateMoves` / `kifuTactics` はすべて `kifuId` を FK に
持つため、棋譜を別テーブルに分けると**解析系を丸ごと二重化するか、参照を polymorphic にする**ことになる。
どちらも後から戻せない重さで、得られるのは「混ざらない」という性質だけ。同じ性質は列と既定フィルタで
得られる。

```
kifus.source: enum('manual' | 'swars' | 'video')  NOT NULL DEFAULT 'manual'
```

⚠ **既定値は安全側（`manual`）に倒す。** 列を nullable にすると「NULL は自分の棋譜か動画か」が
呼び出し側の解釈になる。

### 2.2 一覧・分析・統計からは既定で除外する

🔒 **`source <> 'video'` は引数で外せる条件にしない。** 一覧クエリビルダ（`kifu-list-query.ts`）と
集計（`stats-tactics-query.ts`）に**埋め込む**。

「動画解析を含める」トグルを置かないのは、集計の意味が UI 状態に依存するのを避けるため。分析ページの
数字は「自分の成績」であり、そこに他人の対局が混ざったとき **SQL は何も言わない**。

⭐ **棋譜ビューア（`/kifus/$id`）は共用する。** 除外するのは一覧と集計であって、個別の閲覧ではない。

### 2.3 動画解析では取れないもの

| 列 | 状態 | 理由 |
|---|---|---|
| `result`（勝敗） | **NULL** | 終局（投了）の検出が未実装。断片は「盤が初期局面に戻った」か動画の終わりで切れる |
| `sente` / `gote` | **NULL** | 画面に対局者名は出ているが読み取りは未実装 |
| `playedAt` | **NULL** | 対局日時は動画から分からない |

⭐ **`playedAt` が NULL であることが、worker のキュー順を自然に正しくする**（§4.4）。

## 3. データモデル

### 3.1 `videoKifuSources`（動画由来メタ・`kifus` と 1:1）

```
videoKifuSources
├── kifuId: bigint PK/FK → kifus.id (CASCADE)
├── videoId: varchar(32)         -- 動画の識別子
├── gameIndex: int               -- その動画の何局目か（1 始まり）
├── startedAtSec: int            -- 断片の開始秒
├── endedAtSec: int              -- 断片の終了秒
├── bottomIsSente: bool          -- 画面の下が先手か（録画者の側を示す）
├── extractorRev: varchar(40)    -- 走査時のコミット
└── raw: json                    -- 走査の生出力（range / replay / moves[]）
    UNIQUE (videoId, gameIndex)
```

**`kifus` に列を足さず 1:1 に外出しする**のは、自分の対局行で常に NULL になる列を中心テーブルに
持ち込まないため。

⭐ **`raw` に生出力を丸ごと持つ。** 1 局あたり 8〜16KB と安く、**後から仕様を変えても再走査せずに
派生値を作り直せる**。手ごとのメタ（`time` / `side` / `inferredKind`）はここに入る。

> `inferredKind` は「未確定マスを規則で解いて決めた手」を示す（復元側の `solved` フラグ）。
> **成/不成が不確定だった、という意味ではない**（§8.2）。

🔒 **索引が要ると分かった列だけ、後から `raw` の外に昇格させる。** まだ意味論が固まっていないものに
列を切ると、変えるたびにマイグレーションになる。

### 3.2 `kifuPositions`（局面索引・派生値）

**全棋譜（自分の対局を含む）の全局面**を展開した索引。`kifuTactics` と同じく**派生値**で、正は
`kifus.usiMoves`。

```
kifuPositions
├── kifuId: bigint FK → kifus.id (CASCADE)   ┐ PK
├── moveNumber: int      -- 0 = 初期局面      ┘ ＋単独の INDEX（下記）
├── move: varchar(8)?        -- この局面に至った直前の手（USI）。moveNumber = 0 では null
├── sfen: varchar(200)       -- 局面キー（盤 / 手番 / 持ち駒）  (INDEX)
├── senteSfen: varchar(200)  -- 先手側の配置のみ                (INDEX)
├── goteSfen: varchar(200)   -- 後手側の配置のみ                (INDEX)
├── board: binary(81)        -- 1 マス 1 バイト（下記）
├── hands: binary(14)        -- 側 × 駒種の枚数（先手 7 + 後手 7）
└── sideToMove: enum('b' | 'w')
```

🔒 **キーはハッシュではなく SFEN 文字列そのもの**（§5.1）。**衝突しない**うえ、
URL に載せられ（`/positions?pos=<sfen>`）、DB を直接見たときに人が読める。

**`board` は 1 マス 1 バイト**（`binary(81)`）。マスの状態は **空 + 14 駒種 × 2 側 = 29 通り**あり、
ニブル（4 ビット = 16 値）では表せない。値は `0` = 空、`1..14` = 先手の `P L N S G B R K +P +L +N +S +B +R`、
`17..30` = 後手の同順（上位ビットが側）とする。

> 詰めれば 51 バイト（5 ビット × 81）に収まるが、**24 万行でも差は 7MB** で、詰めた分だけ距離計算
> （§5.2）でビット取り出しが要る。**1 マス 1 バイトにして、比較をバイト単位のままにする。**

⭐ **`move`（この局面に至った手）を持つ。** 局面ハッシュだけでは**枝を指し手で区別できない**——
同じ局面から複数の異なる手が指されていても、`moveNumber` は必ず `+1` になるので集計単位にならない。
`kifus.usiMoves` から取り出すこともできるが、JSON 関数の JOIN になり索引が効かない。**8 バイトの列で
枝の集計が SQL 一本になる**（§5.3）。派生値なので再構築で作り直せる。

⚠ **`moveNumber` には単独の索引が要る。** 近い局面の検索は手数帯で候補を絞る（§5.2）が、
**PK は `(kifuId, moveNumber)` なので先頭列が違い、この範囲条件には使えない**。索引が無いと
ボタンを押すたびに全局面を走査することになる。

行数は総手数ぶん（数百局で数万行、2000 局でも 24 万行）。**全手数を対象にする**——手数帯の絞り込みは
検索時に行えばよく、索引を序盤に限る理由がない。

🔒 **再構築コマンドを用意する**（`tactics:redetect` と同じ形。既定 dry-run / 環境変数で実書込）。
派生値である以上、`usiMoves` が変われば作り直しが要る。

### 3.3 主体側（`kifus.subjectSide`）

**片側だけの比較**（「自分の配置が似ている局面」）には「この棋譜の主体はどちらの手番か」が要る。

```
kifus.subjectSide: enum('sente' | 'gote')?
```

- **動画解析**: `bottomIsSente`（画面の下＝録画者）から確定できる
- **自分の対局**: 所有者の名前候補と `sente`/`gote` の突き合わせ。**現在は web の env が単一の正**
  （`VITE_SELF_NAMES` ∪ `VITE_SWARS_USER_ID`）で server は設定を持たないため、**server 側ユーザーの
  導入が前提**になる（§7 段階 3）

🔒 **主体側を局面索引に焼き込まない。** `senteSfen` / `goteSfen` を両方持ち、どちらを引くかは
クエリ時に `subjectSide` で選ぶ:

```sql
-- 3 状態を明示する。未確定（NULL）を既定側に落とさない
CASE k.subjectSide
  WHEN 'sente' THEN p.senteSfen
  WHEN 'gote'  THEN p.goteSfen
  ELSE NULL
END
```

🔒 **`subjectSide` が NULL の棋譜は、主体側の検索から除外する**（`WHERE k.subjectSide IS NOT NULL`）。
`ELSE p.goteSfen` と書くと**未確定の棋譜が黙って後手側として比較される**。主体が決まらない対局は
実在する——両対局者とも自分の名前候補に一致する場合で、[09](./09-analytics.md) §4 でも
勝率の分母から外す扱いになっている。**同じものを、ここでは「後手」として数えない。**

⚠ **除外した件数は表示する。** 黙って落とすと、結果が少ない理由が「似た局面が無い」のか
「主体が決まらない棋譜を外した」のか区別できない。

理由は 2 つ。**(a) 再構築の範囲** — 名前候補を変えたとき、焼き込んでいれば数万行の索引を作り直すが、
`kifus` の列なら数百行で済む。**(b) 主体と無関係な検索** — 「先手番でこの配置になった局面」は
主体がどちらかと関係なく引きたくなる。両側を持てばタダで付く。

## 4. 取り込み

### 4.1 経路 — server の取り込み API

```
POST /api/video-analysis/kifus   (API_KEY 必須)
```

復元側（`packages/kifu-vision`）の CLI から叩く。compose では server がホストにポートを公開して
いないため、dev では web の開発プロキシ経由になる。

**取り込みの意味論を server の 1 箇所に集約する**のが決め手。KIF 合成・往復検証・差分ログ・
局面索引の構築・戦型ラベルの同期・`analysisRevision` の扱いが、すべてこのハンドラの中に収まる。

⏹ **復元側から DB へ直接繋がない。** 取り込みの意味論が 2 箇所に散り、実験パッケージが DB 資格情報を
持つことになる。

### 4.2 KIF 原文は USI から合成する

`kifus.kifText` は notNull で、動画解析には原文が存在しない。**合成した KIF を入れる。**

`shared` の `buildPositions` と `usiToJapaneseWithPiece` で日本語表記は作れるので、合成コストは小さい。

⭐ **合成 KIF を `parseKif` し直し、元の USI と一致することを検証する**（往復検証）。一致しなければ
取り込みを中止する。復元した棋譜の正しさを外から確かめる手段は乏しく（`kifu-vision` の Phase H）、
**独立した検算が 1 本増えることに意味がある**。

⚠ 合成である以上、`kifText` は「原文」ではない。`source` を見れば区別が付く。

### 4.3 再取り込みは上書き + 差分ログ

`(videoId, gameIndex)` が UNIQUE。**同じ動画の同じ局は 1 つの実体**として上書きする。

抽出器の改善で棋譜が変わることは前提（実際、直近の改善だけで成りが 6 件直っている）。版ごとに行を
増やすと、局面索引が版のぶんだけ膨れ、「この局面を含む棋譜 5 件」が実は同じ 1 局の 5 版、という
ことが起きる。

🔒 **上書き時に旧 `usiMoves` と新 `usiMoves` の差分をログに出す。** 手数・断片・通し再生の指標が
すべて満点でも成/不成の取り違えは残るため、**USI 列そのものの差分でしか変化を見つけられない**
（`kifu-vision` の運用規律をそのまま取り込みに持ち込む）。

差分があれば `analysisRevision` を上げ、`moveAnalyses` を削除して worker に拾い直させる。
差分が無ければ何もしない（冪等）。

### 4.4 戦型ラベルとエンジン解析

- **戦型ラベル**: 取り込み時に既存の同期処理（`packages/server/src/tactics.ts`）を呼ぶ。追加設計は無い
- **エンジン解析**: worker の取得クエリは変更しない。`playedAt` が NULL なので
  `coalesce(playedAt, createdAt)` は投入時刻になり、**過去日時を持つ自分の未解析棋譜より必ず後ろに付く**。
  優先度の仕組みを足さずに、自分の対局が先に解析される

## 5. 局面索引と検索

### 5.1 局面の同一性 — 手順前後を吸収すると DAG になる

局面キーは**盤 + 持ち駒 + 手番**（手数は含めない）。SFEN の先頭 3 フィールドに相当する。

`7g7f 3c3d 2g2f` と `2g2f 3c3d 7g7f` は同じ局面に至るので、**同じノードに合流する**。つまり
構造は木ではなく **DAG**。これは「手順前後を吸収したい」という要求そのものの帰結であり、
定跡データベースが普通に採る形でもある。

⚠ **持ち駒をキーから外さない。** 同じ盤面でも持ち駒が違えば別の局面で、序盤の判断が変わる。

🔒 **キーはハッシュにせず、SFEN 文字列そのものを使う。** 理由は 3 つ:

1. **衝突しない。** ハッシュだと別の局面が同じキーになりうる。確率は小さいが、起きたときの
   症状は「検索結果に無関係な棋譜が混ざる」で、**気づきにくい壊れ方**をする
2. **URL に載せられる**（`/positions?pos=<sfen>`）
3. **人が読める。** DB を直接見たときに、それがどの局面か分かる

⚠ 加えて `shared` は環境非依存（`lib: esnext` / `types: []`）なので、node の `crypto` も
Web Crypto も使えない。ハッシュを自前で書くことになるが、**書かずに済む方がよい。**

### 5.2 距離 — 盤の不一致 + 持ち駒の差

```
dist = Σ(81 マス)[ 駒種・側が不一致 ]
     + Σ(側 × 駒種) | 持ち駒枚数の差 |
```

初期の重みは盤 1 マス = 持ち駒 1 枚 = 1。

**持ち駒を側と駒種まで区別して数える。** 盤から駒が消えたとき、それが**どちらの持ち駒になったか**は
盤面だけでは復元できない。相手の持ち駒か自分の持ち駒かは別の意味を持つので、独立した情報として数える。

🔒 **距離の計算はアプリ側に置く**（SQL に焼き込まない）。「近い」が何を意味するかは使ってみないと
決まらないため、**定義を動かしやすい場所に置く**。数万局面 × 81 マスの比較は数十 ms で済み、
巧妙な SQL を要しない。

#### 近さの検索で外すもの

🔒 **その局面を既に通った棋譜そのものを外す。** 外さないと、序盤では「1 手前の局面（距離 2）」が
**全棋譜ぶん並ぶだけ**になる——どの棋譜も通っているので当たり前の結果しか出ない。
近さが意味を持つのは「**完全一致はしないが似ている**棋譜」で、それを探すのがこの機能の目的。
完全一致した棋譜は §5.3 の一覧の側に出ている。

⭐ **棋譜ごとに最も近い 1 局面へ畳む。** 隣り合う局面は高々 2 マスしか違わないので、畳まないと
**同じ棋譜の連続する局面が上位を埋め尽くし、似た棋譜が 1 局しか出てこない**。

### 5.3 検索の種類

| 種類 | 実装 |
|---|---|
| **完全一致**（両側） | `sfen` の index seek |
| **完全一致**（片側） | `senteSfen` / `goteSfen` の index seek。どちらを引くかは `subjectSide` で決める（§3.3。NULL は除外） |
| **近い局面** | 手数帯で粗く絞り、読み出した行に対してアプリ側で距離を計算（§5.2）。**別エンドポイント**にして、押されたときだけ走らせる——完全一致は index seek で済むが、こちらは手数帯ぶんの行を読むので桁違いに重い |
| **枝の列挙** | 同じ `kifuId` の `moveNumber + 1` を self join し、**次の局面が持つ `move`** で集計 |

近さ検索は**手番を問わず候補に入れ**、結果に手番を表示する。

```sql
-- この局面の次の手と、その出現数
SELECT n.move, n.sfen, count(*) AS games
FROM kifu_positions p
JOIN kifu_positions n ON n.kifuId = p.kifuId AND n.moveNumber = p.moveNumber + 1
WHERE p.sfen = ?
GROUP BY n.move, n.sfen
ORDER BY games DESC
```

## 6. UI

### 6.1 `/video-analysis` — 動画解析データの一覧

動画ごと → 局ごとの階層。各局から `/kifus/$id`（共用の棋譜ビューア）へ遷移する。
区間・手数・戦型ラベル・解析状態を表示する。

### 6.2 `/positions` — 局面検索とツリー（両ソース横断）

**動画解析ページの中に置かない。** 検索の対象は動画解析データだけでなく**自分の対局を含む横断**で
あり、「動画解析」の下に自分の棋譜が並ぶのは名前と中身がずれる。

- 起点から辿る（初期局面 → 枝を降りる）
- 局面を指定して来る（`/positions?pos=<sfen>`）
- 一致・近さの結果に**出所のバッジ**（自分 / 動画）を出す
- 主体側だけ比較 / 両側を比較 をトグルで切り替える（§3.3）

🔒 **打ち切ったら必ず言う。** 到達行には上限がある（server 側 200・画面は 20 ずつ展開）。
初期局面は全棋譜が通るので、棋譜が増えれば必ず当たる。**総数（`total`）と打ち切りの有無
（`hasMore`）を返し、画面に出す**——出ている数が全部だと誤読されると、「この局面を通った
棋譜はこれだけ」という誤った結論になる。

⚠ **序盤の局面はどの棋譜も通る。** 初手付近では到達が数百件になり、全部並べると
**この画面の主役である分岐が棋譜一覧に埋もれる**。行は畳んでおき、総数だけ常に出す。
🔒 **並びは打ち切りとセットで意味を持つ**——到達が早い順 → **同手数では新しい対局順**にする。
切れたときに残るのが古い棋譜では使い物にならない。
⚠ **画面の文言は実際の並びに合わせる。** 第一キーは到達手数なので「新しい N 件」ではない
——手順前後で到達が遅くなった対局は、新しくても上限の外に出る。

### 6.3 棋譜ビューアからの導線

`/kifus/$id` の各局面に「この局面を探す」を置き、`/positions?pos=<sfen>` へ飛ばす。
**表示中の局面**（分岐を辿っている途中ならその局面）を鍵にする。

## 7. 段階分け

| 段階 | 内容 | 依存 | 状態 |
|---|---|---|---|
| **1** | `source` 列 / `videoKifuSources` / KIF 合成 + 往復検証 / 取り込み API / 復元側の import CLI / `/video-analysis` 一覧 | — | ✅ 実装済み |
| **2** | `kifuPositions` + 再構築コマンド / `/positions`（完全一致・枝の列挙）/ 棋譜ビューアからの導線 | 段階 1 | ✅ 実装済み |
| **3** | 近さ検索 / 主体側モード / `kifus.subjectSide` | **server 側ユーザー**（§8.1） | ⬜ 未着手 |

段階 1 の完了条件は「復元済みの棋譜が DB に入り、戦型が付き、worker が解析を始める」こと。
段階 2 の完了条件は「初期局面から枝を辿れて、同じ局面を通った棋譜が出所付きで並ぶ」こと。

## 8. 未決・将来の拡張

### 8.1 server 側ユーザー（段階 3 の前提）

現在「自分」の定義は **web の env が単一の正**で、server は設定を持たない。将来の他ユーザー招待に
備えて server 側にユーザーの概念を持たせる設計が要り、**`subjectSide` の確定はそこに乗る**。
動画解析より先に決める。

### 8.2 不確定手を評価値で選ぶ

「成/不成が不確定なうちに駒が取られた」ような局面で、**その後の展開が合法になる範囲で、その手番から
見て評価値が高い方を選ぶ**——という構想がある。

🔴 **現時点では設計できない。** 復元側は候補が複数残ると手を採らない（`solve.ts` が `null` を返す）
実装で、**「候補 A と候補 B が残った」という情報が出口に無い**。実装するには復元側に候補の出力を
足すところから要る。

⚠ **現在の素材（2 本・5 局）では一度も発火していない**（全局 1 断片・手数の欠落なし）。
**発火してから設計する。**

### 8.3 可視性（他ユーザーへの見せ方）

動画解析データを他ユーザーに見せるかは**未決**。棋譜の手順そのものは事実の記録だが、動画の識別子と
紐づいた形で配ることは公開方針（[README](./README.md) §秘匿方針）の境界に触れる。

単一ユーザーの現在はどちらに倒しても動作が変わらないため、**`visibility` 列を先取りして入れない**。
§8.1 で `ownerId` を導入する際に併せて扱う。

### 8.4 定跡テーブル形式への移行

局面索引は展開テーブル 1 本で始める。将来、**定跡データベースの標準的な形**（`positions` ノード表 +
`positionEdges` 辺表 + 出現回数の集計列）へ作り替える可能性がある。展開テーブルから SQL で導出できる
ので移行は可能。

発火条件: 枝の集計が重くなった / 外部の定跡データを取り込みたくなった / 局面ごとの注釈を持ちたくなった。

## 9. 既知の限界

🔒 **復元された棋譜が正しいことは保証されていない。** `kifu-vision` の指標（通し再生の合法性・
成/不成の色監査・駒種の監査）はいずれも満点だが、**どれも見ていない隙間がある**——手の順序、
演出で捨てた局面、静止の短い応酬。**「3 つの指標が満点」は「誤りが無い」ではない。**

本章の仕組みは**復元の正しさを検証しない**。唯一足すのは KIF の往復検証（§4.2）で、これは
「合成が壊れていないか」しか見ない。
