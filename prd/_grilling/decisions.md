### 時制方針: 「あるべき設計の理想形」を基準にする（2026-07-16）
- PRD は現実装の記録に留めず、**あるべき設計の理想形を正**として書く。
- 現実装が理想と異なる箇所は、理想を本文に書いた上で**現状との gap** として明示・管理する。
- 帰結: 現 DB スキーマ・アーキが理想でない場合、PRD は理想を記述し、実装追従は gap 項目にする。
- 前提は変わらず**個人用・ローカル運用**。理想は「個人用棋譜解析ツールとしての理想」であって
  エンタープライズ化ではない（過剰設計を避ける）。

### 解析来歴（engine/eval）は持たない（2026-07-16）
- **決定**: 解析エンジン・評価関数の識別子（MATERIAL/NNUE・評価関数名）を DB に**記録しない**。
- 理由: 本番は NNUE 単一運用で開発 MATERIAL の数値は一時的な確認用。異常な評価値は目視で気づける。
  エンジン側に自己申告を仕込むのは手間で、個人用途には**過剰設計**。
- 保持するのは `candidateMoves.depth`（候補手単位。既存）のみ。
- **帰結**: 局面単位の再解析は depth 別の複数世代を持たず、**最新 1 世代に上書き**（単一エンジン前提）。

### LLM 解説の生成アーキ（2026-07-16）
- **決定**: プロンプト（解析結果込み Markdown）生成を **server のエンドポイント化**（例 `GET /kifus/:id/commentary-prompt`）。
- **決定（対象範囲）**: **手動トリガーのみ**（解析済み全棋譜への自動付与はしない）。Web の「解説生成」ボタンで
  キュー投入 → commentator が拾って生成。欲しいものだけ生成し LLM コストを制御下に置く。
- **commentator = 軽量な監視スクリプト**（独立 docker container・worker 側デスクトップに配置）:
  **キュー（`commentaries.status = 'queued'`）を polling** → プロンプトを server から fetch → LLM CLI に流す →
  解説を `commentaries` へ書き戻す。commentator 自身は将棋ロジックを持たず薄く保つ。サブスク内で完結し API 従量課金なし。
- web の「LLM プロンプトをコピー」ボタンも同じプロンプトエンドポイントを使い、書式を単一真実にする。

### shared パッケージを作る（旧「作らない」を改定）（2026-07-16）
- **決定**: `packages/shared` を新設する。
- **責務（凝集。junk drawer にしない）**:
  1. 将棋ドメインの**純ロジック**（board 盤面追跡・USI 変換・USI→日本語・悪手判定・kifu-export プロンプト生成）。
  2. **zod 検証スキーマ**（runtime バリデーション）。
- **旧判断の再評価**: 「shared を作らない」は元々「Hono RPC の型共有を使わず zod 定義を shared に溜め込む」
  傾向への予防だった。しかし (1) 対話盤面ロジックを web と server（プロンプト生成）で共有する必要が生じ、
  (2) **型共有だけでは動作時に不正データを弾けず、runtime 検証には zod の実体が要る**。→ shared の意義が明確化。
- **維持する原則**: **API レスポンス/リクエストの型共有は引き続き Hono RPC**。shared に API 型を重複させない。
- **帰結**: board/usi/kifu-export を web→shared へ移設。server は shared の kifu-export でプロンプト生成
  エンドポイントを提供。commentator は薄いまま。web は対話盤面で shared を import。
- KIF/CSA パーサーは現状 server 専用（消費者が server のみ）なので shared に移さない（第2の消費者が出たら再検討）。

### commentaries テーブル（2026-07-16）
- **決定**: `commentaries` は kifu と **1:1**、再生成は**同行を上書き**（解析来歴非保持の方針と揃える）。
- **キューを兼ねる**（別途キューテーブルは持たない。薄い watcher 思想）: `status`(queued/done/failed) を持ち、
  「解説生成」ボタンで `queued` 行を作る/戻す → commentator が `queued` を polling → 生成後 `done`。
  失敗は `failed` + `error` で受け、無限リトライを防ぐ（poison-pill と同じ思想）。
- カラム: `kifuId`(PK/FK), `status`(enum), `body`(text?, 完了まで null), `llmModel`(varchar?),
  `promptVersion`(varchar?), `error`(text?, failed 用), `createdAt` / `updatedAt`。
- Web の「解説あり」表示は `status = 'done'` で判定。

### 入力形式のスコープ（2026-07-16）
- **決定**: Web 手動投入は **KIF 貼り付け（実装済み）+ CSA 直接貼り付け**（既存の CSA→KIF 変換器を再利用）。
- **対象外**: KIF ファイルアップロード / SFEN（単一局面で棋譜解析のスコープ外）。
- CSA→KIF 変換器は現状は取り込み専用ディレクトリ配下だが、CSA 貼り付けは一括取り込みと無関係なので、
  一般的な変換として server 内の中立な場所に置く（消費者は server のみなので shared には移さない）。

### ポイズンピル対策（解析できない棋譜）（2026-07-16）
- **主軸 = worker 側の失敗状態**: kifus に `analysisError`(nullable) を追加。worker はエンジンの
  異常終了/illegal move を検知したら当該 kifu に記録し、**エンジンを再起動して次へ**進む。
  poll は「`analysisCompletedAt IS NULL` かつ `analysisError IS NULL` の最古」を引く。
  → ポイズンピルはスキップされ**キューが詰まらない**。UI に「解析失敗」バッジ、再試行は error クリア。
- **投入時検証は best-effort（保証ではない）**: 完全な合法性検証は将棋ルール一式（打ち歩詰め等）の
  実装が要り容易でない。`applyMove` が破綻しないか程度の軽い整合チェックに留め、取りこぼしは worker 側で受ける。
- 具体的なバグの症状・再現・修正手順といった**作業メモは PRD に書かず** `.claude-personal/` に置く。

### KIF 変換の堅牢化・メタ抽出・失敗時動作（2026-07-17）

実棋譜（`８四全` を含む 70 手）で「記録は入るが解析エンジンが illegal move で異常終了し、以後同じ棋譜を
無限リトライしてキューが停止する」不具合を起点に、入力面と失敗時動作をまとめて詰めた。

- **原因**: KIF パーサが成銀の一文字略記 `全`（同様に `圭`=成桂 / `杏`=成香）を未対応で手 57 が黙って欠落 →
  1 手欠落で手番 parity がズレ、構文上妥当な USI 列のまま盤面が破綻 → illegal move。加えて `kifToUsiMoves` が
  パースエラーを無視して部分的 `usiMoves` を保存していた。
- **入力側の決定**:
  - パースエラー（指し手行の変換失敗）または**非平手手合割**なら `usiMoves = null` で保存（記録・メタは残す）。
    壊れた部分 `usiMoves` を worker に渡さないのが要点。完全合法性チェック（`shared` + `applyMove`）は将来の理想として残し、
    当面はこの軽量ガード＋ worker 失敗状態で受ける（best-effort の具体化）。
  - 成駒略記対応・終局マーカー認識（`詰み` 等・最初のマーカーで指し手収集を打ち切り＝末尾の分岐ブロック混入防止）。
  - メタ抽出（sente/gote/dan/playedAt）。**result は終局マーカー＋手番 parity から swars 互換コードを導出**し、
    既存の勝敗バッジ・LLM エクスポートを無改修で活かす。
  - **タイトル任意化・自動生成**（空なら `${sente} vs ${gote}`）。旧「KIF はユーザー入力」を改定（KIF インポート常用化のため）。
- **失敗時動作の決定**:
  - 失敗分類: 棋譜起因（illegal / エンジン異常終了 / **timeout**）＝恒久（`analysisError` 記録 → poll 除外）、
    インフラ起因（submit 失敗）＝一時（再試行）。恒久時は**エンジン無条件再起動**。
  - `analyze()` はプロセス `close` で即 reject（60 秒ハング解消）。
  - 再試行 UI アクション＝**`POST /kifus/:id/reanalyze`**: `kifText` 再変換で `usiMoves`・メタを作り直し
    `analysisError`/`analysisCompletedAt` をクリアして再キュー（`title`/`memo` は温存）。error クリアだけだと
    壊れた `usiMoves` のまま再度落ちるため、再変換で既存の壊れ棋譜も復旧する。
- **スコープ外（今回入れない）**: `shared` 抽出を伴う完全合法性チェック、KIF ファイルアップロード、駒落ちの USI 変換対応。
- 具体的なバグ症状・再現・修正手順の作業メモは `.claude-personal/`（公開 PRD には書かない）。

### 棋譜詳細の「候補手詳細」テーブルを廃止（2026-07-21）

棋譜詳細ページ下部の折り畳み「候補手詳細」（全局面 × 全候補手のテーブル）を**製品仕様として持たない**と決めた
（[05](../05-analysis.md) §2.5 を改訂。issue #26 / PR #36）。

- **理由（運用）**: 実運用でまず開いていない。読み筋を見たい局面は評価値グラフの悪手マーカーから飛べるので、
  その局面の候補手一覧（[05](../05-analysis.md) §2.2・読み筋 + 探索深さ + 実手マーク + 分岐操作）で用が足りる。
- **理由（コスト）**: `<details>` は閉じていても中身がレンダーされる。この表は局面数 × MultiPV 行を生成し、
  各行の読み筋日本語化が手数ぶん `applyMove`（盤面のディープコピー）を回すため、**詳細ページを開いた瞬間に
  走る盤面コピーの最大の発生源**だった。遅延レンダーや仮想化で覆う手もあるが、使っていない機能のために
  実装を増やす判断はしない。
- **[01](../01-domain.md) §1-2「疑問手と分岐を一望したい」との整合**: この動機は評価値グラフ + 悪手マーカー
  （棋譜全体の俯瞰）と、局面ごとの候補手一覧（深掘り）の組み合わせで満たす。テキストで通して読みたい場合は
  LLM 解説用テキスト（[06](../06-llm-commentary.md)）が**全局面の実手と最善評価値**、および**抽出された注目局面の
  候補手・読み筋**を持つ（全局面 × 全候補手ではない点で廃止テーブルとは非等価）。よって 01 の改訂は不要とした。
- **データ側は不変**: `candidateMoves.pv` は盤面直下の読み筋表示・分岐再生・kifu-export が使い続ける
  （悪手判定は `rank`/`move`/`score` だけを見ており `pv` を参照しない）。
  スキーマ・API・worker に変更なし（表示先が 1 つ減るだけ）。

### 棋譜詳細の描画コスト — 折り畳みの遅延マウントと局面の不変・構造共有（2026-07-21）

「候補手詳細」廃止（上記）と React Compiler 導入（issue #25 / PR #35）でも消えない残りの描画コストを
3 点まとめて詰めた（[05](../05-analysis.md) §2 / §2.5 を改訂。issue #27）。

- **折り畳みは開かれるまで中身をマウントしない**。`<details>` は閉じていても中身がレンダーされるため、
  局面評価値テーブル（局面数ぶんの行 × 日本語変換）と LLM 解説用テキスト（`generateKifuMarkdown` が
  全局面を再構築する）が、閉じたまま毎レンダー走っていた。**折り畳みに重いものを入れる構成自体は良い**ので、
  廃止ではなく描画を遅延させる。一度開いた後はマウントを保つ（開閉の往復が重くならず、メモの下書きも消えない）。
- **全局面は 1 度だけ構築する**。ページと盤面コンポーネントで `buildPositions` を二重に呼んでいた。
  React Compiler が効くのはレンダー間のキャッシュであって、**同一レンダー内の重複計算は消えない**ため、
  ページ側で構築して props で配る形にした。
- **`BoardState` は不変・構造共有**。`applyMove` は毎手 81 マス + 持ち駒をディープコピーしていた。
  変化したマスと手番側の持ち駒だけを差し替え、残りの行・駒オブジェクトは共有する。
  代わりに**局面を破壊的に変更してはならない**という契約が生じるので、型定義と [05](../05-analysis.md) §2 に明記した。
  `shared` 抽出（[08](../08-roadmap.md)）で盤面ロジックを移す際もこの契約ごと移す。
- **不正な手の扱いは変えない**（移動元 == 移動先の退化した手で駒が消える等）。合法性検証は `shared` 抽出時の
  課題として据え置き（[04](../04-ingestion.md) §5）、今回は純粋な性能改善に留める。

### 棋譜詳細の削除・再解析は結果を画面に返す（2026-07-21）

削除・再解析の呼び出しは `res.ok` のときだけ遷移 / 再取得しており、**失敗すると何も起きなかった**
（issue #30 の 1 項目目。[05](../05-analysis.md) §2.5 を改訂）。

- **失敗は握り潰さない**。HTTP エラーは `alert-error` にステータスコードを添えて出し、fetch 自体が
  失敗する（サーバー停止・ネットワーク断）ケースは `try/catch` で「サーバーに接続できません」を出す。
  文言と表示手段は既存の [`KifuMemo`](../../packages/web/src/components/KifuMemo.tsx) / 一覧の取り込み
  （[04](../04-ingestion.md)）に揃えた。
- **トーストライブラリは入れない**。通知は現状この 2 操作とメモ保存・取り込みだけで、いずれも
  操作起点の画面に出せば足りる。依存を増やさず daisyUI の `alert` を使う。
- **再解析は成功も通知する**。解析は worker が非同期に拾うため、成功しても画面はほぼ変化しない
  （`analysisError` の消滅くらい）。「開始しました」を出さないと失敗と区別がつかない。
  削除は成功すると一覧へ遷移するので通知しない。
- **実行中はボタンを無効化する**。二重送信を防ぐ。再解析ボタンはドロップダウンと `analysisError`
  アラート内の 2 箇所にあるため、同じフラグで両方を止める。

### 棋譜再生のキーボード操作と、分岐中の ←→ の意味（2026-07-21）

棋譜ビューアの基本操作である `←` / `→` / `Home` / `End` が無く、1 手進めるたびにボタンを狙う必要があった
（issue #30 の 2 項目目。[05](../05-analysis.md) §2.1 を改訂）。

- **分岐中の `←` / `→` は分岐内を移動する**。分岐（候補手の読み筋再生・[05](../05-analysis.md) §2.2）に入っている
  間は、ユーザが今読んでいるのは分岐の局面であって本筋ではない。ここで `→` が本筋を進めると、
  読んでいた分岐が黙って消える。分岐の先頭で `←` すると `branchDepth` が 0 になり自然に本筋へ戻るので、
  「分岐を抜ける」ための別キーは要らない。マウス操作（本筋は上部コントローラー / 分岐は候補手内の ◀▶）とは
  割り当てが異なるが、**キーボードは常に「今見えている手順」を進退させる**方が迷わない。
- **`Home` / `End` は常に本筋の端へ飛ぶ**（分岐は解除）。「最初 / 最後」は棋譜全体に対する位置であって、
  分岐内の端を指す意味づけは無い。上部コントローラーの ⏮ ⏭ と同じ `goToMain` に揃える。
- **リスナは `window` に張る**。盤面はページの主役で、他にフォーカス可能な操作対象が少ないため、
  盤面へのフォーカスを要求すると「クリックしないと効かない」だけの体験になる。代わりに
  **入力欄（`input` / `textarea` / `select` / `contenteditable`）にフォーカスがある間は何もしない**。
  特にコントローラーの range スライダーは `←→` `Home` `End` をブラウザが既定で処理し `onChange` 経由で
  局面が動くため、ここで介入すると 1 回の打鍵で 2 手進む。
- **修飾キー併用（Ctrl / Meta / Alt / Shift）は横取りしない**。ブラウザの戻る/進む・行選択などと衝突するため。
  該当キーを処理したときだけ `preventDefault()` してページのスクロールを止める。
- **discoverability はボタンの `title` に添える**（「戻る (←)」等）。ショートカット一覧の UI は作らない。
- **端での打鍵は何もしない**（レビュー指摘 `OCL-AA77E8E6` を受けて追記）。本筋の先頭で `←`、末尾で `→`、
  既に端にいる `Home`/`End` は局面が動かない。ここで `goToMain` を呼ぶと**開いている候補手 details が
  閉じられ、閲覧中の読み筋が消える**（画面ボタンは同じ境界で `disabled` になるためこの副作用が無い）。
  移動先が現在位置と異なるときだけ遷移し、分岐が残っているときだけ解除のために同位置へも呼ぶ。

### swars 取り込みのページ数を Web から指定する（2026-07-21）

`POST /api/swars/import` は `pages: 1..10` を受け付けるのに、Web は常に `pages: 1` を送っていて
**過去分を遡れなかった**（issue #30 の 3 項目目。[04](../04-ingestion.md) §4 を改訂）。

- **「更新」ボタンの隣にセレクトを置く**。設定画面や環境変数ではなく取り込みの起点に置く。
  ページ数は「今どこまで遡るか」という**その場の判断**で、恒久設定ではないため。
  daisyUI の `join` でボタンと連結し、1 操作の一部であることを見た目でも示す。
- **選択は永続化しない**（リロードで既定の 1 に戻る）。常用は最新 1 ページで、初回セットアップや
  久しぶりの取り込みだけが例外。10 が残ったまま毎回の更新が 10 ページ分の取得を走らせる方が害が大きい。
- **上限 10 は server の zod と二重に持つ**。`MAX_IMPORT_PAGES` に切り出してコメントで対応を明記した。
  検証スキーマの共有は `shared` 抽出（[02](../02-architecture.md) §3.2 / [08](../08-roadmap.md)）待ちの gap。
- **取得済みの重複を気にせず遡ってよい**。`swarsGameKey` の UNIQUE でスキップされる（§4）ので、
  ページ数を多めに指定しても増えるのは履歴取得のリクエストだけ。セレクトの `title` にもその旨を添えた。

### 一覧の日時列は代替表示であることを明示する（2026-07-21）

棋譜一覧の日時列は `playedAt` が無ければ `createdAt` を**無印で**表示していたため、**見えている日時が
対局日時なのか登録日時なのか区別できなかった**（issue #30 の 4 項目目。[05](../05-analysis.md) §2.5 を改訂）。

- **列そのものは分けない**。一覧の並びが `coalesce(playedAt, createdAt)` 降順（[04](../04-ingestion.md) §6）で
  ある以上、この列は「その棋譜を時系列に置く基準値」であって、対局日時と登録日時を別列にすると
  行ごとにどちらが並び順の根拠なのか読み取れなくなる。**1 列のまま、代替のときだけ但し書きを添える**。
- **代替であることは「（登録）」+ 弱色**（`text-base-content/60`）で示す。バッジは状態列（勝敗・解析済み）で
  既に使っており、日時列にも足すと視線の止まる場所が増える。既定は対局日時であり、目立たせたいのは
  「これは例外」という一点だけなので、弱いシグナルで足りる。
- **`title` に理由を添える**（「対局日時が取得できなかったため、登録日時を表示しています」）。
  但し書きだけでは「登録日時も併記されている」と読めるため、**代替であること**を明文化する。
- **メタ抽出を直す話とは切り離す**。`playedAt` が埋まらない棋譜（TZ 欄なし・ヘッダ欠落等）を減らすのは
  取り込み側の課題（[04](../04-ingestion.md) §2）で、それでも 0 にはならない。一覧は残った欠落を
  正直に見せる側に立つ。

### 一覧の検索・絞り込み・並べ替えは server 側で行い、条件は URL に持つ（2026-07-21）

棋譜一覧は 50件ページングだけで、溜まるほど目的の対局に辿り着けなかった（issue #30 の 5 項目目。
[04](../04-ingestion.md) §6.1 / [05](../05-analysis.md) §2.5 を改訂）。

- **絞り込みは server 側（SQL）で行う**。クライアント側で現在ページの 50件だけを絞ると、
  「ヒット件数」も「次のページ」も嘘になる。**件数・ページングと絞り込みは同じ条件で数える**必要がある。
- **条件は URL のクエリに持つ**（コンポーネント state ではなく）。TanStack Router の `validateSearch` /
  `loaderDeps` に載せることで、リロード・戻る/進む・ブックマークが素直に効き、loader の再取得も
  ルーターに任せられる。既定値（`status=all` 等）は URL に載せない。
- **「自分」の定義は web に置いたまま、勝敗の判定材料だけを `self` で server に渡す**。
  自分の名前候補は `VITE_SELF_NAMES` ∪ `VITE_SWARS_USER_ID`（[01](../01-domain.md)）で、
  一覧の勝敗バッジ・棋譜詳細・LLM 解説（[06](../06-llm-commentary.md)）がすべてこれを見ている。
  server にも `SELF_NAMES` を持たせると**同じ設定が二箇所に分かれ、ずれたときに勝敗バッジと
  絞り込み結果が食い違う**。server は状態を持たず、渡された候補で条件を組み立てるだけにする。
  - **両対局者とも候補に一致する対局は除外する**。`resolveUserSide` が ambiguous として
    勝敗バッジを出さないのと同じ扱いで、バッジと絞り込みの判定を一致させる。
- **並べ替えの基準はセレクトで選ぶ（列ヘッダのクリックにしない）**。既定の「対局日時」は
  `coalesce(playedAt, createdAt)` で、日時列そのものではない（上記の決定）。また「登録日時順」は
  対応する列を持たない。列ヘッダに割り当てると**列と並べ替えキーが 1 対 1 でないことが隠れる**。
- **並びには `id` を副キーとして必ず添える**。同じ日時・同じタイトルの行が 50件境界にまたがると、
  MySQL の順序は不定なのでページ間で行が重複・欠落する。
- **検索語だけ 300ms の debounce**。他は離散的な選択なので即時反映でよいが、テキストは打鍵ごとに
  URL を書き換えると履歴が汚れ、loader も無駄に走る。URL 側が変わったとき（戻る/進む・クリア）は
  入力欄をそちらへ追従させる。
- **検索語の trim は server 側だけで行う**。`validateSearch` で trim すると、入力中の末尾スペースが
  debounce のたびに消えて日本語の分かち書き（「山田 太郎」）が打てなくなる。
- **LIKE のワイルドカードはエスケープする**。`%` を含む対局者名・タイトルを検索したときに
  全件一致になるのを防ぐ（`escapeLike`）。
- **検索語の上限（100字）は web でも頭打ちにする**。server の zod だけに任せると、超えた値で
  一覧全体が 400 になり「検索結果 0 件」ではなく**エラー画面**に切り替わる。入力欄の `maxLength` と
  `validateSearch` の切り詰め（URL 直入力・古いブックマーク対策）の両方で受ける。
  `MAX_IMPORT_PAGES`（§swars 取り込みのページ数）と同じく**上限を二箇所に持つ gap** で、
  検証スキーマの共有は `shared` 抽出（[02](../02-architecture.md) §3.2 / [08](../08-roadmap.md)）待ち。
- **戦型での絞り込みは含めない**。戦型ラベル自体が未実装（[08](../08-roadmap.md)）で、issue #30 の
  範囲外。ここでは対局相手 / 勝敗 / 解析状態 / 期間の 4 つに留める。

### 棋譜詳細の「局面評価値」テーブルを廃止（2026-07-21）

- **データ側は不変**。`analyses` / `candidates` は盤面直下の候補手表示・分岐再生、評価値グラフ、

### 盤面の左右タップで手を送る（2026-07-21）

モバイルで棋譜を並べるとき、盤面下のコントローラー（◀ ▶）まで指を運ぶ必要があった。
盤面そのものの左右をタップして手を送れるようにした（issue #44 / [05](../05-analysis.md) §2.1 を改訂）。
キーボード操作（上記・PR #42）がデスクトップ向けの手当てだったのに対し、こちらはその対になる。

- **左右の判定は画面基準で、盤面反転（`flipped`）の影響を受けない**。反転しても「画面の右 = 進む」のまま。
  すぐ下のコントローラーの並び（◀ が左・▶ が右）と一致していることの方が、盤の向きとの一致より効く。
  実装上も、反転は `BoardGrid` 内部の並べ替えなので、盤面に重ねたオーバーレイは何もしなくてよい。
- **分岐中のタップは本筋へ復帰する**（`goToMain`）。**キーボードの `←` / `→` とは意図的に非対称**:

  | 操作 | 分岐中の挙動 |
  |---|---|
  | キーボード `←` `→` | **分岐内**を移動（先頭で `←` すると本筋へ復帰） |
  | ◀ ▶ ボタン / 盤面タップ | **本筋へ復帰**して 1 手移動 |

  キーボードは読み筋を辿る道具、ボタンとタップは本筋を送る道具、という住み分け。タップは
  「◀ ▶ ボタンを盤面まで広げたもの」なので、ボタン側に揃える方が説明がいらない。
- **全画面幅で有効にする**。デスクトップでも盤面のクリックは現状なにも起きないため衝突せず、
  `md` 未満に限定する分岐を持つ方が複雑になる。
- **端では何もしない**。キーボードと同じガード（移動先が現在位置と同じで分岐も無いなら `goToMain` を呼ばない）を
  共有する。理由も同じで、呼ぶだけで開いている候補手 details が閉じる（上記 `OCL-AA77E8E6`）。
- **`<button>` で置き、タブ順からは外す**（`tabIndex={-1}`）。ポインタ操作専用の冗長な導線で、同じ操作は
  タブ移動できるコントローラー行のボタンが担う。`div` + `onClick` にすると、キーボード操作を持たない
  クリック要素になってしまう。
- **連打対策として `touch-action: manipulation` と `select-none` を効かせる**。付けないと、素早く 2 回叩いた
  ときにダブルタップズームや駒文字の選択が起きて実用にならない。
- 将来マス目自体をタップする機能（局面編集・分岐入力）を入れるなら、盤面全体を覆うこのオーバーレイは
  再設計が要る。現状そうした操作は無いため今回は考慮しない。

### `packages/web` のテスト基盤と `board.ts` の回帰テスト（2026-07-21）

PR #38 で `applyMove` を差分コピー（構造共有）にしたことで `BoardState` に**不変契約**が生じたが、
契約が破れたときの失敗モードは**盤面が静かに壊れる**ことで型検査では捕まらない。一方 web には
テスト基盤が無く、#38 の検証は使い捨てスクリプトで行いリポジトリに残っていない（issue #39）。

- **`shared` 抽出を待たず、先に `packages/web` に入れる**。280 行の `board.ts` を無防備なまま別パッケージへ
  動かすより、**先に回帰の網を張ってから移す方が安全**。`shared` 抽出は確定済みだが着手時期が未定の大玉で、
  待つ間テスト空白が続く（PR #46 でもテスト追加が同じ理由で見送られている）。純ロジックなので移動コストは
  ファイル移動と import パス変更だけ。
- **node 環境の純ロジックのみ。追加依存は vitest だけ**。jsdom / testing-library は入れない。#39 の要求は
  純関数のテストで満たせる一方、DOM 環境は React Compiler との相互作用など**目視で検証しきれない不確実性**を
  持ち込む。UI テストが要る場面が来たら別 issue で基盤ごと判断する。
- **対象は `board.ts` のみ**。`usi.ts`（`detectBlunders`）と `kifu-export`（`selectNotablePositions`）は
  **#28（悪手判定の CPL 化）で仕様ごと書き換わる**ため、今その現行仕様を固定すると #28 で捨てることになり、
  かつ改訂の抵抗にもなる。新仕様のテストは #28 の実装時に書く。
- **実棋譜 1 局分の USI 手列をテスト内にリテラルで持ち、最終局面と持ち駒まで検証する**。#38 でバグを
  検出したランダム 2000 棋譜の差分検証は旧実装が消えた今は再現できないため、代替として**実データの経路を
  1 本通す**。`board.ts` は USI 手列を受け取るので、リテラルで持てば **KIF パーサー（server）への依存が要らない**
  （`sample.kif` を使うと web のテストが server に依存してしまう）。棋譜は
  `packages/server/src/kif/parser.test.ts` と同じ「ムラ vs daiius」70 手を USI に変換して使う。
- **`vitest.config.ts` を `vite.config.ts` と独立させる**。web の `vite.config.ts` は TanStack Router の
  ルート生成・React Compiler の babel 変換・Tailwind を積んでおり、そのままだとテスト実行のたびに
  **副作用（`routeTree.gen.ts` の再生成）と変換コスト**が乗る。純ロジックのテストにこれらは要らない。
- **テスト方針を [02](../02-architecture.md) §7 に明文化する**。方針が PRD に無いため「UI テストを書くべきか」が
  レビューのたびに問われて保留になっていた（PR #46）。書くのは 3 点に限る:
  純ドメインロジックはテストする / UI・DB 接続は目視確認に回す / `shared` 抽出時はテストも一緒に移す。

### 一覧のフィルタバーを折り畳みに収める（2026-07-21・**暫定**）

PR #46 で入れたフィルタバー（検索・解析状態・勝敗・期間・並べ替え・クリア・件数）は、
**現状の絞り込み軸だけでは常時出しておくほど使わず**、一覧の上部を占有しているのが重い（issue #50）。

- **「検索」の `<details>` に収め、既定は閉じる**。機能自体は消さない。
  **これは暫定**で、戦型（戦法）を記録できるようになれば検索の有用性が上がるため、
  常時表示へ戻す判断があり得る（#33）。
- **条件が効いていても自動では開かない。代わりに畳んだままの `summary` に条件を 1 行で出す**。
  条件付きの URL を開いたときやリロード時に、絞り込まれているのに何も見えないと
  「なぜ件数が少ないのか」が分からない。かといって自動で開くと「上部を占有しない」目的と衝突する。
  **畳んだまま理由が読めれば十分**で、変えたいときだけ開けばよい。モバイル幅で溢れないよう
  1 行に切り詰める（全部を読ませる必要はなく「絞り込まれている」と分かればよい）。
- **ヒット件数は折り畳みの外**に置く。閉じている間も見えている必要があるため。
  「条件をクリア」は中のままでよい（0 件のときの本文中のクリアリンクは折り畳みの外にあり、閉じていても押せる）。
- **`LazyDetails`（開くまで中身をマウントしない）は使わない**。あれは局面数ぶんの表のような
  **重い中身**のための部品（上記「ページ下部の折り畳み」の決定）で、フィルタバーは入力要素が数個と軽く、
  **開閉のたびに入力状態を作り直したくない**（検索語のドラフトが消える）。素の `<details>` を使う。
- **条件の要約は `packages/web/src/lib/kifuListFilter.ts` の純関数に切り出し、単体テストを付ける**。
  許可値（`STATUSES` 等）と既定値もそこに集約し、route 側の重複を無くす。分岐（片側だけの期間・
  既定の並べ替えは出さない）が要約の読み方を決めるため、[02](../02-architecture.md) §7 の
  「純ロジックはテストする」に該当する。**server 側のクエリは変更しない**（今回は表示だけ）。

### 解析の進捗を可視化する（2026-07-21）

本番想定の byoyomi モードでは 1 局の解析が十数分〜数十分かかるが、その間 UI のバッジは「未」のままで
**「解析中なのか、キューが止まっているのか」を区別できなかった**（issue #29 / [05](../05-analysis.md)
§1.1b・§2.5 を改訂）。**スコープは進捗の可視化（Step 1）のみ**で、解析結果のチャンク submit は #51 に分離した。

- **粒度は N/M（「解析中 87/154」）**。2 値の「解析中」だけでは worker がハングしても「解析中」のままで、
  区別したかったものが半分しか解決しない。**進捗が動くこと自体が生存確認になる。**
- **進捗は server のメモリに持ち、`kifus` に列を足さない**。理由は 3 つ:
  (1) **#51（チャンク submit）が入れば `moveAnalyses` の件数から導出できる**ため、列にすると捨てることに
  なり migration を 2 回打つ、(2) 数十分の解析中に DB へ UPDATE を繰り返さない、(3) 完了すれば
  `analysisCompletedAt` が正になる**揮発的な情報**である。server 再起動で消えるが worker の次の報告で
  復活し、**stale が自動で消える利点**にもなる。実装は `swars/job-store.ts` と同じモジュールスコープの状態
  （単一プロセス前提は [02](../02-architecture.md) §1 / [07](../07-auth-and-privacy.md) の確定事項）。
- **報告は毎局面。N 局面ごとにしない**。N の適正値は 1 局面あたりの所要時間に依存し、開発 MATERIAL と
  本番 NNUE・depth/byoyomi で桁が変わるため**固定値の根拠が置けない**。メモリ更新だけなので
  150 局面 × 数十分に対して最大 150 リクエストは無視できる。
- ⚠ **報告の失敗は握りつぶして解析を継続する**。server が落ちている・遅いときに解析まで止まるのは本末転倒。
  worker は報告を待たずに次の局面へ進む（投げっぱなし + `catch`）。
  - 投げっぱなしにすると**最終局面の報告が submit より後に届きうる**ため、server 側で
    **完了済み・失敗記録済みへの報告も弾く**。これがないと「終わったのに解析中」がメモリに残り続ける。
  - ⚠ **弾く判定と記録の間にも競合がある**。判定は DB 読み取り（`await`）を挟むため、Node が単一
    スレッドでも await の境界で submit / error / reanalyze / 削除のハンドラが走りきってしまう。
    そこで**メモリへの書き込みはクリアとの compare-and-set** にした（クリアのたびに進む単調カウンタを
    読み取り前に取り、記録時に一致を確かめる）。**カウンタは対象の kifuId が違っても常に進める**
    （エントリがまだ無いうちにクリアされたケースも弾くため）。巻き添えで捨てた報告は
    worker の次の局面の報告で数秒後に復活するので、取りこぼしのコストは低い。
  - 逆に**進捗の後退は弾かない**。submit 失敗 → 次の poll で同じ棋譜を最初から解析し直す経路があり
    （世代は変わらない）、単調増加を強制すると進捗が最大値で凍る。
- **stale は閾値で消さず、経過時間を出して人に委ねる**。[05](../05-analysis.md) §1.3 のとおり byoyomi の
  適正値は吟味中で env 運用、開発 MATERIAL と本番 NNUE で速度が桁違いのため、
  **「何分更新が無ければ死んでいる」の閾値に根拠が置けない**（depth 20+ なら 1 局面数分かかり、正常な解析を
  stale と誤判定しうる）。見るのは自分だけなので経過時間を出せば判断できる。
- **取得口は専用の `GET /api/analysis/progress`**。worker は 1 件ずつ処理するので**解析中は高々 1 件**であり、
  一覧も詳細もこれ 1 つを見て自分の id と照合する。**一覧 SQL を再実行せずに進捗だけポーリングできる。**
- ⚠ **一覧の状態フィルタに「解析中」は足さない**。進捗はメモリにあり SQL で絞り込めないため、PR #46 で
  確定した「絞り込みは server 側（SQL）で行い、件数・ページングも同じ条件で数える」を崩すことになる。
- **解析中は短間隔（5 秒）、非解析中は長間隔（30 秒）でポーリング**する。メモリ参照だけで DB を触らないので安い。
  - **経過時間の表示用に現在時刻を自前で刻む**（10 秒）。SWR は同値なら再レンダーしないため、worker が
    ハングして進捗が止まると**経過時間まで止まって見え**、「更新が止まっていること」を見せたい意図と逆になる。
  - **進捗エントリが消えたらルーターのローダーを作り直す**。一覧のバッジも詳細の解析結果もローダー経由なので、
    作り直さないと「解析中」が消えた後に**古い「未」のまま残る**。完了は数分〜数十分に 1 度なので素朴でよい。
- **報告先は `/api/worker/` 配下**に置き、`analysisRevision` の世代照合も submit / error 報告と揃える
  （reanalyze 後に届いた旧解析の進捗を表示しない）。エントリは
  **submit 成功 / error 報告 / reanalyze / 棋譜削除でクリア**する。
- **経過時間の整形（`formatElapsed`）とストア（`analysis-progress.ts`）は純ロジックなので単体テストを付ける**
  （[02](../02-architecture.md) §7）。エンドポイント自体は DB 接続を伴うため目視確認に回す。

### 解析結果のチャンク submit と再開（2026-07-21）

解析結果を最後に 1 回だけ submit する構造では、byoyomi 運用で数十分かかる解析が submit の失敗で
丸ごと失われる（issue #51）。チャンクに分けて送り、途中から再開できるようにする。

- **チャンクは経過時間で区切る**（前回 submit から T 秒）。抑えたいのは「失敗時に失われる計算時間」
  なので、時間で切れば**失う上限が T 秒に固定**され、開発 MATERIAL でも本番 NNUE depth20 でも同じ
  保証になる。固定局面数だと同じ N で失う量が桁違いになる。T は「失って許容できる時間」であり
  エンジン速度に依存せず決められる。
- **途中まで入った棋譜は続きから再開する。** 再開がないとチャンク submit の価値は半減する:
  poll 条件は `analysisCompletedAt IS NULL` なので、次の poll で同じ棋譜を 0 から解析し直し、
  数十分の計算は結局失われる。救えるのは submit のリトライコストだけになる。
- **チャンク submit の失敗は中断し、次の poll で再開する。** 欠番が生じないので再開位置が
  「入っている件数」だけで決まる。握りつぶして続行すると `moveNumber` に穴が空き、再開位置を
  「連続している最大」で判定する必要が出て設計が複雑になる。また submit が落ちる状況
  （server 停止・DB 障害）では後続も失敗する可能性が高い。**進捗報告（#29）は逆に握りつぶして
  継続する**——進捗は表示だけで失っても実害がないのに対し、チャンクは計算結果そのものだから。
- **`analysisCompletedAt` は server が件数で判定する。** `moveAnalyses` の件数が
  `usiMoves.length + 1` に達したら同じトランザクション内で確定する。`UNIQUE(kifuId, moveNumber)` が
  あるので件数＝揃った局面数。「揃っていれば完了」という不変条件で決まるため、worker のクラッシュ位置や
  チャンク境界に依存しない。worker に `isFinal` を送らせる案は、最終チャンクを送れずに落ちた場合の
  復帰経路（残り 0 局面で何を送るのか）が不自然になる。
- **冪等性の担保は 3 箇所に分散する。** 重複防止は `UNIQUE(kifuId, moveNumber)` の upsert、
  前世代の全消去は **`reanalyze` の DELETE が唯一の経路**（submit 側から DELETE を外すため）、
  完了の確定は件数による `analysisCompletedAt`。世代照合と `FOR UPDATE` は現行のまま維持する。
- **エンジン構成が変わったときの混在は検出しない。** 「解析来歴（engine/eval）は持たない」確定事項に
  より比較する手段がないため、「構成を変えたら `reanalyze` する」を運用注意として PRD に書くことで
  受ける。個人用で構成変更はまれであり、`reanalyze` は既にある。
- **部分結果は UI にそのまま見せる。** 消費者はいずれも部分結果で壊れない——`detectBlunders` は
  `next.moveNumber !== curr.moveNumber + 1` でスキップするため連続ペアのみを判定し、`EvalGraph` は
  `points.length < 2` で null を返し、`kifu-export` は sorted を回すだけ、棋譜詳細は
  `analyses.length > 0` で切り替えるだけ。解析が進んでいく様子が見えることは #51 の副次効果として歓迎する。
- **#29 のメモリ進捗は残す。** チャンク submit が入れば進捗は `moveAnalyses` 件数から導出できるが、
  **メモリ＝表示（毎局面更新で滑らか）/ DB 件数＝再開位置と完了判定（正確）**と役割を分ける。
  DB 件数に一本化すると進捗の粒度が T 秒に落ち、最初の T 秒間は「未解析」に見えてしまう。

### 悪手判定を centipawn loss ベースへ（2026-07-21）

現行の判定（手番側の評価値が 300cp 以上悪化し、**かつ実手が候補手リスト外**）は 3 つの取りこぼしを
構造的に抱えていた（issue #28）。MultiPV=3 のため「3 位の手を選んで 400cp 損した」が永久に悪手に
ならず、しかも実手が候補内ならその手のスコアが DB にあるのに使っていない。詰みで終わった棋譜では
エンジンが詰み局面で info 行を返さず候補が空になるため最終手（頓死）が判定されない。`toSenteEval` が
mate を ±3000 にクランプするため mate → mate の変化が差分 0 になる。

- **CPL = 最善手の評価 − 実手の評価**（手番側視点）を第一級の指標にする。実手の評価は、**候補内なら
  その `scoreValue`、候補外なら次局面の最善値を符号反転**して得る。「実手が候補内なら悪手にしない」
  条件は廃止する。
- **候補外は近似である**ことを受け入れて明記する。候補内の `score` は「その局面から深さ d 読んだ値」、
  次局面の best は「1 手進んだ局面から深さ d 読んだ値」で読みの深さが揃わない。完全に揃えるには
  全候補を深く読む必要があり非現実的。
- **2 段階（悪手 / 疑問手）とし、「好手」は設けない。** 相手が損したのは相手の悪手であって自分の好手
  ではなく、真の好手（エンジンが見つけにくい手・相手の誤りを誘った手）は MultiPV=3 では判定できない。
  CPL を第一級にすると**数値そのものが主**になり、段階は「どこを見るべきか」の目印に過ぎないので
  段階は少なくてよい。
- **mate が絡む変化は CPL を計算せず別カテゴリとして扱い、平均 CPL の集計からも除外する。**
  詰みは連続量ではない。cp に写像すると詰み逃しが 30000 級の損失になり、1 局混ざるだけで平均 CPL
  （#31 の棋力指標の土台）が壊れる。
- **詰み系の重大度には詰み手数を反映する。** 長手数の詰みは気づくのが困難で、3 手詰の見逃しと 27 手詰の
  見逃しを同列に扱うのは実態に合わない。評価値グラフでは **× マーカーの色の赤さ**で手数を表す
  （短手数ほど真っ赤 → 長手数ほど通常の悪手マーカーの赤に近づく）。**透明度は既存どおり自分 / 相手を
  表すために取っておく**——透明度に 2 つの意味を持たせると、薄いマーカーを見たときにどちらの理由か
  読めなくなる。
- **閾値は UI から変更でき `localStorage` に保持する。** 300 という値には根拠が無く（決定ログにも
  記録が無い）、適正値は棋力と目的で変わる。**CPL を第一級にすると閾値は「表示のフィルタ」でしかなく
  なり、数値そのものは閾値に依存しない**ので、後から変えても再計算が要らない——設定可能にするコストが
  構造的に低い。既定は現行踏襲で悪手 300 / 疑問手 150 / 決着 1000。
- **勝負が決した局面にはラベルを付けない**（CPL の計算自体はする）。勝勢 +2000 から +1500 に落ちても
  学びは薄く、平均 CPL に混ぜると指標が汚れる。これまで `kifu-export` の注目局面選定だけが決着後を
  除外しており、**評価値グラフのマーカーとは基準が食い違っていた**ので、判定側に一本化して揃える。
- **CPL は永続化しない。** `candidateMoves` と `usiMoves` から決定的に導出できる。集計のために列を
  持つかどうかは #31 で実装方式とあわせて判断する。

### 設定ページを作り、悪手判定のしきい値をそこに移す（2026-07-22）

しきい値は `localStorage` に **1 組だけ**持ち全棋譜に効く恒常的な好みとして設計した（上の 2026-07-21）。
にもかかわらず設定 UI は棋譜詳細（`/kifus/$id`）の折り畳みの中にあり、**UI の置き場所がデータの寿命と
一致していなかった**（issue #57）。

- **アプリ全体の設定ページ `/settings` を新設し、しきい値の設定 UI をそこへ移す。** 実体が 1 つなのに
  棋譜ごとに設定欄があると**棋譜ごとの設定に見え**、ある棋譜で変えると他の棋譜の表示も変わる。
  しきい値は「棋譜を見ている最中にいじる値」ではなく「一度決めて長く使う値」なので、置き場所を
  データの寿命に合わせる。**`localStorage` に 1 組・全棋譜に効くという性質そのものは変えない。**
- **設定ページでは折り畳みにしない。** そのページに来た時点で目的は設定なので、開く操作を挟む理由が無い
  （折り畳みの遅延マウントは「読むついでのページに重い中身を置く」ための決定であり、ここには当てはまらない）。
- **ヘッダーの導線は歯車アイコン**（`aria-label="設定"` の `btn-square`）。ナビのボタンが 3 つに増えるため、
  モバイル幅で「棋譜を登録」を潰さないよう幅を食わない形にする。
- **既定値を悪手 600 / 疑問手 300 / 決着 3000 に引き上げる**（従来 300 / 150 / 1000）。実際に自分の棋譜で
  使うと、低い値ではラベルが付きすぎて「どこを見るべきか」の目印として機能しない。決着 1000cp は
  **まだ十分に逆転しうる局面**を決着扱いにしてラベルを消していた。**根拠が置けないからこそ設定可能に
  した**という 2026-07-21 の論旨は変わらない——変えたのは初期値だけ。
- **保存済みの値は移行しない。** 既定値は「まだ何も設定していない人に出す初期値」であり、明示的に設定した
  値を勝手に書き換える方が驚きが大きい。既に値がある環境では従来の値が効き続け、新しい既定へは
  設定ページの**「既定に戻す」ボタン**（既存機能）で移れる。移行手段としてこれで足りる。
- **設定を server / DB に持たせる案は採らない**（2026-07-21 の判断を維持）。設定用テーブルが必要になり
  マイグレーションがスコープに入る。
- **しきい値以外の設定項目は今回追加しない。** 設定ページは将来の置き場になるが、取り込み設定（#30）等を
  ここへ集約するかは別途判断する。

### swars 一括取り込みを無効化する（2026-07-25）

- **フロント/API からのアクセスを恒常的に遮断する。** swars は KIF 取り込みに数ステップかかるため
  自動取り込みに依存していたが、**元サービス側のアップデートで KIF を手軽にコピーできるようになり、
  自動取り込みが実質不要**になった。加えて **グレー領域のある機能**（履歴/CSA の取得）なので、露出を
  絞る。KIF は §3 の貼り付け（+ クリップボードペースト）で入れる。具体的な背景は `.claude-personal/`。
- **実装は削除せず残す。** `swars/` モジュール（取得・CSA→KIF・ジョブストア）と server のジョブ起動
  ロジックはコードに残す。将来また必要になったとき復元しやすく、変換器（CSA→KIF）は将来の
  「CSA 直接貼り付け」（[04](../04-ingestion.md) §2）でも再利用しうるため。
- **遮断は「常時 404」を選ぶ**（env フラグではなくコード上の定数 `SWARS_IMPORT_DISABLED`）。
  env フラグだと設定次第で口が開きうるが、グレー機能なので**簡単にオンにできない**方を優先する。
  再有効化には明示的なコード変更（定数を落とす）を要る。
- **404 ガードは `sessionRequired` より前に置く。** 無効化した口では認証状態も body 検証結果も晒さず、
  素直に 404 で「存在しない」ように見せる。
- **フロント（一覧の「更新」ボタン・ページ数セレクト・ポーリング）は撤去する。** 単に隠すのではなく
  コードごと消す（`VITE_SWARS_USER_ID` は「自分」判定にも使うので、そちらの用途では残す）。

### 戦型ラベルの一級市民化（2026-08-04）

`prd/06` §3.2 で「LLM プロンプトの一要素」として控えめに置かれていた戦型ラベルを、ドメインの
第一級属性へ格上げする（issue #33）。本 PR は**設計の確定まで**で、実装は別 PR に分ける。

- **判定は内部 / 一次 / 二次の 3 層に分ける。** 局面述語（内部ラベル）と戦法名（一次ラベル）を混ぜると、
  順序条件が手続きコードとして判定関数の中に埋まり、定義が読めなくなる。
  内部ラベルに**真偽の時系列**を持たせ、一次ラベルはその時系列に対する論理式（同時 / 順序 / 否定）として書く。
  **3 段目より下は作らない**（層を増やすより内部ラベルを足す）。
- **`_角交換`（事象）と `角換わり`（戦法）を別の層に置くのが要点。** 将棋の用語としても別語で、
  3 手目▲2二角成・筋違い角・鬼殺しはいずれも角交換だが角換わりではない。層で表現すれば
  「角交換に序盤 / 相居飛車 / 交換後の駒組みを足したものが角換わり」という定義がそのまま書ける。
- **観測窓に手数の定数を置かない。** 「30 手まで」「この戦法は 20 手まで」といった上限は、
  サンプルに合わせて選んだ数値でしかなく将棋的な説明がない。窓は
  **「駒がぶつかったら閉じる。ただしその述語が駒を取った結果を見ているなら、その駒種は数えない」**
  の 1 規則で決める。除外する駒種は定義の形から機械的に決まる。
  - **却下: 一律の窓。** 窓を狭めると飛車の位置で決まる戦法の精度は上がるが、
    **交換そのものが定義の一部である戦法**（角換わり・相掛かり・横歩取り）は定義の成立前に窓が閉じて
    全滅する。逆に緩めると中盤の駒運びが混ざる。ローカルの実験環境で 4 通りの一律窓を実測して確認した。
  - **一次ラベルの窓は、参照する内部ラベルの除外集合の和**。角換わりは `_角交換`（角を除外）と
    `_双方飛車初期位置`（除外なし）を同時条件で組むため、和を取らないと後者の窓が角交換の手で閉じ、
    **永久に成立しない**。実装で最初に踏んだ罠なので明記する。
- **恣意的な定数を捨てたことで、定義の欠落が露出した。** 例えば相掛かりには「双方が居飛車」という
  定義上必須の条件が抜けていたが、観測窓を 20〜30 手に絞ることで対抗形の棋譜を拾わずに済んでいた。
  **窓は定義の不足を隠す**。これは定数を外す積極的な理由になる。
- **経由形は誤検出として扱わない。** 2八→6八→8八 と振り直す途中で四間飛車が立つのは
  `四間飛車 → 向かい飛車` という正しい記録で、消すと「振り直しが本体」の戦法の情報が失われる。
  よって**飛車の移動元は条件に使わない**（移動元条件を外すと取りこぼしが大きく減り、
  増える誤検出はすべて経由形だったことを実測で確認）。
- **1 局・1 手番に複数のラベルが立ってよい。** 角換わりと矢倉は排他ではなく、
  「7 七銀が角交換の前か後か」で片方を消すと角換わり腰掛け銀のような形が落ちる。
- **残余のラベルは他の一次ラベルの判定結果で取り下げる**（相掛かり）。除外条件を残余側に書き直すと、
  角換わりの順序条件のような作り込みを二重に持つことになる。除外は**双方の判定を見る**
  （相手が横歩を取れば局面全体が横歩取り）。
- **保存は `kifuTactics`（別テーブル）。** JSON 列（`kifus.tactics`）は `JSON_CONTAINS` で書けるが
  索引が効かず、「一覧の絞り込みは server 側の SQL で行い件数・ページングも同じ条件で数える」
  （`prd/04` §6.1 の確定事項）と戦型別の勝率集計（#31）に素直に乗らない。
- **判定バージョンの列は持たない。** 判定を更新したら全件を一括再判定する（解析来歴を持たないのと同じ立場）。
- **成立手数（`turn`）は保存する。** 当初は「絞り込み・集計に要らず、必要なら再計算できる」として
  保存しない判断だったが、**表示の抑制に要ることが分かったので覆した**（`prd/03` §2.1.2）。
  振り直しで複数の振り先ラベルが立つ（実測 4.4% の手番）ため、「最初に振った先だけ出す」を
  SQL のまま書ける必要がある。表示のたびに `usiMoves` から再計算する案は、一覧が毎ページ
  数十局ぶんの盤面追跡を回すことになるので採らない。
  **絞り込み条件には使わない**（再判定で値が動く派生値のため）。
- **観測窓の除外には根拠が 2 つある。** (1) その述語が駒を取った結果を見ているか（述語の形から機械的に決まる）、
  (2) その駒取りが開戦を意味するか。**角交換は駒組み手順であって開戦ではない**ので、(2) により
  角は全ラベルで「ぶつかった」に数えない。(1) だけだと飛車の振り先を見るラベルが角交換の瞬間に
  窓を閉じ、`ダイレクト向かい飛車`（角交換してから 2二飛）が原理的に成立しなくなる。
  歩は別扱いのまま（歩がぶつかるのは急戦の仕掛けそのもの）。
  ⚠ **除外するのは「角交換」であって「角の捕獲」一般ではない**（「取る → 取り返す」で双方が
  角を持ち駒にしたか、で判定する）。一方的な角損・角切りは開戦なので窓を閉じる。
  区別しないと開戦後の駒運びを拾う（実測でも区別した方が居飛車の precision が 98.8% → 99.5%）。
- **表示の抑制は側ごとに独立して掛ける。** 隠す集合を対局で共有すると、先手の `石田流` が
  **後手の** `三間飛車` まで隠す。ただし対局帰属（`both`）のラベルは双方のタグを隠す
  （`相掛かり` は「双方が居飛車」を意味するため）。
- **表示の抑制（per-side）と関係ラベルの導出（対局レベル）は独立した規則で、パイプラインにしない。**
  どちらも入力は「抑制前の全判定結果」。抑制後の集合から関係ラベルを導出すると、`石田流` が
  `振り飛車` を隠している対局（石田流 対 居飛車）で `対抗形` が立たなくなる。
- **ラベルの包含関係（`implies`）は判定側が宣言し、表示で一般ラベルを隠す。** 保存は全部する。
  抑制後を保存すると経由形での絞り込みができなくなる（`prd/01` §6.3 の「経由形は正しい記録」と衝突）。
  ⚠ **含意は「判定条件どうしの含意」であって戦法の分類ではない。** 分類（`石田流` は三間飛車の一種、等）は
  出自の話で、個々の棋譜がその形を通る保証がない。`右四間飛車`・`袖飛車` は振り先が 5 筋より右なので
  振り飛車を含意しない。
- **`label` は表示名そのものを入れる**（enum やコード値にしない）。定義が増えるたびにスキーマ変更を
  伴わせないため。表記ゆれは判定側（`shared`）が単一の出所になることで防ぐ。
- **判定は `shared` に置く。** 将棋ドメインの純ロジックであり、投入時（server）と表示・絞り込み（web）の
  両方から使う（`prd/02` §3.2）。**`shared` 抽出を実利のある形で消化する機会**でもある。

### 戦型ラベルの帰属を 3 種類に分ける（2026-08-04・上記を改訂）

**この節は「両手番に複製する」という直前の決定を覆す。** 実装前に気づいたので、いま変えるのが最も安い。
以下は**なぜ複製に至り、なぜやめたか**の記録（後から見直すときはここを読む）。

#### 経緯: なぜ複製があったか

1. `kifuTactics` は 1 行 = 「どの棋譜の / どちらの手番に / どのラベルが立ったか」。
   **`side` があるのは自分の戦型と相手の戦型を区別するため**（「四間飛車で勝った」と
   「四間飛車に勝った」は別のこと）。
2. ところが `対抗形` のような**関係ラベルは対局全体の性質**で、どちらか一方のものではない。
   手番ごとの表に入れるには `side` に何かを入れるしかないので、**両手番に同じラベルを入れた**。
3. これにより `(kifuId, label)` が 2 行になり、素朴に JOIN すると 1 棋譜が 2 行に増える。
   一覧の件数が倍になり、`LIMIT` が半分になり、勝率の分母が倍になる。**エラーは出ない。**
   PR #73 のレビューで指摘され、`EXISTS` / `COUNT(DISTINCT)` のクエリ契約で回避することにした。
4. そのとき却下したのは **`side` を NULL 可にする案**（主キーに NULL を含められない）と
   **別テーブルに割る案**（絞り込みが常に UNION になる）。
   **`enum` に値を足す案は検討していなかった。**

#### 覆した理由

- **複製を選んだ理由（手番別集計が素直に書ける）が弱かった。** `both` でも
  `JOIN … ON t2.side = 'both'` と条件が 1 つ変わるだけで、複雑さはほぼ同じ。
  一方、複製は**二重計上を避けるクエリ契約を永久に守り続ける**必要を生む。
- **帰属を一律に扱おうとしたのが誤り。** 戦型によって「誰のラベルか」は違う。
  分けて考えると、`both` が必要なラベルはごく一部だと分かった。

#### 確定した 3 種類（`prd/01` §6.3 / `prd/03` §2.1.1）

- **手番固有**（四間飛車・矢倉・筋違い角・横歩取り）= 実行した側だけ。
  見分け方は「**相手の同意なしに成立するか**」。
  - ⚠ `_筋違い角` は当初 `自分の角が4五 || 相手の角が4五` と両側を見ており、**両手番に立って
    しまい自分/相手を区別できなかった**（precision 60.0%）。自分の角だけに絞って 100.0% へ。
    **内部ラベルは「自分の側の事象」に限る**という規律をここで得た。
- **きっかけ帰属**（角換わり）= 双方がその戦型だが、記録するのは**持ち込んだ側**。
  - 「双方の合意で成立するから帰属先が無い」と一度整理したが、**それは誤り**。
    帰属先が決められないことと、きっかけが分からないことは別。先手が手損を承知で角交換に
    踏み込み得意戦法へ持ち込む指し方は実戦で珍しくなく、**乗るか拒むかも相手の選択**である。
    どちらの選択も記録に値する。
  - **役割ラベル（`角交換を挑んだ` / `角交換に応じた`）を別に持つ案は却下。**
    1 局 3 行になりラベルの種類も増える。`side` に持ち込んだ側を入れれば 1 行で済み、
    「応じた側」は導出できる。実装コストは同じ（先に角を持った側を見るだけ）。
  - 実測: 角換わりが立った 25 局すべてで持ち込んだ側が確定（判定不能 0 件）。
    ▲から 11 / △から 14。`一手損角換わり` `木村定跡` とも △から で、原譜と一致。
- **対局帰属**（相掛かり）= `both` で 1 行。
  - **相掛かりにきっかけは定義できない。** 成立条件が「双方が飛車先を伸ばし合った」状態で、
    さらに角換わり・横歩取り・矢倉・雁木・筋違い角の**いずれでもない**という引き算で決まる。
    誰かが持ち込んだのではなく「他の戦型にならなかった」結果。
  - 「先に飛車先の歩を交換した側」は取れるが、**手順の情報であって戦型の帰属ではない**
    （`中原流相掛かり` のように交換を保留するのが特徴の指し方がある）。
- **関係ラベル（`対抗形` / `相居飛車` / `相振り飛車`）は保存しない。**
  双方の一次ラベルから導出できる。導出できる値を持たない方針（成立手数・判定バージョンと同じ立場）に揃える。
  絞り込みで `EXISTS` が 2 つ必要になるのが代償。

#### 結果として

`both` を取るラベルは**相掛かりだけ**になり、`(kifuId, label)` が複数行になる状況がほぼ消えた。
`side` の意味がラベルによって変わるので、**判定側（`shared`）が種別の一覧を単一の出所として持ち**、
表示・集計はそれを参照する。

以下はレビュー指摘（PR #73）で補った点:

- **層をまたぐ窓は「一次ラベルの判定結果をそのまま受け取る」。** 二次ラベルが一次ラベルを参照するとき、
  参照先は既にその一次ラベル自身の窓で判定済みなので、除外集合を二次側へ持ち込まない。
  - **却下: 推移的に和を取る**（参照した一次ラベルの依存を再帰的に足す）。窓が必要以上に広がり、
    中盤の駒運びを拾う方向に働く。例えば `石田流` が角を除外するラベルを参照しただけで、
    角の取り合いの後まで飛車の位置を見続けることになる。
  - 二次ラベルが内部ラベルを**直接**参照する経路（`ひねり飛車` → `_飛車先歩交換`）は実在するので、
    そちらは参照先の宣言に含めて和に入れる。**必要な除外は「直接参照するものを宣言する」ことで漏れなく入る。**
- 🚫 **【撤回済み・2026-08-04】関係ラベルは両手番に複製して保存する。**
  **この項は実装契約として読まないこと。** 下の「戦型ラベルの帰属を 3 種類に分ける」節で覆した
  （関係ラベルは**保存せず導出**する）。当時の判断として残すが、現行の正典は
  `prd/01` §6.3 と `prd/03` §2.1.1。
  - 当時の理由: 対局単位の性質だが、手番を持たない行を混ぜると同じ表に粒度の違う行が同居し、
    集計のたびに場合分けが要る。複製しておけば「振り飛車で対抗形のときの自分の勝率」を
    `(kifuId, side)` の粒度のまま書ける。
  - 当時認識していた代償: `(kifuId, label)` が 2 行になり、素朴に JOIN すると 1 棋譜が 2 行になる。
    そこで用途ごとの SQL 契約（相関 `EXISTS` / `COUNT(DISTINCT kifuId)` / `(kifuId, side)` 粒度）を
    `prd/03` に置いていた。**この契約も撤回済み**（`both` を取るラベルが相掛かりだけになり不要になった）。
  - 当時却下した案: 関係ラベルだけ対局単位で保存する（`side` を nullable にする / 別テーブルに分ける）。
    `side` が NULL だと主キーに含められず、表が 2 つに割れると「戦型で絞る」クエリが常に UNION になる。
    **`enum` に値を足す案は当時検討しておらず、それが撤回の入口になった。**
- **`usiMoves` を作成・更新するすべての経路で戦型を判定し直す。** 投入時だけでなく `reanalyze`
  （`kifText` の再変換）も対象で、`kifus` の更新と `kifuTactics` の置換を同一トランザクションに入れる。
  当初は生成契機を「投入時」と「判定更新時の一括再判定」に限っていたが、それだと**KIF パーサーの修正で
  指し手列が変わったのに保存済みラベルだけが旧指し手列由来のまま残る**。派生値の契約は
  「いつ作るか」ではなく「**元が変わったら必ず作り直す**」で書く。
  再変換に失敗して `usiMoves` が null になったときはラベルを**空に置換**する
  （指し手列が無い以上、戦型は「不明」であって「以前の値」ではない）。
- **戦型の再判定は棋譜単位で原子的に置換する**（同一トランザクションでの `DELETE` → 一括 `INSERT`、
  判定成功後にのみ置換）。この表は絞り込みと集計に使われるため、中間状態が読まれると
  **その棋譜だけ静かに条件から外れ、件数や勝率が誤る**。エラーにならないので気づけないのが問題。
  一括再判定**全体**を単一トランザクションにはしない（棋譜ごとに独立して置換してよい）。

### 分析ページ（戦型別成績）の設計（2026-08-05）

仕様は [`prd/09-analytics.md`](../09-analytics.md)。ここには**捨てた案と、途中で覆した判断**を残す。

- **主軸は「相手の戦型」**。自分の戦法がほぼ固定なので、勝率を動かす変数は相手側にある。
  `side` を見ない集計を主軸にすると、自分の固定戦法がほぼ全局に立って情報量が消える。
- **集計は生ラベルで数える（`suppressForDisplay` を掛けない）。** ⚠ **一度は「抑制を掛ける」で
  決めたが覆した。** 決め手は 3 つで、いずれも抑制案では解けなかった:
  1. 抑制すると `振り飛車` の行がほぼ常に消える（`IMPLIES` により振り先ラベルがすべて含意する）。
     それは [01](../01-domain.md) §6 が挙げた動機「振り飛車相手だと勝率が落ちる」そのもの。
     一度は「上位は見ない」で受けたが、次の 2 で行き詰まった。
  2. **一覧へのドリルダウンで件数が食い違う。** 分析ページが抑制後（`三間飛車` に石田流の局を含まない）、
     一覧が `EXISTS(label='三間飛車')`（含む）になり、「8 局」をクリックして 14 件出る。
  3. **一覧側を TS で畳んで直すことはできない。** 絞り込みは server の SQL で行い件数・ページングも
     同じ条件で数える（[04](../04-ingestion.md) §6.1）ので、`count()` と LIMIT/OFFSET が壊れる。
  → 生ラベルなら定義が原理的に一致し、しかも `suppressForDisplay` が集計から消えて `GROUP BY` 一本になる。
  代償は「局数の合計 ≠ 総局数」だけで、総局数の別掲で受ける。
- **階層は `IMPLIES` をそのまま使い、不自然な形を隠さない。** `矢倉`・`角換わり`・`横歩取り` は
  `居飛車` を含意しないので根に並ぶ。一度は「階層をやめてフラット」に振れたが、**根に並ぶラベルの多さが
  `IMPLIES` の未整備をそのまま映すので、表が判定定義の診断を兼ねる**という理由で階層に戻した。
  表示専用の分類ツリーは持たない（親の値と子の関係が包含でなくなり、表の読み方が壊れる）。
- **取りこぼしの判定に `lib/cpl.ts` を使わない。** 「最善が自分の詰みなのに実手が詰みでない」のうち
  **「実手が詰みでない」は「その局を負けた」に含まれる**（詰みを実行していれば負けていない）。
  結果、`rank=1 AND scoreType='mate' AND 1 ≤ scoreValue ≤ N` と `moveNumber` の parity だけの
  素の SQL 述語になり、`cpl.ts` の `shared` 抽出を待たずに実装できる。
- **却下: `kifuTactics` に `display` 列を足す。** 抑制後を保存すれば分析・一覧・タグ表示が一致するが、
  生ラベルにすれば**そもそも一致する**。抑制規則を変えて再判定を忘れると集計が静かに誤る、という
  失敗様式（[03](../03-data-model.md) §2.1 が警戒しているもの）を増やすだけになる。
- **却下: 抑制述語を SQL に生成する。** `both` が両側を隠す規則と振り直しの `turn` 最小規則を
  SQL に書き直すことになり、**`shared` のテストが SQL を守らない**。`suppressForDisplay` は
  「集合を 1 つで共有すると先手の石田流が後手の三間飛車まで隠す」バグを既に踏んでおり、
  同じ罠を SQL 側にもう一度作ることになる。
- **却下: web 側で集計する。** 唯一の利点だった「閾値変更が再フェッチ不要」が成立しない。
  取りこぼしは `candidate_moves` を読まないと出せず、ブラウザには送れない。
- **性能は方式選択の争点にならなかった。** 支配項は `candidate_moves` の走査（1000 局 ≒ 12 万行）で、
  ラベルの畳み方による差はその誤差。**やるべき最適化は方式の選択ではなく索引 1 本**
  （`INDEX(scoreType, scoreValue)`）で、これはどの方式でも独立に足せる。

### 検討モードと局面評価（position lab）の設計（2026-08-20）

仕様は [`prd/12-position-lab.md`](../12-position-lab.md)。ここには決定の骨子と、捨てた案の理由を残す。

- **自由編集・合法手生成器は作らない**: 検討盤はフル編集（到達不能な仮想局面も許す）を採るため、
  合法性は問わない。代わりに**エンジンをクラッシュ・ハングさせない最小検証**（両玉の存在・二歩・
  行き所のない駒・駒数上限・手番側が相手玉を即取れる状態）だけを `shared` に置き、失敗は 4xx で弾く。
- **worker 相乗り**: interactive な局面評価は既存の棋譜解析エンジンに相乗りし、**局面境界で優先処理**する。
  USI は毎回 `position` で局面を明示するため割り込みによる状態汚染がなく、個人用途の同時要求は
  ほぼ 1 件なので専用エンジン・別 worker は過剰。パラメータは棋譜解析と同一。
- **メモリ内キュー兼キャッシュ（DB テーブルは足さない）**: キーは正規化 SFEN（+ 評価種別・名指し手）。
  再起動で消えることは許容する（web が再要求すれば済む）。エンジン構成変更時の古いキャッシュも
  再起動で消え、「解析来歴は持たない」方針（上記 2026-07-16）と整合する。
- **評価は明示ボタンのみ・自動トリガーなし**。評価リクエストは**自分手番の局面に固定**し、
  表示は**自分視点**（評価値グラフの先手視点とは意図的に異なる。検討モード内は「自分がこの手なら」の文脈）。
  名指し評価は `go searchmoves` で行い、エンジン非対応なら「手を適用した局面を評価して符号反転」の
  フォールバックで同じ API 契約を守る。
- **手順は一本道 + undo・保存しない**（分岐ツリー・variations 保存は後続候補）。検討モードは
  棋譜詳細ページのトグルとして置く（専用ページは作らない。現在表示中の局面が起点）。
- **LLM への提供は REST + 薄い stdio MCP（`packages/mcp`）・ツールは 4 つの最小セット**
  （`list_kifus` / `get_kifu` / `evaluate_position` / `evaluate_move`）。MCP はデスクトップ側で動かし、
  まず MCP 対応の LLM クライアント（ローカルの LLM CLI 等）から接続する。
- **却下**: interactive 専用エンジン・別 worker（過剰）/ 評価結果の DB 永続化（応答が速く
  キャッシュ喪失の痛みが小さい）/ 評価の自動トリガー（明示ボタンを選択）/ 分岐ツリー・変化の保存
  （後続候補）/ web チャット UI（server 内で LLM を動かさない方針と状態管理が絡む大物。後続候補）。
  詰み探索（`go mate`）・分析ページ連携・commentator のツール裏取り解説も後続候補。

### モバイルで操作ボタンの位置が動かないようにする（2026-08-27）

モバイルで棋譜を進める / 戻るを連打していると、**操作ボタンの位置が変わる**・**テキスト選択が暴発する**・
**押した覚えのない「この局面を探す」で局面検索へ飛ぶ**、という訴えがあった（[05](../05-analysis.md) §2.1 を改訂）。

- **原因は情報行の折り返し**。コンパクト情報行が `flex-wrap` で、符号（`▲２二角成(88)` の形が最長）や
  評価値（`先手勝ち(15手詰)` のような詰み表示で伸びる）が長くなると、右ブロック
  （この局面を探す / 手数 / 分岐バッジ）が折り返して**行が 1 行 → 2 行に増える**。
  その結果**すぐ下のコントローラー行が丸ごと下へずれ**、連打中の指の下に「この局面を探す」が来ていた。
  「ボタンが追加された」ように見えたのはこれで、リンク自体は常設である。
- **実測**（iPhone 14 / 390px・dev-gallery の 3 ケースで修正前後を対比）:

  | 状態 | 修正前 | 修正後 |
  |---|---|---|
  | 最短（初期局面・評価値なし） | 423px | 423px |
  | 中間（通常の符号 + 数値の評価値） | **447px**（情報行 48px = 2 行） | 423px |
  | 最長（成りの符号 + 詰み評価） | **447px**（同上） | 423px |
  | 最長 + 分岐バッジ | （未測定） | 423px |

  ⚠ **この 423 / 447 は dev-gallery の Case 枠上端から操作ボタン行までの距離**であって、実画面の絶対座標ではない。
  見るべきは絶対値ではなく**状態を変えても動かないこと**。
- **採った手段**: 情報行を**折り返さない**構造にし、**最小高で床を作る**。はみ出しは右ブロックを縮めずに
  **符号・評価値を truncate** して吸収し、**削るのは評価値の方から**（符号の方が棋譜を読むのに要る）。
  truncate した全文へは `title` で到達できるようにする。モバイルでは「この局面を探す」を**アイコンのみ**にして
  右ブロックを細くし、符号・評価値に 1 行ぶんの幅を残す。
- **`min-h-6` が要る理由**: 「初期局面」の表示は `text-sm`、符号は `text-base` で**行高が 4px 違う**。
  折り返しを止めて行数を 1 に揃えるだけでは、中身次第でこの 4px が動く。最小高で床を作って初めて一定になる。
- **分岐中は md 未満で評価値を隠す**。分岐バッジが加わった状態では 390px で符号と評価値が両方 truncate され、
  **ホバーの無いモバイルでは `title` からも全文に届かない**。分岐中の評価値は候補手の行にも出ている
  重複情報なので符号を残す。**md 以上は幅が足りるので隠さない**（幅があるのに隠す理由がない）。
- **タッチの暴発対策は `no-tap-select`（`packages/web/src/app.css`）にまとめた**。`user-select: none` +
  `-webkit-touch-callout: none` + タップハイライト透明 + `touch-action: manipulation` を 1 つのユーティリティにし、
  情報行・コントローラー行・盤面・分岐の送りに当てる。
  - ⚠ **`select-none` だけでは iOS Safari の長押しメニュー（callout）が残る**ので `-webkit-touch-callout` を併記する。
  - ⚠ **グローバルには敷かない**。KIF コピー用の `<pre>` など**選択させたい場所**を巻き込むため、
    クラスで明示した要素だけに当てる。
  - 上記「盤面の左右タップで手を送る（2026-07-21）」で決めた「`touch-action: manipulation` と `select-none` を
    効かせる」の**上位互換**にあたる（当時の 2 つを含み、callout とタップハイライトを足したもの）。
- **確認方法を dev-gallery に置いた**。`/kifus/$id` は認証が要り、極端な状態も実データ頼みになるため、
  DEV 専用ギャラリーに最短 / 中間 / 最長のケースを固定した。盤面はハードコードせず `shared` の盤面追跡で
  指し手から導出する（実装が変わってもギャラリーが嘘をつかないように）。
- **未検証**: **実機 iOS Safari のタッチ挙動（callout 抑止・ダブルタップ拡大の抑止）は未確認**。
  playwright では再現できていない。レイアウトの不動は 390px の実測で確認済み。
- **却下した案**:
  - **右ブロックを常時 2 行目へ出す** — 高さは固定できるが、「この局面を探す」が操作ボタンの真上に常駐し、
    誤タップまでの距離がむしろ縮む。
  - **符号だけ縮まないようにする（`shrink-0`）** — 符号単体が幅を超えたとき、親からはみ出して右ブロックに重なる。
  - **`items-baseline` の維持** — truncate した要素は baseline がボックス下端に合成されて縦位置がずれるため、
    `items-center` に変えた。

#### 追記: 狭い画面では評価値を短い形にする（2026-08-27・レビュー `OCL-E85F428F` 対応）

「削った全文には `title` で到達できる」と書いたが、**モバイルにはホバーが無く、しかも `no-tap-select` で
callout を無効化しているため、truncate された全文にモバイルから到達できない**という指摘を受けた。
全文を出す仕組みを足すのではなく、**そもそも削らずに済む情報量にする**方を採る。

- **実測（実画面相当・情報行の幅 358px @ 390px）**:

  | 状態 | 左に使える幅 | 符号 + 評価値に必要な幅 | 余裕 |
  |---|---|---|---|
  | 最短（初期局面） | 262px | 56px | 206px |
  | 中間（`▲７六歩(77)` + `+120 (先手有利)`） | 262px | 205px | 57px |
  | **最長（`▲２二角成(88)` + `先手勝ち(15手詰)`）** | 262px | 226px | **36px** |
  | 最長 + 分岐（評価値は隠れる） | 212px | 105px | 107px |

  390px では切れないが余裕は全角 2 文字ぶん。**320px 幅の端末では 34px 足りず実際に切れる**ので、指摘は空振りではない。

- **`formatScore` が返す形は 2 系統だけ**（`scoreType` は `cp` / `mate` の 2 値）。
  cp は `+120 (先手有利)` のように**数値と言葉の両方**、mate は `先手勝ち(13手詰)` のように**全体が言葉**。
  `mate 0`（既に詰んでいる）と値が壊れている場合は `詰み`（**勝者は元から出ていない**）。
- 🔑 **cp と mate では「どちらが勝つか」の担い手が違う**。
  - **cp は符号（`+` / `-`）と言葉の二重**——言葉を落としても情報は減らない。
  - **mate は言葉だけ**——`先手勝ち(13手詰)` と `後手勝ち(13手詰)` は**その語しか違わない**。
    同じ `mate 13` でも局面の手番が変われば勝者が入れ替わる。**情報行の左端の ▲ / △ は「直前に指した側」**であって
    勝者ではないので、そこからも推測できない。
- **却下: 手数だけにする（`13手詰`）。** 頓死の前後（`先手勝ち(13手詰)` → 次の手で `後手勝ち(1手詰)`）が
  **数字が 13 → 1 に変わるだけになり、勝敗が入れ替わったことが情報行に出ない**。まさにこのアプリが
  見つけたい場面なので採らない。同じ局面の勝者を出す場所は他になく（候補手の行は**1 手前の局面**の評価で、
  かつ上端固定の外にあってモバイルではスクロールが要る／悪手ラベルの `詰み逃し（N手詰）` はラベルが付く手だけ／
  評価値グラフは上下で読めるがこれもスクロールの先）、**この 1 箇所を落とすと画面から消える**。
- **却下: 言葉を記号に置換するだけ（`▲勝ち(13手詰)` / `+120 (▲有利)`）。** 情報は落ちないが、
  **減るのは mate で 14px・cp で 18px** にとどまり、320px で足りない 34px に届かない。
- **採用: 狭い画面だけ短い形にする**（`formatScoreShort`）。**cp は数字のみ**（`+120`）、
  **mate は詰ます側の記号 + 手数**（`▲13手詰` / `△13手詰`）、`詰み` はそのまま。
  符号（`▲２二角成(88)`）と並べた合計幅は **226px → 154px**（cp は 205px → 142px）で、
  **320px でも 24px 残る**。案「手数だけ」との差は全角 1 文字ぶん（14px）で、
  **その 14px で唯一の勝者情報を買える**なら安い。
  - **記号は ▲ / △ に揃えた**。アプリ全体で手番記号として使っている語彙で、
    `先13手詰` のような別表記より説明が要らない。同じ行の符号でも ▲ / △ を使っており、
    そこでは「指した側」を意味する点は承知のうえ（将棋の慣習で ▲ は常に先手なので誤読は小さいと判断した）。
- 🔒 **広い画面は変えない。** 幅が足りているので短くしても得るものが無く、`(▲有利)` は `(先手有利)` より
  読み下しに一手間かかる。**狭い画面は「削らずに済む情報量にするための妥協」、広い画面は「そのまま読める形」**と
  役割を分ける。`formatScore` の既定の戻り値は変えず（候補手の行・LLM 用テキストなど他の利用箇所を壊さない）、
  短い形は別の関数として足して**呼び分けは表示側**で行う。
- **分岐中に md 未満で評価値を隠す規則は残す**（短い形で足りるようになったかは別途測って判断する）。

### 検討盤の評価ボタンを 1 つに統合し、直前の手の損失を出す（2026-08-29）

**決定**: web の検討盤（[12](../12-position-lab.md) §3.2）の評価ボタン 2 つ
（「この局面を評価」= 局面評価 /「この手を読む」= 名指し評価）を、**「評価する」1 つ**にまとめる。
押すと現在の検討局面を評価し、**直前が盤上の指し手なら 1 手前の局面も並行して評価**して、
**直前の手が最善とどれだけ離れていたか（損失）**を出す。

#### なぜ 2 つを 1 つにしたか

- **返る数字が同じで符号だけ反転していた。** 名指し評価は「盤に指した直後の手」しか対象にできず、
  指してしまえば局面評価が同じ値を相手番視点で返す。§2.6 の再利用判定には、名指し評価を
  **「手を適用した局面の評価の符号反転」で代用する経路**すらある。
- **読み筋も局面評価が上位互換。** 名指しの `pv[1]` 以降は相手の応手なので、
  候補手を 3 本返す局面評価に含まれる情報を超えない。
- つまり**同じ数字を 2 つのボタンで出していた**。押し分けの判断をユーザに負わせるだけで、
  得られるものが無い。

#### 代わりに出すもの（採点）

- **指した手の評価値** = 現局面の評価値の**符号反転**（現局面の評価は相手番視点）。
- **最善** = 1 手前の局面の rank 1 の候補手とそのスコア（指した側視点）。
- **損失** = 最善のスコア − 指した手のスコア。指した手が rank 1 そのものなら「最善手」と出す。
- 🔒 **損失の数値は両方 `cp` のときだけ。** `mate` は「詰みまでの手数」で `cp` と単位が違い、
  `mate` 同士でも引き算に意味が無い（`mate 3` − `mate 5` は 2 点差ではない）。
  どちらかが `mate` なら**数値を出さず両者を並べるに留める**。
- 🔒 **副次の要求が主を壊さない。** 1 手前の評価が失敗・busy・中断でも、
  主の局面評価の結果は必ず出す（採点だけ省く）。
- ⚠ 2 本並行になっても**世代（token）は 1 つ・`AbortSignal` は共有**する。
  `begin()` を 2 回呼ぶと 1 本目が自分自身の 2 本目に捨てられ、
  「待ちの間に盤を動かしたら旧局面の結果を捨てる」判定（レビュー `OCL-AED22F46`）が崩れる。

#### 🔒 名指し評価は API に残す

**外すのは web の UI からだけで、server / worker / shared には触らない。**
`go searchmoves` が代替不能になるのは「**盤に指さずに手を指定する**」場合だけで、
それは [12](../12-position-lab.md) §4 の MCP（`evaluate_move`）の用途。
盤に指す前提の web と違い、MCP には「この手はどうか」を局面を動かさずに問う使い方がある。

#### 結果ヘッダーを 1 行にまとめる

  ボタンが 1 つになって**どちらの評価かを言う必要が無くなった**ので、

### 検討の操作パネルを 1 行に収める（2026-08-29）

**決定**: 検討中の操作パネル（[12](../12-position-lab.md) §3.1）の 4 つを**アイコン化して 1 行**に収める。
ラベルのままだと 390px で「棋譜に戻る / 手番 ☖後手 / 成にする」と「評価する」の 2 行に折り返していた。

| ボタン | 見た目 | 理由 |
|---|---|---|
| 棋譜に戻る | 戻るアイコンのみ（枠付き） | 枠が無いと押せるものだと分からない（下記の追記で確定） |
| 手番 | 入れ替えアイコン + `☗` / `☖` | 下記 |
| 成 / 不成 | `成` / `不成` の字 | 成 / 不成に対応する図像が無く、**字の方が短く読める** |
| 評価する | ラベルのまま（幅は md を境に変える） | **主操作をアイコンに畳まない**（押し間違えたくない側） |

- 🔴 **手番ボタンの記号は落とさない**（ユーザ判断）。このボタンは操作であると同時に
  「**今どちらの手番か**」という状態表示を兼ねている。手番を自由に入れ替えられる検討盤で
  記号を消すと、今どちら番なのかが画面から消える——**評価値の視点は手番側**（§2.3）なので、
  読み違いがそのまま数字の読み違いになる。
- 🔒 **アイコンのみのボタンは正方形**にして 44px 基準（[05](../05-analysis.md) §2.1）を守る。
  高さだけ 44px にしても**幅が潰れれば的は小さいまま**なので、高さと同じ幅を明示して
  内側の余白を消す。同じ行の「評価する」が伸びる幅（md 未満）では、アイコン側を縮まない設定にする
  （さもないと伸びる側に押されてアイコンボタンから潰れる）。
- 🔒 **`aria-label` を必ず付ける**（ラベルが画面から消えるため）。`title` も残す。
  アイコンは `components/icons.tsx` に足して 1 か所に集める（既存の chevron と同じ流儀）。
- ⚠ **「成 / 不成」は条件付きで出入りする**ので、その分の幅が動いても崩れない組み方にする。
- ⚠ **320px では折り返して 2 行になる**（許容）。パネルはコントローラー行より**下**なので、
  折り返しても盤・◀ ▶ は動かない（PR #105 の教訓）。

#### 追記: 実測して確定した 3 点（2026-08-29・実機確認）

390px の実機と 1280px のデスクトップで見て、ユーザが次のとおり決めた。

- **「評価する」の幅は md を境に変える**（md 未満は残り幅いっぱい / md 以上は内容ぶん）。
  - 並べた 2 案は**モバイルでは差が 10px しか出なかった**（390px で 96px と 86px。アイコン 3 つと
    「検討中」バッジで幅がほぼ埋まっているため）。一方**デスクトップでは残り幅いっぱいが
    534px の帯**になる（棋譜詳細の行幅 736px）。
  - つまり残り幅いっぱいは「**狙いだったモバイルでは効かず、デスクトップだけ壊れる**」形だった。
    それでもモバイル側で残すのは、**「成」の出入りで空く幅を吸って行の見え方が安定する**利点が
    害なく取れるため。**見比べ用の props と 2 ケースは落とす。**
- **「棋譜に戻る」も枠付き（`btn-outline`）にする。** アイコンのみになった以上、

- **手番ボタンは記号（`☗` / `☖`）のままで確定。** ⚠ ただし 390px では**塗り分けが判別しづらかった**ので、
  記号を**枠内で読める大きさ**にする。**字（先 / 後）を足すのではなく今ある記号を読めるようにする**

### 検討中は候補手一覧を隠し、評価値グラフのクリックを無効にする（2026-08-29）

実機で見つかった。検討中（盤を動かして「検討中」バッジが出ている状態）でも、盤の下には
**棋譜側の手数に紐づいた候補手一覧と評価値グラフ**がそのまま残っていた。

- 初期局面から ▲８八角×２二 と動かしても、下の候補手は**初期局面のもの**のまま
  （出所は棋譜側の `moveIndex - 1` の解析結果で、検討状態とは無関係）。
- 🔴 **候補手の「分岐を進む」を押すと「検討中」バッジが消えた** = **検討セッションが黙って破棄される**。
  検討盤は「棋譜側が今どこを見ているか」（手数 + 分岐位置）が変わったら検討を捨てる作りなので、
  分岐操作がそれを踏む。**評価値グラフのクリック（手送り）でも同じことが起きる。**
- これは [12](../12-position-lab.md) §3.1 の「**検討を抜けるのは『棋譜に戻る』を押したときだけ**」に反する。
  出口が 2 つ余計に開いていた。

**決定**（ユーザ判断）:

- **候補手一覧は検討中は出さない。** 盤の局面と対応しない候補手を同じ画面に置くと、
  **どの局面の話なのか読めなくなる**。出口を塞ぐだけなら分岐ボタンの無効化でも足りるが、
  そもそも噛み合っていない情報なので隠す方を採った。
- **評価値グラフは出したまま、クリックによる手送りだけ無効にする。**
  グラフは「棋譜全体の評価値の推移」であって**現在局面に紐づく主張が弱く**、検討しながら見る
  価値がある。⚠ 現在位置マーカーは棋譜側の手数（＝検討の起点）を指したままでよい。
  押せないことは**薄さで示す**に留める（目立たせすぎない）。
- 🔒 **検討中かどうかの出所は 1 つに保つ。** 検討状態は検討盤（`StudyBoard`）の中にあるので、
  棋譜側（`ShogiBoard`）に同じ state をもう 1 つ持たせない。候補手・グラフは
  **スクロール領域（sticky グループの外）**にあって既存の `children` の位置には置けないため、
  **検討盤に「操作パネルより下」を描くスロット（`footer`）を足し、`StudyControls` を渡して**
  出し分けを検討盤側の状態だけで決める形にした。
  ⚠ sticky グループを作る `div` も検討盤側へ移した（`groupClassName`）——`footer` がグループの
  **外**に出る必要があるため。DOM の構造とクラスは変えていない。
- ⚠ 検討中に候補手が消えると `CandidateList` はアンマウントされるので、**開いていた読み筋
  （`details`）の開閉と「もっと見る」の状態は失われる**。「棋譜に戻る」で戻ったときは
  閉じた状態から始まる。これは許容（棋譜側の手数を動かしたときも同様に閉じる作りになっている）。

### 「成にする」を常時表示 + 無効化にし、打った駒も成らせられるようにする（2026-08-29）

**決定 1: 条件付き非表示をやめ、常に出して無効にする**（ユーザ判断「操作版のレイアウトがズレるので、
非表示にするのでなく無効の方が良い気がします」）。
出し入れしていると**成れる手かどうかで操作行の幅が変わり、他のボタンの位置がズレる**——
[05](../05-analysis.md) §2.1 の「連打中に指の下の要素を入れ替えない」に反する。
無効になるのは「検討していない / 直前が編集 / 成れない駒（金・玉）/ 元から成っている駒を動かした手」。
`title` に条件を書く。

**決定 2: 駒打ちの直後も成らせられる**（ユーザ判断「自由編集できるならあってもいい気がします」）。
これまで弾いていた理由は **USI の駒打ち表記に `+` を付けられない**ことだけだった。
しかし検討盤は**合法性を問わないフル編集**（[12](../12-position-lab.md) §2.5 / §3.2）で、
「５五に成銀がある局面」はエンジンにも渡せる正当な局面。**表記の都合で局面編集を禁じない。**
実装は打ち直しではなく**盤に乗っている駒の成りを反転する**（持ち駒は増減しない）。

#### `StudyStep.move` の 3 つの用途を見直した

`move`（この段に至った USI）には **(a) 盤の直前手の強調 (b) 成 / 不成の指し直し (c) 直前の手の採点**の
3 つがぶら下がっていた。打った駒を成らせた段は `move` が `B*5e` のままなのに局面には成駒が乗る
——**`move` を適用した局面と一致しない**段が初めて生まれる。用途ごとに要求を確かめると:

| 用途 | 一致が要るか |
|---|---|
| 盤の直前手の強調 | **要らない**（移動先は同じ） |
| 成 / 不成の指し直し | **要らない**（むしろこの段が対象） |
| 直前の手の採点 | 🔴 **要る**。「1 手前の最善」と「その手を指した結果」を突き合わせるので、局面が `move` の結果と違えば**比較そのものが嘘**になる |

→ **分かれるのは採点だけ**なので、`StudyStep` に**真偽値 1 つ（`faithful`）**を足して採点の可否だけを
分けた。**state を無闇に増やさない**（用途ごとに別フィールドを持たせる案は、上の表のとおり
2 つは同じ条件なので過剰）。⚠ 不成へ戻せば `faithful` は true に戻り、また採点の対象になる。

#### 追記: 採点の要求は主の表示をブロックしない（2026-08-29・レビュー `OCL-BE4CEA52` 対応）

主（現在局面）と副次（1 手前の局面）を `Promise.all` で**揃えて待って**いたため、
**主が返っていても副次が返るまで画面が「評価中」のまま**だった。副次はキュー待ちや長い探索で
大きく遅れうるので、上の「**副次が失敗・busy・中断でも主は必ず出す**」を満たしていない
（副次が応答しなければ主が永久に出ない）。

→ **2 本は同時に投げるが、待ち方を分ける。** 主が返った時点で `done` を表示し、
採点は後から `grade` として追記する。追記の前に**世代（token）を再確認**し、さらに
**今出ている状態が `done` のときだけ**足す（`stale` や新しい評価へ移っていたら触らない）。

⚠ **発行の順も効く**（レビュー `OCL-17AFF653`）。要求は**呼んだ順に POST が出る**ので、
副次を先に呼ぶと**評価キュー（有限。§2.4）の最後の 1 枠を副次が取り、主が 503 になる**——
「採点は進んでいるのに主は『キューが一杯』」という**優先順位の逆転**が起きる。
→ **主の要求を先に発行してから副次を発行する**（同時実行は保ったまま、await の順は主が先）。


### 局面評価 API を非同期にする（long-poll の撤回・2026-08-29）

**本番で踏んだ**: 検討盤の「評価する」を押すと**1 回目は「サーバーに接続できません」**になり、
**もう一度押すと評価が出る**。dev では起きない。

切り分けの結果:

1. **前段が 504 を返していた。** 本番は server の前段にタイムアウトを持つ層が複数段あり、
   その期限は server の期限（`POSITION_EVAL_QUEUE_TIMEOUT_MS` + `POSITION_EVAL_RUN_TIMEOUT_MS`・
   最大 240 秒）よりずっと短い。**エンジン評価が終わる前に接続が切られていた。**
2. **2 回目で出る理由**: server は接続が切れても計算を続け、結果をキャッシュに載せる。
   だから押し直すと即答になる。**成功しているのに失敗して見えていた。**
3. **文言まで嘘をついていた**（下記）。

#### 決定 1: POST は受け付けて即座に返し、結果は別リクエストで取りに行く

[12](../12-position-lab.md) §2.4 の **long-poll（「結果が出るまで待って返す」）を撤回する**
（元の決定は 2026-08-20）。POST は `202` + `jobId` を返し、GET `/api/positions/evaluate/:jobId` で
取りに来る。クライアントはポーリングし、**画面の状態は `loading` のまま**（表示は途切れない）。

**却下した案**: クライアントが 1 回の HTTP を前段より十分短く打ち切り、同じ内容で投げ直す。
server はキーごとにジョブを相乗りさせるので二重計算にはならず、修正は web だけで済む。
しかし「**クライアントの 1 回あたりの予算 < 前段のタイムアウト**」という**不等式に依存する**。
前段の設定値は server 側から確かめられず将来も変わりうるので、**崩れたら同じ事故がまた起きる**
（しかも「成功しているのに失敗して見える」という気づきにくい形で）。
→ **1 往復を短くしてしまえば、どの層が何秒で諦めるかは問題にならない。**

**取得の形は 2 案あった**。(a) ジョブ ID、(b) 同じ body を投げ直すとキーで引ける。
(b) は ID を持たなくて済み冪等だが、**「まだ出ていない」と「新しいジョブを作った」が同じ応答に
見え**、キューが一杯のときの意味も曖昧になる。**(a) を採る**——ただし POST は同じキーの
既存ジョブに相乗りして**同じ `jobId` を返す**ので、(b) の冪等性も実質的に得ている。

🔴 **server の待ち時間は縮めない。** 期限が来ると `settleJob` がジョブを消すので、縮めると
押し直しても最初からやり直しになる。**非同期化してもエンジンの思考時間は変わらない。**
代わりに**完了した結果の寿命**を設計した（`jobId` で 5 分・キーでは LRU 200 件）——
**結果を取りに行く前に消えると、永久に取れない要求が生まれる**。
消えていた場合（404）は `pending` と区別し、クライアントは**投げ直す**（画面に失敗は出さない）。

#### 決定 2: 本文のパースはステータス判定より後ろでやる

`requestPositionEval` は `await res.json()` が**ステータス判定より前**にあったため、504 の本文
（前段が返す HTML）でパースが落ちて `catch` に入り、**すべて「サーバーに接続できません」**に
なっていた。本来 `サーバーエラー (504)` と出るべきものが出ず、**原因が画面から分からなかった**。

→ パースをステータス判定の後ろへ移し、パースに失敗しても落ちないようにする。
「サーバーに接続できません」は**本当に fetch が失敗したときだけ**に絞る。
⚠ **`AbortError` かどうかで「誰が止めたか」を判断しない**——自前の打ち切りも呼び出し側の中断も
同じ形の例外になる（`AbortSignal.timeout()` に至っては `TimeoutError`）。**打ち切ったことは
フラグで持つ。**

⚠ **`EvalRequestTracker.begin()` をポーリングで呼ばない**（`OCL-AED22F46`）。`begin()` は
`cancel()` 経由で世代を進めるので、呼ぶと**同時に走っている採点用の副次要求を自分で捨ててしまう**。
ポーリングは `requestPositionEval` の内部に閉じ込め、**per-attempt の `AbortController`** を使う。
### 表示サイズを設定可能にし、操作ボタンの 44px 基準に「選択制の例外」を設ける（2026-09-01）

**実使用で出た**: モバイルの縦画面（実機 390x844）で盤を横幅いっぱいまで大きくすると、
**盤の下の評価値・読み筋・候補手が画面の外へ押し出されて読めない**。盤を大きくしたこと
（[12](../12-position-lab.md) §3.3・2026-08-28 の 40px 拡大）自体は意図した決定で、
撤回するような失敗ではない——**縦のスペースの奪い合いが顕在化しただけ**。

#### 決定 1: 表示サイズを 3 つの 2 択にする（既定はすべて現状維持）

盤 / 操作ボタン / 評価値グラフを `/settings` から切り替える（[05](../05-analysis.md) §2.5）。

- **一方に決め打たない。** 3 つとも「盤・操作の見やすさ」と「評価値・読み筋の見やすさ」の
  奪い合いで、**モバイルの縦画面では両方を同時に満たせない**。どちらが欲しいかは端末の高さと
  その時の使い方（盤を眺めているのか、手を送り続けているのか）で変わる。
  → **悪手判定のしきい値（[05](../05-analysis.md) §2.3）を設定可能にしたのと同じ筋**で、
  **根拠が置けないからこそ選べるようにする。**
- 🔒 **既定はすべて現状維持。** 設定を触らなければ見た目は変わらない。
  設定を足すこと自体が既存の見え方を動かす変更になってはいけない。
- 🔒 **盤の縮小は算出式を書き換えず、結果に率を掛ける。** [12](../12-position-lab.md) §3.3 の
  「使える幅と高さから算出する」を壊さないため。
  ⚠ **縦の予約ぶんを膨らませる形は却下**——予約は「盤と操作行が画面に収まる」ための見積もりなので、
  表示の好みで膨らませると**横画面でその保証が嘘になる**。
  ⚠ **頭打ちの上限にも率が掛かる形にする**——幅に余裕のある端末では上限側が効いており、
  上限を据え置くと**その端末だけ設定が何も変わらない**（実装時に気づいた）。
- ⚠ **具体的な縮小率・グラフの px 値は PRD に置かない**（[12](../12-position-lab.md) §3.3 と同じ理由。
  実装式と実機の見え方で詰めるもので、書けば誤った期待値として使われる）。
  代わりに**落としてはいけないもの**を仕様に書いた（グラフを縮めても視点ラベル・
  悪手 / 詰みマーカー・現在手の位置は残す）。
- ⚠ **保存は 1 キーにまとめ、読み込みは項目ごとに既定へフォールバックする。** 実際に踏みかけた——
  グラフの設定は盤・操作ボタンより後から足したので、**その項目を持たない保存値が既に手元にあった**。
  オブジェクト全体を捨てる作りだと**項目を 1 つ足すたびに既存の設定が全部リセットされる**。

#### 決定 2: 44px 基準に「利用者が明示的に選んだときだけ」の例外を設ける

レビュー指摘 `OCL-7DEFA2D8`（Medium）: `controlSize: 'compact'` は検討盤の操作ボタンまで 32px に
落とすが、[05](../05-analysis.md) §2.1 の 44px 基準は**盤マスだけを例外**としており、
**利用者の選択は例外として仕様化されていない**。

→ **実装が仕様に反しているのではなく、仕様が追いついていない**と判断し、PRD を更新した。

- **なぜ例外を認めるか**: 44px 基準を厳守した状態は、モバイル縦画面では
  「**押しやすいが読めない**」——的は大きいのに、その操作で何が起きたかを見るために毎回スクロールが要る。
  押しやすさと読みやすさのどちらを取るかは端末と使い方で変わるので、**利用者に選ばせる**。
  🔒 **決め打たないことが例外の本体**なので、**既定を 32px 側へ動かすのは例外の濫用**。
- **誤タップの手当ては 2 つだけ**: **間隔 8px は維持する**（的を縮めた上に詰めない）、
  **この行に取り返しのつかない操作を増やさない**（削除・再解析は ⋯ ドロップダウン側のままで 44px を保つ）。
- 🔒 **棋譜の操作ボタン行と検討盤の操作パネルは同じ設定で同時に切り替える。** 検討パネルは
  コントローラー行のすぐ上に並ぶので、別々に選べると**隣り合う行で的の大きさが食い違う**。
  **検討盤だけの設定は作らない。**

#### 却下: タップ領域だけ 44px に保って見た目を縮める

bot の対応案（透明なパディング・疑似要素・44px のラッパーで的を維持する）は**採らない**。

**その 44px は縦のスペースを消費し続ける。** 画面から消えるのは枠線だけで、
**評価値・読み筋は 1px も上がってこない**。この設定の目的は**縦を空けることそのもの**なので、
目的を果たさないまま基準との衝突だけを消す**辻褄合わせ**にしかならない。
⚠ 一見すると両立案に見えるため**繰り返し提案される**。却下の理由は
[05](../05-analysis.md) §2.1 の本文にも残した（リンク先に飛ばすと読まれないため）。

#### 盤マスの例外と操作ボタンの例外は別物

⚠ **根拠が違う。** 盤マスは **9 列 x 44px = 396px が iPhone 14 の 390px にも収まらない**という
**幅の制約から常に**基準を下回る（[12](../12-position-lab.md) §3.3）。操作ボタンは
**利用者が選んだときだけ**下がり、**既定では 44px を保つ**。
🔒 **盤の例外を根拠に「操作ボタンも既定で縮めてよい」とは読まない。** 片方を広げても
もう片方は広がらない。§3.3 の文言も「盤だけは例外」から「**盤マスは常時の例外**」へ改めた。

### 咎め筋の再生中も編集できるようにする（2026-09-01・2026-08-28 の「読み専用」を更新）

ユーザ指摘: 「自由編集の読み筋 3 種類を再生しているときは自由編集ができない。
基本的に自由編集は常にできる様にしたい」。

**2026-08-28 の判断を否定しない。** 当時の要求「手順と undo スタックの意味を保つ」は今も正しく、
「編集させない」はその要求を確実に満たす最小の答えだった。変わったのは**満たし方が他にも
あると分かったこと**:

> **PV の手は指し手そのものなので、そのまま手順へ 1 手 1 段で積める。**
> 積めば表示局面は手順の上の局面になり、以後の編集は普通の編集になる。

実装から見ても、再生の表示局面は既に `applyMove` を PV に順に適用して作っている
（[12](../12-position-lab.md) §3.2）。**確定して積む局面は、直前まで画面に出ていた局面と同一。**
別に計算し直す部分が無いので、ずれようがない。

- **確定の単位は 1 手 1 段**（まとめて 1 段にしない）。`StudyStep.move` の「盤上の手 1 本」という
  契約に、直前手の強調・成 / 不成の指し直し・採点がぶら下がっているため。◀ で 1 手ずつ戻れる。
- **引き金は「盤の状態を変えうる操作」**。⚠ **カーソル移動（◀ ▶ ≪ ≫）は引き金にしない**——
  画面は 1 手戻っただけに見えるのに手順が N-1 手伸び、**画面の動きと手順の伸びが一致しない**。
- **「評価する」は引き金にする。** 押すと候補手一覧が入れ替わり、再生していた読み筋が消えるので、
  確定しないと盤だけが根拠のない局面に取り残される。
- **確定すると評価結果は `stale` になり候補手一覧が消える。** §3.1 の「盤と対応しない候補手を
  同じ画面に置かない」が検討側の候補手に当てはまるため。戻り道はキャッシュ即答で安い。

**引き換えに差し出したもの**（承知の上で採る）:

- 再生が「触っても何も起きない安全な読み物」ではなくなる。うっかり盤を触ると手順が N 手伸びる
  （undo で戻せるが、戻した先で指せば redo 分は捨てられる）。
  → 緩和は**確定が見えること**に置いた。バッジが「読み筋を再生中」→「検討中」へ変わり、
  **盤はその場に留まる**。盤が動く前に確定が画面に出る。
- 確定と同時に咎め筋の文字列と候補手一覧が消える。読み比べながら指すことはできない。

#### 却下: 「ここまでを確定する」ボタンを足す

操作パネルは 1 行に収める決定（2026-08-29）があり 1 つ足すと折り返す。それ以上に、
**明示ボタンを置いても「押さずに盤を触ったとき」の振る舞いを別に決める必要が残り、同じ議論に戻る。**
「触ったら確定」を唯一の規則にすれば分岐そのものが消える。

#### 却下: 確定後も候補手一覧を残す（グレーアウト等）

`EvalState` の `idle` / `stale` を分けたときの決定（別の局面の値を画面に置かない・
[12](../12-position-lab.md) §2.6「値の出所を黙って混ぜない」）に正面から反する。
**失うのは往復 1 回だけ**（同じ SFEN はキャッシュから即答する）。

#### 後続候補: 再生中はコントローラー行の ◀ ▶ を「読み筋の手送り」に振り替える

一貫性はある（盤の下の矢印が 1 組になる）が、**同じボタンが状況で 3 通りに変わる**
（棋譜の手送り / undo / 読み筋の手送り）。§3.1 の表に 3 つ目の意味を足す判断は今回はしない。

#### 後続候補: `StudyStep` に手の出所（エンジンの読み筋 / 自分の手）を持たせる

手順を保存せずセッション内限定である今は、`move` の使い道 3 つ（強調・指し直し・採点）の
どれも出所を要求しない。状態を 1 つ増やす対価に見合わない。
⚠ 分岐ツリー・variations 保存（[12](../12-position-lab.md) §6）が来たら再考する。

### 「評価する」をコントローラー行に常設し、アイコン化する（2026-09-01）

ユーザ要望: 「普段の再生盤から常に『評価する』ボタンを表示しておくのがいい気がしてきました、
全部の評価が終わる前に差し込みで気になるところだけ評価したり、通常の読み筋表示中に（多分最後まで
進めてからが多いと思いますが）評価するボタンが押せたらいいなと。その場合、通常の操作版と同じ行に
評価するボタンを納めたいので、アイコン化するのも一緒にお願いしたい」。

それまで「評価する」は**検討中だけ**出す操作パネルのボタンだった（決定・2026-08-29）。
検討は「駒を動かした時点で始まる」ので、**解析済みの棋譜を眺めているだけでは押せなかった**——
差し込み評価（解析の合間に気になる局面だけ評価する）にはまず駒を動かして検討に入る必要があり、
要望が指す使い方と噛み合っていなかった。

- **段階的開示に反しない理由**: 段階的開示で隠していたのは**検討セッションが無いと意味を
  持たない操作**——戻る先が無い「棋譜に戻る」、指し直す直前手が無い「成 / 不成」。
  **評価は局面さえあれば意味が成立する**ので、同じ理由で隠す根拠が無い。
  🔒 **「検討中かの出所は 1 つ」の設計はそのまま保つ。** 評価の状態（`evaluating` /
  `grading`）も `BoardControls` に別に持たせず、`StudyBoard` の `StudyControls` から渡す
  （検討状態と同じ経路）。
- **引き換えに差し出すもの**: 「駒を動かすまで画面は今までと変わらない」がコントローラー行に
  関しては成り立たなくなる（ボタンが常に見える）。モバイルでは押すまで何が起きるか分からない
  時間ができる。
- **送り先の計算は変えない**（レビュー指摘の集積地に触らない）: `positionEvalTarget(shown)` は
  検討していないときは `session.cursor === 0` の局面（＝ `ShogiBoard` が渡す表示局面そのもの）を
  返すので、**棋譜再生中・棋譜側の読み筋（分岐）を辿っている最中でも計算をやり直す必要が無い**。
  `run()` の中身（token 管理・abort・主 / 副次の発行順・`accepts` の判定）には触らない
  ——`OCL-AED22F46` / `OCL-BE4CEA52` / `OCL-17AFF653` の集積地。変えたのは「呼べる場所」だけ
  （`StudyControls.evaluate` として公開し、コントローラー行からも呼べるようにした）。
- **棋譜側では直前の手の採点を出さない**: 採点の送り先（`lastMoveGradeTarget`）は
  `session.cursor < 1` で `null` を返し、棋譜再生中はカーソルが常に 0 なので**追加のコードを
  足さなくても自然にそうなる**。
  - 実手の損失は既に候補手一覧の見出しと評価値グラフに出ている（重複表示を増やさない）。
  - 未解析の棋譜で押すと、局面評価と採点の 2 本を同時に投げてエンジンの評価キュー
    （有限。[12](../12-position-lab.md) §2.4）を 1 押しで 2 枠使う——差し込み評価が重くなる。
  - 読み筋の中の「直前の手」はエンジン自身が示した手なので、採点しても意味を持たない。
- **棋譜側の候補手一覧は隠さない・置き換えない**（[05](../05-analysis.md) §2.2 の
  `CandidateList`）: 分岐（読み筋）の再生操作子がその一覧の中にあるので、隠すと**評価した局面から
  動けなくなる**——「読み筋を進めてから評価する」という要望そのものを壊す。結果、評価結果ブロックと
  候補手一覧が縦に並びうるので、**評価結果ブロックに「この局面の評価」の見出しを足す**
  （棋譜側の一覧は 1 手前の局面の候補手なので、どちらが何の話か読めるようにする）。
  🔒 **検討中と非検討時で見え方を分けない**——状態遷移のたびに見出しが出入りすると雑音になる。
- **検討中の操作パネルからは外す**（同じ操作の入口を 2 つ置かない）。パネルはバッジ + 棋譜に戻る +
  手番 + 成 / 不成になる。2026-08-29 の「ここだけラベルを残す」（主操作をアイコンに畳まない）は
  **撤回する**——当時は「操作パネルの中で主操作を目立たせる」ための判断だったが、主操作が
  コントローラー行の一員になった以上、他の 6 つと同じアイコン + `btn-outline` の流儀に揃える方が
  筋が通る。撤回であって、44px 基準やアイコン化そのものへの反対ではない。
- **見た目**: アイコンは `cpu-chip`（虫眼鏡は情報行の「この局面を探す」と同じ図像になり、
  グラフは真下の評価値グラフと紛れるため避けた）。md 以上はラベル「評価」を添える
  （情報行の「この局面を探す」と同じ流儀）。枠は他の 6 つと揃える（`btn-outline`。1 つだけ
  塗ると手送りの行で主従が入れ替わる）。`aria-label` は固定文言、`title` は
  棋譜側 / 検討中で採点対象あり / 評価中の 3 段で変える（純関数 `lib/evaluateButton.ts` に切り出し）。
- **押せない理由をアイコンに背負わせない**: 評価中だけスピナー + `disabled` + `aria-busy` にし、
  キュー満杯・失敗・不正局面ではボタンを押せるままにする（理由は評価結果ブロックの alert が言う）。
  「棋譜の自動解析が走っている間は押せない」も作らない——差し込み評価が動機そのものなので、
  それを妨げる disabled 条件を足してはいけない。
- **手送りで局面が変わったら結果は `idle` に戻す**（黙って消す）。`stale`
  （「盤が変わったので前の評価は消した」）にはしない——手送りすれば棋譜側の情報行と候補手一覧が
  戻るので「何も無い画面」にはならず、連打のたびに文言が出入りするのが雑音になる。
  ⚠ 検討中の編集（盤を触る等）で局面が変わったときは、従来どおり `stale` を出す
  （既存の `evalStateAfterPositionChange` の規則のままで変えていない）。

#### 却下: ボタンの寸法を差し替えで変える

評価中はアイコンをスピナーに差し替えるが、md 以上のラベル「評価」は残したまま・アイコン /
スピナーは同じ `size-5` の枠に収めた。**差し替えで行が動く**（ラベルごと消す・ボタン全体を
縮める）案は採らない——連打中に指の下の要素が動く、という prd/05 §2.1 の教訓と同じ理由。
