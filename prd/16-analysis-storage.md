# 16. 解析結果の保存形式

本章は、エンジン解析の結果（[03](./03-data-model.md) §3・§4 の `moveAnalyses` / `candidateMoves`）を
**1 棋譜の 1 回の解析につき 1 行**に詰め直す設計を定める。
[14](./14-multi-user.md) §6 の容量見積もりの前提を置き換える。

> **設計確定・未実装**（2026-10-07）。決定の経緯は [決定ログ](./_grilling/decisions.md)「解析結果の保存形式」。

---

## 1. 目的とスコープ

### 目的

- 一般公開（[14](./14-multi-user.md)）で棋譜と解析結果が人数ぶん溜まっても、単一の小規模 VPS のディスクとバックアップに収める
- 🔒 **何も捨てない。** 候補手・評価値・深さ・読み筋は今と同じだけ持つ（[14](./14-multi-user.md) §1「解析結果はグラフ用も詳細も永続保存する」を保つ）。
  減らすのは**保存の形**から来る無駄だけ

### 方針

- 🔒 **検索・集計に使う値は列に出し、表示にしか使わない値は 1 つの `jsonb` に詰める。**
  詰めた側は索引が効かない（範囲の条件は全行の展開になる。§3.3）ので、SQL で棋譜をまたいで引く値は必ず列にする
- **所有者と一般ユーザーで同じ表・同じコード経路**（[14](./14-multi-user.md) §5.1）。違いは MultiPV の本数だけ

### スコープ外

- 詳細検討（[14](./14-multi-user.md) §5.3）の保存。局面（SFEN）単位でユーザーごとに持つ別の表で、本章の対象ではない
- エンジン・評価関数を切り替えたときの扱い（置き換えるか、並べて持つか）。§8 で保留とする
- 局面検索の索引（`kifuPositions`）。形は変えない（序盤に絞る案は §8）

## 2. 今の形と無駄（実測・2026-10-07）

今は「局面ごとに 1 行（`moveAnalyses`）＋ 候補手ごとに 1 行（`candidateMoves`）」で、110 手の棋譜を MultiPV 3 で解析すると 400 行を超える。

| 形 | 1 局面あたり | 110 手の棋譜 |
|---|---|---|
| 今（行ごと・索引込み） | ≒ 1〜2KB | ≒ 120〜230KB |
| 1 棋譜 1 値・MultiPV 3（`jsonb`・lz4） | 150〜210B | ≒ 17〜23KB |
| 1 棋譜 1 値・MultiPV 1（`jsonb`・lz4） | 50〜70B | ≒ 6〜8KB |

- 測り方: dev の 8 局（読み筋の平均 11 手）を棋譜ごとに集約して一時表に入れ、`pg_column_size` で圧縮後の大きさを見た。
  幅は詰め方（`jsonb` かテキストか）による。テキストの方が 3 割ほど小さいが、SQL から中を読めなくなるので取らない（§3.3）
- 今の形の大半は**行ごとの固定コスト**（行ヘッダ・索引の項目）と、**全局面の行に繰り返し入っている来歴**から来る。
  [14](./14-multi-user.md) §2 が「gzip がほとんど効かない」としたのはこのためで、1 局ぶんを 1 つの値にまとめると圧縮が効くようになる

## 3. `kifuAnalyses`

```
kifuAnalyses（1 棋譜の 1 回の解析で 1 行）
├── kifuId: FK → kifus.id (CASCADE)  PK
├── fullCount: int notNull            -- 先頭から何局面までが full か（§4.2）
├── runs: jsonb notNull               -- submit 1 回ごとの来歴と時刻（§3.1）
├── minMateSente: int?                -- 先手番の局面で、最善が「自分が N 手で詰ませる」だった最小の N（§3.2）
├── minMateGote: int?                 -- 後手番の局面で同上
├── detail: jsonb notNull             -- 局面ごとの候補手（§3.1）。列の圧縮は lz4
├── createdAt: timestamp
└── updatedAt: timestamp              -- トリガーで更新（[15](./15-postgres.md) §3.4）
```

- 1 棋譜に 1 行（エンジンの切り替えを保留している間は、主キーは `kifuId` だけ。§8）
- **来歴と解析時刻は submit 1 回ごとに 1 件**持ち（`runs`）、各局面はどの submit で書かれたかを指す。今は全局面の行に同じ値が重複しているが、値が変わるのは submit の境目だけ
- 解析済みの局面数は `jsonb_array_length(detail)`（今の `analyzedCount`）

### 3.1 `detail` の形

```
detail[moveNumber] = [run, 候補手の配列（rank 順。先頭が rank 1）]
候補手 = [move, scoreType, scoreValue, depth, pv]
runs[run] = { profile, engineName, movetimeMs, targetDepth, multiPv, at }
```

- `moveNumber` の意味・`scoreType` / `scoreValue` を手番視点のまま持つこと・`pv` の利用先は今と同じ（[03](./03-data-model.md) §3・§4）
- 配列の添字が `moveNumber`、候補手の位置が `rank` を兼ねるので、両方とも値としては持たない
- `run` は `runs` の添字。**局面ごとの段階・来歴・解析時刻は、その局面を書いた submit の値**になる（今の局面ごとの `profile` / `engineName` / 解析設定 / `createdAt` と同じ情報を、重複なしで持つ）。
  `at` は submit のトランザクションの時刻（今の `createdAt` の既定値 `now()` と同じく、1 回の submit の中で揃う）
- `runs` は追記だけ。上書きで指されなくなった件は次の書き込みで詰めてよい（実装判断）
- 🔒 **CHECK で形を守る**（配列であること）。中身の検査は submit の zod で行う（[14](./14-multi-user.md) §6.2 の上限もここで掛ける）

### 3.2 列に出す値

今のコードで、**棋譜をまたいで 1 手ごとの値を SQL で引いている箇所は 1 つだけ**——一覧と分析ページが共有する
「自分の手番で最善が `limit` 手以内の詰み」の述語（`selfMateExists`。[09](./09-analytics.md) §3.1・§6）。

- `minMateSente` / `minMateGote` を**書き込み時に計算して持てば**、述語は `minMateSente <= limit` になる。
  `limit` を画面で変えても列はそのまま使える
- **解析済みの局面だけ**から計算する（途中まで入った棋譜でも、入っている局面ぶんで値を持つ。今の述語と同じ）
- 🔴 **`detail` を書き換えたら同じトランザクションで計算し直す。** 計算は純粋な関数にしてテストで固定する
- **列を足すときの手順**: 棋譜をまたいで 1 手ごとの値を新しく検索したくなったら、列を足して既存の行ぶんを一括で埋める
  （戦型ラベルの一括再判定と同じ運用。[01](./01-domain.md) §6.4）

### 3.3 `jsonb` にする理由と限界

- `jsonb` なら、いざとなれば中身を SQL で読める（`detail -> 42`・jsonpath）。一度きりの調べものや、列を足す前の試算に使える
- ⚠ **索引は効かない**（GIN が効くのは「含む・等しい」だけで、「10 手以内」のような範囲には効かない）。
  中身を条件にした SQL は全行の展開になる（所有者の 700 局で十数 MB）。**画面の常用の経路には使わない**
- 評価値の配列を `int[]` で別の列に出す案は、今は取らない。棋譜をまたいで評価値を引く処理が無いので、出しても使う箇所が無い

## 4. 書き込み

### 4.1 チャンク submit

- submit は**行を `FOR UPDATE` で取り**、`detail` を読み、チャンクぶんを置き換え・追記して書き戻す（1 トランザクション）
- チャンクの局面は**今の末尾まで**に収まること（重なりは上書き、末尾を越えた飛びは 400）。今の「`UNIQUE(kifuId, moveNumber)` による upsert」
  と同じく、**再送は同じ結果になる**
- `0 <= moveNumber <= usiMoves.length` の検証、完了の確定（段階ごとの件数が `usiMoves.length + 1`）は今と同じ（[03](./03-data-model.md) §3）
- Postgres の更新は値を丸ごと書き直すので、チャンクごとに 1 局ぶん（数十 KB 以下）を書き直す。量として問題にならない

### 4.2 段階（quick / full）

- full は 0 から順に上書きするので、**full の局面は常に先頭からの連続区間**（[05](./05-analysis.md) §1.1d）。`fullCount` はその長さで、`runs` の段階と常に一致する
- 🔴 **`fullCount` の連続性は submit の受理条件で守る**:
  - **full のチャンク**は先頭の局面が `fullCount` 以下であること（重なりは再送として上書き）。越えていれば 400（飛ばした局面を full として数えないため）。
    受理したら `fullCount = max(fullCount, チャンクの末尾 + 1)`
  - **quick のチャンク**は先頭の局面が `jsonb_array_length(detail)` 以下であること。`moveNumber < fullCount` の局面は捨てる（段階の後退防止）。`fullCount` は変えない
- full の再開位置は `fullCount`、quick の再開位置は `jsonb_array_length(detail)`

### 4.3 作り直し

- `reanalyze` と動画解析の差し替えは**行を消す**（今の `moveAnalyses` の DELETE と同じ位置）。前世代の全消去が 1 箇所で済むのは今と同じ

## 5. 読み出し

| 処理 | 今 | 本章 |
|---|---|---|
| 棋譜の詳細（`GET /api/kifus/:id`） | 局面と候補手の行を読んで組み立てる | 1 行を読んで展開する。**応答の形は変えない** |
| 一覧の詰み見逃し・分析の取りこぼし | 候補手の行を索引で探す（`candidate_moves_score_idx`） | `minMate*` の比較（§3.2）。索引は不要 |
| 局面の再利用（[12](./12-position-lab.md) §2.6） | `kifuPositions` → 解析の行（full かつ 3 本揃い）→ 候補手 | `kifuPositions` → 行（`moveNumber < fullCount`）→ `detail -> moveNumber`（候補手が 3 本揃っているものだけ。今と同じ） |
| 出題の抽出（[13](./13-drills.md)） | 1 棋譜ぶんの full の行 | 1 行の先頭 `fullCount` 局面 |
| 解析の進み具合 | 行の件数 | 配列の長さと `fullCount` |

- **局面の再利用で返す解析時刻**は、その局面を書いた submit の `at`（今の局面ごとの `createdAt` と同じ意味）。
  行の `updatedAt` は使わない——別の局面の submit で進むので、局面ごとの新しさを表さない
- `candidate_moves_score_idx`（[09](./09-analytics.md) §6.2）は表ごと無くなる

## 6. 容量の見込み

| 部分 | 所有者（MultiPV 3） | 一般ユーザー（MultiPV 1） |
|---|---|---|
| 棋譜本体 | ≒ 6KB | ≒ 6KB |
| 解析（本章） | ≒ 20KB | ≒ 8KB |
| 局面検索の索引（[14](./14-multi-user.md) §6.3） | ≒ 36KB | ≒ 36KB |
| **合計** | **≒ 60KB** | **≒ 50KB** |

- 一般ユーザーの上限 3,000 局（[14](./14-multi-user.md) §6.2）で 1 人 ≒ 150MB（今の形の見積もり 300MB の半分）
- 解析が小さくなった結果、**いちばん大きいのは局面検索の索引**になる。次に効く手は索引を序盤に絞ること（§8）

## 7. 既存データの移行

- **1 本のマイグレーションで行う**: `kifuAnalyses` を作り、既存の行を SQL で集約して詰め、`minMate*` を計算し、旧 2 表を消す。
  Postgres は DDL もトランザクションに入るので、**途中で失敗したら丸ごと戻る**（[15](./15-postgres.md)）
- `fullCount` は棋譜ごとの `profile='full'` の行数。⚠ **full が先頭からの連続区間になっていない棋譜があれば移行を止める**（前提が崩れているので、黙って詰めない）
- `runs` は、局面の行を `(profile, engineName, 解析設定, createdAt)` の組で束ねて作る。**来歴も時刻も失わない**（段階の中で設定が割れている棋譜も、組が分かれるだけ）
- `minMate*` の計算は SQL と TS の 2 か所に書くことになる。**移行後に TS の計算と突き合わせる検査**（`test:db`）で揃っていることを確かめる
- 戻し方は前日のバックアップと旧イメージ（[15](./15-postgres.md) の切り替えと同じ）。⚠ 旧イメージは新しい表を読めない

## 8. 後に回すもの

- **エンジン・評価関数の切り替え**（[14](./14-multi-user.md) §5.5 の持ち込みを含む）: 置き換えるか、並べて持つかは保留。
  並べるなら主キーに解析の識別（エンジンと評価関数）を足し、一覧・分析が「どの解析を使うか」を選べるようにする。
  🔒 **1 つの棋譜の中で別のエンジンの結果を混ぜない**（評価値の尺度が違い、悪手判定の閾値が合わない）——どちらを選んでも 1 行は 1 エンジン
- **詳細のキャッシュ化**: 容量が足りなくなったら、古い棋譜の `detail` を空にして要約（`minMate*` など）だけ残す運用を足せる。
  消えた局面は開いたときに計算し直す。⚠ 計算し直した結果は元の解析と一致しない（同じエンジンでも揺らぐ。本番を 2 回回した悪手判定の一致は 85%）
- **局面検索の索引を序盤 N 手に絞る**（[14](./14-multi-user.md) §8）

## 9. 段階と残る論点

### 段階

1. 本章の PRD（この PR）
2. スキーマとマイグレーション・書き込み・読み出しの差し替え（1 本の PR。応答の形を変えないので web は触らない）
3. 本番への反映（マイグレーション → server の入れ替え）

### 残る論点

- `detail` の 1 局面の候補手を、配列（本章）にするかキー付きのオブジェクトにするか。配列の方が小さいが、読み手は位置で意味を知る必要がある。実装時に容量を見て確定する
- チャンク submit の行ロックと、一般ユーザーのブラウザ解析（[14](./14-multi-user.md) §5.1）が同じ棋譜を同時に送る場合の扱い（今の世代 `analysisRevision` で足りるかを実装時に確かめる）
