# kifu-vision（実験）

将棋アプリの録画から**盤面の変化を読み取って棋譜（USI 手列）を復元する**実験パッケージ。
取り出した手列は `shared` の戦型判定やエンジン解析に載せることを狙っている。

> ⚠ **実験。** 素材（動画・切り出したフレーム・テンプレートの素材）は追跡しない
> （`data/` は `.gitignore` 済み）。手元の素材でしか再現できない。
>
> **いまの到達点**: レイアウトが固定された将棋アプリの録画 3 本・計 7 局について、
> **各局が初期局面から終局まで 1 本の手列として繋がり、通しの再生で指摘がゼロ**。
> 独立した検算として、**再生した盤の駒の色（成駒は朱・生駒は黒）と駒種を映像と
> 全マス突き合わせる監査**も 3 本すべてで食い違いゼロ。
>
> 🔒 **ただし満点は必要条件であって十分条件ではない。** 成らずと成り、打ちと移動は
> どちらも合法なので、**再生では割れない誤りが残る**（下記「残っていること」）。

## なぜテンプレート照合で足りるのか

実物の将棋盤を撮った写真から局面を読む研究は、輪郭検出・線分検出・射影変換に加えて
駒の分類に CNN を使うのが普通である。**それはカメラで撮るからで、対象がアプリの
画面出力なら事情が変わる。**

- 盤の位置とマスの大きさが**動画をまたいで一定** → 1 度測った定数を使い回せる
- 同じ駒は**毎回ほぼ同じ画素で描かれる** → 照合で分類できる
- 射影変換も照明補正も要らない

結果として依存は `ffmpeg` だけで済み、画像ライブラリも機械学習も使っていない。

## 組み立て

| ファイル | 役割 |
|---|---|
| `src/geometry.ts` | 盤の位置とマスの大きさ。持ち駒が並ぶ帯の座標も |
| `src/frame.ts` | ffmpeg から生の画素を受け取る。1 枚取り／全編を流す／マスの平均色だけ流す。色が要るときは `yuvj444p`（Y が `gray` と完全一致する） |
| `src/occupancy.ts` | マスに駒があるか（輝度の散らばりで判定） |
| `src/template.ts` | 駒テンプレートの生成と NCC 照合 |
| `src/recognize.ts` | 盤面画像 → 駒の配置 |
| `src/moves.ts` | 配置の差分 → USI の手。`applyMove` による検算 |
| `src/legality.ts` | 駒の動きとして有り得るか（合法手生成器ではない）。成れる位置かも |
| `src/ink.ts` | 駒字の**色**。成駒は朱・生駒は黒（`金`⇔`全` を形ではなく色で割る） |
| `src/sanity.ts` | 配置が将棋として成立しているか。偽の駒の除去 |
| `src/solve.ts` | 読めなかったマスの駒種を手の整合性から逆算 |
| `src/calibrate.ts` | 盤の格子を動画ごとに測り直す。駒の絵の位置で詰め直す |
| `src/template-store.ts` | テンプレートの保存と読み込み（寸法が違えば引き伸ばして合わせる） |
| `src/movegen.ts` | その局面で指せる手を全部並べる |
| `src/replay.ts` | 書き出した棋譜を初期局面から通しで再生して確かめる |
| `src/orientation.ts` | 画面の下が先手か後手かを 1 手目から決め、棋譜を実際の先後に直す |
| `src/candidate.ts` | 候補手と読みを突き合わせ、いちばん整合する手を選ぶ |
| `src/tracking.ts` | 盤面だけでなく持ち駒と手番も追う |
| `src/montage.ts` | テンプレートを並べて 1 枚の絵にする（目視で確かめるため） |
| `src/segments.ts` / `src/events.ts` | 局面が変わらない区間の検出（現在は使っていない。下記） |

実行は `extract-simple.ts` が主。`probe-*.ts` は調べもの用。

```
pnpm --filter kifu-vision exec tsx extract-simple.ts <動画パス> [開始秒] [終了秒] [間隔秒]
pnpm --filter kifu-vision exec tsx check-kifu.ts <棋譜 json> ...   # 書き出した棋譜を検査する
pnpm --filter kifu-vision test
```

`ffmpeg` のスレッド数は `KIFU_VISION_THREADS`（既定 4）で変えられる。

## 分かったこと

### 駒の有無は完全に分かれる

マス内側の輝度の**標準偏差**を見ると、空マス 2〜9 / 駒あり 51〜71 と 2 山に割れ、
間に 40 以上の隙間があった。盤の背景演出で明るさの水準は動くが、標準偏差は
水準に依らないので影響を受けない。

### テンプレートは外から用意しなくてよい（が、走査のたびに起こすのはやめた）

平手初期局面が映るフレームさえ見つかれば、そこに並ぶ 40 枚の正解ラベルは
初期配置から自明なので、生駒 8 種 × 2 向きが自動で揃う。

🔒 **ただし「起こせる」ことと「走査のたびに起こす」ことは別である。**
毎回起こすと**どのフレームを引くかで出来が変わる**——対局開始の演出が乗った
フレームを引くと、その動画の全編が静かに劣化する（下記「残っていること」の
解決済み項目）。いまは **一度きれいに採って資産として持ち、走査は保存済みを正典に読む**。
自動生成できる性質は残してあるので、**保存済みに無い駒種は今までどおり動画から補える**
（＝未知の駒デザインの動画でも、生駒だけで今までと同じように動く）。

成駒は初期局面に無いが、**読めなかったマスに駒種を総当たりで割り当て、
ちょうど 1 手で説明が付く割り当てを探す**ことで確定できる（`solveUnknowns`）。
画像ではなく論理で決まるラベルなので信頼でき、そのままテンプレートに加えられる。

⚠ ただし**候補を絞らないと必ず曖昧になる**。角が敵陣に入る手は、移動先を「角」と
置けば成らず、「馬」と置けば成りとして、どちらも 1 手で説明が付いてしまう。
「まだ覚えていない駒種」に候補を限ると一意に定まる。

逆算は 2 段階で試す。まず未学習の駒種（＝成駒の学習）、駄目なら全駒種。
**駒を動かす瞬間マウスは必ず盤上にあり、しかも移動先の上にあることが多い**ので、
読めない駒が成駒とは限らないため。全駒種で曖昧になれば null が返るだけなので、
誤って覚えることはない。

### 合法手生成器は要らない

1 手で変わるマスは高々 2 つなので、差分の形から手が決まる。

```
移動（取らない）: 移動元が空になり、移動先が埋まる
移動（取る）    : 移動元が空になり、移動先の駒が入れ替わる
打ち            : 移動先が埋まるだけ
```

正しさは `shared` の `applyMove()` を適用して次の配置と一致するかで確かめる。

⚠ **`applyMove` の検算だけでは足りない。** あれは「その手を指せばその配置になるか」
しか見ないので、認識がずれて生まれた「銀が届かない距離を飛ぶ」ような手も通る。
駒の動きの側からも弾く必要がある（`legality.ts`）。

### 変化の検出に凝る必要は無かった

「盤面が変わった瞬間」を安く見つけようと、駒の有無や**マスの平均色**で区間を切る
方法を試したが、どちらも「盤面が変わった」以外の理由で立つ。

- 駒の有無 → マウスポインタが空マスに重なると揺れる
- マスの平均色 → 直前に指した手のマスに付くハイライトの明滅でも動く

**読んだ配置そのものを比べれば、こうした揺れは最初から入り込まない。** 認識は
安定している（NCC 中央値 0.98）ので、一定間隔で読んで配置を比べるだけでよい。

唯一の落とし穴は駒がスライドしている途中の絵で、移動元が空いてから移動先が
埋まるまでの数フレーム、駒はどのマスにも属さない。ただし**駒が盤から消えるだけの
手は将棋に無い**ので、この形（`piece-vanished`）は確実に見分けられる。

### マウスポインタは輝度で見つかる

盤の木目は実測 130〜210、ポインタの白い矢印は 240 以上とはっきり分かれる。
マス内に極端に明るい画素が一定割合あれば、そこにポインタがいると判定できる
（`hasPointer`）。**駒を動かす瞬間ポインタは必ず盤上にいる**ので、いちばん
読みたい場面でいちばん邪魔になる。

⚠ この結論に辿り着くまで遠回りした。「桂が 5 枚（上限 4）」という数字から
「5 枚目は成桂だろう」と推測して成駒テンプレートの不足を疑ったが、**実際に
そのマスの画像を集めて並べたら大半がポインタだった**。数字から原因を推測せず、
先に絵を見るべきだった。

### マウスポインタは偽の駒を作る

空マスにポインタが重なると輝度の散らばりが増えて「駒あり」と判定され、照合が
適当な駒を当ててしまう。「桂が 5 枚」「角が 3 枚」といった盤面が実測で 4 割に出た。

対処は**削るのではなく引き継ぐ**のがよい。覆われただけなら駒はそこにあり続けて
いるので、読めなかったマスは「変わっていない」と見なして直前の配置を持ってくる
（`carryUnknowns`）。誤った駒として読むと差分が壊れるが、引き継げば壊れない。

駒が取られて消えた場合は駒の有無の方が変わるので、引き継いでも 1 手差分にならず
`piece-vanished` に落ちる。覆われている間に相手の駒へ置き換わった場合だけは
見逃しうるが、次に読める時点で辻褄が合わなくなるので気付ける。

⚠ 成った駒もテンプレートが無いうちは「読めなかったマス」に入る。引き継ぐと成りが
消えてしまうので、**引き継ぎ版 → 素の読み → 駒種の逆算**の 3 段構えで試す。

一致度の低いマスを**削る**方法（`pruneOverflow`）も書いて試したが、
**逆効果だった**。ポインタは本物の駒にも重なり、そのとき本物の一致度も下がるので、
本物を削って差分を壊す。実測では捨てる絵が減った代わりに
`too-many-changes` が 145 件、`illegal-shape` が 111 件出て、読めた手は増えなかった。
関数は残してあるが使っていない。

### 「駒があるか」と「何の駒か」で見る範囲を変える

どちらもマスの内側を切って見るが、**見たいものが違うので同じ範囲である必要はない**。

- 駒の有無（`CELL_INSET` = 0.18）… 駒の輪郭まで含めた方が輝度が散らばる
- 駒の種類（`MATCH_INSET` = 0.24）… 中心の字だけを見る方がよい

実測（ある局面の 39 マス）では、照合の範囲を 0.18 → 0.24 に寄せると
**最低の一致度が 0.490 → 0.662 に上がった**（いちばん読みにくいマス＝ポインタに
覆われたものが読みやすくなった）。正解数と中央値は変わらない。0.30 まで寄せると
0.640 に下がるので、駒の形の情報が減りすぎる。

直前に指した手のマスに付くハイライトも駒の周囲に強く出るので、同じ理屈で影響が減る。

### 新しいテンプレートは「駒でないもの」とも照合して確かめる

成駒のテンプレートを足したら読める手が減った（61 → 52）。テンプレートどうしの
相関を測ると、龍は生駒どうし（最大 0.415）より紛らわしくない（最大 0.306）。
それでも悪化した。

原因は**マウスポインタだった**。龍が 2 マス出ている局面を見に行くと、片方は
本物の龍で、もう片方は**ポインタしかない空マス**。白い矢印の濃淡が「ス」の字と
相関していた。盤上に龍は 1 枚しかいないので `R` が上限を超え、`sanity` が
盤面ごと捨てる。**「盤面が成立せず捨てた」が 10 件から 507 件に増えていた。**

⚠ **駒どうしで区別できることと、駒でないものを駒と間違えないことは別の話。**
新しいテンプレートを採るときは、ポインタや演出の絵とも照合して確かめる必要がある
（`data/unknown/` に集めたものが使える）。単純な字ほど駒以外と衝突しやすい。

### ポインタと成駒は、性質が違う

どちらも「読めないマス」を作るが、効き方がまったく違う。

| | マウスポインタ | テンプレートの無い成駒 |
|---|---|---|
| 現れ方 | 一時的（動けば消える） | **居座り続ける** |
| 影響 | その瞬間の絵が読めない | **その駒がある間ずっと読めない** |

手順が細切れに途切れる原因は後者。実測では龍（草書体で「ス」と書かれる）が
「桂」と読まれ続け、**8 分間が丸ごと落ちていた**。

成駒は手の整合性から逆算して覚えられる（`solveUnknowns`）が、成りが起きる瞬間は
駒が動いていてポインタも近く、いちばん読みにくい。実際 1 種しか取れなかった。
そこで **`seed-templates.ts` で「この時刻のこのマスはこの駒」と与えて起こす**。
画像を見れば駒種は一目で分かる。作ったものは `data/templates/` に残り、
**レイアウトが変わらない限り他の動画にも使い回せる**。

### テンプレートの無い駒は「居座る」

ポインタの誤認識は動けば消えるが、**テンプレートを持っていない駒はそこに
あり続ける**。実測では 2 分間まるごと「桂が 5 枚（上限 4）」で全フレームが捨てられ、
1 手も読めなかった。盤上の桂は 4 枚しかないので、5 枚目は成桂（圭）が「桂」と
読まれたもの。これが**手順が細切れに途切れる主因**だった。

対処は同じく引き継ぎで、**規定より多い駒種のマスを「読めなかったマス」として
挙げ**（`overflowCells`）、前の配置を持ってくる。駒の枚数という将棋の側の制約が、
そのまま誤認識の検出器になっている。

### 🔴 格子線が合っていても、照合は通らないことがある

外から受け取った盤面の絵（別の端末で撮った解析画面など）をテンプレートの採取源に
使おうとして踏んだ。格子線の当てはめは**うまくいっていた**——線のくっきりさは
盤が写っていない絵の 3 倍以上あり、目視の当たりからのずれも 1 画素以内だった。

ところが、その格子で切り出すと**正解が分かっている 20 マス中 12 マスしか読めず、
NCC も 0.4 前後**。数画素ずらすと 20/20・NCC 0.9 に跳ね上がる。

⭐ **測るべきものが違っていた。** 格子線の位置は合っている。合っていないのは
**駒の絵がマスの中のどこに描かれるか**で、そこは端末やアプリの版で微妙に変わる。

さらに、**最良のずれが列ごとに増えていた**（端から端で 4 画素）。原点だけの
問題ではなく**マス寸法の誤り**である。1 マスずつ測ったずれに直線を当てはめ、
切片を原点の補正、傾きを寸法の補正として取り出す（`refineByTemplates`）。

⚠ 当てはめは**中央値**（Theil–Sen）で行う。手掛かりのマスは全部が読めるとは
限らず、読めなかったマスは「探索範囲の端」というでたらめなずれを返す。
最小二乗は二乗で効かせるので、**外れ値が 2 枚混ざるだけで当てはめが動かなくなった**。

### 🔴 「後手は先手を回したもの」は、ずれ量を中央値で当てる限り成駒には通らない

初期局面から起こせない成駒は、片向きしか手に入らないことがある。そこで
「後手 = 先手を 180 度回して数画素ずらしたもの」として補ってきた。ずれ量は
**両向きそろっている生駒 8 種から測った中央値**を使う。

生駒での一致度は 0.96〜0.99 と高く、これで足りているように見えた。
**測り方が甘かった。** 各駒を*その駒専用の*最良ずれで測っていたので、
高く出るのは当たり前である。実際に使うのは中央値なので、**中央値を当てて**
確かめなければ意味がない。そうすると:

| | その駒専用のずれ | **実際に使う中央値** |
|---|---|---|
| `▲と` → `▽と` | 0.991 | **0.673** |
| `▲馬` → `▽馬` | 0.958 | **0.806** |

ずれは駒ごとに `-2.2〜-6.9` 画素と 4.7 画素も散っていて、中央値では個々に合わない。
そして**片向きしか無い駒には専用のずれが測れない**（測れないから回すのである）。

🔒 **回して補う前に、両向きそろっている成駒で「中央値のずれで」裏取りする。**
通らなければ回さない。手に入るまで、その駒は前の絵のまま使う方がよい。

### ⚠ 閾値は代用でしかない。代用が外れたら閾値を動かさない

「新しいテンプレートが既存のものと 0.6 以上相関したら、それは読み違えである」
という規則を使っていた。これは**「別の駒の写しになっていないか」を相関で代用**
している。

成銀（`全`）がこれに引っ掛かった。金と **0.7〜0.8** 相関し、しかも**位置合わせを
良くするほど上がる**。対照として、同じ出所の生駒どうしの最大相関は 0.415 しか
ないので、閾値をどこに引いても成銀だけが弾かれる。

⭐ 目で見れば簡単だった。**金は点が二つ付き、全は付かない。字は違う。**
似ているのは字画の重心がほぼ同じだからで、NCC はそこをよく拾う。

判定を代用から**本物**へ変えた——**「その生駒自身のマスを横取りするか」**を見る。
ラベルが誤っている（＝実は別の駒の写しである）なら、その駒の本物のマスに対して
本物のテンプレートより高い点を出すはずである。材料は初期局面に全部ある。
この判定なら成銀も通る。ただし余裕は他の 3〜4 分の 1 しかなく、
**読みだけでは決められない**ことが数字として残る。

### ⭐ 絵で割り切れないものが、ルールでは 1 つに決まる

その成銀と金の紛れが、実際に手順を切った。相手が**金を打った**のに、成銀の
テンプレートの方が一致してしまったのである。

だが**打つ手に成駒はあり得ない**。候補は金打ちしか無い。

ここまでの読み方は「81 マス読む → 差分を 1 手として説明できるか」という向きで、
**開いた集合に問いを投げていた**。マスごとに「20 種のどれか」を当てるので、
読めないマスが 1 つあると手が決まらない。合法手はルールで閉じた集合なので、
向きを逆にすると詰まりが消える——**未確定のマスは「情報が無い」として飛ばせばよい**。

設計で効いたのは 3 点:

1. **未確定のマスは数えない**（一致にも食い違いにも入れない）。「読めなかった」を
   「違っていた」と混ぜると、正しい候補が沈む
2. **「食い違いが 0 か」ではなく「食い違いが最も少ないのが 1 つに決まるか」で判断する。**
   追跡中の盤面に古い誤りが残っていると**全候補に等しく食い違いが乗る**ので、
   絶対値で切ると何も選べなくなる
3. 🔒 **分からないときは候補が広がる方へ倒す。** 途中の局面から追跡を始めると、
   盤に無い駒がどちらの持ち駒かは**盤面からは決して分からない**。「持ち駒は無い」と
   狭めると、本当に指された打ちが候補から消えてそこで追跡が切れる

⭐ 副産物として、**成/不成が成駒のテンプレート無しでも決まる**。移動元と移動先が
同じ候補は「X か +X」の 2 つしかなく、**生駒のテンプレートは必ず持っている**ので、
「生駒に見えないなら成っている」という消去法が使える。

### 持ち駒を追うと、偽の打ちが原理的に消える

マウスポインタや演出で駒が湧いて見えると、差分は「空 → 駒」になる。これは
ちょうど**打ちの形**なので、盤の 81 マスだけを見ていると弾けない。
`BoardState`（盤＋持ち駒＋手番）ごと進めれば、持っていない駒の打ちは
候補に現れない。

### 🔴 画面の下が先手とは限らない。しかも合法性では絶対に気づけない

このアプリは**対局者の視点で盤を描く**ので、録画した人が後手の対局では画面の下が
後手になる。読みは「画面の下＝先手」で組んであるから、そのままでは**盤を 180° 回して
先後を入れ替えた別の棋譜**が出来上がる。

⚠ **将棋の初期局面はこの変換で自分自身に移る。** だから出来上がった棋譜は
**合法なまま**で、通しで再生しても、駒数を数えても、二歩を見ても、何も起きない。
実測（1 局目）: 反転したままでも 92 手すべて合法。

⭐ **1 手目を指した側が先手。** これは盤の向きにも追跡の状態にも依らない事実で、
向きを決めるのに使える。⚠ **対局ごとに向きは変わる**（実測: 1 局目は画面の下が
後手、2 局目は先手）。

🔴 **同じ事実を逆向きに使って間違えた。** 「1 手目は必ず先手」を「1 手目が後手の手
なら断る」として使ったが、それは「画面の下＝先手」を前提にしていた。実際には
1 局目の 1 手目は画面の上の手で**それが正しい 1 手目**であり、断ったせいで 1・2 手目の
順序が入れ替わり、「先手の 3 手目が落ちている」ように見えていた。
🔒 **絶対の事実も、疑うべき前提と組み合わせれば凶器になる。**

### 🔴 「駒の判別に色は寄与しない」は誤りだった。**成駒は朱で書かれている**

長らく認識はすべてグレースケールで行い、この文書にも「駒字は黒、盤は木目なので
色は要らない」と書いてあった。**生駒しか見ていなかったときの観察**で、
成駒が出てくると崩れる。

`金` と `全`（成銀）は字が本当に似ていて、NCC で 0.70〜0.81 相関する（位置合わせを
良くするほど上がる）。実測では**自陣で動いた金が「成った銀」に読まれ、そのまま居座って
27 秒ぶんの手を落とした**。形では割り切れない。

⚠ **生の R−G では分かれない。盤の木地自体が橙**で R−G ≒ 47 ある。
**インクの R−G を同じマスの木地の R−G で割る**と、背景の演出で明るさや彩度が動いても
比が保たれる。「成駒と読めた」マスだけを測った分布（4130 マス）:

| 赤み | マス数 | 中身 |
|---|---|---|
| 0.41〜0.50 | 11 | **誤読**（生駒を成駒と読んだ） |
| 0.50〜1.03 | **0** | ← 谷 |
| 1.03〜1.33 | 125 | 本物の成駒 |

**間が 2 倍以上空くので、谷の真ん中（0.76）に線を引ける。**
判定は「朱でなければ成駒ではないので、**生駒に限って読み直す**」——
絵で割り切れないものを**別の証拠で閉じる**形で、下記の `droppable` と同じ構え。

⭐ 副産物として、**指摘ゼロだった動画にも成駒の誤読が数 % 潜んでいた**ことが分かった
（136 中 11）。通し再生をすり抜けていた。

#### 🔴 色を足すために輝度を変えてはいけない

最初 `rgb24` で取って自分で輝度に落としたところ、**別の動画の成績が下がった**。
測ると `-pix_fmt gray` と **72% の画素がずれていた**（最大 18）。動画は YUV で
符号化されているので、rgb24 経由では YUV→RGB→輝度と 2 回変換が入り、レンジの伸長も
挟まる。**`sd` が動けば駒の有無の判定が動く。**

`gray` は本質的に Y 平面そのものなので、**フルレンジの `yuvj444p`** で取れば
Y は `gray` と**画素単位で 100% 一致**する（`yuv444p` では 1.3%。**`j` が要る**）。
ffmpeg の起動も 1 回のままで済み、R−G は色差だけで決まるので RGB に戻す必要もない。

🔒 **新しい情報を足す変更が、既存の情報を静かに変えていないかを確かめる。**

### ⭐ 未確定にする前に照合を見る。**推定は、決定的な証拠に譲る**

「駒があるか」が決まらないマスは、以前は照合にかけずに未確定へ落としていた
（覆われた絵から起こした第一候補は当てにならない、という理屈）。測ったら
**2.7% は決まっていた**（全編 3549 枚・覆われたマス 3288 個）:

| 照合 1 位の NCC | 個数 |
|---|---|
| 0.40〜0.50 | **2622**（決まっていない山） |
| 0.50〜0.70 | 19（**谷**） |
| 0.70〜1.00 | **99**（決まっている山） |

**山が 2 つに割れるので、谷に線を引ける。**

🔴 **決まっている分まで捨てると、打った駒がその場で取られる形が丸ごと消える。**
盤の差分には何も残らないので、そこが唯一の痕跡になる。実測では、打たれた歩は
`sd=18.8` で「駒がある」の門に落ちる一方、照合は ▽歩 0.829 に対して 2 位 0.330 だった。

🔴 **同じことがマウスポインタの判定でも起きていた。** ポインタは白い画素で
見つけるが、**打ちの演出も白い**ので、打たれた駒はポインタと見分けが付かない。

🔒 **`sd` もポインタも「読めなくて当然」という推定にすぎない。**
代用が外れたときに閾値を動かすのではなく（下記）、**別の証拠で門を通す。**

### ⭐ 逆向きも要る。**「駒がある」の門を通っても、駒種が決まっていなければ置かない**

上は「決まっているのに捨てていた」話だが、**その裏返しで「決まっていないのに
置いていた」**。通常の経路は照合 1 位の高さしか見ておらず、2 位との差を見ていなかった。

🔴 実測: **マウスポインタがマスの隅に半分だけ掛かった空マス**が `sd=32.6` で
「駒あり」の門を通り、**▽角 0.467 対 ▽銀 0.454**——差 0.013 で盤に置かれた。
`hasPointer` は「マスの 4% 超が輝度 235 超」で見るので、**隅に掛かった分は通り抜ける**。
差分は「空 → 駒」＝ちょうど打ちの形で、その駒を本当に持っていたので持ち駒の検査も通り、
**偽の打ちが棋譜に入って 13 手が総崩れになった**（断片も切れた）。

⚠ **差だけを見る門にしたら、本物の駒も一緒に落ちた。** もう 1 本の動画で
**本当に打たれた金**（`G*8f`・NCC 0.815・差 0.028）が消え、92 → 75 手に退行した。
金と全は 0.70〜0.81 相関するので**原理的に差が付かない**。

⭐ **1 次元では割れない。2 つを一緒に見ると隅が空く**（2 本・全編 2 秒刻み・
盤に置かれたマス 29350 / 34944 の実測。**NCC < 0.6 の隅**）:

| 1 位と 2 位の差 | 1 本目 | 2 本目 | 2 本目の中身 |
|---|---|---|---|
| < 0.05 | **0** | 11 | 単発の読み。**問題のポインタもここ** |
| 0.05〜0.10 | **0** | 430 | **何分も同じマスに出続ける本物の角**（NCC 0.505） |

**下は「1 枚だけ現れて消える読み」＝演出やポインタの指紋、上は「居座る読み」＝本物の駒。**
だから門は **「よく似ている（NCC ≥ 0.6）」か「紛れていない（差 ≥ 0.05）」のどちらか**にした。
両方とも満たさない読みは、**そこに何かがある以上のことを何も言っていない。**

🔒 **分布が 2 山に割れることは、割れ目が「正しい / 間違い」の境目であることを
意味しない。** 谷は確かにあったが、その下にいたのは本物の駒だった。
**何が入っているかをリストで見てから線を引く。**

### ⚠ `fps=N` で間引くと、`-ss` とは**別のフレーム**が返る

走査時間の 62% は「1 枚ごとに ffmpeg を起動して `-ss` で飛ぶ」費用だった
（デコード自体は全編で 40 秒しか掛からない）。1 パスで流せば消える——のだが、
**間引き方を間違えると絵が変わる**。

| | 何を採るか | 30fps を 0.5 秒刻みにしたときの 1 枚目 |
|---|---|---|
| `-vf fps=2` | 出力区間の**中央**に最も近い入力 | 0.25 秒に最も近い **7 フレーム目** |
| `-ss t` | 区間の**先頭** | **0 フレーム目** |

実測では全編で一定の 7 フレーム（0.2333 秒）ずれ、1 枚あたり 250 万画素が食い違った。
`start_time=0`・PTS も整然としていたので**動画ではなくフィルタの仕様**。

⭐ **フレーム番号で選べば一致する**（`select='not(mod(n,K))'`）。
`select=eq(n,300)` と `-ss 10` が md5 まで同じであることを確かめてから採った。

🔒 **「速くするだけ」の変更が、絵を静かにずらすところだった。**
本線に触る前に、**同じ時刻の絵を画素単位で比べる**こと（2 本 × 90 枚で完全一致を確認）。

⭐ 流し方は**押し出しではなく引き取り**（`next()` で 1 枚ずつ）。本線は
「繋がらない区間を細かく読み直す」ために待ち行列へ時刻を挿し込むので、絵が
勝手に流れてくると噛み合わない。**挿し込みの時刻は必ず格子から外れる**ので、
格子＝流れ / それ以外＝1 枚取り、と機械的に分けられる（実測で 99% が流れから）。

### ⚠ どこが重いかは、測るまで分からない

1 枚あたりの内訳を測ったら、**2 番目に重いのは認識ではなく「対局中の盤が
写っているか」の確認**だった（27.9ms 対 13.3ms）。格子を探す `search` が
1 フレーム 1 軸あたり約 14000 回も当てはまりを計算し、**そのたびに配列を 4 つ
作っていた**。割り当てなしに書き直して 10.5ms（値は 1 ビットも変えていない）。

⚠ 一方、**筋が良さそうに見えた最適化は効かなかった**。列ごとの平均は画素を
1080 バイト飛びに読むのでキャッシュに悪い——正しいが、直しても 29.6 → 27.9ms。

### 1 手ごとの合法性は、棋譜が合法であることを意味しない

走査中も 1 手ごとに合法性は見ている（`legality.ts` / `movegen.ts`）。だがそれは
**追跡中の盤面に対する検査**で、その盤面は映像から再同期される。手を 1 つ
取りこぼしても、次に読めた絵で盤面が実際の局面に戻るので、走査は何事も無かった
ように進む。**書き出された手の列が初期局面から繋がる保証はどこにも無い。**

`src/replay.ts` は初期局面から通しで再生する。実測では、手番の交互率が 0.99 で
「ほぼ完璧」に見えていた棋譜に、**交互率では原理的に見つからない誤り**
（持っていない駒の打ち）が 1 件残っていた。交互は保たれたまま間違えられる。

⚠ **最初の誤りで打ち切らない。** 打ち切ると「1 か所で崩れた」のか「何か所も
独立に落ちている」のかが区別できない。手番は棋譜に記録された手番を正とし、
非合法な手も無理やり盤に反映して続ける。後続がそのまま合法に流れるなら、
誤りは局所的だと分かる。

## 残っていること

- 🔴 **手番の割り当てがずれると、盤に一度も現れない駒が生まれる**（1 件検出・未修正）。
  手番の交互が破れたときに間へ 1 手挿す機構が、**画面で確認できない打ち**を作ることがある。
  その駒が後で「移動」させられると、**移動先の盤・持ち駒は本物の打ちと完全に同一**になるため、
  通しの再生でも色・駒種の監査でも検出できない。
  ⭐ 見つけられたのは、**監査が安全網で捨てた局面**（駒の有無が 1 マス食い違う局面）を
  数え直したから。🔒 **「棋譜は駒があると言うのに映像は空」の向きだけが本物の兆候**——
  逆向き（棋譜は空／映像は駒）は 1 本あたり 1000 件超の背景現象で、数えても意味が無い。
  ⭐⭐ **原因は症状の 110 秒前にあった**——手が続けざまに指される場面で追跡が一度切れ、
  追いついたときに**複数の手を同一時刻の数手に圧縮し、移動を「打ち」と読み違え、
  手番が 1 手ずれた**。🔒 **同じ時刻に複数の手が並んでいることが、そのしるし。**
- ⭐ **時計と持ち駒欄は、手番のずれを盤とは独立に検出できる**（未実装の検算）。
  動いている方の時計が手番なので、各手の直後にどちらの時計が動いているかを見れば
  手番の割り当てを検算できる。🔒 **通し再生も色も駒種も、手番のずれには沈黙する。**
- **盤の差分に痕跡を残さない手を拾う。** 打った駒がその場で取られると、前後の盤は
  1 手で過不足なく説明できてしまい、**失敗としてすら現れない**。いまは手番の交互が
  破れたときだけ間に 1 手挿しているが、**偶数手まとめて落ちると交互は破れない**。
  画面の持ち駒欄・手と手の間隔・演出で読まなかった区間が手がかりになる。
  🔒 **一意に決まるときだけ差し込み、決まらなければ「ここに n 手ある」と穴のまま残す。
  推定した手には印を付け、観測と混ぜない。**
  ⚠ ただし**手元の素材では発火する場面が無く、測れない**。下記のとおり、
  そう見えていた 1 件は「読めているものを捨てていた」だけだった。
- 対局以外の場面を弾く（感想戦は盤のレイアウトが違う。冒頭に対局者紹介が入る）
- 1 本の動画に複数の対局が入るので切り分ける
- 駒のデザインは利用者が変更できる。保存先をデザイン別にし、初期局面の生駒を
  照合して自動判定する。未知のデザインでも**生駒は自動生成されるので同じ性能で動く**
- 画面の持ち駒欄を読む。棋譜の復元には要らない（初期局面から追えば確定する）が、
  追跡した持ち駒と突き合わせれば**手の取りこぼしを独立に検出**できる。
  ⭐ **読めることは確かめた**——駒は幅 97px・高さ 125px・間隔 107px で並び、
  2 枚以上は右上に数字バッジが付く。時系列に並べると**取り合いがそのまま出る**
- 🔴 **永久に未確定のマスは、根拠ゼロの打ちの置き場になる。** 背景の絵が 1 マスを
  横切るだけで `sd` が「空」と「駒あり」の間に何分も居座ることがある（実測 12.4）。
  候補手の採点は未確定のマスを一致にも食い違いにも数えないので、**そこへ打つ候補は
  食い違い 0 で通ってしまう**。実際に偽の角打ちが捏造された
- ~~**テンプレートは初期局面から起こすが、そこに何か乗っていないかを見ていない。**~~
  → **解決した。駒の絵は走査のたびに起こさず、事前に採った資産を使う**
  （`extract-plain-templates.ts` で保存し、走査は保存済みを正典として読む）。
  ⭐ **原因は「片方の動画だけ角が読めない」ではなく「対局開始の演出が乗ったフレームから
  起こしていた」**。キャラクターの絵と光の帯が先手陣に重なり、その下にあった角と飛が濁る。
  **同じ駒どうしで NCC 0.512** までしか合わず、盤上の本物の角はどこでも 0.44 前後になる。
  駒があると分かっているマスが未確定のまま残り、**指した手がそのまま棋譜から落ちた**
  （実測 4 件。うち 1 件は 250 秒後に「偽の打ち」として現れ直していた）。
  🔒 採取するフレームには**受け入れテスト**を課す——**演出の下の駒は輪郭が溶けて互いに似る**ので、
  生駒どうしの最大相関を見れば分かる（演出なし 0.387 / 演出あり 0.664）
- ⏹ **切り出し窓を字の位置から決める案は、測って採らなかった**（2026-08-16）。
  窓は格子から一律に詰めているので、**`金` の下棒・`歩` の左払い・`玉` の点が
  窓の外に出て、上には木地の余白が残る**（拡大して枠を焼き込むと一目で分かる）。
  ⚠ 切れているのは**駒から見た下**で、上側の駒は 180 度回して描かれるから
  **画面では上が切れる**——一律にずらすと必ず片側が悪化する。向きごとに
  ±10px ずらすと、**きれいなマスでは狙いどおり良くなった**（同じ向きどうしの
  最悪の相関 0.411 → 0.335、別の動画を読んだ 1 位と 2 位の差 0.512 → 0.606）。
  🔴 **それでも棋譜は悪くなった**（2 本目 218 → 210 手・断片 4 → 7）。
  🔒 **分離を測ったのは「きれいな初期局面」で、棋譜が切れるマスの代用ではなかった。**
  切れるのはポインタ・演出・ハイライトで半分覆われたマスで、そこでは
  **駒の輪郭という共通の手がかり**が効いている。窓を字に寄せると輪郭を捨てるので、
  **きれいなマスで得をして際どいマスで損をする**。仕組みは `MATCH_DY`（既定 0）と
  `probe-cell-window.ts` に残してある。**同じ道をもう一度掘らないこと**
- ⭐ **人が選んだテンプレートの控えは `templates-selection.txt` に残す。**
  一度失って、保存済みの画素と候補の総当たりで復元する羽目になった
  （生駒 16 種は画素完全一致・`▽馬` は 3 枚平均の組み合わせを解いて食い違い 0）。
  🔒 **選別は人の目でしかできない工程なので、結果は必ず控えを残す**
- ✅ **字の色は両向きに効かせる**（2026-08-16）。「成駒と読めたが朱でない → 生駒に
  読み直す」だけでは足りない。**成った銀を `金` と読むと、色を見る機会が二度と来ない**
  （金と全は NCC 0.70〜0.81 で形では割れない）。実測では「銀が金になった」という
  説明の付かない差分になり、断片が切れていた。逆向き（生駒と読めたが朱 → 成駒に
  限って読み直す）を足して解消。🔒 **上げる側は「駒があると確定したマス」に限る**——
