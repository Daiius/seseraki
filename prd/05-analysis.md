# 05. 解析と可視化

本章は worker のエンジン解析と、Web 棋譜詳細画面での可視化を定める。
データ型は [03](./03-data-model.md)、解析ドメインの用語は [01](./01-domain.md) §5 を参照。

---

## 1. worker のエンジン解析

worker（`packages/worker`）は server とは分離した実行環境で稼働し、USI プロトコルでやねうら王を駆動する（[02](./02-architecture.md)）。

### 1.1 解析フロー

1. server から**未解析の最古の棋譜を 1 件取得**（`GET /api/worker/kifus`、`usiMoves` と
   **既に入っている局面数（`analyzedCount`）**を含む。[04](./04-ingestion.md)）。
   現行の抽出条件は「`analysisCompletedAt IS NULL` かつ `usiMoves IS NOT NULL`」を **`coalesce(playedAt, createdAt)` 昇順**で 1 件
   （`playedAt` が null の棋譜は `createdAt` で並ぶ。`analysisError IS NULL` も条件に含む＝失敗棋譜は除外。[03](./03-data-model.md)）。
   **最古優先（FIFO）**は「全棋譜を時系列で見る」用途に合わせた選択（[decisions](./_grilling/decisions.md)）。
2. `usiMoves` を使って各局面を **MultiPV（既定 3）で解析**。定跡ヒット時はエンジンが即座に候補手を返す。
   **`analyzedCount` の局面から再開**する（§1.1c）。
3. **1 局面解析するたびに進捗を報告**（`POST /api/worker/analyses/progress`）。§1.1b。
4. 解析結果を **経過時間で区切ったチャンク**として server に送信（`POST /api/worker/analyses`・
   1 チャンク 1 トランザクション）。**完了（`analysisCompletedAt`）は server が件数で確定**する。§1.1c。
5. **ポーリング間隔（既定 10 秒）**で繰り返す。idle 時はログ出力なし。

- KIF→USI 変換は server 側で済んでおり、worker は KIF パーサーを持たない（[01](./01-domain.md) §2 / [04](./04-ingestion.md)）。

### 1.1b 解析の進捗報告（決定・2026-07-21）

本番想定の byoyomi モードでは 1 局の解析に十数分〜数十分かかる。その間 UI から「解析中なのか、キューが
止まっているのか」を区別できないため、進捗を報告して可視化する（表示は §2.5）。

- worker は**局面を 1 つ解析するたびに**進捗（解析済み局面数 / 全局面数 = `usiMoves.length + 1`）を報告する。
  **毎局面**にするのは、N 局面ごとにすると N の適正値が 1 局面あたりの所要時間（MATERIAL/NNUE・
  depth/byoyomi で桁が変わる。§1.2・§1.4）に依存し、固定値の根拠が置けないため。メモリ更新だけで
  DB 書き込みがないので、150 局面 × 数十分に対して最大 150 リクエストは無視できる。
- 報告には `analysisRevision` を添え、**現在の世代と一致しないときは無視する**（submit / error 報告と
  同じ世代照合。reanalyze 後に届いた旧解析の進捗を表示しない）。**完了済み・失敗記録済みの棋譜への報告も
  無視する**（報告と submit が前後しても「終わったのに解析中」が残らない）。
  - ⚠ この照合は DB 読み取り（`await`）を挟むため、**判定してから記録するまでの間に submit / error 報告 /
    reanalyze / 削除が完了しうる**。古い判定のまま書き込むと終わった棋譜の「解析中」が復活し、
    次の報告が無ければ server 再起動まで消えない。よって**メモリへの書き込みはクリアとの
    compare-and-set** にする（クリアのたびに進む単調カウンタを読み取り前に取り、記録時に一致を確かめる）。
- ⚠ **進捗報告の失敗は握りつぶし、解析を継続する。** server が落ちている・遅いときに解析まで止まるのは
  本末転倒。worker は報告の完了を待たずに次の局面へ進む。
- **進捗は server のメモリに持ち、DB に永続化しない**（`packages/server/src/analysis-progress.ts`。
  `swars/job-store.ts` と同じモジュールスコープの状態。単一プロセス前提は [02](./02-architecture.md) §1 /
  [07](./07-auth-and-privacy.md)）。理由: (1) チャンク submit が入れば `moveAnalyses` 件数から導出できる
  ようになるため、列を足すと捨てることになる（migration を 2 回打つ）、(2) 数十分の解析中に DB へ UPDATE を
  繰り返さない、(3) 完了すれば `analysisCompletedAt` が正になる揮発的な情報である。server 再起動で消えるが
  worker の次の報告で復活し、**stale が自動で消える利点**にもなる。よって [03](./03-data-model.md) に列は足さない。
- worker は棋譜を 1 件ずつ処理するので**解析中の棋譜は常に高々 1 件**。エントリは
  **submit 成功 / error 報告 / reanalyze / 棋譜削除でクリア**する。
- 報告先は既存流儀に倣い **`/api/worker/` 配下**に置く（[04](./04-ingestion.md) §7）。
  理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。

### 1.1c 解析結果のチャンク submit と再開（決定・2026-07-21）

全局面を貯めて最後に 1 回だけ送ると、byoyomi 運用で数十分かかる解析が submit の失敗で丸ごと失われる。
チャンクに分けて送り、途中から再開できるようにする。

- **チャンクは経過時間で区切る**（前回 submit から T 秒）。抑えたいのは「失敗時に失われる計算時間」なので、
  時間で切れば**失う量がエンジン速度によらず T の目安に収まり**、開発 MATERIAL でも本番 NNUE depth20 でも
  同じ感覚で決められる（固定局面数だと同じ N で失う量が桁違いになる。§1.2・§1.4）。T の具体値は実装判断
  （現行は `packages/worker/src/kifu-analysis.ts` の `CHUNK_INTERVAL_MS`）。
  - ⚠ **厳密な上限は「T + 実行中だった 1 局面分」**。境界の判定は 1 局面を解析し終えた後にしか来ないため、
    1 局面が T を超える設定（depth 20+ で数分。§1.4）では上振れする。局面の途中で送る仕組みは持たない
    （エンジンの探索を中断して部分結果を採る話になり、解析の意味が変わる）。T を選ぶときは
    **「T + 1 局面」で見積もる**こと（[decisions](./_grilling/decisions.md) は決定当時の文面
    「失う上限が T 秒に固定」のまま残してある。実装上の厳密な上限はこちらが正）。
- **途中まで入った棋譜は続きから再開する。** `GET /api/worker/kifus` が `moveAnalyses` の件数
  （`analyzedCount`）を返し、worker は `moveNumber = analyzedCount` から解析する。チャンク submit の
  失敗は解析ごと中断する（下記）ので `moveNumber` に穴が空かず、**件数がそのまま再開位置**になる。
  再開がないと、poll 条件は `analysisCompletedAt IS NULL` なので次の poll で同じ棋譜を 0 から
  解析し直し、数十分の計算は結局失われる。
- **`analysisCompletedAt` は server が件数で判定する。** submit のたびに `moveAnalyses` の件数を数え、
  `usiMoves.length + 1` に達したら**同じトランザクション内で**立てる（[03](./03-data-model.md) §3）。
  「揃っていれば完了」という不変条件で決まるため、worker のクラッシュ位置やチャンク境界に依存しない。
  - worker は解析を終えたら**最終チャンクを空でも送る**（再開位置が既に全局面に達しているケースで、
    送らないと「全局面が揃っているのに未完了」の棋譜を拾い直し続ける）。
  - ⚠ 件数で決める以上、**`moveNumber` が棋譜の有効範囲（`0..usiMoves.length`）にあることを
    submit 側で検証する**（外れていれば 1 件も書かずに 400）。範囲外を受け入れると欠番のまま
    件数だけが達して完了扱いになり、poll から外れて自動再開でも直らない（[03](./03-data-model.md) §3）。
- **世代照合（`analysisRevision`）と `FOR UPDATE` による reanalyze との直列化は現行のまま**。
  チャンクごとに世代を確認し、不一致なら破棄する（§1.1a）。
  - **完了済み・失敗記録済みの棋譜へのチャンクも破棄する**（＝**完了後の解析結果は不変**）。
    片方が完了させた後に遅れて届いたチャンクを受け入れると、完了済みの結果が部分的に別実行の値で
    上書きされ、`analysisCompletedAt` も更新され続ける。作り直しは `reanalyze` の経路だけにする。
- ⚠ **worker は単一インスタンス運用を前提とする**（同一棋譜を複数 worker が並行解析する構成は取らない）。
  `GET /api/worker/kifus` は lease を取らないため、2 つの worker が同じ棋譜・同じ世代を掴むと、完了前に
  互いのチャンクが交互に入って**1 棋譜の解析結果に複数実行の値が混ざる**（世代照合・完了/失敗の排他は
  状態の矛盾を防ぐが、この混在は防げない）。並行解析を許すなら poll 時の lease（＝解析実行の識別子）が
  要るが、**列の追加を伴うため #51 の承認範囲外**（[08](./08-roadmap.md) の未確認・将来の論点）。
  worker を 1 つに保つ前提は [02](./02-architecture.md) §1・§5（worker は解析用ホストに 1 つ）と、
  §1.1b の「解析中の棋譜は常に高々 1 件」に揃っている。
- **冪等性の担保は 3 箇所に分散する**（submit の DELETE を廃止するため）。どこが何を担保するかは
  [03](./03-data-model.md) §3 に書く。
- 進捗（§1.1b）のメモリ保持は**残す**。**メモリ = 表示**（毎局面更新で滑らか）/ **DB 件数 = 再開位置と
  完了判定**（正確）と役割を分ける。DB 件数に一本化すると進捗の粒度が T 秒に落ち、最初の T 秒間は
  「未解析」に見えてしまう。
- 理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。

### 1.1a ポイズンピル対策（解析失敗の扱い）

- **不正棋譜はエンジンを異常終了させうる**（KIF→USI 変換の不備で illegal move になる等）。何もしないと同じ
  kifu を無限に拾い直してクラッシュし続け、キューが詰まる。
- **失敗の分類**:
  - **棋譜起因＝恒久失敗**: illegal move / エンジンプロセスの異常終了 / 解析タイムアウト。当該 kifu の
    `analysisError` に理由（例 `illegal move at move 57`）を記録し（`POST /api/worker/kifus/:id/error`）、
    **エンジンを無条件で再起動**してクリーンな状態に戻してから次の kifu へ進む。error 付き kifu は poll から
    除外される（[03](./03-data-model.md)）。timeout も同じ depth/byoyomi では再発する二次ポイズンピルなので恒久扱い。
  - **インフラ起因＝一時失敗**: server への解析結果 submit 失敗（ネットワーク/DB）等。棋譜自体は正常なので
    `analysisError` は立てず、次の poll で再試行する（エンジン再起動もしない）。
    - ⚠ **チャンク submit の失敗は、その棋譜の解析を中断し、次の poll で続きから再開する**（§1.1c）。
      握りつぶして続行すると `moveNumber` に穴が空き、再開位置を「入っている件数」で決められなくなるため。
      §1.1b の「**進捗報告**の失敗は握りつぶして継続」とは**逆**である点に注意——進捗は表示だけで失っても
      実害がないのに対し、チャンクは計算結果そのものだから。
- worker はエンジンの死（プロセス `close`）を検知したら解析中の待機を即座に打ち切る（60 秒タイムアウトまで待たない）。
- **エンジン再起動が失敗したら**（binary 不在等）、worker は `engineReady = false` にして**復旧できるまで次の kifu を
  取得しない**（dead なエンジンで後続の正常棋譜まで恒久失敗扱いする連鎖を防ぐ）。以降の poll は kifu 取得前に再起動を再試行する。
- worker の報告（submit / error）は取得時の **`analysisRevision` を添える**。server は現在の revision と一致するときだけ
  適用するため、reanalyze でリセットした後に届いた**旧解析の報告は破棄**される（世代競合対策。[03](./03-data-model.md)）。
- UI は「解析失敗」バッジ＋理由を出す。**再試行は `POST /api/kifus/:id/reanalyze`**（[04](./04-ingestion.md) §6）＝
  `kifText` を再変換して `usiMoves`・メタを作り直し、旧 `moveAnalyses` を削除、`analysisError` をクリア、`analysisRevision`
  を +1 して再キューする。これによりパーサ修正が既存の失敗棋譜にも反映される（error クリアだけだと壊れた `usiMoves` のまま再度落ちる）。
- 投入時の整合チェック（[04](./04-ingestion.md) §5）は best-effort で、完全な合法性保証はしない。取りこぼしはここで受ける。

### 1.2 エンジン構成（開発 / 本番）

| | 開発用 (Dockerfile) | 本番用 (Dockerfile.prod) |
|---|---|---|
| EDITION | MATERIAL（駒得。開発環境の低スペック向け軽量版） | NNUE |
| 評価関数 | なし | 評価関数（`nn.bin`, ~60MB） |
| 定跡 | なし | 定跡（ペタブック系） |
| TARGET_CPU | OTHER | OTHER |

> ⚠️ **評価値の精度**: 開発 MATERIAL は駒得ベースのため序盤の評価値が大きめに振れる。
> 本番 NNUE で再解析すると安定する想定（[01](./01-domain.md) §5）。同じ棋譜でもエンジンが変われば数値が変わる。

> ⚠️ **運用注意: エンジン構成（MATERIAL↔NNUE・depth/byoyomi）を変えたら `reanalyze` すること**（決定・2026-07-21）。
> 解析は途中から再開する（§1.1c）ため、構成を変えると 1 つの棋譜に**異なる基準の評価値が混ざりうる**。
> [08](./08-roadmap.md) の確定事項「解析来歴（engine/eval）は持たない」により、再開時に前回のエンジンを
> 比較する手段はない——**検出はせず運用で受ける**（個人用で構成変更はまれ・`reanalyze` は既にある）。

### 1.3 エンジンオプション

| オプション | 環境変数 | 既定 | 説明 |
|---|---|---|---|
| Threads | `ENGINE_THREADS` | 1 | |
| USI_Hash | `ENGINE_HASH` | 128 (MB) | 本番は 1024。過不足は `hashfull` で判断する（§1.3c） |
| MultiPV | `ENGINE_MULTIPV` | 3 | 候補手数 |
| — | `ENGINE_DEPTH` | 10 | 探索深さ |
| — | `ENGINE_MOVETIME` | 未設定 | 1 局面あたりの思考時間(ms)。設定時は depth より優先（局面の複雑さで深さを自動調整） |
| EvalDir | `ENGINE_EVAL_DIR` | — | 本番: 評価関数ディレクトリ |
| BookDir | `ENGINE_BOOK_DIR` | — | 本番: 定跡ディレクトリ |
| ConsiderationMode | — | true | 読み筋を置換表から延長して出力する（§1.3a） |

- 定跡関連の細目（BookFile / IgnoreBookPly / FlippedBook / BookOnTheFly / BookMoves / BookEvalDiff /
  BookDepthLimit 等）は BookDir 設定時に本番向けの値へ自動設定される（メモリ節約・回転局面ヒット・末端採用など）。
- **本番の解析モードは時間指定（`ENGINE_MOVETIME`）を志向**する（局面の複雑さに応じて深さを自動調整）。ただし
  **適正値は吟味中**で、具体値はリポジトリに固定せず env 運用にとどめる（[decisions](./_grilling/decisions.md)）。

#### 1.3a 時間で区切るときは `go movetime`（`go byoyomi` ではない）

USI で思考時間を指定する方法は 2 つあるが、**解析には `go movetime` を使う**。`byoyomi` は対局用の指定で、
やねうら王が「floodgate で切れ負けしないため」に `NetworkDelay2`（既定 1120ms）を差し引くため、
**指定値どおりの思考時間にならない**。

| 指定（いずれも 1000ms を要求） | 実際の思考時間 |
|---|---|
| `go btime 0 wtime 0 byoyomi 1000` | 102ms（1120ms 引かれ、下限に張り付く） |
| `go movetime 1000` | 1001ms |

`movetime` はやねうら王で「時間固定モード」として扱われ、`NetworkDelay` も `MinimumThinkingTime` も
経由せず指定値がそのまま思考時間になる。設定値と実際の解析時間が一致するので、1 局の所要時間を見積もれる。

> ⚠️ `ENGINE_BYOYOMI` は廃止した。残っていると解析時間が静かに変わるので、worker は起動時に警告を出す。

#### 1.3b `ConsiderationMode` を有効にする

時間で探索を打ち切ると、最後に出る info 行が探索途中の暫定値になり、読み筋が 1〜2 手しか埋まっていない
ことがある（iteration の途中で最善手が入れ替わったまま時間切れになるケース）。やねうら王は検討モードの
とき読み筋を置換表から辿って補完するため、打ち切られた局面でも読める長さの読み筋が出る。
探索アルゴリズムには影響しない（読み筋を出力する瞬間に置換表を辿るだけ）。

定跡にヒットした局面は別経路（採用手の確定行が depth 0・pv 2 手固定）でこの補完が効かない（#67）。

#### 1.3c `USI_Hash` の過不足は `hashfull` で判断する（決定・2026-08-08）

**置換表のサイズを「多めに取っておく」で決めない。** 判断材料は info 行の `hashfull`（使用率・パーミル）で、
worker は 1 局面ごとのログに出し、1 局の完了ログに**この実行の最大値**を出す。

```
[Analysis] 42/113 1502ms d21 3candidates hashfull 284‰
[Worker] Completed kifu 57 (113 moves, 113 positions analyzed, peak hashfull 284‰ / USI_Hash 1024MB)
```

目安は Stockfish の実測（15.1 / 60+0.6・[Useful data](https://official-stockfish.github.io/docs/stockfish-wiki/Useful-data.html)）:
**300‰ までは実質無害、500‰ で約 −10 Elo、700‰ で約 −20 Elo、900‰ で約 −50 Elo 相当**（探索速度 2 倍 ≒ +50 Elo
換算で、それぞれ 15% / 30% / 2 倍の速度低下に相当する）。**peak が 300‰ を大きく下回るならサイズは余っている。**

⚠ **置換表は局面をまたいで残る**（`usinewgame` も `Clear Hash` も送らない）。1 局面ぶんではなく
**棋譜 1 局ぶんの蓄積**で埋まるので、対局エンジン向けの目安より積み上がる。一方、1 手ずつ進める解析では
直前の局面で読んだ木がそのまま次の局面の部分木になるため、**この蓄積自体が速度に効いている**（消さない理由）。

#### 1.3d worker のメモリを食うのは置換表ではなく `Threads`（実測・2026-08-08）

`USI_Hash` を削ってもメモリはさほど減らない。エンジンプロセスの実測は次の式に乗る:

```
yaneuraou の RSS ≒ 70MB（エンジン + 評価関数） + 108MB × Threads + USI_Hash
```

| Threads（`USI_Hash` 128MB 固定） | RSS |
|---|---|
| 1 | 305MB |
| 2 | 414MB |
| 4 | 630MB |
| 8 | 1060MB |

- **スレッドあたり約 108MB** は探索の history テーブル（`ContinuationHistory` は駒種 × マスの
  二重配列で、将棋では駒種が多く大きくなる）と見られ、**設定では削れない**。
- **定跡はメモリを消費しない。** `BookOnTheFly=true`（§1.3 の自動設定）が効いており、
  同じ `Threads` / `USI_Hash` で定跡あり・なしの RSS が一致する（実測 1060MB / 1060MB）。
- ⚠ **メモリを削りたいときに `Threads` を下げると解析スループットが直接落ちる。**
  先に `USI_Hash` を §1.3c の `hashfull` 実測で見直すこと。

### 1.4 解析 depth の目安

| depth | 用途 | 時間/局面（1CPU） |
|---|---|---|
| 10–12 | 簡易解析 | 数秒 |
| 15–18 | 標準解析 | 数十秒 |
| 20+ | 詳細解析 | 数分 |

## 2. Web 棋譜詳細画面（`/kifus/$id`）

盤面 + 評価値 + 解析結果を**縦に並べる**。順序は **上端に固定するまとまり（盤面 + コンパクト情報行 +
コントローラー。§2.1）→ 候補手 → 評価値グラフ → 折り畳みの詳細**。**狭い画面を基準に組み、広い画面でも
並び順を変えない**（同じ画面の見え方を幅ごとに覚え直さずに済む）。広い画面では**読みやすい幅で頭打ちにし、
横いっぱいには広げない**。

> **盤面追跡・USI 変換・USI→日本語表記・悪手判定のロジックは `shared` パッケージに置く**（純 TS）。
> web は対話盤面のためクライアント側でこれを import し、server は同じロジックでプロンプトを生成する
> （[02](./02-architecture.md) §3.2 / [06](./06-llm-commentary.md)）。

**局面（`BoardState`）は不変として扱う**。`applyMove` は変化したマス（移動元・移動先）と手番側の持ち駒だけを
差分コピーし、残りの行・駒オブジェクトは元の局面と共有する（1 手ごとに 81 マスをディープコピーしない）。
受け取った側は局面を破壊的に変更してはならない。**全局面は棋譜詳細ページで 1 度だけ構築**し、盤面コンポーネントへ
props で渡す（同一レンダー内で作り直さない）。理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。

### 2.1 盤面と操作

- **将棋盤**: 9x9 のテキスト盤面。**マスの寸法は使える幅と高さから算出し、上限で頭打ちにする**
  （決定・2026-08-28。固定値をブレークポイントで刻む形から改めた。理由と実測は
  [12](./12-position-lab.md) §3.3）。上限はモバイル（md 未満）40px / md 40px / lg 48px / xl 56px 相当で、
  🔴 **モバイルの 40px は現行の 32px からの意図的な拡大**（タップが操作の主役になるため）。
  **md 以上の上限は現行どおりで、デスクトップの見え方は変わらない。** 筋段のラベル・駒文字はマスと
  同じ比率で揃え、どの幅でも盤の見え方を保つ。先手は黒字、後手は赤字 +180 度反転。
  **直前の指し手の移動先マスを強調する**。**解析前でも `usiMoves` があれば表示可能**。
  後手ユーザーの場合はデフォルト反転。
- **持ち駒表示**: 盤面の上下（反転で入替）。プレイヤー名を左、持ち駒を右。
- **コンパクト情報行**: 直近の指し手 + 局面評価値 + 手数/N + 「分岐」バッジ（分岐中のみ）+
  局面検索への導線（[10](./10-video-analysis.md) §6.3）を 1 行に収める。
- 🔒 **情報行の高さは内容によって変わってはいけない**（決定・2026-08-27）。指し手や評価値の長さで行が増減すると、
  **すぐ下の操作ボタンの位置が動き、連打している最中に押すつもりのないものを押してしまう**（実際に踏んだ）。
  収まりきらない情報は**行を増やして逃がすのではなく、表示の側で吸収する**。
  - **削る順序を決めておく**。残すのは**指し手**、削るのは**評価値**から。指し手は棋譜を読むために要る情報で、
    評価値は候補手側（§2.2）にも出ているため。
  - 🔒 **削るのは最後の安全網。読めなくなる握り潰しはしない。** そのために、**想定する幅では削らずに収まるよう、
    情報量の側を先に減らす**（下の 2 つがその手当て）。**削らずに済んでいることの根拠は幅の実測**で、
    実測と、どこまでの幅を想定するかは [`_grilling/decisions.md`](./_grilling/decisions.md)。
    - ⚠ **想定より狭い環境では削らざるをえない。** そのときに全文へ到達する手段は**ホバーのある環境を前提**とし、
      **タッチだけの環境では「削らずに済ませること」で担保する**（タップで全文を出す導線は置かない——
      連打中に押すつもりのないものを押さない、というこの節の目的と逆を向くため）。
    - ⚠ 想定する幅を**下回る素材が出てきたら、この割り切り自体を見直す**。
  - **画面が狭いときは、評価値の補足を落として短い形にする**。形勢を言い表す言葉は落としてよいが、
    🔒 **どちらが勝つかは落とさない**（数値評価は符号がそれを担っているが、詰みは言葉だけが担っているため、
    短い形でも勝つ側を残す）。広い画面は言葉のある形のままにする（幅が足りており、言葉の方がそのまま読める）。
    詰みの表記は §2.2 の表に従う（`▲9手詰` / `▲必至(9)` / `▲9手で詰`。いずれも 4–7 字で現行と同等）。
  - **画面が狭いときは、副次的な導線の表示を切り詰めてよい**（局面検索への導線はラベルを省いてよい）。
  - **分岐を辿っている間、狭い画面では評価値を出さない**。分岐中の評価値は候補手側にも出ている重複情報で、
    分岐の表示が加わると指し手まで削ることになるため。
- **タッチターゲットの基準**（決定・2026-08-27）: モバイル幅では**操作系の要素を 44×44px・間隔 8px**とし、
  **375px 未満の幅でだけ 40×40px・間隔 4px**へ落とす。デスクトップは小さいボタン（32px 相当）でよい。
  メニュー項目の高さも 44px を基準にする。⚠ **基準が掛かるのは操作系の要素**（ボタン・メニュー項目）で、
  盤マスは例外（9 列が幅に収まらないため。[12](./12-position-lab.md) §3.3）。
  - 🔴 **利用者が明示的に選んだときだけ、操作ボタンは 32px 相当まで下がる**（決定・2026-09-01）。
    `/settings` の「表示サイズ」（§2.5）で**操作ボタン = 小さめ**を選んだ場合に限り、モバイル幅でも
    デスクトップと同じ 32px 相当にする（**間隔 8px は維持**）。
    🔒 **既定は 44px のまま。** 何も設定していない利用者の的は縮まない。
    - **なぜ例外を認めるか**: モバイルの縦画面では、44px 基準を守るほど盤の下の
      **評価値・読み筋・候補手が画面の外へ押し出される**。基準を厳守した状態は
      「**押しやすいが読めない**」——的は大きいのに、その操作で何が起きたかを見るために
      毎回スクロールが要る。**押しやすさと読みやすさのどちらを取るかは、端末の高さと
      その時の使い方で変わる**（盤を眺めている時間が長いのか、手を送り続けているのか）。
      一方に決め打つ根拠が置けないので**利用者に選ばせる**——しきい値（§2.3）を設定可能に
      したのと同じ筋で、**根拠が置けないからこそ選べるようにする**。
      🔒 **決め打たないことがこの例外の本体**なので、既定を 32px 側へ動かすのは例外の濫用。
    - ⚠ **タップ領域だけ 44px に保って見た目を縮める案は採らない**（決定・2026-09-01）。
      透明なパディング・疑似要素・44px のラッパーで的を維持すると、**その 44px は縦のスペースを
      消費し続ける**。画面から消えるのは枠線だけで、**評価値・読み筋は 1px も上がってこない**——
      この設定の目的は縦を空けることそのものなので、**目的を果たさないまま基準との衝突だけを
      消す辻褄合わせ**になる。⚠ 一見すると両立案に見えて繰り返し提案されるため、
      **採らない理由をここに残す**。
    - ⚠ **誤タップのリスクは、選んだ人が負う。** 的が縮めば隣を押しやすくなるのは設定の性質上
      避けられない。手当ては 2 つだけ置く: **間隔 8px を維持する**（的を縮めた上に詰めない）、
      **この行に取り返しのつかない操作を増やさない**。⚠ 削除・再解析は今も ⋯ ドロップダウン側に
      あり（§2.5）、**そちらは 44px を保つ**——この設定の対象は手送り・検討の操作に限る。
    - **効く範囲は「操作ボタン」全体**: 棋譜のコントローラー行（⏮ ◀ ▶ ⏭・盤面反転）と、
      検討盤の操作パネル・咎め筋の再生（[12](./12-position-lab.md) §3.1 / §3.2）を**同時に**切り替える。
      🔒 **片方だけ小さくできる形にしない。** 検討パネルはコントローラー行のすぐ上に並ぶので、
      別々に選べると**同じ画面の隣り合う行で的の大きさが食い違う**。
- **操作系ではタッチの暴発を止める**（決定・2026-08-27）。情報行・操作ボタン・盤面・分岐の送り（§2.2）では、
  連打やダブルタップで**文字選択・長押しメニュー・画面の拡大**が起きないようにする（操作そのものが中断されるため）。
  ⚠ **選択させたい場所（KIF のコピーなど）を巻き込まない。** 抑止は操作系に限って当てる。
  理由と実測は [`_grilling/decisions.md`](./_grilling/decisions.md)。
- **コントローラー**: ⏮ ◀ slider ▶ ⏭ + 盤面反転をアイコンで並べる。**狭い画面では slider を出さず、
  送りのボタン（◀ ▶）を大きくする**（指で連打する道具なので押しやすさを優先する）。
  **広い画面ではボタンを小さくし、slider を出す**。
- **キーボード操作**（決定・2026-07-21）: `←` / `→` で 1 手戻る / 進む、`Home` / `End` で最初 / 最後へ。
  **分岐中（§2.2）の `←` / `→` は分岐内を移動**し、分岐の先頭で `←` すると本筋へ復帰する。`Home` / `End` は
  分岐を解除して本筋の端へ飛ぶ（コントローラーの ⏮ ⏭ と同じ）。入力欄（slider・メモ等）にフォーカスがある間と
  修飾キー併用時はブラウザ既定に譲る。理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。
- **盤面の左右タップ**（決定・2026-07-21）: 盤面の右半分をタップで 1 手進む / 左半分で 1 手戻る（モバイルで
  コントローラーまで指を運ばずに並べるため。全画面幅で有効）。左右の判定は**画面基準**で、盤面反転の影響を
  受けない。挙動は ◀ ▶ ボタンと機械的に同じ＝**分岐中のタップは本筋へ復帰**する（キーボードの `←` / `→` は
  分岐内を移動するので非対称。キーボードは読み筋を辿る道具、ボタンとタップは本筋を送る道具という住み分け）。
  端では何もしない（開いている候補手の読み筋を無用に閉じないため）。理由は
  [`_grilling/decisions.md`](./_grilling/decisions.md)。
  - 🔴 **この左右タップは廃止する**（決定・2026-08-28）。盤面のタップは駒の選択になるため
    （[12](./12-position-lab.md) §3.1）。手送りはコントローラーとキーボードに一本化する。
- **上端固定**: 盤面 + コンパクト情報行 + コントローラーを画面の上端に固定し、下へスクロールしても操作を続けられる。

### 2.2 評価値と候補手

- **局面評価値**: 実手後の局面のスコアを **先手視点へ正規化**して表示（保存値は手番視点。moveNumber の parity で
  符号反転する `toSenteEval`。[01](./01-domain.md) §5 / [03](./03-data-model.md)）+ 形勢判断ラベル（互角/有利/優勢/勝勢/詰み）。
- 🔴 **mate の表記は読み筋の形で決める**（設計 Phase A）。`score mate N` の N は **plies（受方の応手・
  逆王手・合駒込み）**で、詰将棋の「N手詰」とは数え方が違う（[01](./01-domain.md) §5）。そのまま
  「N手詰」と書くと読み手を誤らせるので、**既定は「N手で詰み」**とし、**読み筋（pv）を `shared` の
  `classifyMateLine` で辿って形が判ったときだけ**語を強める。分類は保存済みの `pv` を盤面追跡で
  進めるだけで、追加の探索も DB の変更も要らない。

  | 読み筋の形 | 広い形（`formatScore` / `formatTurnScore`） | 短い形（`formatScoreShort`） |
  |---|---|---|
  | `checkmate`（**pv 上で**攻方の手が全て王手） | `先手勝ち(7手詰)` | `▲7手詰` |
  | `hisshi` / `forced`（形は問わない）**かつ詰まされる側が王手中でない** | `先手勝ち(必至・9手で詰み)` | `▲必至(9)` |
  | **詰まされる側が王手中** / `unknown` / pv が無い | `先手勝ち(9手で詰み)` | `▲9手で詰` |
  | `gameover`（王手されている手番側の `resign`） | `後手勝ち(詰み)` | `△詰み` |
  | `mate 0`（既に詰み・勝者不明） | `詰み` | `詰み` |

  - 🔴 **「受けが無い」を担保しているのは pv ではなく mate スコアの方。** engine が `mate N` を返した
    時点で「**受方がどう応じても N 手以内に詰む**」ことは読み切られている（受方は最長になる応手を選ぶ）。
    分類器が pv から取り出しているのは「攻方の手が王手だったか」の一点だけなので、
    **読み筋の形は必至の条件ではない**（次項）。
  - 🔴 **必至は「詰まされる側」に王手が掛かっていない局面にだけ使う。受けが無いことは mate スコアが
    保証しており、読み筋の形は条件ではない**（レビュー `OCL-2C1FDEAD`）。
    - `hisshi` と `forced` の違いは**手順の形だけ**（初手が静かな手か、途中に静かな手や玉の逃げが
      混ざるか）で、受けの有無とは関係が無い。よって**表示では両者を分けず「必至」に統一する**。
      「受けなし」を第三の概念のように立てるのは、実装の都合を将棋の言葉のように見せるもの。
    - 語が不適切になるのは **詰まされる側にいま王手が掛かっているとき**だけ。必至は「**受けられない
      詰めろ**が掛かっている」状態を指す語で、王手中は詰めろの段階ではなく**既に詰まし合いの最中**だから。
    - 🔴 **見るのは詰まされる側であって手番側ではない。勝つ側（攻方）が王手されていることは、
      必至かどうかと何の関係も無い。**
    - 🔴 **分類（`kind`）だけでは弾けない。** 王手されている側が**玉を逃げる手**は王手ではないので、
      分類の上では「静かな手」として数えられ、形は `hisshi` にも `forced` にもなりうる。
      そこで `classifyMateLine` は **`matedSideInCheck`（現局面で**詰まされる側**の玉が王手されているか）**を
      `MateLine` に添え（`isAttackedBy` で盤面から安く確かめる）、表示側は
      **`hisshi` / `forced` かつ `matedSideInCheck === false`** のときだけ「必至」を出す。
      詰まされる側は **mate の符号で決まる**（正なら手番側の相手、負なら手番側自身）。
      🔒 これは `mateValue < 0` のときに**分類**へ使っている王手判定（「**受方**の玉」）と**同じもの**
      なので、実装では 1 回だけ求めて共有する（分類は「玉が盤上に無い」を `unknown` の根拠に使い、
      表示はそれを `false` に潰す、という差だけが残る）。
    - 🔒 **`checkmate` にはこの除外を掛けない。** 王手を受けている側が、王手を解除しつつ王手を
      掛ける手から詰ますことはある。それは正真正銘の即詰みなので `N手詰` のままが正しい。
      除外するのは**必至を名乗る側だけ**。
    - 🔒 **`unknown` は必至に含めない。** 形を追えなかった以上、**盤面の状態そのものを信用し
      きれない**（pv が読めない・mate 距離より短いケースを含む）。
    - ⚠ **実際に踏んだ**: 最初の実装（#114）は**手番側**の玉を見ていた。kifu1 #103（後手番・
      後手玉に王手・`mate 5` で後手が詰ます）は、詰まされる先手玉に王手が無いので**必至**なのに、
      勝つ側（後手）の王手を理由に必至を取り下げて `△5手で詰` と表示していた。回帰テストで固定。
    - ⚠ **現状のデータでは、この除外は発火しない。** dev DB の rank1 mate 行 14 件では、
      **詰まされる側が王手されている行は例外なく `checkmate` か `gameover`** で、`hisshi` / `forced`
      には現れなかった（実質は「mate が出ていれば必至」）。🔒 それでも規則としては正しいので残す。
  - 🔴 **「必至」が保証しているのは「受けが無いこと」だけで、「いま詰めろが掛かっていること」ではない**
    （レビュー `OCL-91BC8098` への回答）。
    - **保証していること**: engine が `mate N` を返した時点で、詰まされる側は**最善に応じても詰む**
      （＝受けが無い）ことは読み切り済み。深さ不足で検出できない（false negative）ことはあっても、
      誤って必至と言う（false positive）ことは実質無い。
    - **保証していないこと**: **いまこの瞬間に詰めろが掛かっていること**。厳密な必至は「詰めろが
      掛かっていて、それが受からない」であり、詰めろかどうかは**手番を相手に渡しても詰むか**を
      確かめないと判定できない（[12](./12-position-lab.md) の後続候補・現時点では未実装）。
    - **具体的にずれる場面**: **攻方が王手されている局面**。攻方はまず王手を外す必要があるので、
      その瞬間には相手へ詰めろは掛かっていない。それでも「受けが無い」ことは変わらないため、
      本サービスでは `必至` と表示する。
      - 実例（実測・dev DB・2026-08-29）: kifu 1 の 103 手目——後手が `mate 5` を持つが後手玉が
        王手されている局面。詰めろ自体は 100 手目（△9二銀打）に掛かり、先手の王手を挟んだ
        102 手目・104 手目でも継続している（手番を反転して撃つと 1 手詰が返る）。103 手目だけ
        判定できないのは、手番を反転すると玉を取れる非合法局面になるため。
    - **お互いが詰めろの乱戦のとき**: 先に詰ます側が勝ち、負ける側は `必至` と表示される。
      「負ける側にも詰めろがあった」ことはこの表示からは分からない（候補手一覧と評価値グラフで見る）。
      これは必至という語の問題ではなく、**詰めろを検出していないことの帰結**。
  - **必至を名乗れない場合の短い形は `▲5手で詰`**（詰まされる側が王手中 / `unknown` / pv なしに共通）。
    かつての `▲詰(5)` は**「詰み」に見えて**しまい、実際には「まだ詰んでいないが、応じても 5 手後に
    詰む」局面を誤って伝えていた。`N手で詰` なら広い形の `5手で詰み` と同じ読み下しになり、
    数は `手` で終わるので括弧も要らない。
  - 🔒 **分類のコード（`MateLineKind` の `hisshi` / `forced`）は残す。** 手番を反転して探索する
    判定を将来入れて「詰めろ」を正しく名乗れるようになったとき、また分ける余地にする。
    **統一したのは表示だけ。**
  - ⚠ **`checkmate` は「pv 上で攻方の手が全て王手だった」という観測事実**であって、pv に現れない
    受け方まで検証したものではない（他の応手では静かな手が混ざりうる）。手数も engine の距離のままで
    **合駒を含む**。それでも表示を `N手詰` に据え置くのは、**従来の表示を維持している側**だから
    ——ここを弱めると別の後退になる（レビュー `OCL-72421091` への回答）。
  - ⚠ **深さ不足による false negative は許容する**（読み切れず mate が出なければ分類の対象にならない）。
    取りこぼし（[09](./09-analytics.md) §3.1）と同じ性質。
  - 🔒 **投了（`resign`）は 3 条件を全て満たすときだけ `gameover`**（レビュー `OCL-DA238CEA`）。
    `resign` は「engine が指す手を持たない」ことの表明でしかなく、それ単体では盤面の状態を証明しない。
    1. `pv[0]` が `resign`（**`win` = 入玉宣言勝ちは外す**。手番側が**勝つ**手なので意味が正反対）
    2. `mateValue < 0`（投了するのは手番側）
    3. **手番側の玉が王手されている**（`isAttackedBy` で盤面から確かめる）

    ⚠ **これは詰みの証明ではない。** 「合法手が無い」ことの検証には合法手生成が要り、それは
    作らないと決めてある（[12](./12-position-lab.md) §2.5）。根拠にするのは**盤面から確かめられる
    範囲の観測事実**——「王手されている」＋「engine が指す手を持たない」の 2 つだけ。
    3 を満たさない `resign`（見切り投了）と `win` は `unknown` に落とす。
  - 🔒 **`gameover` を「読めない指し手」（`unknown`）と混ぜない。** 混ぜると**終局局面が `△1手で詰` と
    表示される**（実際に踏んだ。kifu 1 の 106 手目が `mate -1` / pv `["resign"]`）。本当に pv が
    壊れている場合と区別できる形にする。
  - 🔒 **`gameover` は手数を出さないが勝者は残す**（`後手勝ち(詰み)` / `△詰み`）。手数は意味を
    持たないが、勝者は `mate` の符号から判るので落とす理由がない（§2.1）。
    **勝者不明の `詰み` は `mate 0` の側だけ。**
  - 🔒 **短い形でも勝者（▲ / △）は落とさない**（§2.1）。
  - **短い形の手数は括弧で括る**（決定 2026-08-29・実機で確認）。`▲必至9` は
    「必至9」が 1 語に見えて手数が読み取りにくい。`▲9手詰` / `▲9手で詰` は語尾の `手詰` / `手で詰` が
    数の終わりを示すので括弧を付けない。
  - 受方が王手中に打って直後に取られた駒は**合駒**として数え、`checkmate` の広い形にだけ
    `(7手詰・合駒2)` のように添える（「N手詰」を名乗るときだけ、手数が合駒で伸びていることを断る）。
    ⚠ **手数そのものは書き換えない**——engine の距離と食い違う数字を主役にすると、候補手一覧や
    取りこぼしの閾値（[09](./09-analytics.md) §3.1）と一致しなくなる。
- **候補手一覧**: 各候補を `<details name="candidates">` の排他アコーディオンで展開。
  展開時に読み筋 + 探索深さ + 実手マーク + 最善手との差異 + **分岐操作 ◀▶** を表示。
  本筋を進めると ref 経由で開いている details を自動クローズ。初期 3 件、4 件以上は chevron で折り畳み。
  md+ は `cursor-default` で常時表示ベース。
- **直前の実手の判定を見出しに出す**（決定・2026-07-21）。「候補手」の行に、段階バッジ
  （悪手 / 疑問手 / 詰み逃し・詰まされ（n手で詰み））と**損失（CPL）の数値**を並べる（§2.3）。
  **CPL が第一級の指標なので、ラベルが付かない手でも損失そのものは常に出す**（段階は「どこを見るべきか」の
  目印に過ぎない）。近似（実手が候補外）には `≈` を添える。最善手が指されなかったときの候補行の枠は
  悪手・詰み系で error 色、疑問手で warning 色、ラベル無しなら枠を出さない。
- **日本語表記**: USI→駒名付き日本語変換（例 `▲７六歩(77)`）。盤面追跡で駒名を解決（[01](./01-domain.md) §2）。

### 2.3 悪手判定（centipawn loss ベース・決定 2026-07-21）

**CPL = 最善手の評価 − 実手の評価**（手番側視点。[01](./01-domain.md) §5）を第一級の指標にする。
実装は `packages/web/src/lib/cpl.ts`（`computeMoveLosses` / `labelOf`）。

- **実手の評価の取り方**:
  - 実手が候補手に含まれる → **その候補の `scoreValue`**。同一局面・同一手番なので符号処理は要らない。
  - 候補外 → **次局面の最善値を符号反転**（1 手進んで手番が入れ替わるため）。
- ⚠ **候補外は近似である。** 候補内の `score` は「その局面から深さ d 読んだ値」、次局面の best は
  「1 手進んだ局面から深さ d 読んだ値」で**実質的な読みの深さが揃わない**。完全に揃えるには全候補を
  深く読む必要があり非現実的なので、この非対称は受け入れ、表示では `≈` を添える。
- ❌ **旧条件「実手が候補手リスト外」は廃止。** MultiPV=3 のため「3 位の手を選んで 400cp 損した」が
  永久に悪手にならなかった（[issue #28](https://github.com/Daiius/seseraki/issues/28)）。
- **最終手の扱い**: 候補内の実手は次局面を必要としないため、**詰みで終わった棋譜の最終手（頓死）も
  判定できる**（エンジンは詰み局面で info 行を返さず候補が空になるため、従来はそこで判定が
  打ち切られていた）。**候補外の最終手だけ**が判定不能として残る。
- **段階（ラベル）**: 悪手（CPL ≧ 悪手閾値）/ 疑問手（疑問手閾値 ≦ CPL < 悪手閾値）の 2 段階 +
  詰み系（詰み逃し / 詰まされ）。**勝負が決した局面（|最善評価値| ≧ 決着閾値）にはラベルを付けない**
  ——挽回不能な局面のぬるい手に学びは薄い。**詰み系は cp の量ではないので決着閾値の対象外**
  （詰み逃しは勝勢の局面でこそ起きる）。詰み → より長手数の詰み（遠回り）はカテゴリを設けない
  （詰み手順の各手が軒並みラベル対象になり目印として機能しなくなるため）。
- ✅ **閾値は表示のフィルタであり、CPL 自体は閾値に依存しない。** 閾値を変えても再計算・再解析は不要。
  実装でも算出（`computeMoveLosses`）とラベル付け（`labelOf`）を分ける。閾値の設定 UI は §2.5。
- 表示: 悪手・詰み系 = error 色、疑問手 = warning 色。出す場所は**盤面直下の候補手一覧**（§2.2）と、
  棋譜全体を俯瞰する**評価値グラフのマーカー**（§2.4）。
- 理由・却下した案は [`_grilling/decisions.md`](./_grilling/decisions.md)。

### 2.4 評価値グラフ

- visx（`@visx/responsive` `@visx/scale` `@visx/shape`）による SVG 折れ線グラフ。先手有利 = 上、後手有利 = 下。
  塗りは評価値 0 の中央線を基準に上下へ描く。
- 幅は `ParentSize` でコンテナ幅に追従（実寸描画で歪みなし）。非常に長い棋譜のみ下限幅まで広げ横スクロール。
- コントローラー / コンパクト行と連動、クリックで局面移動。現在手位置に縦線。
- **悪手マーカー**（先手 ▲ / 後手 ▽、相手の悪手は透明度を下げる）に加え、**詰み系は × マーカー**を出す
  （決定・2026-07-21）。**視覚要素の意味を三分離する**（透明度に 2 つの意味を持たせない）:

  | 要素 | 表す情報 |
  |---|---|
  | 形（× / ▲▽） | 詰み系か、悪手か |
  | **色の赤さ** | **詰み手数**（短手数ほど真っ赤 → 長手数ほど通常の悪手マーカーの赤に近づく） |
  | 透明度 | 自分 / 相手（既存ルールを維持） |

  意図は「長手数の詰みは気づくのが困難なので、**短手数の見逃しほど強く目立つ**」。
  - **疑問手はグラフに出さない**。俯瞰の用途では悪手と詰み系に絞る（数が増えると目印として機能しない）。
  - マーカーは**実手後の局面**に置く。詰みで終わった棋譜は最終局面の解析が無く点が存在しないため、
    その手を指す前の局面に置いて末尾に出す（§2.3 で判定できるようになった頓死を見えなくしないため）。
  - マーカーには `<title>`（手数・段階・損失）を付ける。
- モバイルは高さ 180px・余白詰めでナビゲーション用途を強化、デスクトップは 120px。

### 2.5 一覧・ヘッダー・設定ページ・折り畳み

- **棋譜一覧（`/`）**: テーブル表示。解析済み/未バッジ、勝敗バッジ（自分の名前候補 `VITE_SELF_NAMES` ∪ `VITE_SWARS_USER_ID` に一致時）。
  サーバー未接続時は警告。既定は対局日時の新しい順・ページネーション付き。
  （かつて置いていた swars 取り込みの「更新」ボタンは**撤去**した。取り込みの無効化。[04](./04-ingestion.md) §4）
  - **日時列は「対局日時」だが、`playedAt` が無い棋譜は登録日時（`createdAt`）で代替する**（一覧の並びも
    `coalesce(playedAt, createdAt)` 降順・[04](./04-ingestion.md) §6）。代替表示のときは
    **「（登録）」を添えて弱色にする**（決定・2026-07-21）。理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。
  - **検索・絞り込み・並べ替えは server 側で行い、条件は URL のクエリに持つ**（決定・2026-07-21）。
    テーブル上部に、検索語（タイトル・対局者名）/ 解析状態 / 勝敗 / 期間 / 並べ替えの基準・向き /
    「条件をクリア」を並べる。パラメータは [04](./04-ingestion.md) §6.1 と同じ。
    - **フィルタバーは「検索」の折り畳み（`<details>`）に収め、既定は閉じたままにする**（暫定の決定・2026-07-21）。
      現状の絞り込み軸だけでは常時出しておくほど使わず、一覧の上部を占有するため。
      **条件が効いていても自動では開かず、効いている条件を畳んだままの `summary` に 1 行で出す**
      （条件付きの URL やリロードで「なぜ件数が少ないのか」が読めないと困る一方、自動で開くと
      占有を減らす目的と衝突するため）。**ヒット件数は折り畳みの外**に置き、閉じていても見えるようにする。
      中身は入力要素が数個で軽く、開閉のたびに状態を作り直したくないので
      **遅延マウント（本節「ページ下部の折り畳み」の決定）は使わない**。
      戦型を記録できるようになれば常時表示へ戻す判断があり得る。理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。
    - 検索語だけ 300ms の debounce でドラフトを URL に反映する（打鍵ごとに履歴を積まない）。
      長さの上限（100字）は入力欄の `maxLength` と URL の正規化の両方で頭打ちにする
      （超えた値を送ると server が 400 を返し、一覧全体がエラー表示になるため）。
    - **解析中の棋譜は「未」バッジの代わりに「解析中 N/M」+ 最終更新からの経過を出す**（決定・2026-07-21）。
      2 値の「解析中」だけでは worker がハングしても「解析中」のままで、「解析中なのか、キューが
      止まっているのか」を半分しか解決しない。**進捗が動くこと自体が生存確認になる。**
      - ⚠ **stale は閾値で消さない。** §1.3 のとおり byoyomi の適正値は吟味中で env 運用であり、
        開発 MATERIAL と本番 NNUE で 1 局面あたりの所要時間が桁違いになるため、「何分更新が無ければ
        死んでいる」の閾値に根拠が置けない（depth 20+ なら 1 局面数分かかり、正常な解析を stale と
        誤判定しうる）。**経過時間を出して判断は人に委ねる。**
      - 取得は専用の **`GET /api/analysis/progress`**（[04](./04-ingestion.md) §6）。解析中は高々 1 件なので、
        一覧も詳細もこれ 1 つを見て自分の id と一致したら表示する。**一覧 SQL を再実行せずに進捗だけ
        ポーリングできる。**
      - ⚠ **状態フィルタ（`all` / `analyzed` / `unanalyzed` / `failed`）に「解析中」は追加しない。**
        進捗はメモリにあり SQL で絞り込めないため、「絞り込みは server 側（SQL）で行い、件数・ページングも
        同じ条件で数える」（[04](./04-ingestion.md) §6.1）を崩すことになる。
      - **解析中は短間隔、非解析中は長間隔でポーリング**する（進捗エンドポイントはメモリ参照だけで
        DB を触らないので安い）。進捗エントリが消えた＝完了/失敗なので、そのタイミングで
        ルーターのローダーを作り直す（一覧のバッジ・詳細の解析結果はローダー経由のため、
        作り直さないと「解析中」が消えた後に古い「未」のまま残る）。
    - **勝敗のセレクトは自分の名前候補が設定されているときだけ出す**（判定できないため）。
    - 絞り込みを変えたら `page` を 1 に戻す。0 件のときの案内は絞り込みの有無で出し分ける。
    - 理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。
- **詳細ヘッダー**: 「← 一覧」+ タイトル + ⋯ ドロップダウン（再解析・削除を格納し誤操作防止）。
  - **削除・再解析は結果を必ず画面に返す**（決定・2026-07-21）。失敗（HTTP エラー / 接続不能）は
    ページ上部の `alert-error`、再解析の受理は `alert-info` で通知し、実行中は両ボタンを無効化する。
    削除は成功すると一覧へ遷移するため通知しない。理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。
  - **解析中はページ上部に「解析中 N/M・◯前に更新」+ 進捗バー**を出す（決定・2026-07-21）。一覧と同じ
    `GET /api/analysis/progress` を見て、`kifuId` が一致したときだけ表示する（§2.5 の一覧バッジと同源）。
  - **解析中は部分結果がそのまま見える**（決定・2026-07-21）。チャンク submit（§1.1c）で途中まで入った
    解析結果が、評価値グラフ・候補手・悪手判定にそのまま反映される（解析が進んでいく様子が見えるのは
    歓迎する副次効果）。**UI 側の特別な対応は入れない**——消費者はいずれも部分結果で壊れない
    （`computeMoveLosses` は判定に必要な局面が揃った手だけエントリを作り・`EvalGraph` は
    2 点未満で描画しない・`kifu-export` は入っている局面を回すだけ）。解析中の棋譜から LLM 解説用テキストをコピーすると途中までの内容に
    なるが、**無効化も警告もしない**（途中までの解説が欲しい場面もありうる）。
- **設定ページ（`/settings`）**: アプリ全体の設定を置く。ヘッダーのナビ右側（「棋譜を登録」と
  「ログアウト」の間）から歯車アイコンで辿る。認証はルートの `beforeLoad` が全ルートに掛かる。
  - **悪手判定のしきい値は UI から変更でき `localStorage` に保持する**（決定・2026-07-21）。
    既定は **悪手 600cp / 疑問手 300cp / 決着 3000cp**。**server・DB は変更しない。**
    数値そのものに根拠は無く適正値は棋力と目的で変わる一方、**CPL を第一級にすると閾値は「表示の
    フィルタ」でしかなく数値そのものは閾値に依存しない**ので、後から変えても再解析が要らない
    ——**根拠が置けないからこそ設定可能にした**（そのコストが構造的に低い。§2.3）。
    - **設定 UI は棋譜詳細ではなく設定ページに置く**（決定・2026-07-22）。値は `localStorage` に
      1 組しか無く全棋譜に効くのに、棋譜ごとの画面にあると**棋譜ごとの設定に見える**（ある棋譜で
      変えると他の棋譜の表示も変わる）。UI の置き場所をデータの寿命に合わせる。設定ページでは
      折り畳みにしない——来た時点で目的が設定なので、開く操作を挟む理由が無い。
    - **既定値は 300 / 150 / 1000 から引き上げた**（決定・2026-07-22）。実運用では低い値だと
      ラベルが付きすぎて目印として機能せず、決着 1000cp は「まだ十分に逆転しうる局面」を決着扱いにして
      ラベルを消していた。**保存済みの値は移行しない**（既定は「まだ設定していない人に出す初期値」。
      明示的に設定した値を勝手に書き換える方が驚きが大きい）。新しい既定へは「既定に戻す」で移れる。
    - 保存先は **`localStorage`**。閾値は恒常的な好みなので URL クエリには持たない
      （一覧の絞り込みはその場の操作という違い）。server にも持たない（設定用のテーブル/列が必要になり
      DB マイグレーションがスコープに入る）。
    - **疑問手閾値 > 悪手閾値**（疑問手が一切出なくなる不整合）を作らせないよう、片方を動かしたら
      もう片方を追従させる。**保存値の読み込み時にも同じ正規化をかける**——値ごとに既定へ
      フォールバックする実装では、片方だけ壊れた保存値から不整合な組み合わせが生まれうるため。
    - 効く範囲は**盤面直下の候補手一覧・評価値グラフのマーカー・LLM 解説用テキストの注目局面**で、
      すべて同じ値を見る（[06](./06-llm-commentary.md) §2.1）。理由は
      [`_grilling/decisions.md`](./_grilling/decisions.md)。
  - **表示サイズは UI から変更でき `localStorage` に保持する**（決定・2026-09-01）。
    盤 / 操作ボタン / 評価値グラフの 3 つを、それぞれ **2 択**で切り替える。
    🔒 **既定はすべて現状維持**——設定を触らなければ見た目は変わらない。

    | 設定 | 既定 | もう一方 |
    |---|---|---|
    | 将棋盤 | 幅と高さから算出した寸法のまま（[12](./12-position-lab.md) §3.3） | **少し小さめ**（算出した寸法に一定の率を掛ける） |
    | 操作ボタン | モバイル 44px（§2.1） | **小さめ**（モバイルでも 32px 相当。§2.1 の例外） |
    | 評価値グラフ | 現行の縦幅（§2.4） | **半分** |

    - **なぜ設定にするか**: 3 つとも「**盤・操作の見やすさ**」と「**評価値・読み筋の見やすさ**」の
      奪い合いで、**モバイルの縦画面では両方を同時に満たせない**。どちらが欲しいかは端末の高さと
      使い方で変わり、一方に決め打つ根拠が置けない（しきい値・§2.3 と同じ筋）。
      ⚠ **「モバイルで盤を大きくした」こと自体は撤回しない**（[12](./12-position-lab.md) §3.3 の
      40px 拡大は意図した決定）。ここで足すのは**その決定を利用者が引き戻せる余地**であって、
      決定の見直しではない。
    - 🔒 **盤の縮小は、算出式そのものを書き換えず結果に率を掛ける形にする**
      （[12](./12-position-lab.md) §3.3「使える幅と高さから算出する」を壊さないため）。
      ⚠ **縦の予約ぶんを膨らませて縮める形にはしない。** 予約は「盤と操作行が画面に収まる」ための
      見積もりなので、表示の好みで膨らませると**横画面でその保証が嘘になる**。
      ⚠ **頭打ちの上限にも同じ率が掛かるようにする。** 幅に余裕のある端末では上限側が効いており、
      上限を据え置くと**その端末だけ設定が何も変わらない**。
    - ⚠ **具体的な縮小率・グラフの px 値は PRD に置かない**（[12](./12-position-lab.md) §3.3 と同じ理由。
      実装式と実機の見え方で詰めるもので、書けば誤った期待値として使われる）。代わりに
      **落としてはいけないもの**を書く: 評価値グラフを縮めても、**▲ / △ の視点ラベル・
      悪手 / 詰みマーカー・現在手の位置は残す**（§2.4 の「形・色・透明度で三分離する」が
      読めなくなったら縮めすぎ）。
    - 保存先は **`localStorage`**（しきい値と同じ。恒常的な好みで全画面に効き、server・DB は変更しない）。
      🔒 **キーは 1 つにまとめ、読み込みは項目ごとに既定へフォールバックする。**
      設定を後から足すと**その項目を持たない保存値が既に利用者の手元にある**ため、
      オブジェクト全体を捨てる作りにすると**項目を 1 つ足すたびに既存の設定が全部リセットされる**。
    - ⚠ **反映は最初の描画より前に行う。** 遅れると**盤が一瞬大きく描かれてから縮む**（ちらつく）。
      **設定ページを開かなくても効くこと**（起動時に 1 回反映する）。
- **ページ下部の折り畳み**（`<details>`・既定閉じ）: KIF テキスト /
  LLM 解説用テキスト（[06](./06-llm-commentary.md)）/ メモ。
  - **KIF テキスト・LLM 解説用テキストには「コピー」ボタンを置く**（`navigator.clipboard.writeText`）。
    共通の `CopyButton`（アイコン主体・モバイルはアイコンのみ・`sm` 以上でラベル・コピー後 2 秒だけ
    チェック表示）を使う。swars 取り込みの無効化（[04](./04-ingestion.md) §4）で KIF を手で扱う機会が
    増えたため、詳細画面から KIF をそのまま持ち出せるようにする。
  - **開かれるまで中身をマウントしない**（決定・2026-07-21）。`<details>` は閉じていても中身がレンダーされるため、
    エクスポート用テキスト生成のような重い処理が閉じたまま毎レンダー走ってしまう。一度開いた後はマウントしたままにする
    （開閉の往復を軽くし、メモの入力中の下書きも失わない）。理由は [`_grilling/decisions.md`](./_grilling/decisions.md)。
  - **全局面を 1 行ずつ並べたテーブルは持たない**（決定・2026-07-21）。全局面 × 全候補手の「候補手詳細」に加え、
    全局面 × 最善手 1 件の「局面評価値」テーブルも置かない。読み筋・評価値の閲覧は盤面直下の候補手一覧と
    コンパクト情報行（§2.2）を局面移動しながら使い、棋譜全体を俯瞰する用途は評価値グラフ + 悪手マーカー
    （§2.4）と LLM 解説用テキスト（[06](./06-llm-commentary.md)）が担う。理由は
    [`_grilling/decisions.md`](./_grilling/decisions.md)。
