# 09. 分析ページ（戦型別成績）

溜め込んだ棋譜を**戦型で横断して数える**画面（`/stats`）。[01](./01-domain.md) §6 が戦型ラベルの動機として
挙げた「『振り飛車相手だと勝率が落ちる』を数字で見る」に答えるのがこのページの役目で、
[03](./03-data-model.md) §2.1 が `kifuTactics` を別テーブルにした理由（横断集計を JOIN 一本にする）を
初めて使う場所でもある。

> 設計は 2026-08-05 の grill で確定。**実装済み**——`shared` の語彙（§6.1）・一覧の絞り込み（§7）・
> `candidate_moves` の索引（§6.2）・集計エンドポイント（§6）に加えて、
> **`/stats` ページ本体（§2.3・§2.4 の階層と並び、§3 の表、§5 の UI）と一覧への導線（§7）** が入った。
> 表示ロジック（階層・並べ替え・期間プリセット・率の整形）は `packages/web/src/lib/statsTactics.ts` に
> **純関数として単体テスト付きで**置き、ページ（`routes/stats.tsx`）はその表示に徹する。
> 残るのは §8 の将来の軸だけ（[08](./08-roadmap.md)）。

## 1. このページが答える問い

**主軸は「相手が何を採ったか」**。自分の戦法はほぼ固定なので、勝率を動かす変数は相手側にある。

⚠ **`side` を見ない集計（対局の戦型）を主軸にしてはいけない。** 自分の固定戦法がほぼ全局に立つため、
その行が「四間飛車＝全局」になって情報量が消える。手番固有ラベルは**相手側に立ったもの**を数える。

「自分が採った戦型別」「自分の戦型 × 相手の戦型」の軸は**持たない**（§8）。

## 2. 行の定義

### 2.1 生ラベルで数える — `suppressForDisplay` を掛けない

`kifuTactics` に入っているラベルを**そのまま**数える。相手が石田流なら `石田流`・`三間飛車`・`振り飛車`
の 3 行すべてに 1 局として乗る。

- **局数の合計は総局数を超える。** 各行は独立した問い（「相手が振り飛車だった局の勝率」と
  「相手が四間飛車だった局の勝率」はどちらも知りたい）への答えであり、分割ではない。
  総局数はページ上部に別掲して誤読を防ぐ。
- ⚠ **`suppressForDisplay` は表示専用で、集計に持ち込まない。** 掛けると `振り飛車` の行が
  ほぼ常に消える（`IMPLIES` により中飛車 / 四間飛車 / 三間飛車 / 向かい飛車がすべて `振り飛車` を含意するため）。
  それは [01](./01-domain.md) §6 が挙げた動機そのものを消すことになる。
- **一覧の絞り込みと定義が一致する。** 一覧は `EXISTS (… WHERE label = ?)`（[03](./03-data-model.md) §2.1.1）で
  絞るので、生ラベルで数えていれば**表の局数とクリック先の件数が原理的に一致する**（§7）。

### 2.2 帰属で分母が切り替わる

`side` の意味はラベルによって変わる（[03](./03-data-model.md) §2.1.1）。**判定側（`shared` の
`attributionOf`）が単一の出所**で、集計はそれを参照する。

| 帰属 | 例 | 分母 |
|---|---|---|
| **手番固有** | 四間飛車・矢倉・横歩取り・筋違い角 | `side = 相手の側` に立った局 |
| **きっかけ帰属** | 角換わり | **`side` を見ず 1 行に畳む**。双方がその戦型なので「相手の型」でもある |
| **対局帰属** | 相掛かり | `side = 'both'` の 1 行 |

- **角換わりを「自分から / 相手から」に割らない。** 持ち込んだ側は別の問いで、この表の主語ではない。
  行数を増やさず n も割れない方を採る。知りたくなったら §8。
- きっかけ帰属・対局帰属のラベルは **1 局 1 行しか無い**（[03](./03-data-model.md) §2.1.1）ため、
  `side` を無視しても重複は生じない。

### 2.3 階層は `IMPLIES` をそのまま使う

行は `shared` の `IMPLIES` で親子に組んでインデント表示する（`振り飛車` > `三間飛車` > `石田流`）。
親の局数は子を含む**包含関係**であり、子の合計ではない。

```
振り飛車 ├ 中飛車 / 四間飛車 / 三間飛車 ├ 石田流
         └ 向かい飛車
居飛車   ├ ひねり飛車 / 縦歩取り / 右四間飛車 / 袖飛車 / 相掛かり
矢倉     ← 根に並ぶ
角換わり ← 根に並ぶ
横歩取り ← 根に並ぶ
筋違い角・鬼殺し・角頭歩戦法 ← 根に並ぶ
```

⚠ **`矢倉`・`角換わり`・`横歩取り` が `居飛車` の下に来ないのは正しい。** `IMPLIES` は
**判定条件どうしの含意**であって戦法の分類ではなく、これらは成立時点の飛車位置しか見ていないため
居飛車を含意しない（角交換のあとで振る形が実在する。`shared/src/tactics/index.ts` の `IMPLIES` コメント）。

- **表示用の分類ツリーを別に持たない。** 「一般に矢倉は居飛車の一種」という分類を持ち込むと、
  親の値と子の関係が包含でなくなり、表の読み方が壊れる。
- ✅ **不自然な階層は隠さず出す。** 根に並ぶラベルが多いことは `IMPLIES` の未整備がそのまま
  見えている状態で、**この表が判定定義の診断を兼ねる**（判定を直せば階層が締まる）。
- **中間のラベルに行が無ければ、存在する最も近い祖先へ繰り上げて繋ぐ**（実装）。
  期間の絞り込みで `三間飛車` の行だけが落ちたときに `石田流` を根へ出すと、`振り飛車` との
  包含関係が表から読めなくなる。⚠ **行は 1 つも落とさない**——`IMPLIES` に循環があって根から
  辿れない行が出たら根に出す（黙って消えると集計を誤読するため）。

### 2.4 並び

- 既定は階層内で**局数降順**。列ヘッダのクリックで勝率順にも並べ替えられる。
  **並べ替えは兄弟どうしで効き、親子関係は崩れない**（同順位はラベル昇順で安定させる。
  ⚠ ロケール依存の `localeCompare` は使わない——同じデータなら同じ順序であることを優先する）。
- **局数の少ない行は淡色にするだけで隠さない。** n=1 で 100% の行が上に来るのを防ぐのは既定の並びの役目で、
  珍しい戦型を指されたこと自体は情報。閾値未満をまとめる「その他」行も、信頼区間も持たない（§8）。
  淡色の目安は **5 局未満**（`LOW_SAMPLE_GAMES`）。⚠ **表示だけの定数で、集計にも並びにも効かない。**

## 3. 列

| 列 | 内容 |
|---|---|
| 全体 | 局数 / 勝率 |
| 先手時 | 自分が先手だった局の 局数 / 勝率 |
| 後手時 | 自分が後手だった局の 局数 / 勝率 |
| 取りこぼし | `N 手詰以下を逃して落とした局 / 解析済みの負け局`（率） |

**手番は列として並置する**（ページ全体のフィルタにしない）。相手の戦型は自分の手番と相関する
（後手番の相手が振り飛車になりやすい等）ため交絡因子であり、並べて見比べられる形にする。

### 3.1 取りこぼし — 短手数の詰みを逃して落とした局

**定義**: 自分の手番の局面で `rank = 1` の候補手が `mate` かつ `1 ≤ scoreValue ≤ N` であるものが存在し、
**かつその局を負けた**。手番は `moveNumber` の parity で決まる（`moveNumber = 0` が初期局面＝先手番。
[03](./03-data-model.md) §3）。`scoreValue` は**手番視点のまま**保存されている（[03](./03-data-model.md) §4 /
[01](./01-domain.md) §5）ので、自分の手番の局面では正の `mate` が「自分が詰ませる」を意味する。

- ✅ **`lib/cpl.ts` の悪手判定を使わない。** `classifyMate` は「最善が自分の詰みなのに実手が詰みでない」で
  詰み逃しを判定するが、**「実手が詰みでない」の確認は「その局を負けた」に含まれる**
  （詰みを実行していれば負けていない）。結果として**素の SQL で書ける**述語になる。
- **分母は「解析済みの負け局」**。「この型の負けのうち N% は本来勝てた」を直接読める。
  勝率と分母が違う（勝率は対象局全体、取りこぼしは解析済みの負け局）ことは表記で明示する。
- **手数の上限 N はユーザー設定**（既定 10）。`/settings` に持ち、このページ上でもいじれる（§5）。
  上限は精度の担保も兼ねる——解析 depth の範囲で読み切れた詰みしか `mate` として出ないため、
  **深い詰みは検出漏れ（false negative）の方向にノイズが出る**。
- **投了時の局面も対象に入る。** 最終局面（`moveNumber = usiMoves.length`）が自分の手番で詰みがあれば、
  勝ち局面で投了したということであり、取りこぼしとして正しい。
- ⚠ **勝った局の詰み逃しも、相手の詰み逃しも数えない。** 「本来の結果と違った局」のうち
  自分の反省材料になる側だけを見る（[08](./08-roadmap.md) の発展余地は §8）。

## 4. 分母から外すもの

次は**分母に載せず、除外件数を内訳付きでページ上部に出す**（「対象 94 局 / 除外 6 局（自分未確定 2・引き分け 3・結果不明 1）」）。

| 除外 | 条件 | 理由 |
|---|---|---|
| 自分未確定 | 両対局者とも自分の名前候補に一致 / どちらも一致しない | 自分の側が決まらなければ「相手の型」も勝敗も決まらない |
| 引き分け | `result` が `DRAW_REPETITION` / `DRAW_IMPASSE` | 千日手は指し直しになるもので、勝敗として数えると意味がずれる |
| 結果不明 | `result` が null（中断・導出不能） | — |

「自分」の定義は **web の `VITE_SELF_NAMES` ∪ `VITE_SWARS_USER_ID` が単一の正**で、server は設定を持たず
クエリで名前候補を受け取る（一覧の `outcome` 絞り込みと同じ扱い。[01](./01-domain.md) §3）。
両者一致を ambiguous として扱う点も一覧と揃える。

## 5. フィルタ

| フィルタ | 内容 |
|---|---|
| 期間 | プリセット（全期間 / 直近 1 年 / 直近 3 ヶ月）+ カスタム。基準は一覧と同じ `coalesce(playedAt, createdAt)`（[04](./04-ingestion.md) §6.1） |
| 取りこぼしの詰み手数 `N` | 既定 10。`/settings` に持ち、このページ上でも変更できる |

解析状態・対局者名・相手の段位での絞り込みは持たない（§8）。

### 5.1 実装で決めた細部（web 側）

- **URL に持つのは集計そのものを変える条件だけ**（`from` / `to` / `mateMax`）。
  ⚠ **並べ替え（§2.4）は URL に置かずコンポーネントの state にした。** server への問い直しを伴わない
  表示だけの状態であるうえ、**TanStack Router は全ルートの検索スキーマを 1 つに合流させる**ので、
  `sort` / `order` をここでも使うと一覧の `sort`（対局日時 / 登録日時 / タイトル）と値の型が衝突する
  （実際に typecheck が落ちた）。
- **`mateMax` は URL と `/settings`（localStorage）の二段**。URL が「いま見ている条件」、
  localStorage が「次に開いたときの既定値」で、**URL が優先**。⚠ **既定値と一致していても URL から
  落とさない**——落とすと保存された既定値に戻り、10 を選んだのに 8 で集計される食い違いが起きる。
- **期間プリセットは下端だけを決め、上端は開けたままにする。** 未来日の対局は無いので `to` を
  今日に閉じても件数は変わらず、日付をまたいだときに URL が古くなるだけになる。
- **プリセットの選択状態は `from` / `to` から逆算する**（`presetOf`）。URL 直入力やカスタム入力の
  あとでもセレクトの表示が実際の条件と食い違わない。
- **名前候補が未設定なら問い合わせない。** 自分の側が決まらなければ全局が `ambiguousSelf` に落ちる
  （§6）ので、0 が並ぶ表ではなく設定を促す文言を出す。

## 6. 集計方式（実装済み）

**server に集計エンドポイントを 1 本置く**（`GET /api/stats/tactics`・`sessionRequired`）。生ラベルで数えると
決めたことで `suppressForDisplay` が集計から消え、**`GROUP BY` 一本の SQL**になる。組み立ては
`packages/server/src/stats-tactics-query.ts`（一覧と同じく **DB 接続を持たない純粋な組み立て**を分けてテストする）。

```
GET /api/stats/tactics?self=…&mateMax=10&from=…&to=…

{
  totalGames, excluded: { ambiguousSelf, draw, unknownResult },
  rows: [{ label, attribution, games, wins,
           senteGames, senteWins, goteGames, goteWins,
           analyzedLosses, missedMateLosses }]
}
```

- **階層は web 側で組む。** `IMPLIES` は `shared` にあるので web から参照でき、server は平坦な行を返す。
  木の形を API の応答に焼き付けない（判定を更新したら木が変わる）。
- **結合条件は `t.side = <相手の側> OR t.label IN <帰属が side でないラベル>`**（§6.1）。
- **自分の側は SQL 内で決める**。一覧の `outcomeCondition`（`packages/server/src/kifu-list-query.ts`）と
  同じ組み立てを使う。
- 先手時 / 後手時は条件付き集計（`sum(case when … end)`）で 1 クエリに収める。
- `attribution` は `shared` の `attributionOf(label)` をそのまま返す（`side` / `trigger` / `game`）。
  web が帰属バッジと分母の説明（§2.2）を出すのに使う。**帰属の表を web に写さない。**

### 6.0 実装で決めた細部

仕様に書いていなかった点を実装時に決めた。**応答の形は上記のとおりで変更していない。**

- **クエリは 2 本**（`GROUP BY` 一本、という表現は行の集計についての話）。総局数と除外の内訳は
  **ラベルに関係ない**ので、`kifu_tactics` を結合しない別クエリで期間内の全局を母集団に数える。
  結合したクエリからは「ラベルが 1 つも付いていない局」が落ちるため、同じクエリでは出せない。
- **除外の内訳は期間内の全局を 4 つに分割する**（自分未確定 → 引き分け → 結果不明 の優先順）。
  引き分け・結果不明の側に「自分の側が確定していること」を掛けており、
  `totalGames + ambiguousSelf + draw + unknownResult = 期間内の全局数`が成り立つ。
  ⚠ **`ambiguousSelf` を「自分未確定のうち勝敗がついた局」にしない。** 自分が決まらなければ
  引き分けかどうかも読む意味がなく、内訳が足し合わせられなくなる。
  ⚠ **この等式は `result` が `*_WIN_*` / `DRAW_*` / null のいずれかであることに依存する。**
  どれにも当てはまらない結果コードが入ると**どのバケツにも入らず、合計が静かに合わなくなる**
  （エラーにはならない）。結果コードの網羅性は未確認事項として残っている
  （[01](./01-domain.md) §7）ので、**コードを追加するときはこの内訳も見直す**。
  構造的に閉じる（「勝敗が読めない残り全部」を `unknownResult` にする）ことは SQL の三値論理を
  踏むため採らなかった——`result` が null のとき `result NOT IN (…)` も `NOT (result LIKE …)` も
  NULL になり、`coalesce` を挟まないと**現在正しく数えられている null の局が落ちる**。
- **`games` は `count(*)`**。`kifu_tactics` の主キーが `(kifuId, side, label)` なので、§6 の結合条件で
  拾える行は 1 局 1 ラベルにつき高々 1 行になり、`count(distinct)` を要さない
  （手番固有ラベルは `side = 相手` の 1 行、帰属が `side` でないラベルは 1 局 1 行。§2.2）。
- **`analyzedLosses` の「解析済み」は一覧の `status=analyzed` と同じ述語**
  （`analysisCompletedAt` が not null かつ `analysisError` が null）。**失敗した棋譜は分母に入れない。**
- **行の並びは局数降順・同数はラベル名昇順**で返す。並べ替えと階層は web の役目（§2.4）だが、
  応答の順序が不定だと差分が読めないので既定の並びだけ server 側で確定させる。
- **`mateMax` は 1〜99 の整数**（既定 10）。上限は 99 という意味のある数ではなく、
  桁数の暴走を止めるだけのもの。
- **期間のプリセット（全期間 / 直近 1 年 / 直近 3 ヶ月）は web が `from` / `to` に落とす**（§5）。
  server は日付の両端だけを受け、「直近」の解釈を持たない。
- **自分の側の判定・取りこぼしの述語は一覧と共有する**（`kifu-list-query.ts` の `selfSides` /
  `bySelfSide` / `selfMateExists` / `missedMateCondition` を export して使う）。⚠ **書き直さない。**
  同じ意味論が 2 か所にあると片方だけ直り、§2.1 が約束した「表の局数とクリック先の件数が一致する」が
  静かに壊れる。期間の境界と「解析済み」の述語も同じ理由で共有している。

### 6.1 絞り込みの語彙は `shared` の公開 API から取る（実装済み）

集計の結合条件（§6）と一覧の `tacticSide=any`（§7）はどちらも「角換わり・相掛かりのような、`side` で
絞ってはいけないラベル」の一覧を要る。選択肢を出す側は「保存されうるラベル名」の一覧を要る。
**どちらも `shared` が名前付きの公開 API として持つ**（判定側が単一の出所、という
[03](./03-data-model.md) §2.1.1 の方針をラベル本体だけでなく帰属・語彙にも及ぼす）。

| export | 中身 | 導出元 |
|---|---|---|
| `NON_SIDE_ATTRIBUTED_LABELS` | 帰属が `side` でないラベル（`角換わり` / `相掛かり`） | `ATTRIBUTION` |
| `STORED_TACTIC_LABELS` | `kifuTactics` に保存されうるラベル名 | `PRIMARY` + `SECONDARY` − `NOT_STORED` |

- ⚠ **参照側（server の絞り込み・集計、web の選択肢）で配列を書き直さない。** どちらも判定側の定義から
  導出しているので、**判定にラベルが増えても `shared` だけで追随できる**。
- **名前付きで出す理由**: `NON_SIDE_ATTRIBUTED_LABELS` は `[...PRIMARY, ...SECONDARY]` の `name` を
  `attributionOf` で絞れば導出できるが、それでは**語彙の組み立て方を参照側に持たせる**ことになる。
  `STORED_TACTIC_LABELS` も、`NOT_STORED`（役割ラベル `角交換を挑んだ` / `角交換に応じた`）が
  非 export なので、これが無いと web が役割ラベルをハードコードすることになる。
- 由来: 当初この節は「`ATTRIBUTION` から生成する」と書いていたが、`ATTRIBUTION` は**モジュール内の
  非 export 定数**で参照できず、仕様どおりに実装できなかった（レビュー指摘 `OCL-79B974CD`）。
  **公開 API の不足は仕様の側で明示する**（「shared の定数から生成」で済ませると、参照できるかどうかが
  実装まで分からない）。

### 6.2 `candidate_moves` に索引を 1 本足す（マイグレーション生成済み）

```sql
CREATE INDEX candidate_moves_score_idx ON candidate_moves (scoreType, scoreValue);
```

取りこぼしの判定は解析済み局面ぶんの `candidate_moves` を見る。既存の索引は
`UNIQUE(moveAnalysisId, rank)` だけで `scoreType` / `scoreValue` を含まないため、局面数ぶんの
行読み出しになる（1000 局 × 120 手 ≒ 12 万行）。`mate` 行は全体のごく一部なので、この索引で
**読む行が mate 行だけに落ちる**。数千局規模まで効く。

> 生成は `db:generate`、適用は本番イメージ同梱の `dist/migrate.js`（[AGENTS.md](../AGENTS.md)）。

### 6.3 採らなかった集計方式

| 案 | 落とした理由 |
|---|---|
| server で読んで TS で畳む | 生ラベルにした時点で畳む処理が不要になった（`suppressForDisplay` を集計に使う前提の案） |
| 抑制述語を SQL に生成する | 同上。加えて `both` が両側を隠す規則と振り直しの `turn` 最小規則を SQL に書き直すことになり、**`shared` のテストが SQL を守らない**。`suppressForDisplay` は「集合を 1 つで共有すると先手の石田流が後手の三間飛車まで隠す」バグを既に踏んでおり、同じ罠を SQL 側にもう一度作る |
| `kifuTactics` に `display` 列を足す | 抑制後を保存すれば分析・一覧・タグ表示が一致するが、生ラベルにすれば**そもそも一致する**。抑制規則を変えて再判定を忘れると集計が静かに誤る、という失敗様式を増やすだけになる |
| web 側で集計する | 唯一の利点だった「閾値変更が再フェッチ不要」が成立しない。取りこぼしは `candidate_moves` を読まないと出せず、ブラウザには送れないため、`N` を変えれば結局サーバに問い直す |

## 7. 一覧へのドリルダウン

行をクリックするとその戦型で絞った棋譜一覧へ、取りこぼしのセルからはその局だけの一覧へ飛ぶ。
**一覧側の絞り込み・`/stats` からの導線とも実装済み**（[04](./04-ingestion.md) §6.1 の枠内）。

| パラメータ | 内容 |
|---|---|
| `tactic` | ラベル名。`STORED_TACTIC_LABELS`（§6.1）の語彙で検証する |
| `tacticSide` | `self` / `opponent` / `any`。帰属が `side` でないラベル（角換わり・相掛かり）は `any` 相当（§6.1） |
| `missedMate` | 詰み手数の上限。指定時は「その手数以下の詰みを逃して落とした局」に絞る |

- **`missedMate` は負け条件を内包する**（§3.1 の定義そのもの）。`outcome=loss` を別途付ける必要はなく、
  単独で意味が閉じたパラメータにしてある。
- **`missedMate` に専用の入力 UI は持たない。** `/stats` からの導線でしか付かないので、指定時に
  一覧上部へバッジと解除リンクを出す（URL でしか指定できないぶん「なぜ件数が少ないのか」が
  分からなくなるのを防ぐ）。
- **側で絞れないラベルへ切り替えたら `tacticSide` を URL から落とす。** 効いていない条件が
  URL に残り続けると、後で開いたときに何で絞ったのか読めない。
- **導線が渡すもの**（実装）: `tactic` は行のラベル、`tacticSide` は**帰属が `side` の行だけ
  `opponent`**（それ以外は付けない＝ `any` 相当）、期間（`from` / `to`）はそのまま引き継ぐ。
  取りこぼしのセルからは加えて `missedMate = 表示中の N` と `status=analyzed`。
- ⚠ **母集団も渡さないと件数が一致しない**（指摘 `OCL-35520A6B` / `OCL-2D4D27E5`）。
  §2.1 が「表の局数とクリック先の件数が原理的に一致する」と言えるのは**ラベルの数え方について**で、
  **分母（§4）の除外は別に効かせる必要がある**:
  - 集計の対象局は「自分の側が確定し、勝敗がついた対局」なので、戦型・側・期間だけで飛ぶと
    **引き分け・結果不明・自分未確定が一覧に混ざる**。→ 一覧に **`outcome=decided`**（勝敗がついた）
    を足し、導線から常に渡す。`bySelfSide` を通るので自分未確定も落ちる。
  - 取りこぼしの分子は「解析済み」に限られるが、一覧の `missedMate` にはその条件が無い。
    **途中まで解析された棋譜・のちに失敗した棋譜に部分的な `candidateMoves` が残りうる**
    （[05](./05-analysis.md) §1.1c のチャンク submit）。→ 取りこぼしの導線だけ `status=analyzed` を足す。
  - ⚠ **`missedMate` 側の定義に「解析済み」を織り込む案は採らなかった。** 一覧の絞り込みとしての
    意味が変わり、この導線以外の使い方（URL 直指定）にも波及するため。導線側で明示する。
- **取りこぼしが 0 件の行はリンクにしない**（飛び先が必ず 0 件になるため）。
  解析済みの負け局が 0 なら率も出せないので `−` を出す。

- ⚠ **相関 `EXISTS` で書き、JOIN しない**（[03](./03-data-model.md) §2.1.1）。JOIN は `count()` と
  LIMIT/OFFSET を壊す。**一覧の絞り込みは server の SQL でなければならない**ので（[04](./04-ingestion.md) §6.1）、
  TS 側で畳んで辻褄を合わせることはできない。この制約が「分析も生ラベルで数える」判断の決め手になった。
- `missedMate` も `candidate_moves` への `EXISTS` になるため一覧クエリが重くなるが、§6.2 の索引で吸収する。

## 8. 未確定・将来の論点

- **自分が採った戦型軸 / 自分 × 相手の組み合わせ軸。** 自分の戦法が固定である間は情報量が乏しい。
  戦法を変えたら、あるいは組み合わせで見たくなったら軸を足す。
- **角換わりの「自分から / 相手から」の内訳。** きっかけ帰属を活かす唯一の場所。行を割るか展開にするかは
  そのとき決める。
- **勝率の推移グラフ。** 「最近この型に対策できてきた」を見る。n が少ないとノイズだらけになるため、
  母数が育ってから。
- **平均 CPL・悪手 / 疑問手率。** 「勝っているが内容はひどい」が見える。`lib/cpl.ts` の `shared` 抽出
  （[08](./08-roadmap.md)）が前提で、分母が解析済み局に限られる点も取りこぼしと同じ扱いになる。
- **相手の段位での層別。** 「勝率が低いのは型のせいか相手が強いのか」を切り分ける。n がさらに割れる。
- **信頼区間 / 最低局数のしきい値。** いまは淡色表示だけで受けている。行数が増えて読みにくくなったら考える。
- **相手の詰み逃し（拾った勝ち）・詰まされ（`into`）。** 反省材料としては取りこぼしが主で、
  残りは母数が育ってから足すか判断する。
